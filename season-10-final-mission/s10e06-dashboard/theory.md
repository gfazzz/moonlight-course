# Теория — s10e06

## 1. Экран — это функция от состояния

Правило, вокруг которого построена серия:

```c
void render(const OpState *s, char scr[H][W]);
```

`const` здесь — не украшение, а контракт: **представление не вычисляет и не меняет ничего**. Всё, что показано, посчитано до вызова.

Зачем так строго. Как только экран начинает досчитывать величины на лету, появляется второй источник истины. Разойдутся они не сразу — при первой же правке логики, сделанной в модели и забытой в рендере. Диагностировать такое неприятно: данные верные, экран врёт, и никто не понимает почему.

Побочная выгода — тестируемость. Чистая функция от состояния проверяется сравнением кадра с эталоном, без терминала, без таймингов, без окружения. Именно поэтому тест этой серии может быть посимвольным.

Разделение известно под многими именами — MVC, MVP, «функциональное ядро в императивной оболочке». Суть одна: **вычисление и отображение живут в разных местах**.

## 2. Возраст данных — такая же величина, как значение

Самая содержательная идея серии, и она не про программирование.

Датчик замолчал. Последнее полученное значение осталось в памяти и выглядит совершенно нормально: число как число, в допустимом диапазоне. Оператор смотрит на экран и принимает решение по реальности сорокасекундной давности.

Отсутствие данных он бы заметил. Правдоподобное старое значение — нет.

Отсюда три состояния вместо двух:

| Состояние | Значение | Что показывать |
|---|---|---|
| `ok` | свежее | значение + возраст |
| `stale` | старше порога | значение + возраст + явная пометка |
| `down` | нет | `---`, `no data` |

Порог — часть контракта системы, а не деталь оформления. Тридцать секунд для телеметрии и тридцать секунд для курса валюты — разные вещи; величина выбирается из физики процесса.

В промышленном мониторинге это называют **staleness detection**, и отсутствие такой проверки — регулярная причина инцидентов: дашборд зелёный, потому что метрики перестали приходить, а «нет данных» отрисовалось как «нет проблем».

Смежное правило: **не рисуйте ноль там, где данных нет**. Ноль — это значение, и график с провалом до нуля читается как «показатель упал», хотя показатель просто неизвестен.

## 3. Рендер в буфер

```c
char scr[H][W];
memset(scr, ' ', sizeof scr);
/* ... заполнение ... */
for (int y = 0; y < H; y++) { fwrite(scr[y], 1, W, stdout); putchar('\n'); }
```

Что это даёт:

**Детерминизм.** Никаких управляющих последовательностей, никакой зависимости от `TERM`, размера окна и поддержки цвета. Кадр одинаков везде.

**Атомарность.** Пользователь не видит наполовину отрисованный экран. При выводе по мере вычисления мелькание неизбежно.

**Тестируемость.** Буфер сравнивается с эталоном как обычный текст. Это единственный способ проверить визуальный вывод в автотесте.

**Возможность диффа.** Приём из s09e06: сравнить новый кадр со старым и вывести только изменившиеся ячейки. На медленном канале разница между полной перерисовкой и диффом — десятки раз по трафику.

## 4. Ширина символа против размера ячейки

Внутри экрана ячейка хранит символ целиком, а не байт, — и ограничения на ASCII нет.

Причина: ячейка буфера — один `char`, то есть один байт. Кириллица в UTF-8 занимает два байта на символ, и строка «Источник» длиной 8 символов запишет в буфер 16 позиций. Рамка уедет, тест упадёт.

Проблема шире, чем кириллица: даже при корректной работе с многобайтными символами остаётся **ширина отображения**. У иероглифов и эмодзи она равна двум ячейкам, у комбинирующих диакритических знаков — нулю. Правильный расчёт делается через `wcwidth`, и это отдельная работа.

Практическое решение, принятое в курсе: **русский текст снаружи экрана, ASCII внутри**. Заголовки, пояснения и итоги печатаются обычным `printf`, а всё, что попадает в сетку, — латиницей.

Та же ошибка встречалась в курсе трижды: в s08e04 кириллическая подпись сломала выравнивание `printf("%-16s")`, потому что спецификатор считает байты; в s05e08 она разобрана до конца; в s09e06 применена к сетке экрана. Лечится везде одинаково: считать знакоместа, а не байты и не символы.

## 5. Сводный статус выводится, а не назначается

```c
const char *status(const OpState *s) {
    if (s->up < s->total)      return "DEGRADED";
    if (any_stale(s))          return "STALE DATA";
    return "NOMINAL";
}
```

Три правила проектирования такого индикатора:

**Порядок важен.** Проверки идут от худшего к лучшему: деградация ядра перекрывает устаревание данных. Обратный порядок покажет `STALE DATA` там, где половина подсистем лежит.

**Статус — функция, а не поле.** Хранить его в структуре значит завести четвёртый источник истины и обязанность его обновлять. Вычисляйте.

**Промежуточное состояние обязательно.** Бинарный индикатор «работает / не работает» бесполезен: реальные системы деградируют постепенно, и ценность мониторинга именно в том, чтобы увидеть ухудшение до отказа.

## 6. Что показывать оператору

Экран ограничен, поэтому выбор — содержательное решение. Полезная рамка:

- **что происходит сейчас** — значения;
- **насколько этому можно верить** — возраст и состояние источников;
- **куда всё движется** — тренд или обратный отсчёт (окно связи);
- **что уже сломано** — деградация подсистем.

Чего на экране быть не должно: величин, по которым не принимают решений. Каждая строка занимает место и внимание; строка, на которую никто не смотрит, ворует и то и другое.
