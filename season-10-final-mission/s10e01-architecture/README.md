**Season 10: Final Mission · Серия 1 из 8 · ~90 мин**

## Теория: направление и порядок

```
platform -> data -> logic -> ui        зависеть можно только ВНИЗ
```

Порядок запуска вычисляется топологической сортировкой: обход в глубину, три состояния (`не посещён / в обработке / готов`). Возврат в узел «в обработке» = **цикл**, то есть система, которую нельзя собрать в принципе.

Останавливают модули **в обратном порядке**, иначе кто-то обратится к уже погашенной подсистеме. Подробнее — [`theory.md`](theory.md).

## Проверка на канале

```
[LUNA] Два вопроса, прежде чем ты соберёшь ядро.
```

**1.** LUNA: «Почему цикл в зависимостях нельзя просто "обойти в рантайме"?»

<details><summary>Ответ</summary>

Цикл означает, что нет ни одного модуля, который можно запустить первым: каждому нужен тот, кто ещё не готов. Это не проблема реализации, а свойство графа — линейного порядка не существует. Ошибку ловят статически и исправляют архитектурно (разрывают зависимость через интерфейс или событие).
</details>

**2.** LUNA: «Модули запустились снизу вверх. В каком порядке их гасить?»

<details><summary>Ответ</summary>

Строго в обратном. Если погасить `storage` раньше `analytics`, тот успеет обратиться к мёртвой подсистеме. Поэтому порядок вычисляют один раз и разворачивают при завершении — та же логика, что у деструкторов и `atexit`.
</details>

```
[LUNA] Верно. Собирай ядро.
```

## Разбор типичных ошибок

1. **Запускать модули в порядке регистрации.** Работает случайно и ломается при добавлении модуля.
2. **Не различать «в обработке» и «готов».** Без трёх состояний цикл не отличить от повторного посещения.
3. **Стартовать модуль с неготовой зависимостью.** Получишь обращение к неинициализированной подсистеме.
4. **Падать при отказе.** Лучше явная деградация с сообщением, что именно не поднялось.
