## Теория: где теряются записи

### Баланс

```
принято + отвергнуто == подано на вход
```

Равенство простое и ловит целый класс ошибок: запись, исчезнувшую молча.

Тот же принцип встречается везде, где данные проходят через границы:

| Область | Форма баланса |
|---|---|
| бухгалтерия | двойная запись |
| сети | принято + отброшено = получено |
| очереди сообщений | подтверждено + отклонено + в работе = опубликовано |
| конвейер данных | принято + отвергнуто = подано |

Если баланс не сходится, искать надо не производительность, а дыру в обработке исходов.

### Один вход — один исход

Типичные способы нарушить:

| Ошибка | Последствие |
|---|---|
| ранний возврат без учёта | запись исчезла |
| двойной учёт при повторе | запись посчитана дважды |
| исход «прочее» для всего непонятного | ошибка есть, но невидима |

Отсюда правило: исходы оформляются **перечислением**, а не логическим «ок / не ок». Тогда видно не только сколько отвергнуто, но и почему.

### Деградация — штатный режим

Хранилище меньше потока — не аварийная ситуация. Правильная реакция: отвергнуть с явной причиной и продолжить.

| Стратегия при переполнении | Оценка |
|---|---|
| притормозить источник | лучшая, если источник управляем |
| сбросить старые записи | приемлема для потоковых метрик |
| приоритеты | приемлема при разной ценности данных |
| **выбросить молча** | недопустима всегда |
| уронить конвейер | недопустима почти всегда |

### Сквозная целостность

Баланса на входе мало — данные могут исказиться по дороге:

```
записей в хранилище == записей в агрегатах
сумма в хранилище   == сумма в агрегатах
записей журнала     == записей данных
```

Последняя строка — проверка того, что правило упреждающей записи из s09e05 не нарушено.

### Порядок стадий

Дешёвые проверки идут раньше дорогих операций. Отвергнуть пакет по сигнатуре — несколько тактов; записать в журнал и хранилище, а потом обнаружить брак — несопоставимо дороже.

Правило общее: **фильтровать как можно раньше**.

## Проверка на канале

```
[LUNA] Два вопроса про интеграцию.
```

**1.** LUNA: «Почему потерянная запись хуже отвергнутой?»

<details><summary>Ответ</summary>

Потому что отвергнутая учтена: известна причина, её видно в метриках, по ней можно принять решение — починить источник, увеличить буфер, ослабить проверку. Потерянная невидима: система рапортует об успехе, а данных нет. Такие дыры обнаруживаются месяцами позже, по расхождению отчётов, и к тому моменту потерянное уже не восстановить. Равенство «принято плюс отвергнуто равно поданному» ловит их немедленно и стоит одной строки кода.
</details>

**2.** LUNA: «Хранилище меньше потока. Это ошибка проектирования?»

<details><summary>Ответ</summary>

Не обязательно — буфер конечен всегда, и вопрос лишь в том, что происходит при его заполнении. Реакция обязана быть штатной: отвергнуть с явной причиной, учесть в счётчиках и продолжить работу. Варианты получше существуют — притормозить источник, сбрасывать старые записи, ввести приоритеты, — и выбираются они из того, что дороже потерять. Недопустимы ровно два поведения: выбросить молча и уронить конвейер целиком. Первое скрывает потерю, второе превращает штатную ситуацию в отказ.
</details>

## Разбор типичных ошибок

1. **Возврат без учёта исхода.** Запись исчезает, баланс не сходится.
2. **Логический результат вместо перечисления.** Видно, что отвергнуто, не видно почему.
3. **Падение при переполнении.** Штатная ситуация не должна останавливать систему.
4. **Дорогие операции до валидации.** Сначала дешёвые проверки.
5. **Агрегаты считаются независимо от хранилища.** Рассинхрон не обнаружится.
6. **Баланс проверяется глазами.** Нужна арифметическая проверка в коде.
