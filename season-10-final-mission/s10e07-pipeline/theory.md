# Теория — s10e07

## 1. Интеграция ломается на стыках

> *— Инженерия начинается там, где перестают спрашивать «работает ли». И начинают спрашивать «как я узнаю, что перестало».*

Модули по отдельности покрыты тестами и работают. Отказы возникают **между** ними:

| Причина | Как проявляется |
|---|---|
| ошибка стадии не проверена | запись идёт дальше как корректная |
| формат данных чуть разошёлся | молчаливое искажение |
| запись «проглочена» обработчиком | исчезновение без следа |
| стадии считают по-разному | расхождение в отчётах |

Все четыре не ловятся модульными тестами: каждый модуль ведёт себя правильно с точки зрения собственного контракта.

Отсюда практика: интеграционная проверка смотрит не на внутренности стадий, а на **сквозные свойства** цепочки.

## 2. Баланс

```
принято + отвергнуто == подано на вход
```

Равенство ловит целый класс ошибок — молчаливую потерю. Это худший вид сбоя: система выглядит здоровой, метрики зелёные, данных нет.

Тот же принцип везде, где данные пересекают границы:

| Область | Форма |
|---|---|
| бухгалтерия | двойная запись, дебет равен кредиту |
| сети | принято + отброшено = получено |
| очереди сообщений | подтверждено + отклонено + в работе = опубликовано |
| конвейер данных | принято + отвергнуто = подано |

Двойная запись появилась в XV веке и решала ровно ту же задачу: сделать невозможным незаметное исчезновение.

Важная деталь: баланс должен проверяться **в коде**, а не глазами по отчёту. Проверка глазами выполняется один раз, при написании.

## 3. Один вход — ровно один исход

| Ошибка | Последствие | Как видно в балансе |
|---|---|---|
| ранний возврат без учёта | запись исчезла | сумма меньше поданного |
| двойной учёт при повторе | запись посчитана дважды | сумма больше поданного |
| исход «прочее» | ошибка невидима | баланс сходится, причина неизвестна |

Третья строка — самая коварная: формально всё правильно, но диагностическая ценность потеряна.

Отсюда правило: исходы оформляются **перечислением**, а каждая причина считается отдельно. Логическое «ок / не ок» отвечает на вопрос «сколько», но не на вопрос «почему», а именно второй нужен для принятия решений.

Практическая проверка качества учёта: можно ли по счётчикам понять, что изменилось в источнике? Если рост отказов виден, а его причина — нет, счётчиков недостаточно.

## 4. Деградация вместо падения

Хранилище меньше потока — ситуация штатная. Буфер конечен всегда; вопрос лишь в том, что происходит при заполнении.

| Стратегия | Когда уместна | Цена |
|---|---|---|
| обратное давление | источник управляем | замедление всей цепочки |
| сброс старых записей | важны свежие данные | потеря истории |
| сброс новых записей | важна полнота начала | потеря актуальности |
| приоритеты | данные разной ценности | сложность |
| **молчаливый сброс** | никогда | скрытая потеря |
| падение конвейера | почти никогда | отказ вместо деградации |

**Обратное давление** заслуживает пояснения: вместо того чтобы отбрасывать, система замедляет приём, и давление распространяется вверх по цепочке до источника. Работает, когда источник можно притормозить; для эфира или сетевого потока — нет.

## 5. Сквозная целостность

Баланса на входе недостаточно — данные могут исказиться по дороге:

```
записей в хранилище == записей в агрегатах
сумма в хранилище   == сумма в агрегатах
записей журнала     == записей данных
```

Последняя строка проверяет, что правило упреждающей записи из s09e05 не нарушено.

Проверки дёшевы и находят рассинхрон, который иначе всплывёт через недели в виде необъяснимых цифр в отчёте.

Обобщение приёма — **сверка** двух независимо посчитанных величин. Промышленные системы делают её регулярно: пересчитывают агрегаты из исходных данных и сравнивают с накопленными. Расхождение означает ошибку, которую иначе не увидеть.

## 6. Порядок стадий

Дешёвые проверки идут раньше дорогих операций:

```
сигнатура (такты) -> длина (такты) -> контрольная сумма (микросекунды)
-> журнал (миллисекунды) -> хранилище (миллисекунды)
```

Отвергнуть пакет по сигнатуре стоит несколько тактов; записать его в журнал и хранилище, а потом обнаружить брак — на порядки дороже.

Правило общее: **фильтровать как можно раньше**. То же самое в базах данных, где предикаты проталкиваются ближе к чтению, и в сетевых стеках, где отбрасывание происходит на входе.

Исключение из правила — случаи, когда дешёвая проверка требует дорогих данных. Тогда порядок определяется не стоимостью проверки, а стоимостью её подготовки.
