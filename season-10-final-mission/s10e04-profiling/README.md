## Теория: где на самом деле время

```
S = 1 / ((1 − p) + p/k)        предел при k → ∞:  1/(1 − p)
```

При `p = 98.5%` потолок — 65.8×, а ускорение оставшихся 1.5% в десять раз даёт **1.01×**. Отсюда правило: вкладываться только в доминирующую часть.

Метрика — **счётчик операций**, а не время: время невоспроизводимо (тот же принцип, что в S7 и S8). Подробнее — [`theory.md`](theory.md).

## Проверка на канале

```
[LUNA] Два вопроса про производительность.
```

**1.** LUNA: «Ты ускорил кусок кода в 10 раз, а программа быстрее почти не стала. Как так?»

<details><summary>Ответ</summary>

Ускорен холодный путь. По закону Амдала выигрыш ограничен долей: если на этот участок приходилось 1.5% работы, максимум — около 1.015×. Нужно было сначала измерить и найти те 98.5%, где программа реально проводит время.
</details>

**2.** LUNA: «Оптимизация ускорила конвейер в 32 раза, но сумма изменилась на единицу. Годится?»

<details><summary>Ответ</summary>

Нет. Оптимизация, меняющая результат, — это не оптимизация, а внесённый баг. Поэтому обе версии обязаны сверяться по контрольным величинам, и расхождение должно останавливать сборку.
</details>

```
[LUNA] Верно. Меряй.
```

## Разбор типичных ошибок

1. **Оптимизировать до измерения.** Почти всегда мимо: интуиция подводит систематически.
2. **Не сверять результат.** Быстрая программа с другим ответом бесполезна.
3. **Мерить время в тесте.** Невоспроизводимо; считай операции.
4. **Микрооптимизации вместо смены алгоритма.** `O(n)` → `O(1)` даёт больше, чем любые трюки.

## Debriefing

Конвейер укладывается в окно с запасом. Но он принимает данные **из эфира** — то есть от источника, которому нельзя доверять. Быстрый код, падающий на первом же некорректном пакете, бесполезен.

```
[LUNA] Быстро. Теперь — безопасно.
[LUNA] Всё, что приходит из эфира, — враждебно, пока не доказано обратное.
[LUNA] Переполнение буфера, битая длина, целочисленное переполнение. Дальше — s10e05.
```

**Навык разблокирован:** профилирование, закон Амдала, дисциплина оптимизации.
