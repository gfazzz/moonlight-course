# Теория (углублённо) — s10e05

## 1. Граница доверия

Ключевое понятие безопасности — **trust boundary**: линия, за которой данные перестают быть твоими. Всё, что пересекает её (сеть, файл, аргументы, переменные окружения, эфир), считается враждебным, пока не проверено.

Ошибка новичка — проверять «на всякий случай» в глубине кода. Правильно — **на границе**, один раз и полностью: дальше по коду данные уже валидны, и каждая функция не обязана повторять проверки.

## 2. Четыре классические дыры

**Переполнение буфера.** Длина берётся из пакета, копирование идёт в буфер фиксированного размера. Классика с 1988 года (червь Морриса) и до сих пор в топе CWE. Лечение: сравнивать длину с **ёмкостью приёмника**, а не только с размером пакета.

**Целочисленное переполнение в самой проверке.** Тонкий случай:

```c
if (len + HEADER > size) reject();     // ПЛОХО: len + HEADER может завернуться
if (size - HEADER < len) reject();     // ХОРОШО: size >= HEADER уже проверено
```

При `len = 255` и узком типе сумма переполняется, проверка проходит — и происходит именно то, что она должна была предотвратить. Так ломали ядра и парсеры не раз.

**Строка без завершающего нуля.** `strlen`/`strcpy` уйдут за границу буфера, читая чужую память (по этой схеме работал Heartbleed — правда, там читали по чужой длине). Лечение: не полагаться на источник, а **дописывать ноль самому**, зарезервировав под него место (`len >= out_cap` — отказ, не `>`).

**Индекс из пакета.** `channel` используется как индекс массива. Без проверки `channel < NCHANNELS` получаем запись в произвольную память.

## 3. Порядок проверок

Проверки образуют цепочку, где каждая следующая опирается на предыдущую:

```
1. size >= минимального заголовка   ->  можно читать raw[0..4]
2. сигнатура                        ->  это вообще наш пакет
3. channel < NCHANNELS              ->  можно использовать как индекс
4. len помещается в пакет           ->  можно читать payload
5. len помещается в буфер           ->  можно копировать
6. crc                              ->  данные не искажены
```

Переставить пункты нельзя: проверка 4 использует арифметику, безопасную только после пункта 1.

## 4. Fail closed

Правильное поведение при сомнении — **отказать**, а не «попробовать разобрать». Отказ должен:

- возвращать код и причину (для диагностики);
- **не ронять** процесс — иначе один битый пакет = отказ в обслуживании;
- не раскрывать лишнего в сообщении (в реальных системах подробности идут в лог, наружу — общий код ошибки).

Отдельная тонкость: для сравнения секретов (токенов, хешей) используют **сравнение за постоянное время**, иначе по времени ответа восстанавливают значение побайтово.

## 5. Инструменты

- **Санитайзеры**: `-fsanitize=address` (выход за границы, use-after-free), `undefined` (переполнения, кривые сдвиги), `memory`. Дёшево и находит то, что глазами не видно, — поэтому тест этой серии обязательно собирает код с ними.
- **Фаззинг**: AFL++, libFuzzer генерируют миллионы случайных и мутированных входов. Разборщик пакетов — идеальная мишень: 20 минут фаззинга находят то, что не найдёт ревью.
- **Статический анализ**: `-Wall -Wextra -Wconversion`, clang-tidy, Coverity.
- **Property-based тесты**: проверять инварианты («парсер никогда не пишет за пределы буфера»), а не отдельные случаи.

## 6. Смежные приёмы защиты

Компилятор и ОС дают эшелоны обороны, но они не заменяют проверок: **stack canary** (`-fstack-protector-strong`), **ASLR**, **NX-бит**, **RELRO**. Они превращают эксплуатацию в падение — а падение всё равно означает отказ в обслуживании. Единственная настоящая защита — не допустить ошибку.
