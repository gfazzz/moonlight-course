# Теория — s10e05

## 1. Граница доверия

> *— Проверка, которая сама может сломаться, — это не проверка. Это ритуал, дающий ложное спокойствие. Такие опаснее их отсутствия: без них ты хотя бы осторожен.*

Ключевое понятие — **граница доверия**: линия, за которой данные перестают быть вашими.

| Источник | Доверенный |
|---|---|
| собственные вычисления | да |
| сеть, эфир | **нет** |
| файл на диске | **нет** |
| аргументы командной строки | **нет** |
| переменные окружения | **нет** |
| ввод пользователя | **нет** |

Ошибка новичка — проверять «на всякий случай» в глубине кода. Правильно — на границе, один раз и полностью: дальше данные валидны, и каждая функция не обязана повторять проверки.

Обратная ошибка тоже встречается: считать доверенным то, что прошло через свой же код. Данные, записанные в файл и прочитанные обратно, снова пересекли границу.

## 2. Четыре классические дыры

### Переполнение буфера

Длина берётся из пакета, копирование идёт в буфер фиксированного размера.

Классика с 1988 года — червя Морриса, использовавшего переполнение в `fingerd`, — и до сих пор в первой пятёрке списка самых частых уязвимостей.

Лечение: сравнивать длину с **ёмкостью приёмника**, а не только с размером входных данных. Эти два условия различны, и нужны оба.

### Переполнение в самой проверке

```c
if (len + HEADER > size) reject();     /* ПЛОХО */
if (size - HEADER < len) reject();     /* ХОРОШО, если size >= HEADER проверено */
```

При большом значении и узком типе сумма заворачивается, условие не срабатывает, и происходит ровно то, что проверка должна была предотвратить.

Общее правило беззнаковой арифметики: **не складывать величины, которые могут быть большими**, — переносить слагаемое в другую часть неравенства.

Дополнительная тонкость: вычитание тоже переполняется, если уменьшаемое меньше вычитаемого. Поэтому порядок проверок жёсткий.

### Строка без завершающего нуля

Функции работы со строками ищут ноль до упора и уходят за границу буфера, читая чужую память.

Лечение: не полагаться на источник, а дописывать ноль самому, зарезервировав место. Отказ при `len >= ёмкость`, а не `>`.

### Индекс из внешних данных

Номер канала используется как индекс массива. Без проверки диапазона — запись в произвольную память.

Отдельный случай — **отрицательный индекс** при знаковом типе: проверка `idx < N` пройдёт, а обращение уйдёт назад по памяти. Проверять надо обе границы либо использовать беззнаковый тип.

## 3. Порядок проверок

Проверки образуют цепочку, где каждая опирается на предыдущую:

```
1. size >= минимального заголовка   ->  можно читать поля
2. сигнатура                        ->  это наш пакет
3. channel < NCHANNELS              ->  можно использовать как индекс
4. len помещается в пакет           ->  можно читать данные
5. len помещается в буфер           ->  можно копировать
6. контрольная сумма                ->  данные не искажены
```

Переставить нельзя. Проверка 4 использует арифметику, безопасную только после пункта 1.

Обратите внимание на положение контрольной суммы: она **последняя**. Это может показаться странным — интуиция подсказывает проверять целостность первой, — но для её вычисления нужно знать длину, а длина сама подлежит проверке.

Тот же порядок разбирался в s06e05 применительно к промышленному протоколу: сначала границы, потом целостность, потом смысл.

## 4. Отказ по умолчанию

При сомнении — отказать, а не пытаться разобрать.

| Требование | Почему |
|---|---|
| возвращать код и причину | без этого диагностика невозможна |
| **не ронять** процесс | иначе один пакет = отказ в обслуживании |
| не раскрывать деталей наружу | подробности в журнал, наружу общий код |

Третья строка неочевидна и важна: подробное сообщение об ошибке помогает атакующему понять устройство разборщика.

Отдельная тонкость для сравнения секретов — токенов, хешей, ключей — **сравнение за постоянное время**. Обычное посимвольное сравнение завершается на первом различии, и по времени ответа значение восстанавливается побайтово.

## 5. Инструменты

| Инструмент | Что находит | Цена |
|---|---|---|
| санитайзер адресов | выход за границы, использование после освобождения | замедление в 2 раза |
| санитайзер неопределённого поведения | переполнения, кривые сдвиги | небольшая |
| фаззинг | входы, до которых не додумались | часы работы |
| статический анализ | подозрительные конструкции | ложные срабатывания |

**Санитайзеры** дёшевы и находят то, чего не видно глазами. Тест этой серии обязательно собирает код с ними — не как дополнение, а как часть критериев приёмки.

**Фаззинг** заслуживает отдельного упоминания: он генерирует миллионы мутированных входов и следит за покрытием кода, направляя мутации туда, где появляются новые пути. Разборщик пакетов — идеальная мишень; двадцать минут фаззинга находят то, что не найдёт код-ревью.

**Тестирование свойств** проверяет инварианты («разборщик никогда не пишет за пределы буфера») вместо отдельных случаев — и потому покрывает входы, которых никто не придумывал.

## 6. Эшелоны обороны

Компилятор и операционная система дают дополнительные механизмы:

| Механизм | Что делает |
|---|---|
| защитное значение в стеке | обнаруживает затирание адреса возврата |
| рандомизация адресов | усложняет предсказание расположения кода |
| запрет исполнения данных | не даёт исполнить код в буфере |
| защита таблиц связывания | усложняет перехват вызовов |

Все они превращают эксплуатацию в падение. Падение — тоже отказ в обслуживании, поэтому механизмы не заменяют проверок, а лишь снижают тяжесть последствий.

Единственная настоящая защита — не допустить ошибку.
