## Теория: порядок проверок и безопасная арифметика

```
1. size >= заголовка   2. сигнатура   3. channel < NCHANNELS
4. len влезает в пакет 5. len влезает в буфер   6. crc
```

Переставить нельзя: пункт 4 использует арифметику, безопасную только после пункта 1.

```c
if (len + 5 > size) reject();     // ПЛОХО: сумма переполняется
if (size - 5 < len) reject();     // ХОРОШО: size >= 5 уже проверено
```

Завершающий ноль дописываем **сами** — источнику не доверяем. Подробнее — [`theory.md`](theory.md).

## Проверка на канале

```
[LUNA] Два вопроса про недоверенный ввод.
```

**1.** LUNA: «Проверка `if (len + 5 > size) reject();` выглядит правильной. Где дыра?»

<details><summary>Ответ</summary>

В самой проверке. При большом `len` и узком типе сумма `len + 5` переполняется и «заворачивается» в маленькое число — условие не срабатывает, и пакет проходит. Безопасный вариант — вычитание: `size - 5 < len`, но только после того, как проверено `size >= 5`.
</details>

**2.** LUNA: «Пакет пришёл без завершающего нуля в данных. Отвергнуть?»

<details><summary>Ответ</summary>

Нет — принять, но ноль поставить **самому**. Наличие нуля вообще не должно зависеть от источника: мы копируем ровно `len` байт и дописываем терминатор, заранее зарезервировав под него место (отказ при `len >= ёмкость`, а не `>`).
</details>

```
[LUNA] Верно. Держи эфир.
```

## Разбор типичных ошибок

1. **Проверка после обращения.** Прочитал `raw[3]`, потом убедился, что пакет достаточно длинный, — поздно.
2. **Переполнение в условии.** `len + HEADER > size` — дыра ровно там, где стояла защита.
3. **Доверять терминатору.** Строка из эфира может не иметь нуля; дописывай сам.
4. **Падать при отказе.** Один битый пакет не должен приводить к отказу в обслуживании.
