## Теория: порядок и безопасная арифметика

### Цепочка проверок

```
1. size >= минимального заголовка   ->  можно читать поля
2. сигнатура                        ->  это вообще наш пакет
3. channel < NCHANNELS              ->  можно использовать как индекс
4. len помещается в пакет           ->  можно читать данные
5. len помещается в буфер           ->  можно копировать
6. контрольная сумма                ->  данные не искажены
```

Переставить нельзя: пункт 4 использует арифметику, безопасную только после пункта 1.

### Безопасное сравнение

```c
if (len + 5 > size) reject();     /* ПЛОХО: сумма переполняется   */
if (size - 5 < len) reject();     /* ХОРОШО: size >= 5 уже проверено */
```

Разница в одной строке и в том, останется ли программа под контролем.

### Четыре дыры

| Дыра | Как выглядит | Лечение |
|---|---|---|
| переполнение буфера | длина из пакета, буфер фиксирован | сравнивать с **ёмкостью приёмника** |
| переполнение в проверке | `len + HEADER > size` | вычитание вместо сложения |
| строка без нуля | `strlen` уходит за границу | дописывать ноль **самому** |
| индекс из пакета | `channel` как индекс массива | проверять диапазон |

Третья строка требует внимания к мелочи: место под ноль резервируется заранее, и отказ наступает при `len >= ёмкость`, а не `>`.

### Отказ по умолчанию

При сомнении — отказать, а не пытаться разобрать. Отказ обязан:

- возвращать код и причину;
- **не ронять** процесс — иначе один битый пакет означает отказ в обслуживании;
- не раскрывать лишнего наружу.

## Проверка на канале

```
[LUNA] Два вопроса про недоверенный ввод.
```

**1.** LUNA: «Проверка `if (len + 5 > size) reject();` выглядит правильной. Где дыра?»

<details><summary>Ответ</summary>

В самой проверке. При большом значении длины и узком типе сумма `len + 5` переполняется и заворачивается в маленькое число — условие не срабатывает, и пакет проходит именно тогда, когда должен был быть отвергнут. Дыра оказывается ровно там, куда поставлена защита. Безопасный вариант записывается через вычитание: `size - 5 < len`, но только после того, как проверено, что `size` не меньше пяти, — иначе переполнится уже вычитание. Общее правило для беззнаковой арифметики: не складывать величины, которые могут быть большими, а переносить слагаемое в другую часть неравенства.
</details>

**2.** LUNA: «Пакет пришёл без завершающего нуля в данных. Отвергнуть?»

<details><summary>Ответ</summary>

Нет — принять, но ноль поставить самому. Наличие терминатора вообще не должно зависеть от источника: мы копируем ровно столько байт, сколько заявлено и сколько помещается, и дописываем ноль в заранее зарезервированное место. Отсюда деталь, которую часто упускают: отказывать надо при `len >= ёмкость`, а не при `len > ёмкость`, иначе для терминатора не останется байта. Доверие к внешнему нулю — источник целого класса уязвимостей, потому что дальше строку будут обрабатывать функции, которые ищут его до упора.
</details>

```
[LUNA] Верно. Держи эфир.
```

## Разбор типичных ошибок

1. **Проверка после обращения.** Прочитал поле, потом убедился в длине — поздно.
2. **Переполнение в условии.** Дыра ровно там, где стояла защита.
3. **Доверие к терминатору.** Строка из эфира может не иметь нуля.
4. **Падение при отказе.** Один битый пакет не должен приводить к отказу в обслуживании.
5. **Длина проверяется один раз.** Нужно дважды: помещается в пакет и в буфер.
6. **Причина отказа не возвращается.** Диагностика станет невозможной.
