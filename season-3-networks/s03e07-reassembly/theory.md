# Теория — s03e07

## 1. Порядок событий и порядок смысла

> *— Не путай последовательность событий с последовательностью смысла. В сети это разные вещи.*
> *— А где ещё?*
> *— В разведке. То, что ты узнал первым, почти никогда не оказывается началом истории.*

`seq` — не порядковый номер сегмента, а **смещение его первого байта в потоке**. Разница принципиальна:

```
seq=0,  len=7   →  байты 0..6
seq=7,  len=7   →  байты 7..13
seq=14, len=7   →  байты 14..20
```

Отсюда сборка становится не сортировкой, а укладкой по индексу — операцией без сравнений вообще.

Почему выбрано смещение, а не счётчик: сегменты имеют разную длину (зависит от MTU пути и от того, сколько данных было готово к отправке), при повторной передаче границы могут не совпасть с исходными, и один сегмент может быть переслан частями. Нумерация байтов разрешает всё это единообразно.

## 2. Начальный номер не ноль

В реальном TCP `seq` первого байта — не ноль, а случайное **начальное число последовательности** (ISN), выбираемое при рукопожатии.

Причина — безопасность. Предсказуемый ISN позволяет постороннему вклиниться в чужое соединение: зная адреса, порты и следующий ожидаемый номер, можно подделать сегмент, который примут за настоящий. Атака известна с 1985 года (Роберт Моррис-старший, работа «A Weakness in the 4.2BSD Unix TCP/IP Software») и была практически применена Кевином Митником в 1994-м.

RFC 6528 предписывает вычислять ISN как функцию от адресов, портов и секрета — так номер остаётся непредсказуемым для постороннего, но детерминированным для стека.

Практическое следствие для анализа: **работать надо с относительными номерами**. Wireshark по умолчанию показывает именно их, вычитая ISN, — иначе в глазах рябит от девятизначных чисел. В нашей задаче поток начинается с нуля намеренно, чтобы не отвлекать.

## 3. Перекрытия и почему они опасны

Повторно переданный сегмент может частично перекрыть уже полученные данные. Вопрос: чьи байты оставить?

Однозначного ответа стандарт не даёт, и реализации расходятся: одни оставляют первые полученные, другие — последние. На этом построен целый класс атак на системы обнаружения вторжений: злоумышленник шлёт перекрывающиеся сегменты так, чтобы анализатор собрал одно, а целевой хост — другое. Анализатор видит безобидный текст, хост получает атаку.

Отсюда правило для разбора: **перекрытия надо не просто обработать, а зафиксировать**. Если сегменты противоречат друг другу, это само по себе сигнал.

В учебной задаче перекрытий нет, но укладка по смещению устойчива к ним по построению: дубликат перезапишет то же место теми же байтами.

## 4. Пропуски: почему нельзя «почти всё»

Если сегмент не дошёл, на его месте в буфере останется то, чем буфер был инициализирован. Нули выглядят как данные, мусор из кучи — тем более.

```c
uint8_t covered[MAX] = {0};
/* при укладке: */ memset(covered + seq, 1, len);
/* после:      */ for (i = 0; i < total; i++) if (!covered[i]) gaps++;
```

Отслеживание покрытия — не украшение, а единственный способ отличить «байт равен нулю» от «байта нет».

Почему нельзя обрабатывать поток с дырой: результат окажется **правдоподобным**. Расшифровка XOR испортит ровно недостающие байты, остальной текст останется читаемым, и вы получите сообщение, в котором не знаете, какая часть настоящая. Это хуже, чем не получить ничего, — тот же класс, что и порт 47873 из s03e03.

Для больших объёмов вместо массива флагов держат **список интервалов**: пара «начало, конец» на каждый непрерывный кусок, с объединением соседних. Память пропорциональна числу дыр, а не размеру потока. Так устроены и очередь пересборки в ядре, и SACK-блоки в самом TCP.

## 5. Что делает ядро

Реальный приёмник TCP:

1. держит **окно приёма** — сколько ещё байт готов принять;
2. подтверждает **наибольший непрерывный префикс** (`ACK` на первый недостающий байт);
3. хранит данные за дырой в очереди пересборки, но приложению их не отдаёт;
4. при поддержке SACK сообщает отправителю, какие куски за дырой уже есть, — чтобы тот переслал только недостающее.

Пункт 3 объясняет, почему приложение никогда не видит пропусков: `read` вернёт только непрерывную часть. Анализатор трафика в другом положении — он не участник соединения, переспросить не может и обязан работать с тем, что перехватил.

Пункт 1 объясняет, откуда берётся ограничение скорости на длинных каналах: за время пути туда-обратно отправитель может послать не больше окна. Отсюда формула пропускной способности `окно / RTT` и необходимость масштабирования окна на быстрых линиях.

## 6. Граница буфера — недоверенный ввод

```c
memcpy(stream + seg.seq, seg.data, seg.len);     /* seq пришёл из сети */
```

`seq` и `len` берутся из перехваченного пакета, то есть контролируются кем угодно. Без проверки это запись по произвольному смещению — готовая уязвимость:

```c
if (seg.seq > STREAM_MAX || seg.len > STREAM_MAX - seg.seq) return -1;
```

Обратите внимание на форму второго условия: `seg.seq + seg.len > STREAM_MAX` было бы неверно — сумма может переполниться и проверка пройдёт. Вычитание вместо сложения устраняет переполнение.

Этот приём — «переставить неравенство, чтобы не складывать» — стоит запомнить: он встречается в разборе любых форматов и будет отдельной темой в s10e05.

## 7. Где это ещё встречается

Сборка из фрагментов по смещениям — не только TCP:

- **IP-фрагментация** — то же самое уровнем ниже, со своими перекрытиями;
- **докачка файлов** по HTTP Range — клиент собирает файл из кусков, полученных в произвольном порядке;
- **BitTorrent** — блоки приходят от разных пиров вразнобой;
- **журнал упреждающей записи** в базе данных (Season 9) — записи с последовательными номерами, восстановление по непрерывному префиксу.

Общий принцип везде один: **позиция важнее момента прибытия**, и незакрытая дыра означает, что данных нет.
