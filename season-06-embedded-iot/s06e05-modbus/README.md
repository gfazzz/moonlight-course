## Теория: кадр и проверка

### Запрос и ответ

```
запрос:  [адрес][функция][старт_hi][старт_lo][кол_hi][кол_lo][CRC_lo][CRC_hi]
ответ:   [адрес][функция][байт данных][данные...][CRC_lo][CRC_hi]
```

Обратите внимание на асимметрию: в запросе указывается **количество регистров**, в ответе — **количество байт**. Это не небрежность, а следствие того, что регистр всегда шестнадцатибитный: три регистра дают шесть байт.

Порядок байтов внутри полей — **старший первым**, как в сети. А вот CRC передаётся **младшим байтом вперёд**. Несогласованность историческая, и она регулярно ломает первую реализацию.

### CRC-16/MODBUS

```c
uint16_t crc = 0xFFFF;
for (size_t i = 0; i < len; i++) {
    crc ^= data[i];
    for (int b = 0; b < 8; b++)
        crc = (crc & 1) ? (crc >> 1) ^ 0xA001 : (crc >> 1);
}
```

Восемь итераций на байт: если младший бит единица — сдвиг и «исключающее или» с полиномом, иначе просто сдвиг.

Начальное значение `0xFFFF` не декоративно: оно позволяет обнаружить лишние нули в начале кадра, которые при нулевой инициализации не изменили бы результат.

Полином `0xA001` — это `0x8005` в обратном представлении, потому что сдвиг идёт вправо.

### Чем CRC лучше чётности

| Ошибка | Чётность (s06e02) | CRC-16 |
|---|---|---|
| один бит | да | да |
| два бита | **нет** | да |
| любая нечётная | да | да |
| пакет до 16 бит подряд | нет | **да** |
| перестановка байтов | нет | **да** |
| случайное искажение | 50% | 99.998% |

Последняя строка — главная. Вероятность пропустить случайное искажение у чётности около половины, у CRC-16 примерно один случай на 65 тысяч.

Строка про пакет ошибок объясняет, зачем это нужно на длинной линии: помеха обычно портит не один бит, а несколько подряд.

### Проверка сводится к нулю

Приём, который вы уже видели дважды — с XOR-суммой в s01e02 и с интернет-суммой в s03e06:

```c
crc16(frame_with_crc, full_length) == 0
```

Если CRC дописан в конец кадра, то расчёт по всему кадру вместе с ним даёт ноль. Сравнивать не с чем — достаточно проверить.

## Проверка на канале

```
[LUNA] Два вопроса. Первый — про две строки кода.
```

**1.** LUNA: «Почему начальное значение CRC — `0xFFFF`, а не ноль?»

<details><summary>Ответ</summary>

Чтобы обнаруживать лишние нули в начале кадра. При нулевой инициализации ведущие нулевые байты не меняют регистр: `0 ^ 0 = 0`, сдвиги дают ноль, — и кадр `00 00 11 03` даст ту же сумму, что `11 03`. Инициализация единицами делает результат чувствительным к длине и к ведущим нулям. Это общий приём в CRC: начальное значение и финальная инверсия выбираются так, чтобы вырожденные случаи не проходили — как разные схемы чётности в Wiegand.
</details>

**2.** LUNA: «CRC сошёлся. Кадр точно от контроллера?»

<details><summary>Ответ</summary>

Нет, и это ровно та же граница, что у чётности в s06e02 и контрольной суммы в s03e06. CRC считается по открытым данным без всякого секрета: любой, кто подключился к линии, посчитает его сам. Он отвечает на вопрос «дошло ли неискажённым» и ничего не говорит об отправителе. В Modbus нет ни аутентификации, ни шифрования — команду может выдать кто угодно, имеющий физический доступ к витой паре.
</details>

```
[LUNA] Верно. Разбирай кадры.
```

## Разбор типичных ошибок

1. **CRC передан старшим байтом вперёд.** В Modbus он идёт младшим — в отличие от данных.
2. **Начальное значение ноль.** Кадры с ведущими нулями пройдут проверку.
3. **Полином `0x8005` вместо `0xA001`.** При сдвиге вправо нужен обратный порядок бит.
4. **CRC считается без учёта адреса и функции.** В расчёт входит весь кадр до самого CRC.
5. **Количество регистров перепутано с количеством байт.** В запросе регистры, в ответе байты.
6. **Повреждённый кадр разбирается.** Проверка целостности идёт до извлечения данных.
