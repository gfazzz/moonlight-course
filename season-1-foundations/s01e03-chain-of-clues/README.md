## Теория: решение как код

### `if` и порядок проверок

```c
if (lat < -90.0 || lat > 90.0)  reject("широта вне диапазона");
else if (id <= 0)               reject("идентификатор должен быть положительным");
else                            accept();
```

Ветви проверяются **сверху вниз**, до первого совпадения. Отсюда правило: сначала отсеиваем невозможное, потом обрабатываем нормальное. Перепутаешь порядок — редкий случай никогда не сработает, потому что его перехватит более общее условие выше.

### Сокращённое вычисление

`&&` и `||` вычисляют правую часть **только если нужно**:

- `a && b` — если `a` ложно, `b` не вычисляется вовсе;
- `a || b` — если `a` истинно, `b` не вычисляется.

Это не оптимизация, а гарантия языка, и на ней держится идиома:

```c
if (p != NULL && p->value > 0)   // безопасно: разыменование только при p != NULL
```

Поменяй местами — получишь падение на первом же `NULL`. Тем же приёмом ставят дешёвую проверку перед дорогой: `if (len > 0 && expensive_check(data))`.

### `switch` — когда вариантов много

Для сравнения одного значения с набором констант:

```c
switch (type) {
    case TYPE_COORD: /* ... */ break;
    case TYPE_TIME:  /* ... */ break;
    default:         /* неизвестный тип — тоже случай! */ break;
}
```

Две вещи, о которых стоит знать сразу. Первая: **без `break` управление проваливается** в следующий case — иногда это нужно, чаще это баг. Вторая: `default` обязателен не формально, а по смыслу — данные пришли извне, и «неизвестный тип» встретится обязательно.

### Диапазоны — не формальность

| Величина | Допустимо | Почему |
|---|---|---|
| широта | −90 … 90 | полюса |
| долгота | −180 … 180 | меридианы |
| час | 0 … 23 | не 24 |
| минута | 0 … 59 | не 60 |
| идентификатор | > 0 | ноль обычно значит «не задан» |

Значение `99.99` в поле широты — не ошибка округления. Это флаг: кто-то либо не проверял ввод, либо положил маркер намеренно.

## Проверка на канале

```
[LUNA] Два вопроса, прежде чем ты поверишь этому файлу.
```

**1.** LUNA: «Почему `if (p != NULL && p->value > 0)` безопасно, а с переставленными частями — нет?»

<details><summary>Ответ</summary>

Из-за сокращённого вычисления: `&&` не трогает правую часть, если левая ложна. При `p == NULL` до `p->value` дело не дойдёт. В обратном порядке разыменование произойдёт первым — и программа упадёт. Язык гарантирует именно такой порядок, поэтому на нём можно строить защиту.
</details>

**2.** LUNA: «Зачем `default` в `switch`, если все возможные типы перечислены?»

<details><summary>Ответ</summary>

Потому что «все возможные» — это про твои ожидания, а данные приходят извне. Появится новый тип, придёт битая запись, кто-то подменит байт — и без `default` такая запись молча провалится мимо всех веток, как будто её и не было. Молчаливый пропуск хуже явной ошибки.
</details>

```
[LUNA] Верно. Разбирай цепочку.
```

## Разбор типичных ошибок

1. **Проверять после использования.** Сначала диапазон, потом обработка — иначе мусор уже разошёлся дальше.
2. **`switch` без `default`.** Неизвестный тип пройдёт незамеченным.
3. **Забыть `break`.** Управление провалится в следующий case, и запись обработается дважды.
4. **Сравнивать вещественные через `==`.** Для координат работает только сравнение диапазонов.
