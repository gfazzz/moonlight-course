## Теория: функция как обещание

### Две стратегии результата

```c
void xor_crypt(unsigned char *buf, int len, unsigned char key) {
    for (int i = 0; i < len; i++) buf[i] ^= key;
}

unsigned char checksum(const unsigned char *buf, int len) {
    unsigned char sum = 0;
    for (int i = 0; i < len; i++) sum = (unsigned char)(sum + buf[i]);
    return sum;
}
```

`checksum` **возвращает** значение и ничего не портит — её можно звать сколько угодно раз с одинаковым результатом. `xor_crypt` **меняет данные** по переданному адресу; возвращать ей нечего, поэтому `void`.

Разница видна и в объявлении: у `checksum` буфер помечен `const` — это обещание не трогать данные, которое проверит компилятор. Ставить `const` там, где не пишешь, стоит с самого начала: он документирует намерение и ловит ошибки.

### Аргументы копируются

C передаёт всё **по значению**: функция получает копию. Изменишь параметр внутри — снаружи ничего не произойдёт.

Массив — исключение, но не потому, что для него особое правило, а потому что в аргументе он превращается в указатель. Функция получает копию **адреса** — и по этому адресу лежат те же самые данные. Отсюда правило, которое ты уже видел в s01e02: длину надо передавать отдельно, `sizeof` внутри функции размера массива не покажет.

Указатели по-настоящему — Season 2. Сейчас достаточно: `buf` — это адрес, `len` — сколько там байт, и оба нужны.

### Что даёт декомпозиция

XOR написан один раз — значит, и чинить его придётся в одном месте. Но выигрыш не только в этом: `main` начинает читаться как описание задачи, а не как её реализация.

```c
xor_crypt(data, len, KEY);
printf("%s\nChecksum: 0x%02X\n", data, checksum(data, len));
```

Три строки вместо двух циклов. Тот, кто это читает, видит **что** происходит; **как** — лежит уровнем ниже и не мешает.

## Проверка на канале

```
[LUNA] Два вопроса про функции.
```

**1.** LUNA: «`xor_crypt` возвращает `void`. Как тогда результат доходит до `main`?»

<details><summary>Ответ</summary>

Через указатель. Функция получает копию адреса, но данные по этому адресу — те же самые, что и в `main`. Изменения видны снаружи, поэтому возвращать нечего. Это и называется побочным эффектом: результат работы — не возвращённое значение, а изменённое состояние.
</details>

**2.** LUNA: «Почему `len` передают отдельно, а не берут `sizeof(buf)` внутри?»

<details><summary>Ответ</summary>

Потому что в параметре массив уже распался до указателя: `sizeof(buf)` вернёт размер указателя — 8 байт на 64-битной машине, — а не размер данных. Длина в C не путешествует вместе с массивом, её носят рядом.
</details>

Та же расшифровка, но `xor_crypt()` и `checksum()` — отдельные функции, а `main` только их вызывает. Вызови `xor_crypt()` дважды — расшифровать и зашифровать обратно: тот же код, разное назначение. ТЗ — в [`mission.md`](mission.md), каркас — в [`starter.c`](starter.c).

## Разбор типичных ошибок

1. **XOR-цикл остался в `main`.** Задача не в том, чтобы код работал, а в том, чтобы логика переехала. `main` только вызывает.
2. **`sizeof(buf)` внутри функции.** Размер указателя вместо размера данных.
3. **Путаница стратегий.** `xor_crypt` меняет буфер и возвращает `void`; `checksum` ничего не трогает и возвращает число. Смешивать — значит делать функцию непредсказуемой.
4. **Забыть `const` там, где не пишешь.** Компилятор перестаёт помогать, а читающий теряет гарантию.
