# Теория (углублённо) — s01e06

## 1. Функция: контракт

Функция — именованный блок с входом (параметры) и выходом (возврат). Она прячет «как» за «что»:

```c
void xor_crypt(unsigned char *buf, int len, unsigned char key);
```

Это объявление (прототип): имя, типы параметров, тип возврата. Определение (тело) — отдельно. Разделение объявления и определения и есть основа модульности.

Параметры в C передаются по значению (копией). Чтобы функция меняла данные вызывающего, передают указатель на них — поэтому `xor_crypt` принимает `unsigned char *buf` и правит буфер «на месте». (Указатели детально — Season 2; здесь достаточно интуиции «адрес, по которому лежат данные».)

## 2. Заголовок и реализация: `.h` / `.c`

- `crypto.h` — интерфейс: что модуль умеет (прототипы, типы, константы). Его включают другие файлы.
- `crypto.c` — реализация: как именно. Компилируется отдельно.

Header guard защищает заголовок от двойного включения:

```c
#ifndef CRYPTO_H
#define CRYPTO_H
/* ... объявления ... */
#endif
```

Без него при двойном `#include` компилятор увидит объявления дважды и выдаст ошибку переопределения.

## 3. Раздельная компиляция и линковка

`gcc crypto.c decoder.c -o decoder` делает два шага:
1. Компиляция: каждый `.c` → объектный файл (`.o`) независимо.
2. Линковка: объектные файлы связываются в один исполняемый; на этом шаге `decoder.o` находит `xor_crypt`, определённый в `crypto.o`.

Отсюда два типичных класса ошибок: **ошибка компиляции** (синтаксис/типы в одном файле) и **ошибка линковки** («undefined reference» — объявил в `.h`, но не определил в `.c`, или забыл добавить `.c` в сборку).

## 4. Почему это лучше копипаста

XOR теперь в одном месте. Нашёл багу — правишь один файл, а не три. Понадобился XOR в Season 3 — просто `#include "crypto.h"`. Это и есть кумулятивность курса: модули S1 переиспользуются дальше через `#include`.
