## Чему ты научишься

- Разделению на интерфейс (`.h`) и реализацию (`.c`), и зачем нужен header guard.
- Раздельной компиляции: `.c` → `.o` → исполняемый файл.
- Различию между ошибкой компиляции и ошибкой линковки — и почему `undefined reference` лечится не там, где кажется.

## Теория: интерфейс и реализация

### Два файла вместо одного

```c
/* crypto.h — интерфейс: что можно звать */
#ifndef CRYPTO_H
#define CRYPTO_H

void          xor_crypt(unsigned char *buf, int len, unsigned char key);
unsigned char checksum(const unsigned char *buf, int len);

#endif /* CRYPTO_H */
```

```c
/* crypto.c — реализация: как оно работает */
#include "crypto.h"

void xor_crypt(unsigned char *buf, int len, unsigned char key) { ... }
```

Заголовок читают **люди и компилятор**; реализацию — только компилятор. Поэтому в `.h` кладут ровно то, что нужно вызывающей стороне, и ни строчкой больше: чем меньше интерфейс, тем свободнее менять реализацию.

**Header guard** (`#ifndef`/`#define`/`#endif`) защищает от повторного включения. Кажется избыточным, пока заголовки не начинают подтягивать друг друга: `a.h` включает `b.h`, `b.h` включает `c.h`, и `c.h` попадает в трансляцию дважды. Без guard — `redefinition`, ошибка.

### Как это собирается

```bash
gcc -c crypto.c -o crypto.o      # компиляция: каждый .c отдельно
gcc -c decoder.c -o decoder.o
gcc crypto.o decoder.o -o decoder  # линковка: связать вместе
```

Компилятор обрабатывает файлы **независимо** — про `crypto.c` он при сборке `decoder.c` не знает ничего, кроме того, что написано в заголовке. Связывает их **линкер**, уже после.

Отсюда разделение ошибок:

| Сообщение | Когда | Что значит |
|---|---|---|
| `implicit declaration of function` | компиляция | забыт `#include` |
| `undefined reference to xor_crypt` | линковка | тела нет или `.c` не добавлен в сборку |
| `multiple definition of xor_crypt` | линковка | символ определён дважды |

### Чего делать нельзя

`#include "crypto.c"` — включать реализацию. Формально сработает, а при второй такой сборке даст `multiple definition`: тело функции попадёт в два объектных файла.

## Проверка на канале

```
[LUNA] Три вопроса про модули.
```

**1.** LUNA: «Что попадает в `#include`, а что — в команду сборки?»

<details><summary>Ответ</summary>

В `#include` — только заголовок `.h`: это объявления, они нужны компилятору в каждой трансляции. Файл `.c` в сборку добавляют аргументом командной строки — его компилируют один раз, отдельно. Включать `.c` нельзя: тело попадёт в несколько объектных файлов, и линкер увидит дубль символа.
</details>

**2.** LUNA: «Компиляция прошла, а линкер говорит `undefined reference to xor_crypt`. Диагноз?»

<details><summary>Ответ</summary>

Объявление есть, тела нет. Либо функция не определена в `crypto.c`, либо `crypto.c` просто не попал в команду сборки. Ключ к диагностике — момент ошибки: раз компиляция прошла, значит, с заголовками всё в порядке и проблема на этапе связывания.
</details>

**3.** LUNA: «Зачем header guard, если я подключаю `crypto.h` ровно один раз?»

<details><summary>Ответ</summary>

Потому что подключаешь не только ты. Заголовки тянут друг друга транзитивно, и через два-три уровня один и тот же файл попадёт в трансляцию дважды — получишь `redefinition`. Guard стоит три строки и пишется всегда, без рассуждений о том, нужен ли он сейчас.
</details>

## Разбор типичных ошибок

1. **`#include "crypto.c"`.** Включают только заголовок; иначе дубли символов на линковке.
2. **Объявил, но не определил.** Прототип в `.h` без тела в `.c` → `undefined reference`.
3. **Нет header guard.** Двойное включение → `redefinition`.
4. **Забыл `crypto.c` в команде сборки.** Компиляция пройдёт, линковка — нет.
5. **Определение переменной в заголовке.** `int counter;` в `.h` попадёт в каждый включивший файл. В заголовке — только `extern`.
