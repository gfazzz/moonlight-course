## Теория: сущность и сборка

### `struct` + `typedef`

```c
typedef struct {
    const char   *label;
    int           len;
    unsigned char sum;
    char          text[128];
} Message;

Message msgs[2];        /* массив структур = таблица записей */
```

`struct` описывает **тип**, `typedef` даёт ему короткое имя. Без `typedef` пришлось бы писать `struct Message m;` каждый раз — привычка C-программистов, идущая от K&R.

Доступ к полям: через точку у самой структуры (`m.len`), через стрелку у указателя (`p->len`, сокращение от `(*p).len`).

Структуру можно **возвращать по значению** — копируются все поля целиком:

```c
Message decode(const char *label, const unsigned char *enc, int len, unsigned char key);
```

Для записи в полторы сотни байт это нормально. Для больших структур копирование заметно, и тогда передают указатель — но не раньше, чем измерят.

### Почему `sizeof(Message)` больше суммы полей

Процессор читает память эффективнее, когда данные лежат по адресам, кратным своему размеру. Компилятор поэтому вставляет **выравнивающие пропуски** между полями:

```c
struct { char a; int b; };     /* 1 + 3 пропуска + 4 = 8, а не 5 */
```

Отсюда практическое следствие, важное с Season 3: **нельзя считать, что структура ляжет в память ровно как сетевой пакет**. Порядок полей влияет на размер, и перестановка от большего к меньшему часто экономит память бесплатно.

### Сборка `.c → .o → бинарь`

```make
artifacts/%.o: artifacts/%.c
	$(CC) $(CFLAGS) -c $< -o $@

moonlight_decoder: artifacts/crypto.o artifacts/decoder.o
	$(CC) $(CFLAGS) -o $@ $^
```

`-c` компилирует без линковки. Автоматические переменные: `$<` — первая зависимость (исходник), `$^` — все зависимости, `$@` — цель. `make` сравнивает даты и пересобирает только устаревшее.

На двух файлах выигрыш незаметен. На двухстах — это разница между секундой и минутой, и именно поэтому весь C-софт собирается так.

## Проверка на канале

```
[LUNA] Последние три вопроса сезона. Соберись.
```

**1.** LUNA: «`m.len` или `m->len` — когда какой?»

<details><summary>Ответ</summary>

Точка — когда слева структура, стрелка — когда указатель на неё. `p->len` это в точности `(*p).len`, просто короче и без скобок, о которых легко забыть: `*p.len` разберётся как `*(p.len)` и не скомпилируется.
</details>

**2.** LUNA: «`sizeof` структуры из `char` и `int` равен 8, хотя полей на 5 байт. Куда делись три?»

<details><summary>Ответ</summary>

Ушли в выравнивание. `int` требует адреса, кратного четырём, поэтому компилятор вставляет три байта пропуска после `char`. Из-за этого структуру нельзя вслепую накладывать на сетевой пакет или содержимое файла — раскладка зависит от компилятора и платформы. Порядок полей от большего к меньшему обычно уменьшает размер.
</details>

**3.** LUNA: «Зачем объектные файлы, если можно собрать всё одной командой `gcc *.c`?»

<details><summary>Ответ</summary>

Ради инкрементальной сборки: при правке одного файла пересобирается один `.o`, остальные берутся готовыми. На двух файлах это неважно, на большом проекте — принципиально. Плюс линковка становится отдельным шагом, и ошибки на ней легче отличить от ошибок компиляции.
</details>

## Разбор типичных ошибок

1. **Точка вместо стрелки.** `p.len` на указателе не скомпилируется — и это удача, потому что могло бы.
2. **`text` без `'\0'`.** Скопировал байты, забыл терминатор — `printf("%s")` уедет за границу.
3. **Переполнение `text[128]`.** Сообщение длиннее буфера затрёт соседние поля структуры. Обрезай до `TEXT_MAX - 1`.
4. **Нет правила на `.o` в Makefile.** «No rule to make target» — опиши шаблон `%.o: %.c`.
5. **Предположение, что структура лежит в памяти без пропусков.** Выравнивание есть всегда.
