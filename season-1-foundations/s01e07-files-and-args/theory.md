# Теория — s01e07

## 1. Как аргументы попадают в программу

> *— Кто кладёт строки в argv? — спросил я.*
> *— Не ты. Оболочка разбирает строку, ядро копирует куски в память нового процесса, стартовый код передаёт указатели в main. Ты получаешь готовое. И чужое.*
> *Виктор постучал пальцем по слову «чужое».*
> *— Всё, что пришло снаружи, — чужое. Запомни это раньше, чем синтаксис.*

Механика такая: командную оболочку просят выполнить `./decoder message.enc`. Она разбивает строку на слова (раскрывая при этом `*`, `~`, переменные), вызывает `execve` со списком аргументов, ядро копирует их в адресное пространство нового процесса, а стартовый код передаёт `argc` и `argv` в `main`.

Важное следствие: **программа не видит исходной командной строки** — только результат разбора. `./decoder *.enc` придёт как несколько аргументов, а не как звёздочка, и обрабатывать шаблон программе не нужно.

Гарантии стандарта:

- `argv[argc] == NULL` — массив завершён нулевым указателем, по нему можно идти без счётчика;
- `argv[0]` — имя программы, но **на него нельзя полагаться**: вызывающий может подставить туда что угодно;
- строки в `argv` изменяемы, но менять их — плохая идея.

## 2. Разбор аргументов по-взрослому

Для одного аргумента хватает `argv[1]`. Как только их становится больше, появляется соглашение, которому лет пятьдесят:

```
program [-опции] [--длинные-опции] аргументы...
```

Разбирать это руками не нужно — в POSIX есть `getopt`:

```c
#include <unistd.h>
int opt;
while ((opt = getopt(argc, argv, "k:v")) != -1) {
    switch (opt) {
        case 'k': key = (unsigned char)strtoul(optarg, NULL, 0); break;
        case 'v': verbose = 1; break;
        default:  usage(argv[0]); return 1;
    }
}
/* optind — индекс первого неопционного аргумента */
```

Двоеточие в строке формата значит «у этой опции есть значение». Отдельно стоит знать соглашение про `--`: всё после него считается аргументами, даже если начинается с дефиса. Это единственный способ обработать файл с именем `-rf`.

## 3. Потоки: `stdin`, `stdout`, `stderr`

Каждый процесс стартует с тремя открытыми потоками:

| Поток | Дескриптор | Назначение |
|---|---|---|
| `stdin` | 0 | ввод |
| `stdout` | 1 | **результат работы** |
| `stderr` | 2 | диагностика |

Разделение stdout/stderr — не формальность, а то, что делает конвейеры возможными:

```bash
./decoder file.enc | grep MOONLIGHT      # по трубе идёт только результат
./decoder file.enc 2> errors.log         # диагностика отдельно
```

Если писать ошибки в `stdout`, они попадут в трубу и испортят данные следующей программы. Правило простое: **в `stdout` — то, ради чего программу запустили; всё остальное — в `stderr`**.

Есть и техническая разница: `stderr` не буферизуется, `stdout` при выводе в файл или трубу буферизуется блоками. Отсюда классическая путаница — при перенаправлении сообщения об ошибках появляются «раньше» обычного вывода. Лечится `fflush(stdout)` перед печатью в `stderr`.

## 4. Буферизованный ввод-вывод и почему он существует

`fopen`/`fread` — это `stdio`, надстройка над системными вызовами `open`/`read`. Надстройка нужна ради буфера: системный вызов стоит переключения в ядро, и читать по одному байту через `read` было бы катастрофически медленно. `stdio` читает блоками (обычно 4 КБ) и раздаёт из своего буфера.

Отсюда особенности, о которых полезно знать:

- `fread` возвращает **число элементов**, а не байт. При `fread(buf, 1, n, f)` они совпадают — поэтому размер элемента обычно и берут равным единице.
- Короткое чтение — норма, не ошибка. Различить конец файла и сбой можно только через `feof(f)` и `ferror(f)`.
- Запись не попадает на диск сразу. `fclose` сбрасывает буфер, `fflush` — по требованию. Программа, упавшая до `fclose`, теряет записанное.
- `fclose` **может вернуть ошибку** — именно на нём обнаруживается неудачная запись. Проверять его результат стоит для выходных файлов.

Реальную долговечность (данные точно на диске) даёт только `fsync`, и о ней всерьёз пойдёт речь в Season 9, когда будешь писать журнал упреждающей записи.

## 5. Размер файла: как узнать и как не надо

Соблазн выглядит так:

```c
fseek(f, 0, SEEK_END);
long size = ftell(f);
fseek(f, 0, SEEK_SET);
```

Работает, но имеет границы применимости: на потоках (труба, терминал) позиционирование невозможно, для текстовых файлов `ftell` формально возвращает не размер, а непрозрачный маркер, и `long` может не вместить большой файл.

Надёжнее — `stat`:

```c
#include <sys/stat.h>
struct stat st;
if (stat(path, &st) == 0) size = st.st_size;
```

Но самый устойчивый подход — **не спрашивать размер вовсе**, а читать в цикле, пока данные идут:

```c
while ((n = fread(buf, 1, sizeof buf, f)) > 0)
    process(buf, n);
```

Такой код одинаково работает с файлом, трубой и сетевым сокетом. К этому мы вернёмся в Season 3, где размер заранее неизвестен принципиально.

## 6. Ошибки и `errno`

Системные функции при неудаче ставят глобальную переменную `errno`:

```c
FILE *f = fopen(path, "rb");
if (!f) {
    perror(path);                          /* "path: No such file or directory" */
    fprintf(stderr, "%s\n", strerror(errno));  /* то же самое строкой */
    return 1;
}
```

Два правила: **`errno` проверяют сразу** — следующий успешный вызов её не обнулит, но может перезаписать; и **`errno` осмысленна только после признака ошибки**, а не сама по себе.

Коды возврата процесса — тоже часть интерфейса: `0` — успех, ненулевое — отказ. Оболочка видит их в `$?`, `make` и CI останавливаются по ним. Программа, которая напечатала «ошибка» и вернула `0`, для автоматики отработала успешно. В финале курса (s10e08) это будет отдельным критерием приёмки.

## 7. Чужие данные — враждебные данные

Имя файла пришло от пользователя, содержимое — из сети. Оба источника недоверенные, и в C это значит конкретные вещи:

- **не копировать путь в фиксированный буфер** без ограничения длины;
- **не подставлять аргумент в `system()`** — это внедрение команд;
- **проверять размер прочитанного** перед разбором: заявленная длина в заголовке пакета не обязана совпадать с фактической;
- **не доверять расширению файла** — оно ничего не гарантирует.

Всё это развернётся в Season 3 (разбор пакетов), Season 7 (запуск процессов) и в s10e05, где программу будут собирать с санитайзерами специально ради враждебного ввода.
