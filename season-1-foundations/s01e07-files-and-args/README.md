## Теория: данные приходят снаружи

### `argc` и `argv`

```c
int main(int argc, char **argv)
```

`argv` — массив строк, `argc` — сколько их. Первым идёт имя самой программы, поэтому для `./decoder message.enc`:

```
argc == 2
argv[0] == "./decoder"
argv[1] == "message.enc"
argv[2] == NULL
```

Отсюда обязательная проверка: **`argv[1]` существует только при `argc >= 2`**. Обратиться к нему без проверки — прочитать за границей массива, и хорошо ещё, если программа сразу упадёт.

Стандартная форма отказа:

```c
if (argc < 2) {
    fprintf(stderr, "usage: %s <файл>\n", argv[0]);
    return 1;
}
```

Три детали здесь неслучайны: сообщение идёт в `stderr`, а не в `stdout`; имя программы берётся из `argv[0]`, а не вписывается строкой; код возврата ненулевой. Так устроены все утилиты в системе, и именно этого от них ждут скрипты.

### `fopen` / `fread` / `fclose`

```c
FILE *f = fopen(argv[1], "rb");
if (f == NULL) { perror(argv[1]); return 1; }

unsigned char buf[4096];
size_t n = fread(buf, 1, sizeof buf, f);
fclose(f);
```

Три правила, каждое оплачено чужими ошибками:

1. **`fopen` возвращает `NULL`, если не смог.** Файла нет, прав нет, путь неверен — причин много, и все нормальны. `perror` напечатает системное объяснение.
2. **`fread` возвращает, сколько прочитал.** Не сколько просили — сколько получилось. Файл короче буфера, поэтому цикл идёт по `n`, а не по `sizeof buf`.
3. **Каждый `fopen` закрывается.** Дескрипторы конечны; программа, открывающая файлы в цикле без `fclose`, упрётся в лимит.

Режим `"rb"` — бинарное чтение. На Unix буква `b` ничего не меняет, на Windows предотвращает превращение `\r\n` в `\n`, которое испортило бы зашифрованные данные. Писать её стоит всегда: она бесплатна и однажды спасёт.

## Проверка на канале

```
[LUNA] Два вопроса. Здесь легко потерять ресурс и не заметить.
```

**1.** LUNA: «Почему цикл идёт по `n` из `fread`, а не по размеру буфера?»

<details><summary>Ответ</summary>

Потому что `fread` сообщает, сколько байт реально прочитано — 75 из запрошенных 4096. Остальная часть буфера содержит неинициализированный мусор; пройти по ней значит вывести случайное содержимое стека. Границу данных задаёт только возвращённое значение.
</details>

**2.** LUNA: «`fopen` вернул `NULL`. Что делать?»

<details><summary>Ответ</summary>

Сообщить и выйти с ненулевым кодом, не трогая `f`. Разыменование `NULL` — падение, а молчаливое продолжение хуже падения. `perror(argv[1])` выведет имя файла и системную причину («No such file or directory», «Permission denied») — этого обычно достаточно, чтобы понять, что произошло.
</details>

```
[LUNA] Верно. Читай файл.
```

## Разбор типичных ошибок

1. **Нет проверки `argc`.** Запуск без аргумента — обращение за границу `argv`.
2. **Нет проверки `fopen`.** `NULL` уедет в `fread` и уронит программу.
3. **Цикл по размеру буфера.** Выведет мусор за концом данных.
4. **Забыт `fclose`.** Утечка дескриптора; на одном запуске незаметна, в цикле — фатальна.
5. **`usage` в `stdout`.** Диагностика идёт в `stderr`, иначе она попадёт в перенаправленный вывод и испортит данные.
