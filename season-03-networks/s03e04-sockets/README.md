## Теория: соединение как процедура

### Две стороны, разное количество работы

```c
/* сервер */
int s = socket(AF_INET, SOCK_STREAM, 0);
bind(s, (struct sockaddr *)&addr, sizeof addr);
getsockname(s, (struct sockaddr *)&addr, &len);   /* узнать назначенный порт */
listen(s, 1);
int c = accept(s, NULL, NULL);                    /* блокирует до подключения */

/* клиент */
int c = socket(AF_INET, SOCK_STREAM, 0);
connect(c, (struct sockaddr *)&addr, sizeof addr);
```

Обратите внимание: `accept` возвращает **новый** дескриптор. Исходный `s` остаётся слушающим и продолжает принимать следующих. Это разделение позволяет серверу обслуживать много клиентов одновременно.

### Адрес

```c
struct sockaddr_in addr = {0};
addr.sin_family = AF_INET;
addr.sin_port   = htons(0);                    /* 0 = «дай любой свободный» */
addr.sin_addr.s_addr = htonl(INADDR_LOOPBACK); /* 127.0.0.1 */
```

Порт и адрес **всегда** в сетевом порядке — это требование формата структуры, а не свойство передачи. Даже если обе стороны на одной машине.

Порт `0` означает «назначь свободный сам». Узнать, какой достался, — через `getsockname`. Для тестов это правильный подход: жёстко заданный порт может оказаться занят, и тест станет нестабильным.

### TCP — поток, а не сообщения

Самое важное в серии:

```c
write(c, "PING", 4);
n = read(c, buf, sizeof buf);   /* n может быть 1, 2, 3 или 4 */
```

TCP гарантирует, что байты придут **в том же порядке** и **без потерь**. Он не гарантирует, что они придут одной порцией. Отправленное одним `write` может прийти двумя `read`, а два `write` — слиться в один `read`.

На loopback с четырьмя байтами это почти никогда не проявляется — и потому проблема доживает до продакшена, где появляется настоящая сеть. Отсюда правило: **читать в цикле, пока не набрано ожидаемое количество**, и заранее знать, сколько ожидается: из фиксированного размера, поля длины или разделителя.

**1.** LUNA: «Зачем `htons` для порта, если клиент и сервер на одной машине?»

<details><summary>Ответ</summary>

Потому что порядок байтов в `struct sockaddr_in` — часть определения структуры, а не свойство передачи. Ядро ожидает поле `sin_port` в сетевом порядке всегда, независимо от того, куда пойдёт пакет и пойдёт ли вообще. Без `htons` на x86 вы попадёте на порт с переставленными байтами: вместо 8080 — 36895.
</details>

**2.** LUNA: «`write` отправил 4 байта, `read` вернул 3. Это ошибка?»

<details><summary>Ответ</summary>

Нет, это нормальная работа TCP. Протокол гарантирует порядок и целостность, но не границы сообщений: он передаёт поток байтов, а не пакеты. Один `write` может прийти несколькими `read`, несколько `write` — слиться в один. Правильно читать в цикле до набора ожидаемого количества, а количество определять по фиксированному размеру, полю длины или разделителю.
</details>

## Разбор типичных ошибок

1. **`sin_port` без `htons`.** Соединение не сойдётся или уйдёт не туда.
2. **Печать из обоих процессов.** Вывод перемешается непредсказуемо, тест станет нестабильным.
3. **Одиночный `read` вместо цикла.** На loopback сработает, в реальной сети — нет.
4. **Жёстко заданный порт.** Занят другим процессом — тест падает. Порт `0` плюс `getsockname`.
5. **Нет `waitpid`.** Зомби-процесс и недетерминированный порядок завершения.
6. **Не закрыт слушающий сокет в дочернем процессе.** Дескриптор наследуется при `fork`; лишняя копия мешает закрытию соединения.
