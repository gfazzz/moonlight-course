# Теория — s03e04

## 1. Асимметрия ролей

> *— Клиент делает один вызов и получает соединение. Сервер делает четыре и получает право ждать.*
> *— Почему так криво?*
> *— Это не криво, это честно. Тот, кто предлагает услугу, берёт на себя работу: занять адрес, объявить о готовности, держать очередь, принимать. Тот, кто приходит, только приходит. В жизни так же.*

| Сервер | Что делает |
|---|---|
| `socket` | создать дескриптор |
| `bind` | занять адрес и порт |
| `listen` | объявить готовность, задать длину очереди |
| `accept` | взять соединение из очереди — **новый** дескриптор |

| Клиент | Что делает |
|---|---|
| `socket` | создать дескриптор |
| `connect` | инициировать рукопожатие |

Ключевая деталь: `accept` возвращает новый дескриптор, а слушающий продолжает жить. Один сокет принимает, много сокетов обслуживают — на этом стоит вся серверная архитектура.

## 2. Что происходит при `connect`

Трёхстороннее рукопожатие:

```
клиент → SYN      → сервер
клиент ← SYN+ACK  ← сервер
клиент → ACK      → сервер
```

`connect` возвращает управление после третьего шага; `accept` на другой стороне — тоже, соединение к этому моменту уже в очереди.

Второй аргумент `listen(s, backlog)` — длина очереди **завершённых** рукопожатий, ожидающих `accept`. Переполнение означает отказ или таймаут для новых клиентов.

Историческая деталь: атака SYN-flood (1996) работала на переполнении очереди **незавершённых** рукопожатий — злоумышленник слал SYN и не отвечал на SYN+ACK, а сервер хранил состояние для каждого. Ответом стали SYN-cookies: сервер кодирует состояние в сам номер последовательности и не хранит ничего до третьего пакета.

## 3. `struct sockaddr` и её странность

```c
struct sockaddr_in addr = {0};
addr.sin_family      = AF_INET;
addr.sin_port        = htons(port);
addr.sin_addr.s_addr = htonl(INADDR_LOOPBACK);

bind(s, (struct sockaddr *)&addr, sizeof addr);
```

Приведение к `struct sockaddr *` выглядит как хак — и является им. API проектировался до того, как в C появился внятный способ выразить полиморфизм: одна функция должна принимать и IPv4-адрес, и IPv6, и Unix-сокет. Решением стал «базовый» тип, к которому приводят конкретный.

Формально это на грани строгого алиасинга, но освящено практикой и поддерживается всеми компиляторами. Современная альтернатива для хранения адреса любого семейства — `struct sockaddr_storage`.

Обнуление структуры обязательно: в `sockaddr_in` есть поле `sin_zero`, и некоторые реализации его проверяют.

## 4. TCP — поток, и это главное

Самое частое заблуждение: «отправил одним `write` — получу одним `read`». Неверно.

TCP гарантирует:

- **порядок** — байты придут в той же последовательности;
- **целостность** — без потерь и дубликатов;
- **контроль потока** — быстрый отправитель не завалит медленного.

TCP **не** гарантирует границ сообщений. Четыре отправленных байта могут прийти как 1 + 3; два `write` по 4 байта — одним `read` на 8.

Причины реальные: алгоритм Нейгла склеивает мелкие отправки, MTU режет большие, а получатель забирает столько, сколько лежит в буфере на момент вызова.

Правильное чтение фиксированного количества:

```c
size_t got = 0;
while (got < need) {
    ssize_t n = read(fd, buf + got, need - got);
    if (n < 0) { if (errno == EINTR) continue; return -1; }
    if (n == 0) return -1;              /* соединение закрыто другой стороной */
    got += (size_t)n;
}
```

Три случая обработаны: ошибка, прерывание сигналом (`EINTR` — не ошибка, надо повторить) и закрытие соединения.

Отсюда требование к любому протоколу: **у сообщения должна быть длина или разделитель**. Фиксированный размер, поле длины в заголовке или терминатор вроде `\r\n`. Без этого протокол нерабочий — принимающая сторона не знает, где кончилось одно сообщение.

## 5. Порт 0 и детерминизм тестов

```c
addr.sin_port = htons(0);                          /* пусть ядро выберет */
bind(s, ...);
getsockname(s, (struct sockaddr *)&addr, &len);    /* узнать, какой достался */
```

Ядро выдаст свободный порт из эфемерного диапазона (на Linux обычно 32768–60999).

Для тестов это единственно верный способ: жёстко заданный порт может быть занят чужим процессом, и тест начнёт падать через раз на чужой машине. Частный случай общего правила: **тест не должен зависеть от состояния системы, которым он не управляет.**

## 6. `TIME_WAIT` и `SO_REUSEADDR`

После закрытия соединения сокет остаётся в `TIME_WAIT` на несколько десятков секунд. Это не дефект: состояние гарантирует, что запоздавшие пакеты старого соединения не попадут в новое с теми же адресами и портами.

Практическое следствие — перезапущенный сервер получает `bind: Address already in use`. Лечится опцией:

```c
int yes = 1;
setsockopt(s, SOL_SOCKET, SO_REUSEADDR, &yes, sizeof yes);
```

Ставить её на серверном сокете — стандартная практика.

## 7. Дескрипторы и `fork`

При `fork` таблица дескрипторов копируется: у ребёнка те же открытые сокеты. Отсюда два правила.

**Закрывать ненужное в каждом процессе.** Ребёнку-клиенту слушающий сокет не нужен, родителю-серверу клиентский — тоже. Лишняя открытая копия мешает закрытию соединения: оно закроется, только когда исчезнут все ссылки.

**Ждать ребёнка через `waitpid`.** Иначе останется зомби, а порядок вывода станет непредсказуемым — и тест перестанет быть детерминированным.

Процессы, `fork` и зомби подробно — Season 7.
