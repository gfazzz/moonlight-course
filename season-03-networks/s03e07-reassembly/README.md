> *— Не путай последовательность событий с последовательностью смысла, — говорил Виктор. — В сети это разные вещи. И в разведке тоже: то, что ты узнал первым, редко оказывается началом истории.*

У каждого сегмента есть `seq` — смещение его первого байта в потоке. Не порядковый номер, а именно **позиция**: место, куда сегмент нужно положить.

```
[LUNA] Заведи буфер и клади каждый сегмент на своё смещение.
[LUNA] Порядок прихода перестанет иметь значение — как и должно быть.
[LUNA] И считай, все ли байты покрыты. Дыра в потоке — это не «почти всё».
```

## Теория: позиция вместо очереди

### `seq` — это смещение

```
пришло:   [seq=49] [seq=42] [seq=35] ... [seq=0]
уложено:  [0..6][7..13][14..20][21..27][28..34][35..41][42..48][49..54]
```

Сегмент с `seq = 21` и длиной 7 занимает байты потока с 21-го по 27-й. Куда бы он ни пришёл — первым или последним, — его место одно и то же.

Отсюда алгоритм сборки в три строки:

```c
memcpy(stream + seg.seq, seg.data, seg.len);
if (seg.seq + seg.len > total) total = seg.seq + seg.len;
covered[...] = 1;                       /* отметить покрытые байты */
```

Никакой сортировки не нужно: укладка по индексу и есть сортировка.

### Пропуски

Отметка покрытых байтов нужна не для красоты. Если какой-то сегмент не дошёл, в буфере на его месте останется мусор или нули — и то и другое неотличимо от данных.

```c
for (size_t i = 0; i < total; i++) if (!covered[i]) gaps++;
```

Поток с пропусками **нельзя обрабатывать дальше**. Не «можно, но осторожно» — нельзя: расшифровка неполного потока даст правдоподобный текст с искажённым фрагментом, и вы не узнаете, каким именно. Правильное поведение — сообщить о дыре и отказаться.

### Что делает настоящий TCP

Ядро занимается ровно этим, только сложнее: держит окно приёма, подтверждает полученное, запрашивает повтор недостающего и отдаёт приложению **только непрерывный префикс** потока. Данные за дырой лежат в буфере ядра и приложению не видны, пока дыра не закрыта.

Поэтому приложение никогда не видит пропусков — но анализатор трафика, как ваш, видит. Он не участник соединения и переспросить не может.

## Проверка на канале

```
[LUNA] Два вопроса про порядок.
```

**1.** LUNA: «Почему сборку делают укладкой по `seq`, а не сортировкой пришедших сегментов?»

<details><summary>Ответ</summary>

Потому что `seq` — это смещение в байтах, а не порядковый номер. Сегменты могут иметь разную длину, могут частично перекрываться при повторной передаче, а один сегмент может прийти дважды. Сортировка по номеру всего этого не разрешает; укладка по смещению разрешает автоматически — дубликат просто перезапишет то же место теми же байтами.
</details>

**2.** LUNA: «В потоке одна дыра в семь байт. Можно расшифровать остальное?»

<details><summary>Ответ</summary>

Технически можно, практически нельзя. XOR обрабатывает байты независимо, поэтому испорченными окажутся ровно семь символов — но вы не будете знать, какие именно, а текст останется читаемым и правдоподобным. Получится сообщение, которому нельзя доверять, и выглядеть оно будет как сообщение, которому можно. Правильное поведение — отказаться и сообщить о пропуске.
</details>

```
[LUNA] Верно. Собирай.
```

## Разбор типичных ошибок

1. **Сборка в порядке прихода.** Получится каша — с этого серия и начинается.
2. **Сортировка сегментов вместо укладки.** Не разрешает перекрытия и дубликаты.
3. **Пропуски не отслеживаются.** Дыра станет неотличима от данных.
4. **Длина потока как сумма длин сегментов.** При перекрытии завысит; правильно — максимум `seq + len`.
5. **Нет проверки границ буфера.** `seq` приходит из сети: `memcpy` по нему без проверки — запись за границей.
