## Теория: конвейер

### Порядок операций

```
сегменты  →  укладка по seq  →  проверка покрытия  →  XOR  →  текст
                                       │
                                       └─ есть дыра? стоп, отказ
```

Почему сборка строго перед расшифровкой: XOR обрабатывает каждый байт независимо, но **байт должен стоять на своём месте**. Расшифровать сегменты по отдельности и потом склеить — то же самое по результату **только** если границы сегментов совпали идеально и ни один не потерялся. Первое условие неочевидно, второе не гарантировано.

Общее правило конвейеров: **каждый этап получает на вход то, что предыдущий гарантировал**. Расшифровка гарантированно работает на непрерывном потоке; на «почти непрерывном» она не гарантирует ничего.

### Отказ как правильное поведение

```c
if (gaps != 0) {
    fprintf(stderr, "поток неполон: %zu пропущенных байт\n", gaps);
    return 1;
}
```

Соблазн расшифровать «что есть» велик — тем более что результат будет выглядеть прилично. Именно поэтому отказ должен быть встроен в код, а не оставлен на усмотрение оператора в три часа ночи.

Это тот же принцип, который вы видели с битой свечой в s05e01 (её отбрасывают, а не «чинят») и с проверкой длины пакета в s03e05. Формулировка одна: **сомнительные данные отвергают, а не улучшают**.

### Чем это не является

XOR с однобайтовым ключом — не шифрование. Вы вскрыли его в первую ночь, зная один символ открытого текста; частотный анализ ломает его без всякого знания.

Он здесь ровно потому, что вы уже умеете его читать: серия про конвейер, а не про криптографию. Настоящая криптография — на USB, который передадут через двадцать минут.

## Проверка на канале

```
[LUNA] Последние два вопроса сезона.
```

**1.** LUNA: «Почему сначала сборка, а потом расшифровка? XOR ведь побайтовый.»

<details><summary>Ответ</summary>

Потому что побайтовость означает независимость от **соседей**, а не от **позиции**. Расшифровав сегменты по отдельности и склеив их в порядке прихода, вы получите правильно расшифрованные куски в неправильном порядке. А если применять ключ с позиционным сдвигом — то и сами куски окажутся неверными. Порядок этапов в конвейере не вопрос вкуса: каждый следующий опирается на гарантию предыдущего.
</details>

**2.** LUNA: «В потоке одна дыра. Расшифровать остальное и прочитать, что получится?»

<details><summary>Ответ</summary>

Нет. Результат будет читаемым и правдоподобным, а несколько слов в нём — ложью, причём вы не узнаете какой именно. Это хуже, чем отсутствие результата: на отсутствие вы отреагируете, на правдоподобную подмену — нет. Программа обязана отказаться сама, а не оставлять решение человеку.
</details>

```
[LUNA] Верно. Запускай.
```

## Разбор типичных ошибок

1. **Расшифровка до сборки.** Мусор на стыках или полная бессмыслица.
2. **Обработка потока с пропусками.** Правдоподобная ложь вместо честного отказа.
3. **Пропуски считаются, но не проверяются.** Число выведено, программа продолжила.
4. **Границы буфера не проверены.** `seq` приходит из сети.
5. **Вывод сообщения без завершающего нуля.** Печать уедет за границу.
