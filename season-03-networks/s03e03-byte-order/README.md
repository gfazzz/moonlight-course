## Теория: одно число, два прочтения

### Что происходит

Число `0x01BB` занимает два байта. Порядок их размещения в памяти — вопрос соглашения:

```
little-endian (x86, ARM):   BB 01     младший байт первым
big-endian (сеть):          01 BB     старший байт первым
```

Внутри одной машины разницы не видно: программа кладёт и читает одинаково. Разница появляется, когда байты пересекают границу — уходят в сеть или в файл.

### Как узнать свою машину

```c
uint32_t probe = 1;
int little = (*(unsigned char *)&probe == 1);
```

Если первый байт числа `1` равен единице — младший байт лежит первым, машина little-endian. Приведение к `unsigned char *` здесь законно: смотреть на объект побайтово через `char *` стандарт разрешает явно (единственное исключение из правила строгого алиасинга).

### Конвертация

```c
uint16_t on_wire = htons(443);      /* host to network short */
uint16_t port    = ntohs(on_wire);  /* network to host short */
```

Функции меняют **порядок байтов**, а не значение. На big-endian машине они не делают ничего и компилируются в пустоту — но писать их надо всегда, иначе код перестанет работать при переносе.

Правило без исключений: **каждое многобайтовое поле при записи в пакет проходит через `hton*`, при чтении из пакета — через `ntoh*`**. Однобайтовые поля не нуждаются ни в чём.

[LUNA] Два вопроса. Здесь ошибаются и опытные.

**1.** LUNA: «Что вернёт `htons(443)` на big-endian машине?»

<details><summary>Ответ</summary>

`443` без изменений. На big-endian хост уже хранит байты в том порядке, который принят в сети, поэтому конвертация — тождественная операция и компилятор выбрасывает её целиком. Именно поэтому вызовы `hton*` пишут всегда: на такой машине они бесплатны, а на little-endian необходимы. Код, работающий «потому что архитектура совпала», ломается при первом же переносе.
</details>

**2.** LUNA: «Прочитал два байта порта в `uint16_t`, получил 47873. Что забыл?»

<details><summary>Ответ</summary>

`ntohs`. Байты пришли в сетевом порядке — `01 BB`, — а процессор прочитал их как little-endian и собрал `0xBB01`, то есть 47873. После `ntohs` получится `0x01BB` = 443. Обратите внимание: программа не упала и не пожаловалась. Она вернула правдоподобное число, и это худший вид ошибки.
</details>

```
[LUNA] Верно. Переворачивай правильно.
```

## Разбор типичных ошибок

1. **Чтение поля пакета без `ntoh*`.** Правдоподобный мусор вместо числа.
2. **Запись своего числа без `hton*`.** Получатель прочитает не то, что вы отправили.
3. **Конвертация однобайтовых полей.** Бессмысленна: у одного байта нет порядка.
4. **Двойная конвертация.** `ntohs(ntohs(x))` вернёт исходное значение — ошибка, которую легко не заметить на симметричных числах вроде `0xABAB`.
5. **Предположение «мы всегда на x86».** Определяйте или конвертируйте всегда.
