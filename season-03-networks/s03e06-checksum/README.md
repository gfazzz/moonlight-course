## Теория: сумма, которая сворачивается в ноль

### Алгоритм

```c
uint16_t inet_checksum(const uint8_t *data, size_t len) {
    uint32_t sum = 0;
    for (size_t i = 0; i + 1 < len; i += 2)
        sum += ((uint32_t)data[i] << 8) | data[i + 1];
    if (len & 1) sum += (uint32_t)data[len - 1] << 8;      /* нечётный хвост */

    while (sum >> 16) sum = (sum & 0xFFFF) + (sum >> 16);  /* свернуть переносы */
    return (uint16_t)~sum;
}
```

Три шага: сложить 16-битные слова, вернуть перенос в младшие разряды, взять побитовое дополнение.

Свёртка переносов — это сложение в **обратном коде**. Оно даёт главное свойство: результат не зависит ни от порядка слов, ни от порядка байтов машины. Big-endian и little-endian получат одинаковую сумму — редкий случай, когда конвертация не нужна вовсе.

### Проверка сводится к нулю

Поле суммы перед вычислением обнуляют, результат записывают на его место. Тогда у получателя:

```
сумма по всему заголовку, включая поле, == 0x0000
```

Сравнивать не с чем — достаточно проверить ноль. Приём тот же, что с XOR-суммой в s01e02, и он же вернётся с CRC-16 в s06e05.

### От чего защищает

| Ситуация | Поймает |
|---|---|
| одиночная ошибка бита | да |
| искажение одного байта | да |
| перестановка **слов** | нет — сложение коммутативно |
| компенсирующие ошибки в двух словах | нет |
| намеренная подделка | **нет** — сумму пересчитают |

Последняя строка — содержание серии. Контрольная сумма защищает от **случайного** искажения, и только. Против подделки нужна подпись на секрете, которого у противника нет: HMAC, а не сумма. Это Season 4.

## Проверка: LUNA задаёт вопросы
```
[LUNA] Два вопроса. Второй важнее первого.
```

**1.** LUNA: «Зачем сворачивать перенос обратно, а не отбросить старшие биты?»

<details><summary>Ответ</summary>

Потому что это сложение в обратном коде, а не обычное по модулю 2¹⁶. Возврат переноса в младшие разряды делает сумму независимой от порядка слагаемых и от порядка байтов машины — благодаря этому big-endian и little-endian получают одинаковый результат без конвертации. Простое отбрасывание переноса это свойство сломало бы.
</details>

**2.** LUNA: «Сумма сошлась. Значит ли это, что пакет прислал тот, кто указан в поле источника?»

<details><summary>Ответ</summary>

Нет. Сумма считается по открытым данным, без всякого секрета, — пересчитать её может кто угодно, изменив хоть все поля. Она отвечает на вопрос «дошло ли без искажений», а не «кто отправил». Для второго нужна подпись на ключе, которого нет у постороннего: HMAC или цифровая подпись. Путать целостность с подлинностью — распространённая и дорогая ошибка.
</details>

```
[LUNA] Верно. Считай.
```

## Разбор типичных ошибок

1. **Перенос отброшен вместо свёртки.** Сумма перестанет быть независимой от порядка.
2. **Поле суммы не обнулено перед вычислением.** Результат окажется другим.
3. **Забыто дополнение `~`.** Проверка не сведётся к нулю.
4. **Нечётная длина не обработана.** Последний байт потеряется.
5. **Накопление в `uint16_t`.** Переносы пропадут; нужен `uint32_t`.
6. **Попытка применить `htons` внутри алгоритма.** Не нужна и всё сломает.
