## Обстановка

Оба пакета заявляют одного отправителя. Один настоящий, второй — подделка. По содержимому не различить.

Различит контрольная сумма — если подделывавший её не пересчитал.

## Приказ

Написать `artifacts/checksum.c`: реализовать интернет-контрольную сумму, вставить её в заголовок, проверить сведение к нулю и показать, что порча одного байта проверку ломает.

## Дано

Заголовок IPv4 из предыдущей серии. Алгоритм — RFC 1071: сумма 16-битных слов, свёртка переносов, побитовое дополнение.

## Критерии приёмки

- [ ] Компилируется с `-Wall -Wextra -std=c11` без предупреждений.
- [ ] Накопление идёт в **32-битной** переменной, иначе переносы теряются.
- [ ] Переносы **сворачиваются** обратно в младшие разряды, а не отбрасываются.
- [ ] В конце берётся побитовое дополнение.
- [ ] Нечётная длина обработана: последний байт учитывается как старший байт слова.
- [ ] Поле суммы **обнуляется** перед вычислением.
- [ ] После вставки сумма по всему заголовку равна `0x0000` — проверка сводится к нулю, а не к сравнению.
- [ ] Порча одного байта даёт ненулевую сумму и вердикт `INVALID`.
- [ ] Вывод совпадает с `tests/expected.txt`; `make test` → `PASS`.

## Выполнение

```bash
cp starter.c artifacts/checksum.c
make test
```

Ожидается `computed checksum = 0x2053`, затем `0x0000 -> valid` и после порчи `0x9700 -> INVALID`. Эталон — в `solution/`.

## Диагностика

| Симптом | Причина |
|---|---|
| проверка не даёт ноль | забыто дополнение `~` или поле не обнулено |
| сумма зависит от платформы | переносы отбрасываются вместо свёртки |
| последний байт не влияет на результат | не обработана нечётная длина |
| сумма всегда мала | накопление в `uint16_t` |
| значения не совпадают с эталоном | применён `htons` внутри алгоритма — он тут не нужен |

## После выполнения

Настоящий пакет пройдёт проверку, поддельный — нет. И станет видно, что настоящих сегментов с того же адреса не один, а несколько десятков — и приходят они вперемешку.
