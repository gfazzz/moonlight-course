# Теория — s03e02

## 1. «Похож на своего» и «свой»

> *— Вот два адреса. Который из них в моей сети?*
> *Я посмотрел: `192.168.1.14` и `192.168.2.100`.*
> *— Ну, первый точно. Второй… наверное, тоже, они же оба 192.168.*
> *— «Наверное» — это не ответ, а надежда. Ты не знаешь маску. Без неё вопрос не имеет смысла: при /16 оба свои, при /24 — только первый, при /30 — ни одного.*
> *— То есть один и тот же адрес может быть и своим, и чужим?*
> *— Он всегда и свой, и чужой. Пока ты не сказал, где граница.*

Ключевая мысль: **адрес сам по себе не принадлежит никакой сети**. Принадлежность появляется только вместе с маской, и одно без другого бессмысленно. Поэтому в конфигурациях адрес всегда пишут вместе с префиксом: `192.168.1.14/24`.

## 2. Маска: как строится и почему так

Маска — это `n` единиц слева и `32 − n` нулей справа:

```
/24 → 11111111 11111111 11111111 00000000 → 255.255.255.0
/20 → 11111111 11111111 11110000 00000000 → 255.255.240.0
```

```c
uint32_t mask = (n == 0) ? 0 : (0xFFFFFFFFu << (32 - n));
```

**Про сдвиг на 32.** Стандарт объявляет неопределённым сдвиг на количество бит, большее или равное разрядности типа. Это не педантизм: инструкция `shl` на x86 берёт счётчик по модулю 32, поэтому `x << 32` вернёт `x`, а не ноль. Компилятор, вычисляя константу на этапе компиляции, может получить ноль — и код начнёт вести себя по-разному в зависимости от того, известно ли `n` заранее. Отсюда отдельная ветка для `/0`.

Второй способ, свободный от этой проблемы:

```c
uint32_t mask = n ? ~((1u << (32 - n)) - 1) : 0;   /* всё равно нужен случай n == 0 */
uint32_t mask = (uint32_t)(0xFFFFFFFFULL << (32 - n));  /* 64-битный сдвиг безопасен */
```

Последний вариант работает и для `/0`, потому что сдвиг на 32 в 64-битном типе определён.

## 3. Три адреса, которые нельзя выдавать

```c
network   = ip & mask;
broadcast = network | ~mask;
```

| Адрес | Значение |
|---|---|
| `network` | идентификатор самой сети; в таблицах маршрутизации именно он |
| `broadcast` | «всем узлам этой сети»; пакет доставляется каждому |
| хосты | всё между ними |

Отсюда «минус два» в подсчёте: `/24` даёт 256 адресов и 254 пригодных.

**Исключения, о которых полезно знать.** Для соединений точка-точка два потерянных адреса из четырёх — расточительство, поэтому RFC 3021 разрешает `/31`: оба адреса используются как хостовые, broadcast не нужен, потому что «все» — это и есть второй конец. А `/32` описывает единственный адрес и применяется для маршрутов к конкретному хосту и loopback-интерфейсов.

## 4. Почему CIDR заменил классы

До 1993 года адрес делился на сеть и хост по первым битам:

| Класс | Префикс | Сетей | Хостов в сети |
|---|---|---|---|
| A | `/8` | 128 | 16 777 214 |
| B | `/16` | 16 384 | 65 534 |
| C | `/24` | 2 097 152 | 254 |

Проблема очевидна на цифрах: организации на тысячу машин класс C (254) мал, а класс B (65 534) избыточен в шестьдесят раз. Выдавали B — и адреса кончались катастрофически быстро.

**CIDR** (RFC 4632) отменил классы: префикс стал произвольным. Организации на тысячу машин выдают `/22` — 1022 адреса. Плюс появилась **агрегация маршрутов**: соседние блоки объединяются в один маршрут с более коротким префиксом, что удерживает таблицы магистральных маршрутизаторов от неконтролируемого роста.

Слова «класс A» и «класс C» до сих пор в ходу как жаргон, но в протоколе их нет уже тридцать лет.

## 5. Самое длинное совпадение

Маршрутизатор хранит записи вида «префикс → куда слать» и для каждого пакета выбирает **самый длинный совпавший префикс**:

```
0.0.0.0/0        → шлюз по умолчанию
203.0.0.0/8      → провайдер A
203.0.113.0/24   → провайдер B
```

Пакет на `203.0.113.42` совпадёт со всеми тремя записями и уйдёт по третьей — она конкретнее. Правило одно и то же для домашнего компьютера и для магистрального маршрутизатора; разница только в размере таблицы (в глобальной их около миллиона).

Отсюда, кстати, устройство маршрута по умолчанию: `0.0.0.0/0` совпадает с чем угодно и имеет нулевую длину, то есть проигрывает любому другому совпадению. «Всё остальное — туда».

## 6. Подмена источника и как её ловят

Поле адреса источника в IP-заголовке заполняет отправитель, и никто не мешает написать там что угодно. Отсюда два класса проблем:

- **отражённые атаки** — запрос с подделанным источником, ответ уходит жертве. Особенно эффективно там, где ответ намного больше запроса (DNS, NTP);
- **обход доверия по адресу** — сервис пускает «локальных», атакующий называется локальным.

Основная защита — **фильтрация по обратному пути** (RFC 3704): пакет отбрасывается, если пришёл с интерфейса, через который до заявленного источника не добраться. Проверка ровно та же, что в задаче серии, — сравнение адреса с подсетью интерфейса.

Практический вывод, который стоит вынести за пределы курса: **адрес источника не является идентификацией**. Он подсказка, а не доказательство. Всё, что строит доверие на адресе, строит его на песке.

## 7. Битовые приёмы, которые пригодятся

```c
/* сколько адресов в подсети */
uint32_t count = (n == 32) ? 1 : (1u << (32 - n));

/* префикс из маски: подсчёт единиц */
int prefix = __builtin_popcount(mask);          /* GCC/Clang */

/* проверка, что маска валидна: единицы только слева */
int valid = (mask == 0) || ((~mask + 1) & ~mask) == 0;
```

Последняя проверка стоит объяснения: у корректной маски единицы идут непрерывно слева, поэтому `~mask` — это `2^k − 1`, а такое число обладает свойством `(x + 1) & x == 0`. Маска вида `255.0.255.0` его не проходит — и правильно, такой маски быть не может.
