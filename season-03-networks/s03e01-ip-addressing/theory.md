# Теория — s03e01

## 1. Точки придумали для людей

> *Виктор написал на салфетке `3232235876` и подвинул ко мне.*
>
> — Что это?
> — Число.
> — Это `192.168.1.100`. Точки — оформление, чтобы человек не считал в уме. Машине они не нужны: в заголовке пакета лежат четыре байта подряд, и никаких точек там нет.
> — Тогда зачем вообще октеты?
> — Чтобы можно было отрезать кусок. Маска режет число по битам, а по точкам это удобно объяснять. Октеты — компромисс между тем, как работает железо, и тем, как думает человек.

Формально: IPv4-адрес — беззнаковое 32-битное целое. Запись через точку (dotted-quad) — способ его отображения, один из нескольких. Исторически `inet_addr` принимал и `0xC0A80164`, и `3232235876`, и даже `192.11010660` — сокращённые формы до сих пор понимает `ping` в большинстве систем.

Это не курьёз, а источник уязвимостей: проверка «строка выглядит как приватный адрес» обходится записью того же адреса в другой форме. Правило: **сравнивать разобранные числа, а не строки**.

## 2. Сборка из октетов и почему приведение обязательно

```c
uint32_t ip = ((uint32_t)a << 24) | ((uint32_t)b << 16)
            | ((uint32_t)c << 8)  |  (uint32_t)d;
```

Без приведения `a << 24` вычисляется в `int` (32 бита со знаком). При `a >= 128` единица заезжает в знаковый бит, и стандарт объявляет это **неопределённым поведением**.

Коварство в том, что на большинстве компиляторов «работает». Ошибка спит, пока адреса начинаются с чисел меньше 128, и просыпается на `192.x`, `203.x`, `224.x` — то есть на настоящих.

Общее правило, стоящее заучивания: **битовые операции — только на беззнаковых типах**. Знаковые сдвиги, знаковое переполнение и знаковое расширение при повышении типов дают три разных способа получить сюрприз.

Обратная операция:

```c
printf("%u.%u.%u.%u\n", (ip >> 24) & 0xFF, (ip >> 16) & 0xFF,
                        (ip >>  8) & 0xFF,  ip        & 0xFF);
```

Маска `& 0xFF` нужна везде, кроме старшего октета, но пишут её везде — единообразие дешевле рассуждений.

## 3. `sscanf`: удобно и опасно

```c
if (sscanf(s, "%d.%d.%d.%d%c", &a, &b, &c, &d, &extra) != 4) return INVALID;
```

Приём с завершающим `%c` — стандартная идиома: он ловит мусор после адреса. Требование `== 4` означает «четыре поля разобраны, пятое не совпало».

О чём стоит знать, пользуясь `sscanf`:

- **`%d` принимает знак.** `-1.2.3.4` разберётся, и проверка диапазона обязана это отсечь.
- **Пробелы пропускаются.** `" 1 . 2 . 3 . 4"` пройдёт формат — если это недопустимо, проверяйте отдельно.
- **`%s` без ограничения ширины — переполнение буфера.** Всегда `%31s` для `char buf[32]`.
- **Возврат `EOF`** отличается от нуля: строка кончилась до первого преобразования.

Альтернатива для настоящего кода — `inet_pton`:

```c
struct in_addr addr;
if (inet_pton(AF_INET, s, &addr) != 1) return INVALID;
```

Она строже (никаких сокращённых форм), работает и с IPv6, и возвращает результат уже в сетевом порядке байтов. В этой серии разбор делается руками намеренно — чтобы было видно, что внутри.

## 4. Специальные диапазоны

| Диапазон | Назначение | RFC |
|---|---|---|
| `0.0.0.0/8` | «этот хост», неизвестный адрес | 1122 |
| `10.0.0.0/8` | приватный | 1918 |
| `127.0.0.0/8` | loopback — **вся сеть /8**, не только `.1` | 1122 |
| `169.254.0.0/16` | link-local, автонастройка при отсутствии DHCP | 3927 |
| `172.16.0.0/12` | приватный | 1918 |
| `192.0.2.0/24`, `198.51.100.0/24`, `203.0.113.0/24` | **для документации** | 5737 |
| `192.168.0.0/16` | приватный | 1918 |
| `224.0.0.0/4` | multicast | 5771 |
| `255.255.255.255` | широковещательный | 919 |

Две детали, которые часто удивляют.

**Loopback — это `/8`, а не один адрес.** `127.0.0.2` и `127.13.37.1` тоже loopback; этим пользуются, чтобы разнести локальные сервисы по адресам.

**`203.0.113.42` — не случайный адрес.** Диапазон `203.0.113.0/24` зарезервирован RFC 5737 специально для примеров и документации, чтобы в учебных текстах не фигурировали чужие настоящие серверы. По той же причине в курсе встречаются `192.0.2.x` и `198.51.100.x`.

## 5. Порядок байтов: почему это будет проблемой

Число `0xC0A80164` в памяти лежит по-разному:

```
little-endian (x86):  64 01 A8 C0
big-endian (сеть):    C0 A8 01 64
```

В сети принят big-endian — его называют **сетевым порядком**. Поэтому адрес, прочитанный из пакета как четыре байта подряд, на x86 нельзя просто скопировать в `uint32_t`: получится перевёрнутое число.

Отсюда семейство функций:

```c
uint32_t htonl(uint32_t);   /* host to network long  */
uint32_t ntohl(uint32_t);   /* network to host long  */
uint16_t htons(uint16_t);   /* то же для 16 бит: порты */
```

На big-endian машинах они не делают ничего, но писать их надо всегда — иначе код перестанет работать при переносе. Подробно — s03e03, там это отдельная тема с задачей.

## 6. Почему адресов не хватило

32 бита — примерно 4.3 миллиарда адресов, из которых значительная часть зарезервирована. Свободные блоки IANA закончились в 2011 году.

Решения, работающие сегодня:

- **NAT** — за одним публичным адресом прячется целая частная сеть. Ломает исходную идею интернета «каждый узел адресуем» и создаёт всю сложность с пробиванием соединений.
- **CIDR** — отказ от классов A/B/C в пользу произвольной длины префикса (s03e02); позволил выдавать блоки по потребности, а не кратно классу.
- **IPv6** — 128 бит. Внедряется третье десятилетие.

Знать это стоит не ради истории: NAT объясняет, почему приватный адрес в перехвате — сильная улика (источник в той же сети), и почему прямое соединение между двумя узлами за NAT требует отдельных ухищрений.
