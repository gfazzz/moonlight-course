## 1. Арифметика вместо отладки

> *— Ошибку в реализации ловит отладчик. Ошибку в алгоритме не ловит ничто, кроме арифметики. Считай варианты до того, как напишешь первую строку.*

Наивный алгоритм:

```c
for (i = 0; i < n; i++)
    swap(a, i, random_below(n));      /* НЕПРАВИЛЬНО */
```

`n` шагов по `n` вариантов — `nⁿ` равновероятных путей. Перестановок ровно `n!`.

| `n` | путей `nⁿ` | перестановок `n!` | делится |
|---|---|---|---|
| 3 | 27 | 6 | нет |
| 4 | 256 | 24 | нет |
| 5 | 3125 | 120 | нет |

Деления нет никогда при `n > 2`, потому что `nⁿ` содержит только простые делители самого `n`, а `n!` содержит все простые числа до `n`.

Значит, часть перестановок достигается большим числом путей, чем другие. Смещение структурное: **никакой генератор его не устраняет**.

Замер даёт отклонение 11.7 % при 60000 испытаний. Отличить систематику от шума просто: увеличьте число испытаний вдесятеро. Шум упадёт примерно втрое, систематика останется.

## 2. Фишер — Йетс в форме Кнута

```c
for (i = n - 1; i > 0; i--)
    swap(a, i, random_below(i + 1));   /* ПРАВИЛЬНО */
```

На шаге `i` выбор из `i + 1` вариантов. Всего путей `n · (n−1) · … · 2 = n!` — ровно столько, сколько перестановок, и каждая достигается **единственным** путём. Отсюда строгая равномерность при идеальном источнике.

Две детали, которые ломают алгоритм при небрежности:

**Диапазон включает `i`.** Элемент обязан иметь право остаться на месте. Сужение до `[0, i)` даёт другое смещение — перестановки без неподвижных точек становятся вероятнее.

**Направление и диапазон согласованы.** Восходящая форма тоже верна:

```c
for (i = 0; i < n - 1; i++)
    swap(a, i, i + random_below(n - i));
```

но смешивать половинки двух форм нельзя — получится третий, неправильный алгоритм.

История: Фишер и Йетс описали процедуру в 1938 году для таблиц случайных чисел, Дурстенфельд в 1964-м переписал её для работы на месте за линейное время, Кнут привёл в TAOCP как алгоритм P.

## 3. Смещение остатка

```c
int idx = rand() % n;        /* смещено, если RANGE % n != 0 */
```

Источник даёт `RANGE` равновероятных значений. При `RANGE % n != 0` первые `RANGE % n` остатков получают на один исход больше.

Источник `[0, 10)`, `n = 3`:

```
остаток 0 <- {0, 3, 6, 9}   4 исхода
остаток 1 <- {1, 4, 7}      3 исхода
остаток 2 <- {2, 5, 8}      3 исхода
```

Перекос 33 % на первую корзину. В замере видно 20 % — часть гасится другими эффектами выборки.

Отбраковка:

```c
uint32_t limit = RANGE - (RANGE % n);
do { r = next(); } while (r >= limit);
return r % n;
```

Отбрасывается «неудобный хвост» — та часть диапазона, которая не укладывается в целое число полных циклов.

**Цена.** Вероятность отбраковки не превышает `n / RANGE`, то есть при разумных `n` — доли процента. Математическое ожидание числа попыток меньше 1.01. Утверждение «отбраковка медленная» — миф; медленным бывает деление, а не цикл.

**Почему не «просто игнорировать».** На диапазоне `2³¹` и `n = 3` перекос порядка `1e-9`. Но код переживает условия, для которых писался: ту же функцию вызовут с `n` в миллионы или с 16-битным источником. Отбраковка стоит дёшево — пишется всегда.

## 4. Качество генератора

Линейный конгруэнтный генератор `x = a·x + c` удобен, воспроизводим и слаб:

| Слабость | Проявление |
|---|---|
| короткий период младших битов | младший бит чередуется 0-1-0-1 |
| точки ложатся на плоскости | теорема Марсальи: в `k` измерениях не более `(k!·m)^(1/k)` гиперплоскостей |
| предсказуемость | состояние восстанавливается по нескольким выходам |

Первая строка объясняет `>> 16` в коде: старшие биты качественнее младших.

Вторая — почему линейный генератор нельзя использовать в многомерных симуляциях: точки `(x₁, x₂, x₃)` укладываются на небольшое число плоскостей, и интегрирование по объёму даёт систематическую ошибку.

| Применение | Чем пользоваться |
|---|---|
| воспроизводимые тесты | LCG, если качество не критично |
| статистика и симуляции | Mersenne Twister, PCG, xoshiro |
| криптография, секреты, токены | только `getrandom` / `/dev/urandom` |

Проверяют генераторы батареями: Diehard, TestU01, NIST STS. Mersenne Twister проваливает часть тестов TestU01, что для симуляций обычно неважно и делает его непригодным для криптографии.

## 5. Зачем это в машинном обучении

| Где | Как проявляется смещение |
|---|---|
| разбиение на обучение и проверку | классы распределены неравномерно, оценка неправдива |
| порядок примеров при обучении | сходимость зависит от систематики в перемешивании |
| бутстрап | доверительные интервалы смещены |
| перекрёстная проверка | фолды неоднородны |

Первая строка — самая дорогая, и она смыкается с подгонкой из s05e05. Общий принцип формулируется одинаково: **проверка, устроенная удобно для проверяемого, ничего не проверяет**.

## 6. Резервуарная выборка

Родственная задача: взять `k` равновероятных элементов из потока неизвестной длины, храня только `k`.

```c
if (i < k)  reservoir[i] = x;
else {
    size_t j = random_below(i + 1);
    if (j < k) reservoir[j] = x;
}
```

Доказательство равномерности индукцией по `i`; результат тот же, что у Фишера — Йетса, но без знания длины заранее.

Применяется там же, где всё остальное из s08e01: логи, потоки событий, данные, которые не помещаются в память.

## 7. Python как компаньон

`random.shuffle` и `numpy.random.permutation` реализуют Фишера — Йетса, `np.random.default_rng()` использует PCG64.

Внутренности всё равно стоит знать:

- `random.seed()` даёт воспроизводимость, потому что состояние генератора детерминировано;
- брать `%` от `randint` вручную нельзя по той же причине, что и в C;
- для токенов и паролей существует модуль `secrets` — обычный генератор предсказуем по нескольким выходам, и это не теоретическая угроза: онлайн-казино теряли деньги именно так.
