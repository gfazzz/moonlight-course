## Теория: считать, не загружая

### Отображение вместо чтения

```c
const double *data = mmap(NULL, size, PROT_READ, MAP_PRIVATE, fd, 0);
```

Файл становится массивом. Страницы подгружаются по обращению и вытесняются при нехватке памяти — куча под данные не расходуется вовсе.

| Подход | Память | Когда применим |
|---|---|---|
| `malloc` + `read` целиком | размер файла | файл меньше памяти |
| чтение блоками | размер блока | всегда, но код сложнее |
| `mmap` | страницы по требованию | последовательный и случайный доступ |

### Один проход

Если данные не помещаются в память, алгоритм обязан быть однопроходным: каждый элемент читается один раз, состояние — фиксированный набор накопителей.

Минимум, максимум, сумма и среднее считаются так тривиально. Дисперсия — нет.

### Где ломается школьная формула

```
Var = (Σx² − n·mean²) / (n − 1)
```

Математически безупречно. Численно — ловушка.

При значениях около `1e8` и разбросе в сотню оба слагаемых огромны и почти равны. Их разность съедает значащие цифры: остаются младшие биты, состоящие в основном из ошибок округления.

Явление называется **катастрофическим вычитанием**, и в этой задаче оно даёт `874.25` вместо `835.36` — почти пять процентов. При большем смещении формула способна выдать отрицательную дисперсию, что уже хотя бы заметно.

### Метод Уэлфорда

```c
delta = x - mean;
mean += delta / (i + 1);
m2   += delta * (x - mean);   /* mean уже обновлён — так и надо */
var = m2 / (n - 1);
```

Больших чисел друг из друга не вычитается: всё считается через отклонения от текущего среднего, а они малы. Плюс среднее доступно в любой момент, а не только в конце.

Алгоритм опубликован в 1962 году и с тех пор не улучшен для однопроходного случая.

## Проверка: LUNA задаёт вопросы
```
[LUNA] Два вопроса, прежде чем ты тронешь дамп.
```

**1.** LUNA: «Данные около `1e8`, разброс — сотня. Почему школьная формула здесь врёт?»

<details><summary>Ответ</summary>

Потому что `Σx²` и `n·mean²` получаются огромными и почти равными, а их разность — маленькой. При вычитании старшие разряды сокращаются, и от результата остаются только младшие биты, которые к этому моменту состоят преимущественно из накопленных ошибок округления. Это катастрофическое вычитание: сама операция вычитания точна, но точность потеряна раньше — при сложении больших величин. В задаче ошибка составляет почти пять процентов, а при большем смещении формула может выдать отрицательную дисперсию.
</details>

**2.** LUNA: «Почему `mmap`, а не `malloc` плюс `read`?»

<details><summary>Ответ</summary>

Потому что `malloc` требует памяти на весь файл сразу, а файл может быть больше оперативной памяти на порядки. `mmap` отображает файл в адресное пространство: ядро подгружает страницы по обращению и вытесняет их при нехватке памяти, так что расход ограничен рабочим множеством, а не размером данных. Дополнительный выигрыш — отсутствие копирования: при `read` данные идут через буфер ядра в буфер программы, при отображении читаются на месте.
</details>

## Разбор типичных ошибок

1. **Школьная формула дисперсии.** На смещённых данных теряет точность вплоть до отрицательных значений.
2. **Файл читается в массив.** Для больших данных не работает.
3. **Результат `mmap` сравнивается с `NULL`.** Ошибка — это `MAP_FAILED`.
4. **Второй проход по данным.** Для потоковой обработки недопустим.
5. **Размер задан константой, а не взят из `fstat`.** Программа сломается на другом файле.
6. **`munmap` и `unlink` не вызваны.** Отображение и временный файл останутся.

## Python как компаньон

То же самое на Python — три строки:

```python
import numpy as np
a = np.memmap("data.bin", dtype="float64")
print(a.mean(), a.var(ddof=1))
```

`numpy` использует тот же приём отображения и внутри устойчив к катастрофическому вычитанию. Разделение труда практическое: **Python — для исследования и графиков, C — для горячего пути и вывода на устройстве**.

Понимая C, вы понимаете и почему `df.apply()` в сто раз медленнее векторизованной операции: первое — цикл интерпретатора, второе — тот же цикл, но скомпилированный.
