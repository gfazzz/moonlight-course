## Теория: `malloc` / `free`

```c
int *buf = malloc((size_t)n * sizeof(int));   // n int'ов, размер в БАЙТАХ
if (buf == NULL) { perror("malloc"); return 1; }  // может не хватить памяти

for (int i = 0; i < n; i++) buf[i] = i * i;   // работаем как с обычным массивом

free(buf);    // вернули память системе
buf = NULL;   // чтобы не воспользоваться освобождённым (dangling)
```

Три вещи, которые отличают кучу от стека:

- размер задаётся в рантайме (`n` может прийти из файла/сети);
- память живёт, пока не вызовешь `free` (а не до конца функции);
- `malloc` **не** обнуляет память — там мусор (нужны нули — `calloc`).

Правила гигиены (нарушишь — утечки и крахи, s02e07–e08): каждый `malloc` → свой `free`; `free` ровно один раз; после `free` — `NULL`. Подробнее — [`theory.md`](theory.md).

## Проверка на канале

```
[LUNA] Два вопроса. Куча ошибок не прощает — она их копит.
```

**1.** LUNA: «Почему `malloc(n)` под `n` целых — это баг, а `malloc(n * sizeof(int))` — нет?»

<details><summary>Ответ</summary>

Аргумент `malloc` — размер в байтах. `malloc(n)` даст `n` байт (хватит только на `n/4` int'ов). Нужно `n * sizeof(int)`.
</details>

**2.** LUNA: «Зачем `buf = NULL` после `free(buf)`?»

<details><summary>Ответ</summary>

После `free` указатель «висячий»: показывает на возвращённую память. Обнуление превращает случайное использование в честный крах на `NULL`, а не в тихую порчу данных.
</details>

```
[LUNA] Верно. Бери память.
```

## Разбор типичных ошибок

1. **`malloc(n)` вместо `malloc(n*sizeof(int))`.** Размер в байтах; недобор памяти → выход за границы.
2. **Нет проверки `NULL`.** `malloc` может не дать память; работа с `NULL` — краш.
3. **Забыл `free`.** Утечка. Каждый `malloc` — свой `free`.
4. **`free` дважды / использование после `free`.** Double-free и dangling — порча кучи. После `free` → `NULL`.
