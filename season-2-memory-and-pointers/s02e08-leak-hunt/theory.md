# Теория (углублённо) — s02e08

## 1. Освобождение связного списка

У списка на каждый узел — минимум две аллокации (сам узел и его данные). Освобождать надо обе, и в правильном порядке:

```c
LogEntry *e = head;
while (e != NULL) {
    LogEntry *nx = e->next;   // сохранить next ДО free(e)
    free(e->message);         // сначала данные узла
    free(e);                  // потом сам узел
    e = nx;
}
```

Главная ловушка: если сделать `free(e)` до чтения `e->next`, получишь use-after-free (читаешь поле освобождённого узла). Поэтому `next` сохраняют заранее.

## 2. Кто владеет памятью

«Владение» (ownership) — кто отвечает за `free`. В логгере: `add_log` **выделяет** узел и строку, но освобождать их — работа `free_all`. Чёткое правило «кто выделил / кто освобождает» убирает и утечки, и double-free. В больших системах владение проектируют сознательно (это основа RAII в C++ и borrow-checker в Rust).

## 3. Инструменты охоты

- **AddressSanitizer**: `gcc -fsanitize=address -g prog.c`. На Linux включает LeakSanitizer — при выходе печатает `SUMMARY: … N byte(s) leaked in M allocation(s)` с трассой аллокаций.
- **valgrind** (Linux): `valgrind --leak-check=full ./prog` — без перекомпиляции, но медленнее.
- **leaks** (macOS): `leaks --atExit -- ./prog`.

Цель — не «вроде не течёт», а нулевой отчёт: `no leaks are possible` / `без утечек`.

## 4. Дисциплина, а не везение

Утечка в короткой программе незаметна (ОС всё вернёт при выходе). В демоне/сервере (Season 7) она копится сутками и кладёт систему — ровно то, чем был троян. Поэтому память чинят инструментом и дисциплиной владения, а не «на глаз».
