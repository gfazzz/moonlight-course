## Теория: метрики вместо точности

### Матрица ошибок

|  | предсказано «угроза» | предсказано «норма» |
|---|---|---|
| **реально угроза** | TP | FN |
| **реально норма** | FP | TN |

```
precision = TP / (TP + FP)     из помеченных угрозами — сколько верных
recall    = TP / (TP + FN)     из реальных угроз — сколько найдено
F1        = 2·P·R / (P + R)    гармоническое среднее
```

### Почему гармоническое среднее

Оно жёстко штрафует перекос:

| precision | recall | обычное среднее | F1 |
|---|---|---|---|
| 1.0 | 0.0 | 0.50 | **0.00** |
| 0.9 | 0.9 | 0.90 | 0.90 |
| 1.0 | 0.5 | 0.75 | 0.67 |

Первая строка описывает модель, которая пометила одну-единственную угрозу и не ошиблась. Обычное среднее выдало бы ей половину баллов, F-мера — ноль, и это честно.

### Три правила честной оценки

| Правило | Что нарушается |
|---|---|
| оценивать на **отложенных** данных | иначе это подгонка, как в s05e05 |
| перемешивать **честно** | иначе разбиение смещено, как в s08e03 |
| нормировать по статистикам **обучающей** части | иначе утечка данных |

Третье правило тоньше первых двух. Если среднее и стандартное отклонение посчитаны по всему набору, статистики проверочной части просачиваются в обучение — оценка получается завышенной, а причину найти почти невозможно.

### Зачем нормировка вообще

Признак «пакетов в секунду» измеряется десятками, «доля ошибок» — сотыми. Без приведения к общей шкале градиент по первому весу на порядки больше, допустимый шаг определяется им, и обучение по остальным признакам ползёт.

### Цена ошибок асимметрична

| Ошибка | В безопасности стоит |
|---|---|
| пропущенная угроза | взлом |
| ложная тревога | время аналитика |

Порог `0.5` не священен. Снижая его, поднимаете полноту ценой точности. Выбор порога — решение о том, какая ошибка дороже, и это ровно тот же разговор, что был в s06e07 про детектор движения.

## Проверка на канале

```
[LUNA] Два вопроса. Последние в этом сезоне.
```

**1.** LUNA: «Твоя модель дала точность 0.980. Хороший результат?»

<details><summary>Ответ</summary>

Сам по себе — неизвестно. Угрозы составляют 21 % выборки, поэтому тривиальная модель «всегда норма» даёт 0.810 без единой строки обучения. Разница между 0.810 и 0.980 — вот что нужно объяснять, а не само число. Судить следует по редкому классу: точность 0.947, полнота 0.947, F-мера 0.947. Общее правило: любую метрику надо проверять тривиальным решением, и если оно набирает много очков — метрика измеряет не то.
</details>

**2.** LUNA: «Где в этом коде можно случайно устроить утечку данных?»

<details><summary>Ответ</summary>

В нормировке. Если считать среднее и стандартное отклонение по **всему** набору, статистики проверочной части попадут в обучение: модель косвенно узнает о данных, которых видеть не должна, и оценка окажется завышенной. Правильно — считать статистики только по обучающей части и применять их к проверочной. В учебной задаче это упрощено сознательно, но в рабочем коде так делать нельзя. Утечка коварна тем, что не даёт ошибки: модель выглядит лучше, чем есть, и расхождение обнаруживается только в эксплуатации.
</details>

## Разбор типичных ошибок

1. **Модель оценивается по точности.** При дисбалансе она маскирует неспособность найти редкий класс.
2. **Разбиение без перемешивания.** Если данные упорядочены, «первые 300» — систематическая ошибка.
3. **Обучение затрагивает проверочную часть.** Оценка теряет смысл.
4. **Нормировка пропущена.** Признак с большой шкалой задавит остальные.
5. **Статистики нормировки посчитаны по всему набору.** Утечка данных.
6. **Порог взят `0.5` без обсуждения.** Он должен следовать из цены ошибок.
