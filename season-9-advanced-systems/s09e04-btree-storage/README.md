## Теория: широкий узел вместо глубокого дерева

### Метрика

| Структура | Ключей в узле | Высота на 11 млн | Чтений |
|---|---|---|---|
| двоичное дерево | 1 | 23 | 23 |
| B-дерево, степень 200 | 199–399 | 3 | **3** |

Асимптотика у обеих `O(log n)`. Разница — в основании логарифма, и она восьмикратная.

### Устройство

Дерево минимальной степени `T`:

| Свойство | Значение |
|---|---|
| ключей в узле | от `T−1` до `2T−1` |
| потомков у внутреннего узла | на один больше, чем ключей |
| порядок ключей | отсортированы внутри узла |
| глубина листьев | **одинаковая у всех** |

Последняя строка делает дерево предсказуемым: у него нет плохих случаев, как у несбалансированного двоичного.

### Расщепление

Узел из `2T−1` ключей делится на два по `T−1`, а **средний** ключ поднимается в родителя.

Поднимать именно средний обязательно: иначе половины получатся неравными и инвариант размера сломается уже на следующей вставке.

### Превентивное расщепление

Ключевой приём. Спускаясь при вставке, полного потомка расщепляют **до** того, как в него войти.

```
обычный подход:  спуститься -> вставить -> переполнилось -> тащить наверх
превентивный:    спускаясь, освобождать место заранее
```

Тогда место в родителе есть всегда, и вставка выполняется одним проходом сверху вниз. Рекурсия ничего не возвращает наверх — код заметно проще.

### Рост вверх

Полный корень порождает **новый корень**, а старый становится его потомком.

Это единственный способ сохранить одинаковую глубину всех листьев: новый уровень появляется сразу для всех путей. Обычное дерево растёт вниз и потому теряет баланс.

### Что даёт отсортированный обход

Обход по порядку выдаёт ключи отсортированными без дополнительной работы. Поэтому индекс ускоряет не только поиск по равенству, но и диапазоны, сравнения и упорядочивание.

## Проверка на канале

```
[LUNA] Два вопроса про хранилище.
```

**1.** LUNA: «Почему для базы данных двоичное дерево хуже, хотя асимптотика у обоих одинакова?»

<details><summary>Ответ</summary>

Потому что различается основание логарифма, а метрика — не сравнения, а чтения страниц. У двоичного дерева высота `log₂ n` — около двадцати трёх для одиннадцати миллионов записей; у B-дерева со степенью 200 это `log₂₀₀ n`, то есть три. Причина в том, что диск отдаёт страницу целиком: узел с одним ключом и двумя указателями занимает двадцать байт из четырёх тысяч, и остальные 99.5 % чтения тратятся впустую. B-дерево заполняет страницу целиком и потому платит за неё осмысленно.
</details>

**2.** LUNA: «Почему B-дерево растёт вверх, а не вниз, как обычное?»

<details><summary>Ответ</summary>

Чтобы сохранить инвариант одинаковой глубины всех листьев. Если бы дерево росло вниз, ветви получали бы разную длину, и гарантия предсказуемого числа чтений исчезла бы — появились бы «плохие» ключи, до которых дольше добираться. Расщепление полного корня создаёт новый корень над старым, и новый уровень появляется сразу для **всех** путей одновременно. Это единственная точка, где меняется высота дерева, и потому единственное место, где баланс может быть нарушен, — а он не нарушается по построению.
</details>

```
[LUNA] Верно. Строй индекс.
```

## Разбор типичных ошибок

1. **Расщепление после переполнения.** Придётся тащить его вверх по рекурсии.
2. **Поднимается не средний ключ.** Половины получатся неравными.
3. **Дерево растёт вниз.** Листья окажутся на разной глубине.
4. **При расщеплении забыты потомки.** У внутреннего узла вместе с ключами переезжают и указатели.
5. **Счётчик чтений считает сравнения.** Метрика перестанет отражать работу с диском.
6. **Дубликаты ключей теряются.** По ТЗ они допустимы и должны сохраняться.
