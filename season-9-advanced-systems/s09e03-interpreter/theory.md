# Теория (углублённо) — s09e03

## 1. Что добавляет интерпретатор

Арифметика (s09e02) была **чистой**: одно и то же выражение всегда даёт один результат. Настоящий язык вводит **состояние**:

- переменные живут в **окружении** (environment) — таблице «имя → значение»;
- присваивание меняет это состояние — появляется **побочный эффект**;
- порядок выполнения начинает иметь значение.

Отсюда и новый класс ошибок: **времени выполнения** (runtime). Неизвестная переменная или деление на ноль синтаксически безупречны — программа разбирается, но не может быть исполнена.

## 2. Отложенное вычисление ветвей

Главная тонкость серии. Наивная реализация `if`:

```c
long a = eval(then_branch);      // НЕПРАВИЛЬНО
long b = eval(else_branch);
return cond ? a : b;
```

Так вычисляются **обе** ветви. Для чистой арифметики это лишь трата времени, но с побочными эффектами — катастрофа: обе ветви присвоят переменные, обе напечатают текст.

Правильно — вычислять только нужную. В нашей одноприходной реализации это флаг `exec`:

```c
block(L, exec && cond);        /* then: выполняем при истине */
block(L, exec && !cond);       /* else: выполняем при лжи */
```

Невыбранная ветвь всё равно **разбирается** — иначе поток токенов собьётся и парсер потеряет место. Но ничего не исполняет. Это и есть «пропуск с сохранением синтаксической структуры».

Тот же принцип в C: `&&` и `||` вычисляют правую часть только при необходимости (short-circuit), а `if` не трогает невыбранную ветвь.

## 3. Цикл требует возврата назад

`while` — единственная конструкция, где текст читается **несколько раз**. Условие нужно перевычислять на каждой итерации, значит лексер должен вернуться к его началу:

```c
size_t cond_pos = L->pos;      /* запомнили */
for (;;) {
    L->pos = cond_pos;         /* вернулись и перечитали */
    long cond = expr(L, exec);
    block(L, exec && cond);
    if (!cond) return;
}
```

В интерпретаторе по AST (полноценном) этой возни нет: узел цикла хранит поддеревья условия и тела, и их можно обходить сколько угодно раз. Наш одноприходный вариант компактнее, но платит именно здесь — хороший повод понять, зачем вообще строят дерево.

**Защита от вечного цикла** (счётчик итераций) — не каприз: в интерпретаторе чужих скриптов это обязательная мера безопасности, иначе один битый конфиг вешает систему.

## 4. Окружение и области видимости

У нас окружение плоское: все переменные глобальны. В настоящих языках это **цепочка** окружений:

```
локальное -> охватывающее -> глобальное
```

Поиск идёт от ближайшего к дальнему; так работают лексические области видимости и замыкания. Добавить в MOON функции — значит завести стек окружений, где каждый вызов создаёт своё, а поиск проваливается наружу.

Отдельный вопрос — **время жизни**: при динамическом создании окружений появляется мусор, и нужен сборщик (подсчёт ссылок или mark-and-sweep). Именно с этого места «маленький язык» становится большим проектом.

## 5. Дерево против байткода

Наш интерпретатор — **tree-walking**: он выполняет структуру напрямую. Прост, но медленный: каждый шаг — обход указателей и ветвление по типу узла.

Быстрее — компиляция в **байткод** и виртуальная машина (Python, Lua, JVM): узлы дерева превращаются в плоский массив инструкций стековой машины (напомню: постфиксный обход из s09e02 — это уже почти байткод). Дальше — **JIT**: горячие участки компилируются в машинный код на лету (V8, LuaJIT, PyPy).

Порядок ускорения примерно такой: tree-walking → байткод (5–20×) → JIT (ещё 5–50× на подходящем коде).

## 6. Ошибки: разбора против выполнения

Важно их различать:

| | когда | пример |
|---|---|---|
| синтаксическая | до запуска | незакрытая скобка |
| времени выполнения | во время | `print a + b`, где `b` не определена |

Языки со статической типизацией переносят часть runtime-ошибок в компиляцию (проверка типов) — это отдельный этап между парсером и исполнением, которого у нас нет.
