## Теория: журнал впереди данных

```
1) записи намерений (old -> new) в журнал
2) fsync(журнал)                       <-- без этого шага всё бессмысленно
3) COMMIT + fsync
4) страницы данных (можно лениво)
```

Каждая запись журнала хранит **и старое, и новое** значение: старое нужно для undo, новое — для redo. При восстановлении: есть COMMIT в устойчивой части журнала → доигрываем (redo), нет → откатываем (undo).

Журнал пишется последовательно — это самая дешёвая запись для диска, в отличие от случайных обновлений страниц B-дерева. Подробнее — [`theory.md`](theory.md).

## Проверка на канале

```
[LUNA] Два вопроса про надёжность.
```

**1.** LUNA: «Транзакция считается зафиксированной, когда данные записаны в файл?»

<details><summary>Ответ</summary>

Нет. Когда `COMMIT` оказался **в журнале на диске**. Страницы данных могут быть записаны позже (политика no-force) — если сбой случится до этого, восстановление доиграет их по журналу. Именно поэтому журнал синхронизируется, а данные могут подождать.
</details>

**2.** LUNA: «Зачем в журнале хранить старое значение, если для восстановления достаточно нового?»

<details><summary>Ответ</summary>

Нового достаточно только для redo. Но если сбой случился **до** COMMIT, а часть страниц уже изменилась (СУБД разрешают вытеснять грязные страницы — политика steal), нужен откат к старым значениям — то есть undo. Поэтому запись хранит обе версии.
</details>

```
[LUNA] Верно. Роняй питание.
```

## Разбор типичных ошибок

1. **Писать данные до `fsync` журнала.** Порядок нарушен — WAL перестаёт защищать.
2. **Считать зафиксированным всё, что дописано в журнал.** Устойчива только синхронизированная часть.
3. **Хранить лишь новое значение.** Откат станет невозможен.
4. **Неидемпотентный redo.** «Прибавить 30» при повторном восстановлении прибавит дважды; применяй абсолютные значения.
