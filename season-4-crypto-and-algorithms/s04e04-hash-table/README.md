## Теория: корзины и цепочки

```c
index = djb2(key) % NBUCKETS;      // сразу нужная корзина
```

При коллизии узел добавляется **в голову** цепочки этой корзины — это O(1) (идти до конца не надо):

```c
n->next = t->buckets[idx];
t->buckets[idx] = n;
```

Поиск: тот же индекс, затем проход по короткой цепочке со `strcmp`.

**Load factor** = записи / корзины (у нас 10/8 = 1.25). Чем выше, тем длиннее цепочки и тем ближе поиск к O(n); на практике при ~0.75 таблицу перехешируют (вдвое больше корзин), как рос массив в s02e06.

**Память:** таблица владеет узлами и копиями ключей — значит освобождает оба, сохраняя `next` до `free` (s02e08). Подробнее — [`theory.md`](theory.md).


**1.** LUNA: «Почему вставка в голову цепочки — O(1), а «в конец» — нет?»

<details><summary>Ответ</summary>

В голову: переставить два указателя, независимо от длины цепочки. В конец: сначала дойти до последнего узла — O(длины цепочки). Порядок внутри корзины для поиска не важен, поэтому берут голову.
</details>

**2.** LUNA: «Load factor вырос до 5. Что произойдёт с поиском?»

<details><summary>Ответ</summary>

Цепочки станут длинными, и поиск выродится в линейный проход — O(n) вместо O(1). Лечится перехешированием: больше корзин, записи распределяются заново.
</details>

## Разбор типичных ошибок

1. **Сравнение ключей по хешу.** Одинаковый хеш ≠ одинаковый ключ. В цепочке обязательно `strcmp`.
2. **Не скопирован ключ.** Хранить чужой указатель опасно — строка может измениться/исчезнуть. Копируй (`dup_str`) и освобождай.
3. **`free(n)` до чтения `n->next`.** Use-after-free при обходе — сохраняй `next` заранее.
4. **Освободить узел, но не ключ.** Утечка; ASan поймает.
