# Теория — s04e04

## 1. Любой алгоритм — это размен

> *— Хеш-таблица меняет память на время. Ты платишь массивом, который не заполнишь до конца, а получаешь мгновенный доступ.*
> *— А если памяти мало?*
> *— Тогда платишь временем. Вопрос не в том, есть ли цена. Вопрос в том, знаешь ли ты, какую платишь.*

Сравнение способов хранить пары «ключ — значение»:

| Структура | Поиск | Вставка | Память | Порядок |
|---|---|---|---|---|
| неотсортированный массив | O(n) | O(1) | минимум | нет |
| отсортированный массив | O(log n) | O(n) | минимум | есть |
| хеш-таблица | **O(1)** среднее | O(1) среднее | +25–100% | **нет** |
| сбалансированное дерево | O(log n) | O(log n) | +указатели | есть |

Последний столбец объясняет, почему хеш-таблица не вытеснила деревья: она не хранит порядок. Запросы «все записи с датой между X и Y» или «первые десять по возрастанию» в хеш-таблице невозможны — придётся перебирать всё. Поэтому индексы в базах данных строят на B-деревьях (Season 9), а не на хешах.

## 2. Почему O(1) — это среднее, а не гарантия

Константное время держится на предположении о **равномерном распределении** ключей по корзинам. Формально при цепочках:

- средняя длина цепочки равна коэффициенту заполнения α;
- ожидаемое время поиска — O(1 + α);
- при α порядка единицы это константа.

В худшем случае все ключи попадают в одну корзину, и поиск становится O(n). Случайно так почти не бывает — но может быть **построено намеренно** (см. §6).

Ещё одна тонкость: неудачный поиск в среднем дороже удачного. Удачный останавливается на найденном элементе, в среднем на середине цепочки; неудачный обязан пройти цепочку до конца.

## 3. Цепочки против открытой адресации

**Цепочки** (chaining): каждая корзина — голова связного списка.

```c
Node *buckets[N];
```

Работает при любом заполнении: даже при α = 10 таблица функционирует, просто медленно. Цена — указатель на запись и, что важнее, **разбросанность по куче**: каждый переход по цепочке с большой вероятностью даёт промах кэша.

**Открытая адресация**: все записи в самом массиве, при коллизии ищется следующая свободная ячейка.

| Стратегия | Формула | Проблема |
|---|---|---|
| линейное пробирование | `i + 1, i + 2, …` | первичная кластеризация |
| квадратичное | `i + 1², i + 2², …` | вторичная кластеризация |
| двойное хеширование | `i + k·h₂(key)` | нужна вторая функция |

Плюс — данные лежат подряд, и линейное пробирование прекрасно ложится на кэш: несколько соседних ячеек приходят одной кэш-линией. Именно поэтому современные высокопроизводительные реализации (Google `absl::flat_hash_map`, Rust `hashbrown`) используют открытую адресацию, несмотря на теоретическую уязвимость к кластеризации.

Минус, о котором обычно забывают: **удаление**. Просто обнулить ячейку нельзя — это разорвёт цепочку пробирования для других ключей. Приходится ставить «надгробие» (tombstone), которое занимает место и замедляет поиск, пока таблицу не перестроят.

## 4. Коэффициент заполнения и перестройка

```
α = записей / корзин
```

Пороговое значение — компромисс между памятью и скоростью:

| Реализация | Порог |
|---|---|
| Java `HashMap` | 0.75 |
| Python `dict` | 0.66 |
| Go `map` | 6.5 (у него корзины по 8 элементов) |
| `absl::flat_hash_map` | 0.875 |

При превышении таблица **перестраивается**: выделяется массив вдвое больше, все записи перекладываются заново (хеш от того же ключа даёт другой остаток при другом числе корзин).

Операция стоит O(n), но случается редко: как и с удвоением буфера в s02e06, суммарная стоимость n вставок остаётся O(n), то есть амортизированно вставка константна.

Практическое следствие: **если известно ожидаемое число записей, задайте размер заранее**. Это убирает несколько перестроек и заметно ускоряет заполнение больших таблиц.

## 5. Размер таблицы: степень двойки или простое число

Два подхода, оба живые:

**Простое число корзин.** `hash % 13` перемешивает лучше при слабой хеш-функции: если ключи имеют общий делитель с размером таблицы, при составном размере они скучиваются. Классический совет из Кнута.

**Степень двойки.** `hash & (N - 1)` вместо деления — на порядок быстрее, деление на процессоре дорого. Но требует **хорошей** хеш-функции: остаток по маске берёт только младшие биты, и если функция перемешивает их плохо, распределение развалится.

Современный выбор — степень двойки плюс дополнительное перемешивание. Java, например, делает `h ^= (h >>> 16)`, чтобы старшие биты повлияли на младшие. Это компромисс: скорость взятия остатка при сохранении качества распределения.

## 6. Атака через коллизии

Если хеш-функция известна и не зависит от секрета, атакующий подбирает тысячи ключей с одинаковым остатком. Таблица вырождается в один список, и операция за O(1) становится O(n); при `n` в тысячи это означает миллионы сравнений на запрос.

В 2011 году так уложили веб-фреймворки на PHP, Java, Python, Ruby и ASP.NET одновременно: одного POST-запроса с подобранными именами параметров хватало, чтобы занять процессор на минуты.

Защита — **рандомизированное хеширование**: функция принимает секретный ключ, свой у каждого процесса. Стандартом стал SipHash — быстрый и устойчивый к подбору коллизий без знания ключа.

Отсюда наблюдаемый эффект: `hash("abc")` в Python даёт разные значения в разных запусках. Это не недоработка, а включённая по умолчанию защита.

**Правило:** если ключи приходят снаружи, хеш-функция должна зависеть от секрета.

## 7. Владение памятью в составной структуре

Таблица владеет двумя вещами на запись: узлом и копией ключа.

```c
node->key = strdup(key);     /* копия: чужая строка может измениться или исчезнуть */
```

Хранить указатель на переданную строку — распространённая ошибка. Вызывающий вправе переиспользовать буфер, и таблица начнёт врать, ничего при этом не нарушив формально.

Освобождение — изнутри наружу, по всем корзинам, с сохранением `next` до `free`:

```c
for (size_t i = 0; i < n; i++) {
    Node *e = t->buckets[i];
    while (e) { Node *nx = e->next; free(e->key); free(e); e = nx; }
    t->buckets[i] = NULL;
}
```

Это ровно та дисциплина из s02e08, применённая к структуре на уровень сложнее. Проверяется тем же способом — санитайзером.
