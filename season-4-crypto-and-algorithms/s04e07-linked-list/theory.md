# Теория — s04e07

## 1. Связь работает в обе стороны

> *— Список — это про то, что порядок можно хранить отдельно от данных. А ещё про то, что связь работает в обе стороны: по ней можно идти, и по ней же можно проверить, что никто не вклинился.*

В s02e04 вы **читали** чужую структуру. Здесь строите свою — и разница не в сложности, а в ответственности: за корректность связей теперь отвечаете вы.

Односвязный список — минимальная динамическая структура, какую можно построить:

```c
typedef struct Node { int value; struct Node *next; } Node;
```

Всё остальное — деревья, графы, хеш-таблицы с цепочками, очереди — надстройки над этой идеей.

## 2. Стоимость операций

| Операция | Список | Массив |
|---|---|---|
| вставка в начало | **O(1)** | O(n) — сдвиг |
| вставка в конец | O(n), или O(1) с хвостовым указателем | O(1) амортизированно |
| вставка в середину при известном узле | **O(1)** | O(n) |
| доступ по индексу | O(n) | **O(1)** |
| поиск | O(n) | O(n), или O(log n) если отсортирован |
| память на элемент | +8 байт указателя | 0 |
| локальность | **плохая** | отличная |

Две последние строки объясняют, почему список редко бывает правильным выбором. Узлы разбросаны по куче, и каждый переход по ссылке — вероятный промах кэша: обращение к памяти вместо кэша стоит порядка сотни тактов против единиц.

Практическое следствие: на современном железе **обход миллиона элементов массива быстрее обхода миллиона элементов списка в разы**, при формально одинаковой сложности O(n). Асимптотика не различает эти случаи, а измерение различает.

Когда список всё-таки уместен:

- элемент не должен переезжать (на него держат указатели — в отличие от массива с `realloc`, s02e06);
- вставка и удаление в середине при уже известной позиции;
- нет непрерывного блока памяти нужного размера;
- элемент состоит сразу в нескольких списках (интрузивные списки ядра).

## 3. Разворот: почему ровно три указателя

```c
Node *prev = NULL, *cur = head, *next;
while (cur) {
    next = cur->next;    /* 1. запомнить, пока связь цела */
    cur->next = prev;    /* 2. развернуть                 */
    prev = cur;          /* 3. сдвинуть окно              */
    cur  = next;
}
head = prev;
```

Инвариант, который стоит проговорить: **перед каждой итерацией `prev` указывает на голову уже развёрнутой части, `cur` — на голову ещё не тронутой.**

Из инварианта следует необходимость каждого указателя:

- убрать `next` — на шаге 2 теряется весь остаток списка;
- убрать `prev` — некуда разворачивать текущий узел;
- убрать `cur` — неизвестно, где мы.

Забытая строка `head = prev` — самая частая ошибка: список развёрнут корректно, но переменная указывает на бывшую голову, ставшую хвостом, и снаружи виден список из одного элемента.

Рекурсивный вариант короче, но требует O(n) стека и на длинном списке даёт переполнение — редкий случай, когда итеративное решение строго лучше.

## 4. Алгоритм Флойда и почему он работает

```c
slow = slow->next;
fast = fast->next->next;
```

Доказательство короче, чем кажется. Пусть цикл существует. Быстрый указатель войдёт в него первым и начнёт догонять медленный. На каждом шаге расстояние между ними внутри цикла **сокращается ровно на единицу** — быстрый проходит два звена, медленный одно. Расстояние конечно, значит, оно обнулится, то есть указатели совпадут.

Ключевой момент: сокращение именно на единицу гарантирует, что они не «перепрыгнут» друг друга. При шаге 3 вместо 2 расстояние менялось бы на 2, и на цикле чётной длины они могли бы разминуться навсегда.

Продолжение алгоритма (найти **начало** цикла) выглядит как фокус:

```c
slow = head;
while (slow != fast) { slow = slow->next; fast = fast->next; }
/* теперь slow — начало цикла */
```

Выводится из арифметики: если до цикла `μ` шагов, длина цикла `λ`, а встреча произошла через `k` шагов, то `k ≡ μ (mod λ)`. Отсюда указатель из головы и указатель из точки встречи, идущие с одинаковой скоростью, встретятся ровно на входе в цикл.

Проверка `fast && fast->next` обязательна. Без первой части упадём на списке нечётной длины, без второй — на чётной.

## 5. Где ищут циклы на практике

Задача выглядит учебной и таковой не является:

- **обнаружение утечек в графе объектов** — сборщики мусора ищут циклические ссылки, которые не освобождаются подсчётом ссылок;
- **проверка символических ссылок** в файловой системе; отсюда ошибка `ELOOP`;
- **разрешение зависимостей** — циклическая зависимость пакетов или модулей;
- **обнаружение периода** в псевдослучайных последовательностях; тот же алгоритм оценивает качество ГПСЧ (s08e03);
- **ро-алгоритм Полларда** для факторизации чисел — использует ровно эту конструкцию.

Последнее особенно любопытно: алгоритм поиска цикла в списке оказался инструментом разложения чисел на множители.

## 6. Освобождение и владение

```c
while (head) { Node *nx = head->next; free(head); head = nx; }
```

Та же дисциплина, что в s02e08: сохранить `next` до `free`, иначе use-after-free.

Отдельная тонкость этой серии: **список с циклом освобождать нельзя**. Обход не закончится, а попытка освободить уже освобождённый узел даст двойное освобождение. Порядок обязателен: сначала обнаружить цикл, разорвать его, потом освобождать.

Если узел владеет чем-то ещё (строкой, вложенной структурой), освобождение идёт изнутри наружу — сначала содержимое, потом узел.

## 7. Варианты, которые встретятся дальше

| Вид | Особенность | Где |
|---|---|---|
| двусвязный | ссылки в обе стороны; удаление за O(1) | ядро Linux, LRU-кэши |
| кольцевой | последний ссылается на первый | планировщики, кольцевые буферы |
| с фиктивной головой | пустой узел-заглушка убирает особый случай пустого списка | упрощает код вставки |
| интрузивный | узел встроен в данные, не наоборот | `list_head` в ядре |
| список с пропусками (skip list) | несколько уровней ссылок, поиск за O(log n) | альтернатива деревьям, Redis |

Последняя строка показывает, куда развивается идея: добавив к списку «этажи» ссылок через 2, 4, 8 элементов, получаем поиск за логарифм — структуру, конкурирующую со сбалансированными деревьями и куда более простую в реализации.

**Фиктивная голова** заслуживает отдельного упоминания как приём: заведя пустой узел перед первым настоящим, вы избавляетесь от особого случая «список пуст» во всех операциях. Код становится короче и, что важнее, перестаёт иметь ветку, которая выполняется редко и потому плохо протестирована.
