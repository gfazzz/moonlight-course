# Теория — s04e03

## 1. «Расшифровалось» и «подлинное» — разные утверждения

> — Расшифруется — значит подлинное.
> — Нет. Расшифруется — значит подошёл ключ. Это разные утверждения.

Ева формулирует то, что путают постоянно. Три независимых свойства:

| Свойство | Вопрос | Инструмент |
|---|---|---|
| конфиденциальность | кто может прочитать? | шифр |
| целостность | изменилось ли? | хеш, контрольная сумма |
| подлинность | кто автор? | HMAC, подпись |

Шифр отвечает только на первый вопрос. Расшифровать данные ключом и получить осмысленный текст — не доказательство того, что текст не менялся: во многих режимах шифрования атакующий может предсказуемо изменить открытый текст, не зная ключа (это называется податливостью, malleability). Отсюда современное требование — **шифрование с аутентификацией** (AEAD): режимы GCM, ChaCha20-Poly1305, где целостность встроена.

## 2. Что такое хеш

Функция, отображающая данные произвольной длины в значение фиксированной. Требования — по возрастанию строгости:

| Свойство | Формулировка | Кому нужно |
|---|---|---|
| детерминированность | один вход — один выход | всем |
| равномерность | выходы распределены равномерно | хеш-таблицам |
| лавинный эффект | один бит входа меняет ~половину бит выхода | хеш-таблицам и криптографии |
| стойкость к прообразу | по `h` не найти `x` | криптографии |
| стойкость к коллизиям | не найти `x ≠ y` с `h(x) = h(y)` | криптографии |

Первые три обеспечивают **быстрые** хеши: djb2, FNV, MurmurHash, xxHash. Последние две — **криптографические**: SHA-256, BLAKE3.

Разница в цене: djb2 обрабатывает байт за пару тактов, SHA-256 — на порядок медленнее. Использовать криптографический хеш в хеш-таблице — платить за свойства, которые там не нужны.

Обратное — опаснее: применять быстрый хеш там, где нужна стойкость, значит не иметь защиты вовсе. djb2 обращается за секунды.

## 3. Почему `unsigned char` обязателен

```c
h = h * 33 + (unsigned char)*s;
```

Стандарт не определяет, знаковый `char` или нет: на x86 и ARM в Linux решают по-разному (x86 — знаковый, ARM — беззнаковый). Для байтов со старшим битом это даёт разные значения: `0xD0` — это `208` при беззнаковом и `−48` при знаковом.

Последствия конкретны: хеш строки «Москва» в UTF-8 на x86 и на ARM окажется разным. Хеш-таблица, сериализованная на одной архитектуре, не прочитается на другой; распределённый кэш начнёт промахиваться; контрольные суммы разойдутся.

Общее правило: **работа с байтами ведётся через `unsigned char`**. Это же касается `<ctype.h>` — передача отрицательного `char` в `isalpha` формально неопределённое поведение.

## 4. Разбор двух функций

**djb2** (Дэниел Бернстайн, 1991):

```c
h = h * 33 + c;      /* эквивалентно (h << 5) + h + c */
```

Начальное значение `5381`, множитель `33`. Бернстайн в обсуждении честно писал, что не знает, почему именно `33` работает лучше многих альтернатив, — свойство обнаружено экспериментально. Умножение на 33 дёшево: сдвиг и сложение.

Существует вариант `h = h * 33 ^ c` — по некоторым замерам чуть лучше распределяет.

**FNV-1a** (Фаулер, Нолл, Во):

```c
h ^= c;              /* сначала смешать    */
h *= 16777619u;      /* потом перемешать   */
```

Порядок важен. В исходном FNV-1 сначала умножали, потом складывали по модулю два, и распределение получалось хуже: последний байт влиял только на младшие разряды. Перестановка операций в FNV-1a исправила это — редкий случай, когда улучшение алгоритма состоит из перестановки двух строк.

Константы: `2166136261` и `16777619` для 32 бит — тоже подобраны экспериментально, с оглядкой на свойства простых чисел.

**Что использовать сегодня.** Для хеш-таблиц — xxHash или MurmurHash3: они быстрее (обрабатывают по 8 байт за раз) и лучше распределяют. djb2 и FNV полезны тем, что помещаются в четыре строки и не требуют библиотеки, — поэтому их и изучают.

## 5. Переполнение здесь намеренное

```c
uint32_t h = 5381;
h = h * 33 + c;      /* переполняется постоянно — и это правильно */
```

Беззнаковое переполнение по стандарту определено: результат берётся по модулю 2³². Это и есть механизм перемешивания.

Со **знаковым** типом такое переполнение — неопределённое поведение, и компилятор вправе делать что угодно. Отсюда жёсткое требование: накопитель хеша всегда беззнаковый.

## 6. Коллизии: неизбежность и парадокс дней рождения

Множество входов бесконечно, выходов — 2³². Коллизии обязаны существовать (принцип Дирихле).

Важнее другое — **как быстро они находятся случайно**. Ответ даёт парадокс дней рождения: для `n`-битного хеша коллизия ожидается примерно после `2^(n/2)` попыток, а не `2^n`.

| Хеш | Бит | Коллизия ожидается после |
|---|---|---|
| djb2/FNV-32 | 32 | ~65 000 значений |
| MD5 | 128 | 2⁶⁴ — но сломан: строится за секунды |
| SHA-1 | 160 | 2⁸⁰ — сломан в 2017 (атака SHAttered) |
| SHA-256 | 256 | 2¹²⁸ — недостижимо |

Первая строка объясняет, почему 32-битный хеш нельзя использовать как идентификатор: в таблице из 65 тысяч записей коллизия почти гарантирована. Для корзин это нормально (цепочки разрешают), для «уникального ключа» — нет.

## 7. Атака на хеш-таблицу через коллизии

Если хеш-функция известна и не зависит от секрета, атакующий может **построить** тысячи ключей, попадающих в одну корзину. Таблица выродится в связный список, и операция за O(1) станет O(n).

Так работала атака 2011 года на веб-фреймворки: POST-запрос с тысячами специально подобранных имён параметров нагружал сервер на минуты. Уязвимы оказались PHP, Java, Python, Ruby, ASP.NET — все сразу.

Защита — **рандомизированное хеширование**: в функцию добавляется случайный секрет, свой у каждого процесса (SipHash). Python включает это по умолчанию с версии 3.3, поэтому `hash("abc")` даёт разные значения в разных запусках — это не баг, а защита.

Практический вывод: если ключи приходят снаружи, хеш-функция должна зависеть от секрета.

## 8. Где хеши работают

- **хеш-таблицы** — следующая серия;
- **проверка целостности** — контрольные суммы дистрибутивов, git;
- **дедупликация** — одинаковый хеш означает одинаковые данные (с оговоркой о коллизиях);
- **git** — идентификатор объекта есть хеш его содержимого; поэтому история неизменяема: правка любого коммита меняет все последующие;
- **блокчейн** — s04e08, там же и Proof-of-Work;
- **пароли** — но с оговорками: обычный хеш для паролей **не годится**, нужны bcrypt, scrypt, Argon2 с солью и намеренным замедлением.

Последний пункт стоит запомнить отдельно: SHA-256 слишком быстр для паролей. Перебор на видеокарте даёт миллиарды хешей в секунду; функции для паролей проектируются медленными и требовательными к памяти намеренно.
