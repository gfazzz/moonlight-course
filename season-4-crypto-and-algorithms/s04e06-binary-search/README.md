## Что ты освоишь

- Инвариант двоичного поиска и почему нужен отсортированный массив.
- Идиому `mid = lo + (hi - lo)/2` и знаменитый баг переполнения.
- Практический смысл `O(log n)`: удвоение n = +1 шаг.

Глубже — в [`theory.md`](theory.md).

---

## Теория: делим пополам

```c
int lo = 0, hi = n - 1;
while (lo <= hi) {
    int mid = lo + (hi - lo) / 2;
    if (a[mid] == target) return mid;
    if (a[mid] < target) lo = mid + 1;   // цель правее
    else                 hi = mid - 1;   // цель левее
}
return -1;
```

Инвариант: «если элемент есть, он в `[lo, hi]`». Каждый шаг уменьшает диапазон вдвое → `log₂ n` шагов.

**Почему `lo + (hi - lo)/2`:** `(lo + hi)/2` может переполнить `int` на больших индексах — эта бага годами жила в стандартной библиотеке Java. Подробнее — [`theory.md`](theory.md).

| n | линейный (худший) | двоичный |
|---|-------------------|----------|
| 1 024 | 1 024 | 11 |
| 1 048 576 | 1 048 576 | 21 |

## Проверка на канале

```
[LUNA] Два вопроса про деление пополам.
```

**1.** LUNA: «Чем `(lo + hi) / 2` хуже, чем `lo + (hi - lo) / 2`?»

<details><summary>Ответ</summary>

При больших индексах `lo + hi` может переполнить `int` и дать отрицательный `mid` → выход за границы. Вторая форма считает то же значение без переполнения. Эта ошибка много лет жила в `Arrays.binarySearch` в JDK.
</details>

**2.** LUNA: «Данные не отсортированы. Двоичный поиск сработает?»

<details><summary>Ответ</summary>

Нет — он опирается на порядок: решение «идти влево/вправо» верно только для отсортированного массива. На неотсортированных данных он вернёт мусор или «не найдено», хотя элемент есть.
</details>

## Разбор типичных ошибок

1. **`(lo + hi) / 2`.** Потенциальное переполнение. Только `lo + (hi - lo)/2`.
2. **`while (lo < hi)`.** Пропустит единственный оставшийся элемент. Нужно `lo <= hi`.
3. **`lo = mid` / `hi = mid`.** Без `±1` диапазон перестаёт сжиматься — бесконечный цикл.
4. **Поиск по неотсортированным данным.** Предусловие алгоритма; иначе результат бессмыслен.
