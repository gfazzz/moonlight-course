# Теория (углублённо) — s04e06

## 1. Инвариант двоичного поиска

Условие работы: массив **отсортирован**. Поддерживаем инвариант «если элемент есть, он лежит в `[lo, hi]`»:

```c
while (lo <= hi) {
    int mid = lo + (hi - lo) / 2;
    if (a[mid] == target) return mid;
    if (a[mid] < target) lo = mid + 1;   // левая половина отпадает
    else                 hi = mid - 1;   // правая половина отпадает
}
return -1;
```

Каждый шаг уменьшает диапазон вдвое → число шагов ≈ `log₂ n`.

## 2. `lo + (hi - lo) / 2`, а не `(lo + hi) / 2`

Классическая ошибка: при больших `lo` и `hi` сумма может переполнить `int`. Эта бага почти десять лет жила в `java.util.Arrays.binarySearch` и в JDK, пока Джошуа Блох не описал её в 2006-м. Форма `lo + (hi - lo)/2` даёт то же значение без переполнения.

## 3. Что даёт log n

| n | линейный (худший) | двоичный |
|---|-------------------|----------|
| 1 024 | 1 024 | 11 |
| 65 536 | 65 536 | 17 |
| 1 048 576 | 1 048 576 | 21 |

Удвоение n добавляет двоичному поиску **один** шаг. Поэтому логарифмические алгоритмы «не замечают» рост данных — на этом стоят индексы БД, B-деревья, поиск в отсортированных структурах.

## 4. Цена предварительной сортировки

Двоичный поиск требует отсортированных данных, а сортировка — O(n log n). Если поиск однократный, дешевле линейный проход O(n). Если поисков много (k запросов), выгодно отсортировать один раз: `n log n + k·log n` против `k·n`. Именно так рассуждают при выборе «строить индекс или нет».
