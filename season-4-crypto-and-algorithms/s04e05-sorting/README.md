## Что ты освоишь

- Измерение реальной стоимости алгоритма счётчиком операций.

## Теория: две стратегии

**Вставками** — вставляем элемент в отсортированную левую часть:

```c
while (j >= 0 && a[j] > key) { a[j+1] = a[j]; j--; }
a[j+1] = key;
```

Каждый элемент сравнивается с половиной предыдущих → ~n²/4 сравнений.

**Слиянием** — делим пополам, сортируем половины, сливаем. Глубина `log₂ n`, на каждом уровне O(n) работы → **O(n log n)**. Цена — дополнительный буфер размера n.

Замер из задачи:

| n | insertion | merge | отношение |
|---|-----------|-------|-----------|
| 64 | 1 018 | 303 | 3.4× |
| 256 | 17 141 | 1 727 | 9.9× |
| 1024 | 263 213 | 8 970 | 29.3× |

Отношение растёт как `n / log n` — на 250 000 записей это уже тысячи раз.

[LUNA] Два вопроса. И да, сид генератора не трогай — тест на нём держится.

**1.** LUNA: «Insertion sort — O(n²). Значит, он всегда хуже merge?»

<details><summary>Ответ</summary>

Нет. На почти отсортированных данных внутренний `while` почти не работает, и insertion выходит на ~O(n) — быстрее merge за счёт отсутствия рекурсии и копирования. Поэтому его используют для маленьких подмассивов внутри быстрых сортировок.
</details>

**2.** LUNA: «Откуда в merge sort берётся `log n`?»

<details><summary>Ответ</summary>

Массив делится пополам, пока не останутся единицы: это `log₂ n` уровней. На каждом уровне слияния суммарно проходят все n элементов → `n · log n`.
</details>

```
[LUNA] Верно. Считай сравнения.
```

## Разбор типичных ошибок

1. **Счётчик не там.** Считать надо само сравнение, а не итерации цикла; при `&&` короткое замыкание не должно «съедать» инкремент.
2. **Границы в merge.** Классика — забыть «хвосты» (`while (i < mid)`, `while (j < n)`) после основного слияния.
3. **Забыть `memcpy` обратно.** Слияние пишет в `tmp`; без копирования в `a` массив не изменится.
4. **Утечка буферов.** `malloc` для a/b/tmp — на каждой итерации свой `free` (ASan проверит).
