## Теория: 26 бит пропуска

```
[25]=P0(even по 24..13) | [24..17]=facility | [16..1]=card | [0]=P1(odd по 12..1)
```

```c
uint8_t  fac  = (code >> 17) & 0xFF;
uint16_t card = (code >> 1)  & 0xFFFF;
int lead_ok  = (P0 ==  xor_bits(code, 24, 13));   // even
int trail_ok = (P1 == !xor_bits(code, 12, 1));    // odd
```

Две чётности прикрывают половины кадра; even и odd специально разные — это ловит вырожденные «все нули/все единицы» при обрыве линии. Но Wiegand открыт: карту клонируют за секунды, чётность у клона верна. Поэтому решение принимает **список доступа**, а не только разбор битов. Подробнее — [`theory.md`](theory.md).

## Проверка на канале

```
[LUNA] Два вопроса, прежде чем откроешь дверь.
```

**1.** LUNA: «Зачем в Wiegand-26 две чётности, да ещё разного типа (even и odd)?»

<details><summary>Ответ</summary>

Каждая прикрывает свою половину данных, локализуя ошибку. Разные типы (even/odd) ловят вырожденный случай «все биты 0» или «все 1» на линии (обрыв/КЗ): при одинаковой чётности он бы прошёл, при разной — нет.
</details>

**2.** LUNA: «Клон карты имеет корректную чётность. Почему система всё равно может дать DENY?»

<details><summary>Ответ</summary>

Чётность подтверждает лишь целостность передачи, не легитимность карты. Решение принимает список доступа: если facility не в белом списке (или карта в стоп-листе) — DENY, даже при идеальном кадре. Разбор — необходимое, но не достаточное условие.
</details>


## Разбор типичных ошибок

1. **Одна чётность на все 24 бита.** В Wiegand-26 их две, по половинам, разного типа.
2. **Обе чётности одинаковые.** Ведущая even, замыкающая odd — не перепутай инверсию.
3. **Считать разбор достаточным.** Верный кадр ≠ доступ; проверяй facility по списку.
4. **Сдвиги/маски полей.** facility `(code>>17)&0xFF`, card `(code>>1)&0xFFFF` — легко ошибиться на бит.
