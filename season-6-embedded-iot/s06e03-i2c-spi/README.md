# s06e03 — I2C/SPI

**Season 6: Embedded & IoT · Серия 3 из 8 · ~45 мин**
Концепт: на шине много устройств, у каждого адрес и карта регистров. Задача: опросить датчик, не трогая его физически.

> *«Один провод — один собеседник. Шина — целый зал, и каждого зовут по имени».*

## Previously

Ты читаешь последовательную линию (UART). Но датчики в стойке НИИ висят не на отдельных проводах, а на общей шине — к каждому не подключишься точка-точка. Нужен протокол с адресами.

## Сцена

Серверная НИИ. Дмитрий показывает две тонкие линии, уходящие в стойку с датчиками.

```
[Дмитрий] Здесь SDA и SCL. На них сидят все датчики разом. Это I2C — шина.
[Дмитрий] Хочешь снять показания — назови адрес. Откликнется только нужный.
[LUNA]    Сначала прочитай регистр ID: убедись, что на адресе именно тот чип.
[LUNA]    Потом запусти измерение и собери значение из двух байтов. MSB первым.
```

Сегодня — как один ведущий опрашивает десятки устройств по двум проводам.

## Что ты освоишь

- Модель шины: адрес устройства, карта регистров, ACK/NACK.
- Транзакцию «указать регистр → прочитать/записать байты».
- Сборку 16-битного значения из MSB/LSB и роль регистра ID (WHO_AM_I).

Глубже (и про отличие SPI) — в [`theory.md`](theory.md).

## Теория: выбрал устройство → регистр → данные

```c
i2c_read(addr, reg, &v);     // addr != наш -> NACK
uint16_t raw = (msb << 8) | lsb;   // старший байт первым
```

У датчика карта регистров: ID, конфиг, статус, данные. Читаешь ID (`0xD0`) — проверяешь, что на шине нужный чип. Пишешь в CTRL_MEAS — запускаешь измерение (побочный эффект: STATUS выставляет `data_ready`). Часть регистров только для чтения.

**SPI** отличается транспортом: устройство выбирается не адресом, а линией CS, обмен полнодуплексный. Но логика «регистр → данные» та же. Подробнее — [`theory.md`](theory.md).

## Проверка на канале

```
[LUNA] Два вопроса про шину.
```

**1.** LUNA: «Прежде чем читать данные, зачем вообще читать регистр WHO_AM_I?»

<details><summary>Ответ</summary>

Чтобы убедиться, что по этому адресу отвечает именно ожидаемый датчик. Если ID не совпал — на шине другой чип, сбитый адрес или обрыв. Читать «данные» с неизвестного устройства бессмысленно.
</details>

**2.** LUNA: «Датчик отдаёт значение двумя байтами. Что будет, если перепутать MSB и LSB?»

<details><summary>Ответ</summary>

Получишь другое число: `(lsb<<8)|msb` вместо `(msb<<8)|lsb`. Например `0x0A2B` (2603) превратится в `0x2B0A` (11018). Порядок байт фиксирован datasheet — его нельзя угадывать.
</details>

```
[Дмитрий] Верно. Снимай показания.
```

## Задача: `i2c.c`

Реализовать `i2c_read`/`i2c_write` с ACK/NACK, проверить ID, запустить измерение, прочитать статус и 16-битное значение, обработать read-only регистр. ТЗ — в [`mission.md`](mission.md), каркас — в [`starter.c`](starter.c).

```bash
cp starter.c artifacts/i2c.c
make test
```

Ожидаемо — `PASS`: WHO_AM_I `0x58 → sensor OK`, чужой адрес `NACK`, RAW `0x0A2B = 2603 → 26.03 units`, запись в `0xD0` → `NACK (read-only)`. Эталон — [`solution/i2c.c`](solution/i2c.c).

## Разбор типичных ошибок

1. **Перепутать MSB/LSB.** Байты собираются по datasheet; `(msb<<8)|lsb`, не наоборот.
2. **Не проверять ID.** Без WHO_AM_I читаешь мусор с неизвестного устройства.
3. **Игнорировать NACK.** Ответ по чужому адресу — не данные, а «никто не откликнулся».
4. **Писать в read-only.** ID/статус запись не принимают; ждать эффекта бессмысленно.

## Debriefing

Показания датчиков сняты по шине. Но главная преграда — не сенсоры, а двери: система контроля доступа НИИ читает карты сотрудников по своему протоколу. Чтобы пройти, нужно понять, как кодируется пропуск.

```
[Дмитрий] Датчики — ерунда. Настоящая стена — двери. СКУД, считыватели карт.
[LUNA]    Считыватель шлёт контроллеру 26 бит: код объекта, номер карты, биты чётности.
[LUNA]    Это Wiegand. Разберём пропуск по битам. Дальше — s06e04.
```

**Навык разблокирован:** шины I2C/SPI, адресация, карты регистров, ACK/NACK.
