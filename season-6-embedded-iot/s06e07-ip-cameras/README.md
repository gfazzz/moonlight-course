## Что ты освоишь

- Кадр как 2D-массив `uint8_t[H][W]` и почему при вычитании нужен `int`.
- Разность кадров + порог против шума сенсора.
- Зонирование кадра: не только «есть движение», но и «где» (и где слепо).

Глубже (и про RTSP) — в [`theory.md`](theory.md).

---

## Теория: вычесть и пороговать

```c
int d = abs((int)f2[y][x] - (int)f1[y][x]);   // int! иначе uint8_t переполнится
int changed = d > THRESH;                       // порог отсекает шум сенсора
if (changed) zone[y/(H/2)][x/(W/2)]++;          // в какой квадрант попало
```

Где сцена статична — разность ~0; где сдвинулось — большая. Порог отсекает дрожание сенсора (тот же приём, что фильтр выброса в s06e06, но в пространстве). Зоны дают локализацию: где патруль, где «слепо». Про пределы метода (тени, свет, background subtraction) — [`theory.md`](theory.md).

## Проверка на канале

```
[LUNA] Два вопроса про кадры.
```

**1.** LUNA: «Пиксели — `uint8_t`. Почему перед вычитанием их приводят к `int`?»

<details><summary>Ответ</summary>

`uint8_t - uint8_t` считается в беззнаковой арифметике: `30 - 200` не даст `−170`, а «завернётся» в большое положительное число. Приведение к `int` даёт корректную знаковую разность, а `abs()` — модуль изменения.
</details>

**2.** LUNA: «Зачем вообще порог? Почему не считать движением любой ненулевой diff?»

<details><summary>Ответ</summary>

Сенсор камеры шумит: неподвижная сцена меняется на ±несколько единиц каждый кадр. Без порога этот шум читался бы как движение — сплошные ложные срабатывания. Порог пропускает только значимые изменения.
</details>

```
[Дмитрий] Верно. Ищи слепые зоны.
```

## Разбор типичных ошибок

1. **`uint8_t - uint8_t`.** Беззнаковое переполнение. Приводи к `int`, затем `abs`.
2. **Без порога.** Шум сенсора = сплошные ложные срабатывания. `THRESH` обязателен.
3. **Только суммарный счётчик.** Он говорит «есть движение», но не «где». Считай по зонам.
4. **Путаница индексов зон.** Квадрант — целочисленным делением: `y/(H/2)`, `x/(W/2)`.
