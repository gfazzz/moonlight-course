# Теория — s06e08

## 1. Почему телеметрию не шифруют

> *— Спроси не «почему открыто», а «что стоит закрыть». Телеметрия — это рассказ аппарата о себе. Опасны не рассказы, опасны приказы. Вот только рассказ говорит, где ты, а этого иногда достаточно.*

Причины отсутствия шифрования в телеметрийном канале сложились исторически и держатся до сих пор:

| Причина | Суть |
|---|---|
| стоимость | шифрование на маломощном контроллере — такты и энергия |
| задержка | наземная станция должна видеть состояние немедленно |
| отладка | открытый поток читается любым анализатором |
| модель угроз | считалось, что пассивный слушатель безвреден |

Последняя строка — ошибка. Пассивный слушатель получает координаты, высоту, режим полёта и уровень заряда, то есть полную картину операции без единого переданного байта.

MAVLink версии 2 добавил подпись сообщений, но защищает она **подлинность**, а не тайну: подделать кадр стало нельзя, прочитать — по-прежнему можно. Это осознанное решение, и оно того же рода, что выбор порога в предыдущей серии: закрывают ту угрозу, которая дороже.

## 2. Кадр

```
[0xFE][len][seq][sysid][compid][msgid][payload...][ck_lo][ck_hi]
```

**Признак начала кадра.** Байт `0xFE` для версии 1, `0xFD` для версии 2. Приёмник ищет его в потоке, чтобы поймать границу — задача та же, что была в UART, только на уровне выше. И так же, как там, признак может случайно встретиться внутри данных: окончательное решение принимает контрольная сумма.

**Длина.** Размер полезной нагрузки. Брать её из константы нельзя: у разных типов сообщений разная длина, и декодер, рассчитанный на одно, на другом уйдёт за границу буфера.

**Порядковый номер.** Растёт по модулю 256. Разрыв в нумерации означает потерянные кадры — на радиоканале это штатная ситуация, и по разрывам считают качество связи. Ни Modbus, ни I²C такого поля не имеют, потому что на проводе потеря — это отказ, а не норма.

**Идентификаторы системы и компонента.** Адресация: какой аппарат и какая его часть. Один канал может нести телеметрию нескольких аппаратов одновременно.

**Тип сообщения.** Определяет, как разбирать полезную нагрузку. Значение 33 — глобальная позиция.

## 3. Фиксированная точка

```c
int32_t lat_raw = (int32_t)(p[0] | (p[1] << 8) | (p[2] << 16) | ((uint32_t)p[3] << 24));
double  lat     = lat_raw / 1e7;
```

Координаты передаются целыми, умноженными на 10⁷; высота — в миллиметрах; напряжение — в милливольтах. Причины:

**Стоимость плавающей арифметики.** На контроллере без соответствующего блока операции с `float` эмулируются программно и стоят сотни тактов. У части архитектур `double` вырождается в `float` вовсе.

**Точность предсказуема.** Семь знаков после запятой в градусах — это около сантиметра на местности. Точность фиксирована и не зависит от величины, в отличие от плавающей точки, где шаг растёт вместе с числом.

**Сравнение точное.** Целые числа сравниваются на равенство без оговорок — та самая проблема, которую разбирал s05e02.

Ловушка при разборе — **знаковость**. Широта и долгота бывают отрицательными, и сборка в `uint32_t` без последующего приведения даст для южного полушария число около четырёх миллиардов. Ошибка не проявится на данных, снятых в Новосибирске, и проявится в первом же полёте южнее экватора.

Вторая ловушка — **сдвиг знакового типа**. Выражение `p[3] << 24` при `int` шириной 32 бита и старшем бите байта, равном единице, формально выходит за пределы представимого. Приведение к `uint32_t` перед сдвигом снимает вопрос.

## 4. Контрольная сумма X.25

```c
static void crc_acc(uint16_t *crc, uint8_t b) {
    uint8_t t = b ^ (uint8_t)(*crc & 0xFF);
    t ^= (uint8_t)(t << 4);
    *crc = (*crc >> 8) ^ ((uint16_t)t << 8) ^ ((uint16_t)t << 3) ^ ((uint16_t)t >> 4);
}
```

Это CRC-16 с полиномом `0x1021` в отражённой форме и начальным значением `0xFFFF`. Та же схема применяется в X.25, MCRF4XX и ряде промышленных протоколов — реализация в четыре строки без таблицы, что для контроллера с двумя килобайтами памяти существенно.

Отличия от суммы Modbus из s06e05: другой полином, другое начальное значение, другой порядок обработки. Обнаруживающая способность у обеих схем сопоставима — ловятся все одиночные и двойные ошибки, все нечётные, все пакетные до шестнадцати бит.

### CRC_EXTRA

```c
crc_acc(&crc, CRC_EXTRA[msgid]);
```

Байт, вычисляемый при генерации кода из **определения** сообщения — имён и типов полей. Он не передаётся в кадре: обе стороны знают его из своей версии спецификации.

Эффект: если у отправителя и получателя разные версии протокола, сумма не сойдётся, даже когда физическая передача прошла безупречно.

Решение выглядит грубым, но закрывает проблему, о которую спотыкаются все распределённые системы, — **тихое расхождение схем**. Без такого механизма новое поле, добавленное в сообщение одной стороной, приводит к сдвигу разбора у другой, и вместо ошибки получаются правдоподобные неверные значения. Явный отказ лучше молчаливой лжи.

Тот же принцип встречается в других видах: номер версии в заголовке, хеш схемы в системах сериализации, миграции с проверкой контрольной суммы в базах данных.

## 5. Проверять до разбора

```c
if (!checksum_ok(frame, total_len)) {
    return REJECT;            /* и ни одного поля наружу */
}
```

Четвёртое появление правила за курс — s01e02, s06e04, s06e05 и здесь. Формулировка не меняется: **пока целостность не подтверждена, содержимое кадра не является данными**.

Практическая цена нарушения на радиоканале выше, чем на проводе. Помеха искажает один байт, разбор даёт координату в трёхстах километрах от истинной, и наземная станция рисует аппарат там, где его нет. Разборы происшествий с беспилотниками регулярно упираются именно в такие «прыжки» на треке.

Дополнительная защита в реальных системах — **проверка правдоподобия**: широта вне диапазона −90…90, скачок позиции быстрее физически возможного, высота ниже уровня земли. Контрольная сумма ловит искажения; проверка правдоподобия ловит то, что прошло сумму, но не может быть правдой.

## 6. Что видно из перехваченной телеметрии

| Поле | Что даёт наблюдателю |
|---|---|
| координаты | где аппарат сейчас |
| высота | режим полёта: осмотр, перелёт, посадка |
| заряд | сколько осталось и когда взлетел |
| порядковый номер | как долго канал открыт |
| идентификатор системы | сколько аппаратов в группе |

Ни одно поле по отдельности не выглядит чувствительным. Вместе они дают маршрут, расписание, численность группы и оценку автономности — то есть всё, ради чего обычно и ведут наблюдение.

Это общее свойство: **агрегация меняет чувствительность**. Набор безобидных данных перестаёт быть безобидным, и модель угроз, оценивающая поля по одному, систематически недооценивает риск.

## 7. Сборка сезона

`iot_controller` собирает восемь подсистем: регистры, последовательный канал, шину датчиков, СКУД, промышленный протокол, автомат состояний, детектор движения и телеметрию.

Общее у всех восьми — структура обработки:

```
приём  →  проверка границ  →  проверка целостности  →  разбор  →  действие
```

Отличаются только протоколы. Это и есть содержание сезона: не восемь разных умений, а одно, применённое к восьми задачам.

Модули берутся из двух сезонов — `ml_hash` из Season 4 адресует устройства, `ml_crc` и `ml_wiegand` написаны здесь. Проектный тест проверяет, что реализации не скопированы в `main.c`: повторное использование должно быть настоящим.
