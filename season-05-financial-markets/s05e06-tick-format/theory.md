# s05e06 — Теория: бинарный формат

> Серия про то, чем запись на диске отличается от записи в памяти, и почему смешивать их нельзя.

---

## 1. Выравнивание

Процессор читает память словами. Обращение к четырёхбайтному числу по адресу, не кратному четырём, на одних архитектурах медленнее, на других — сигнал. Поэтому компилятор размещает каждое поле по адресу, кратному его выравниванию, и вставляет между полями пустые байты.

```c
struct {
    uint16_t symbol_id;   /*  0..1  */
                          /*  2..3  дыра   */
    uint32_t ts;          /*  4..7  */
    int32_t  price;       /*  8..11 */
    uint32_t qty;         /* 12..15 */
    uint8_t  flags;       /* 16     */
                          /* 17..19 хвост  */
};                        /* sizeof == 20  */
```

Два вида пустоты, и путать их не нужно:

| Вид | Где | Убирается |
|---|---|---|
| дыра между полями | между `symbol_id` и `ts` | перестановкой полей |
| хвостовое выравнивание | после последнего поля | не убирается |

Хвост нужен для массивов: если бы размер структуры не был кратен её выравниванию, второй элемент массива оказался бы невыровненным.

Правило: **поля по убыванию размера**. Оно не оптимально в общем случае, но убирает дыры почти всегда и не требует размышлений.

### `#pragma pack`

Существует директива, отключающая выравнивание целиком. Для файловых форматов она не нужна и вредна:

- нестандартна, синтаксис у разных компиляторов свой;
- порождает невыровненные поля — медленно, а на части архитектур неопределённое поведение;
- не решает главную проблему — порядок байтов.

Правильный ход не в том, чтобы сделать структуру похожей на файл, а в том, чтобы перестать их отождествлять.

## 2. Сериализация

```c
fwrite(&tick, sizeof tick, 1, f);
```

Три причины, по которым так не делают:

**Раскладка полей зависит от платформы.** Смещения и размер структуры определяются ABI. Пересборка под другую архитектуру меняет файл.

**Порядок байтов зависит от платформы.** `uint32_t` со значением `0x11223344` лежит в памяти как `44 33 22 11` или как `11 22 33 44`.

**Содержимое дыр не определено.** Стандарт не требует ничего класть в выравнивающие байты. Отсюда следствие, о котором забывают: **`memcmp` двух структур не является сравнением на равенство**. Он может дать «не равны» для структур с одинаковыми полями.

Правильно — писать поле за полем:

```c
static void put_u32(uint8_t *p, uint32_t v) {
    p[0] = (uint8_t)(v & 0xFF);
    p[1] = (uint8_t)(v >> 8);
    p[2] = (uint8_t)(v >> 16);
    p[3] = (uint8_t)(v >> 24);
}
```

Сдвиг и маска определены стандартом и не зависят от раскладки в памяти. Код даёт один и тот же файл везде.

### Почему не приведение указателя

```c
uint32_t v = *(uint32_t *)p;   /* так нельзя */
```

Два нарушения сразу: указатель может быть невыровнен (неопределённое поведение), и результат зависит от порядка байтов машины.

### Ловушка чтения

```c
return p[0] | (p[1] << 8) | (p[2] << 16) | (p[3] << 24);   /* ошибка */
```

`p[3]` — это `uint8_t`, который при вычислении продвигается до `int`. Сдвиг на 24 у знакового `int` при значении байта `0x80` и больше даёт переполнение — неопределённое поведение. Приводить нужно до сдвига:

```c
return (uint32_t)p[0] | ((uint32_t)p[1] << 8)
     | ((uint32_t)p[2] << 16) | ((uint32_t)p[3] << 24);
```

Для `uint16_t` ошибка не проявляется — сдвиг на 8 умещается в `int`. Именно поэтому её пишут: на двухбайтных полях всё работает.

### Знаковые числа

```c
static void put_i32(uint8_t *p, int32_t v) { put_u32(p, (uint32_t)v); }
```

Преобразование знакового в беззнаковое определено стандартом (по модулю `2^32`), а сдвиг вправо отрицательного числа — нет. Поэтому знаковое кладут через беззнаковое, а не сдвигают напрямую.

## 3. Заголовок

```
0..3    сигнатура
4..5    версия формата
6..7    байт на запись
8..11   число записей
12..15  запас
```

| Поле | На какой вопрос отвечает |
|---|---|
| сигнатура | это вообще наш файл? |
| версия | понимаю ли я его? |
| байт на запись | где следующая запись? |
| число записей | сколько читать и где конец? |

Запас в конце — не суеверие: он позволяет добавить поле, не сдвигая начало данных, и держит заголовок кратным удобному размеру.

### Совместимость вперёд

Читатель, берущий размер записи **из заголовка**, разбирает известные ему поля, пропускает остаток и переходит к следующей записи по правильному смещению. Незнакомое поле теряется, данные остаются целыми.

Читатель, берущий размер **из `sizeof`**, при первом же расширении формата начнёт разбирать записи со сдвигом. И самое неприятное — правдоподобно: числа останутся числами.

Это и есть причина, по которой лишний байт удалось заметить: файл сам сообщил размер своих записей, и он не совпал с документацией.

## 4. Дельта-кодирование

Свойство временного ряда: соседние значения близки.

```
метки:  34205  34208  34212  34213
дельты:     3      4      1
цены:   18742  18741  18744  18740
дельты:    -1     +3     -4
```

Абсолютная величина требует четырёх байт, разность — одного. Первая запись кладётся целиком как опорная точка.

### Зигзаг

Разности бывают отрицательными, и в дополнительном коде `-1` — это `0xFFFFFFFF`. Записать такое одним байтом нельзя.

Зигзаг перекладывает числа так, чтобы малые по модулю оставались малыми:

```
 0 →  0        1 →  2        2 →  4
-1 →  1       -2 →  3       -3 →  5
```

```c
uint32_t zigzag(int32_t v)   { return ((uint32_t)v << 1) ^ (uint32_t)(v >> 31); }
int32_t  unzigzag(uint32_t v){ return (int32_t)((v >> 1) ^ (~(v & 1) + 1)); }
```

Выражение `v >> 31` даёт все единицы для отрицательных и нули для остальных; сложение по модулю два с этой маской инвертирует биты ровно у отрицательных.

### Что дальше

В промышленных форматах поверх дельт добавляют:

| Приём | Что даёт |
|---|---|
| переменная длина числа (varint) | малые дельты в один байт, большие — в несколько |
| дельта от дельты | у равномерных рядов вторая разность почти всегда ноль |
| XOR соседних значений | для вещественных: одинаковые старшие биты обнуляются |

Формат Gorilla, лежащий в основе современных баз временных рядов, сжимает метки времени в среднем до двух битов на точку. Идея та же, что здесь, доведённая до конца.

Важное свойство: дельта-кодирование **не теряет ничего**. Это смена представления, а не сжатие с потерями, и обратимость обязана проверяться кодом.

## 5. Контекст рынка

**Тик** — одно событие рынка: сделка или изменение лучшей котировки. На ликвидном инструменте их десятки тысяч в секунду.

**Почему бинарный формат.** Дело не только в размере. Разбор текста — это сотни тактов на запись; разбор бинарной записи — единицы. При двенадцати миллионах записей в день разница между «за минуту» и «за час».

**Маршрут исполнения (route).** Заявка может исполняться на бирже, во внутреннем пуле брокера или у внешнего маркет-мейкера. От выбора маршрута зависит цена исполнения, и в США брокер обязан раскрывать статистику маршрутизации — правило 606. Маршрут, которого нет в документации к формату, — не техническая деталь.

**Закрытость форматов.** Каждый крупный участник рынка имеет свой бинарный протокол, и документация к нему выдаётся по договору. Отсюда и ситуация серии: документация есть, но описывает не ту версию.
