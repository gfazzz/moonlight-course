## Теория: три разные вещи

Слово «время» в программе означает по меньшей мере три разных объекта, и путаница между ними — источник почти всех ошибок в этой области.

| Объект | Что это | Пример |
|---|---|---|
| **момент** | точка на оси, одинаковая для всех | `1730609400` |
| **календарная дата** | человеческая запись | `2024-11-03 01:50:00` |
| **пояс** | правило перевода одного в другое | `America/New_York` |

Момент однозначен. Календарная дата без пояса — не момент, а текст, и превратить её в момент можно только зная правило. Правило при этом **меняется во времени** и определяется не физикой, а решением парламента.

### Эпоха

Момент хранят числом секунд от условного нуля — полуночи 1 января 1970 года UTC.

```c
typedef int64_t timestamp;   /* секунды от эпохи */
```

Почему `int64_t`, а не `int32_t`: 32-битный счётчик секунд переполняется 19 января 2038 года. Это не гипотетическая проблема — она уже ломает системы, работающие с тридцатилетними ипотеками.

### Календарь без библиотеки

Перевод даты в число дней делается арифметикой, без циклов и таблиц. Приём: сдвинуть начало года на март.

```c
y -= (m <= 2);   /* январь и февраль относим к предыдущему году */
```

Тогда високосный день оказывается **последним** днём такого года и не разрывает формулу для номера дня в году. Дальше — счёт в эрах по 400 лет: григорианский календарь повторяется ровно через 146097 дней.

Своя реализация нужна здесь не из принципа, а ради теста: он сравнивает вывод посимвольно, а системная база часовых поясов обновляется вместе с дистрибутивом. Тест, зависящий от неё, однажды покраснеет без единой правки в коде.

### Переход на летнее время

Дважды в год местная шкала рвётся.

```
весна:  ... 01:58  01:59  03:00  03:01 ...    часа 02:xx не было
осень:  ... 01:58  01:59  01:00  01:01 ...    час 01:xx прожит дважды
```

Из этого следуют два факта, которые ломают наивный код:

- **отображение «местное время → момент» не взаимно однозначно.** Одна метка может соответствовать двум моментам или ни одному;
- **сутки не всегда 24 часа.** В дни перехода их 23 или 25.

### Обратное преобразование

Прямое — тривиально: зная момент, смотрим правило и прибавляем смещение. Обратное — вот здесь начинается работа, потому что возникает круг: чтобы вычесть смещение, нужно знать смещение, а чтобы узнать его, нужен момент.

Круг разрывается проверкой обеих гипотез:

```c
int64_t c1 = local - std_off;    /* а вдруг действовало зимнее время */
int64_t c2 = local - dst_off;    /* а вдруг летнее                   */

int ok1 = (offset_at(c1) == std_off);   /* гипотеза согласована сама с собой? */
int ok2 = (offset_at(c2) == dst_off);
```

| `ok1` | `ok2` | Смысл |
|---|---|---|
| да | нет | обычное зимнее время |
| нет | да | обычное летнее |
| да | да | **час прожит дважды** — два момента |
| нет | нет | **часа не было** — ни одного момента |

Ключевое слово — «согласована сама с собой». Гипотеза настоящая, если вычтенное смещение совпадает с тем, которое действует в получившийся момент.

### Длительность

Отсюда — правило, которое стоит запомнить целиком:

> **Длительность считают в моментах, а не в календарных датах.**

```c
/* неправильно */  dur = parse_local(t2) - parse_local(t1);
/* правильно   */  dur = utc2 - utc1;
```

И даже UTC не годится для измерения интервалов внутри программы: системные часы можно перевести, они синхронизируются по сети и умеют идти назад. Для измерения длительности существуют **монотонные** часы, которые только растут и не привязаны к календарю:

| Часы | Что показывают | Для чего |
|---|---|---|
| настенные | текущую дату и время | отметить событие |
| монотонные | время от произвольного нуля | измерить интервал |

Правило: **отметить момент — настенными, измерить промежуток — монотонными.** Замер, сделанный настенными часами, однажды даст отрицательную длительность, и воспроизвести это будет невозможно.

## Проверка на канале

```
[LUNA] Два вопроса про время.
```

**1.** LUNA: «Почему местное время нельзя перевести в момент напрямую, вычтя смещение пояса?»

<details><summary>Ответ</summary>

Потому что смещение зависит от момента, а момент — это как раз то, что мы ищем. Круг.

Разрывается он проверкой гипотез: пробуем оба возможных смещения и оставляем те, что согласованы сами с собой — то есть где вычтенное смещение совпадает с действующим в получившийся момент.

Существенно, что вариантов может оказаться **не один**. В час осеннего перехода согласованы обе гипотезы: местное `01:30` соответствует двум разным моментам с разницей в час. В час весеннего перехода не согласована ни одна: местного `02:30` в этот день не было.

Ни то ни другое не является ошибкой ввода. Это свойство календаря, и программа обязана его различать, а не выбирать наугад. Библиотеки, которые молча берут первый вариант, — источник ошибок, всплывающих раз в год.
</details>

**2.** LUNA: «Почему длительность нельзя измерять настенными часами, даже если брать UTC?»

<details><summary>Ответ</summary>

Потому что настенные часы не обязаны монотонно расти. Их переводит администратор, их подтягивает синхронизация по сети, и подтягивать она может **назад** — если часы ушли вперёд. Замер, сделанный в момент такой коррекции, даст отрицательную длительность или скачок в несколько секунд.

Воспроизвести это в отладке практически невозможно: коррекция происходит редко и не по команде. Ошибка выглядит как случайный сбой раз в месяц.

Для измерения интервалов существуют монотонные часы: они отсчитывают время от произвольного нуля, не связаны с календарём и по определению не идут назад. Правило простое: **отметить событие — настенными часами, измерить промежуток — монотонными.**

Замечание: UTC при этом всё равно лучше местного времени. Он не имеет переходов и не зависит от политических решений — но и он подвержен коррекции системных часов.
</details>

```
[LUNA] Верно. Разбирай метки.
```

## Разбор типичных ошибок

1. **Использованы `mktime` и `localtime`.** Результат зависит от переменной `TZ` и от системной базы поясов — тест перестанет быть воспроизводимым.
2. **Смещение вычитается без проверки.** Час осеннего перехода разберётся наугад, час весеннего — молча получит несуществующий момент.
3. **Неоднозначность считается ошибкой ввода.** Это данные: тридцать семь настоящих сделок будут отброшены.
4. **Деление к нулю при переводе секунд в дни.** Для дат до эпохи `-1 / 86400` даёт ноль, и 31 декабря 1969 года окажется 1 января 1970-го.
5. **Високосный год определяется как `y % 4 == 0`.** 1900-й не был високосным, 2000-й был.
6. **Сутки считаются равными 86400 секундам всегда.** В дни перехода их 82800 или 90000.
7. **Длительность считается вычитанием местных меток.** Ровно та ошибка, с которой началась серия.
8. **Метка хранится текстом.** Сортировка строк совпадает с сортировкой по времени только для UTC в формате ISO — и ломается на первой же местной метке.
9. **`time_t` считается 32-битным.** Переполнение наступит 19 января 2038 года.
