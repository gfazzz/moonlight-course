## Обстановка

`Entry arr[256]` переполнится на двести пятьдесят седьмой записи. Не упадёт — начнёт писать в соседнюю память и выдавать правдоподобную чушь.

Размер данных известен только на ходу. Значит, и память надо брать на ходу.

## Приказ

Написать `artifacts/heap.c`: выделить массив на `n` элементов в куче, заполнить, посчитать сумму, корректно освободить.

## Дано

`n` — размер, приходящий «как бы из рантайма». `malloc`, `free` из `<stdlib.h>`.

## Критерии приёмки

- [ ] Компилируется с `-Wall -Wextra -std=c11` без предупреждений.
- [ ] Размер считается **в байтах**: `malloc(n * sizeof *buf)`. Запись `sizeof *buf` предпочтительнее `sizeof(int)` — переживёт смену типа.
- [ ] Результат `malloc` проверен на `NULL` **до** первого обращения.
- [ ] Массив заполнен и просуммирован; на неинициализированную память программа не полагается.
- [ ] `free(buf)` вызван ровно один раз; после — `buf = NULL`.
- [ ] Освобождается **тот же** указатель, что вернул `malloc`, — не сдвинутый арифметикой.
- [ ] Вывод совпадает с `tests/expected.txt`; `make test` → `PASS`.
- [ ] Сборка с `-fsanitize=leak` (или `address`) утечек не находит.

## Выполнение

```bash
cp starter.c artifacts/heap.c
make test
```

Проверить себя санитайзером стоит вручную — это привычка, которая пригодится до конца курса:

```bash
gcc -fsanitize=address -g artifacts/heap.c -o /tmp/heap && /tmp/heap
```

Ожидается 40 байт, `sum = 285`. Эталон — в `solution/`.

## Диагностика

| Симптом | Причина |
|---|---|
| порча данных после нескольких записей | размер в элементах вместо байтов |
| `Segmentation fault` сразу | не проверен `NULL` от `malloc` |
| `LeakSanitizer: detected memory leaks` | забыт `free` |
| `free(): invalid pointer` | освобождается сдвинутый указатель |
| `double free or corruption` | `free` вызван дважды |

## После выполнения

Станет ясно следующее ограничение: размер неизвестен не только заранее, но и в начале работы. Данные идут потоком, и буфер придётся растить.
