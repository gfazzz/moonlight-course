## Теория: память, за которую отвечаешь ты

### Два места, где живут данные

```c
void f(void) {
    int a[256];                  /* стек: умрёт при выходе из функции */
    int *b = malloc(256 * 4);    /* куча: живёт до free */
}
```

| | Стек | Куча |
|---|---|---|
| размер | известен при компиляции | задаётся в рантайме |
| время жизни | до выхода из функции | до `free` |
| кто освобождает | компилятор | вы |
| объём | мегабайты | гигабайты |
| скорость | сдвиг указателя | поиск подходящего блока |

Куча медленнее и требует дисциплины. Взамен даёт две вещи, которых стек не даст никогда: размер, известный только на ходу, и данные, переживающие функцию, которая их создала.

### `malloc`

```c
int *buf = malloc((size_t)n * sizeof *buf);
if (buf == NULL) { perror("malloc"); return 1; }
```

Три детали:

**Аргумент — байты.** `malloc(n)` под `n` целых даст вчетверо меньше нужного. Умножение на `sizeof` обязательно.

**Запись `sizeof *buf` лучше, чем `sizeof(int)`.** Поменяете тип `buf` — выражение останется верным. Это идиома, которую стоит завести сразу.

**Может вернуть `NULL`.** Редко, но может — и тогда работа с результатом уронит программу или, хуже, испортит данные.

**Память не обнулена.** В свежем блоке лежит мусор. Нужны нули — `calloc(n, sizeof *buf)`, который заодно защищает от переполнения при умножении.

### `free` и что бывает без него

```c
free(buf);
buf = NULL;
```

`free` возвращает блок аллокатору. Что происходит, если забыть:

- **утечка** — память занята, но недоступна. Одна утечка незаметна, утечка в цикле съедает всё;
- **use-after-free** — обращение по освобождённому адресу. Данные могут ещё «работать», пока блок не переиспользован, и это худший вид ошибки: она проявится через час, в другом месте;
- **double free** — второй `free` портит служебные структуры аллокатора; падение произойдёт позже и не там.

Присваивание `NULL` после `free` не обязательно, но превращает случайное использование в честное падение вместо тихой порчи.

## Проверка на канале

```
[LUNA] Два вопроса. Куча ошибок не прощает — она их копит.
```

**1.** LUNA: «Почему `malloc(n)` под `n` целых — баг?»

<details><summary>Ответ</summary>

Потому что `malloc` принимает размер **в байтах**, а не количество элементов. `malloc(n)` выделит `n` байт — места хватит на `n/4` целых, а писать вы будете `n`. Получится запись за границей блока: она портит служебные данные аллокатора и проявляется позже, в произвольном месте. Правильно — `malloc(n * sizeof *buf)`.
</details>

**2.** LUNA: «Зачем `buf = NULL` после `free(buf)`?»

<details><summary>Ответ</summary>

Чтобы висячий указатель перестал быть висячим. После `free` память возвращена аллокатору, но указатель по-прежнему хранит адрес, и обращение по нему какое-то время «работает» — пока блок не переиспользован. Это худший сценарий: ошибка проявляется позже и в другом месте. Обнуление превращает её в мгновенное падение на `NULL`, которое отлаживается за минуту.
</details>

```
[LUNA] Верно. Бери память.
```

## Разбор типичных ошибок

1. **`malloc(n)` вместо `malloc(n * sizeof *buf)`.** Размер в байтах.
2. **Нет проверки на `NULL`.** Редкий случай, но именно он даёт необъяснимые падения.
3. **Забыт `free`.** Утечка; в цикле — фатальная.
4. **`free` дважды.** Порча служебных структур аллокатора.
5. **Использование после `free`.** Может «работать» — до первого переиспользования блока.
6. **`free` не того указателя.** Освобождать можно только адрес, который вернул `malloc`, — не сдвинутый арифметикой.
