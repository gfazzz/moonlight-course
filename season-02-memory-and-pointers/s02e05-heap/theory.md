# Теория — s02e05

## 1. Кто отводит память

> *— Локальный массив — это обещание, которое ты даёшь компилятору, — сказал Виктор. — «Мне хватит вот столько». Он верит на слово и отводит место в стеке.*
> *— А если я соврал?*
> *— Никто не проверит. Именно поэтому переполнение буфера на стеке — самая известная уязвимость в истории. Обещание проверяют только атакующие.*

Три источника памяти в C:

| Область | Кто отводит | Когда умирает | Размер |
|---|---|---|---|
| статическая (`.data`, `.bss`) | компоновщик | никогда | известен при сборке |
| стек | компилятор | при выходе из функции | известен при сборке |
| куча | вы | при `free` | любой, в рантайме |

Стек быстр до неприличия: выделение — это вычитание из регистра указателя стека, освобождение — сложение. Никакого поиска, никаких служебных структур. Поэтому локальные переменные бесплатны.

Но стек невелик: по умолчанию 8 МБ на Linux, 1 МБ на основном потоке Windows и меньше в потоках. `int big[1000000]` внутри функции — четыре мегабайта на стеке, и это уже опасно близко к границе. Переполнение стека не диагностируется красиво: программа падает, и стек вызовов в отладчике бесполезен.

## 2. Что на самом деле делает `malloc`

`malloc` — не системный вызов. Это библиотечная функция, которая управляет большим куском памяти, полученным у ядра оптом:

```
ваша программа → malloc → (иногда) brk/mmap → ядро
```

Аллокатор запрашивает у ядра память крупными блоками и потом раздаёт из них мелкие куски, ведя учёт свободных. Поэтому тысяча вызовов `malloc(16)` обычно не означает тысячу обращений к ядру.

**Служебный заголовок.** Перед возвращённым адресом аллокатор хранит размер блока и флаги — обычно 8–16 байт. Отсюда два следствия:

- запрос на 1 байт занимает больше 1 байта: мелкие частые выделения расточительны;
- **запись до начала блока портит заголовок**, и падение случится потом, в чужом `free`.

**Выравнивание.** `malloc` обязан вернуть адрес, пригодный для любого типа: на x86-64 это кратность 16. Поэтому `malloc(1)` и `malloc(16)` часто занимают одинаково.

**`malloc(0)`.** Стандарт допускает и `NULL`, и валидный указатель, который нельзя разыменовать, но нужно освободить. Реализации расходятся — не полагайтесь на конкретное поведение.

## 3. Семейство функций

```c
void *malloc(size_t size);              /* мусор внутри */
void *calloc(size_t n, size_t size);    /* нули; проверяет переполнение n*size */
void *realloc(void *p, size_t size);    /* s02e06 */
void  free(void *p);                    /* free(NULL) — легально и ничего не делает */
```

`calloc` предпочтительнее не только из-за нулей: он **проверяет переполнение при умножении**. Классическая уязвимость выглядит так:

```c
buf = malloc(count * size);   /* count пришёл из файла: 2^32 * 4 переполнится */
```

При переполнении `malloc` получит маленькое число, выделит крохотный блок, а цикл запишет туда `count` элементов. Это готовая дыра, и в реальных CVE она встречается регулярно. `calloc(count, size)` вернёт `NULL` вместо переполнения.

То, что `free(NULL)` легален, экономит проверки в путях очистки:

```c
cleanup:
    free(a); free(b); free(c);   /* безопасно, даже если что-то не выделилось */
```

## 4. Три ошибки, за которые платят

**Утечка (CWE-401).** Блок выделен, указатель потерян. Одна утечка не страшна — ОС вернёт всё при завершении процесса. Смертельна утечка в цикле или в долгоживущей службе.

**Use-after-free (CWE-416).** Обращение по освобождённому адресу. Коварство в том, что оно часто «работает»: пока блок не переиспользован, данные на месте. Ошибка проявится через час под нагрузкой. Это одна из самых эксплуатируемых уязвимостей в браузерах и ядрах: атакующий добивается, чтобы освобождённый блок занял его объект, и получает контроль.

**Double free (CWE-415).** Второй `free` портит списки свободных блоков аллокатора. Исторически — способ получить произвольную запись в память; современные аллокаторы это детектируют и аварийно завершают программу.

Дисциплина, снимающая почти всё:

1. `free` в той же функции и на том же уровне абстракции, где `malloc`;
2. владелец у блока один, и он известен по имени;
3. после `free` — `NULL`;
4. единая точка выхода с очисткой (`goto cleanup` — редкий случай, когда `goto` в C уместен и общепринят).

## 5. Инструменты, которые находят это за вас

Не полагайтесь на внимательность — она кончается на третьем часу.

```bash
# санитайзер адресов: use-after-free, выход за границы, двойное free
gcc -fsanitize=address -g program.c && ./a.out

# только утечки, дешевле
gcc -fsanitize=leak -g program.c && ./a.out

# valgrind: без пересборки, но медленнее в 10-50 раз
valgrind --leak-check=full --track-origins=yes ./program
```

ASan замедляет примерно вдвое и увеличивает потребление памяти — приемлемо для отладочных сборок и тестов. В курсе он используется в тесте s10e05, где программу специально кормят враждебным вводом.

Практическое правило: **любая программа с `malloc` должна хотя бы раз быть запущена под санитайзером.** Это дешевле любого code review.

## 6. Фрагментация

Аллокатор возвращает освобождённые блоки в свой пул, но не всегда может отдать их ядру: если блок в середине занятой области, вернуть его нельзя.

Отсюда явление: программа освободила всё, а потребление памяти по `top` не упало. Это не утечка — это фрагментация.

Смягчают её так:

- **пулы** — выделять объекты одного размера пачками;
- **арены** — выделять всё, что живёт одинаково долго, из одного блока и освобождать разом;
- **переиспользование** вместо освобождения — кольцевой буфер, свободный список.

Эти приёмы понадобятся в Season 9, где кэш страниц базы данных не может позволить себе `malloc` на каждую страницу.

## 7. Почему в C нет сборщика мусора

Вопрос возникает у всех. Ответ прагматичный: сборщик требует знать, какие значения в памяти являются указателями. В C это принципиально невозможно — указатель можно привести к целому, спрятать в `union`, вычислить арифметикой, записать в файл и прочитать обратно.

Существуют консервативные сборщики (Boehm GC), считающие указателем всё, что похоже. Они работают, но дают ложные удержания и не годятся туда, где C обычно применяют.

Настоящая причина глубже: C создавался для системного кода, где момент освобождения важен так же, как сам факт. Пауза сборщика в обработчике прерывания неприемлема. Ручное управление — не недостаток языка, а его позиция: предсказуемость важнее удобства.
