# Теория — s02e03

## 1. Почему индексация — это сложение

> *— Почему массивы в C нумеруются с нуля? — спросил я.*
> *— Потому что нумерация тут ни при чём. `arr[i]` — это `*(arr + i)`. У первого элемента смещение ноль. Не «решили считать с нуля» — просто ноль и есть ноль.*
> *Он написал на полях: `3[arr]`.*
> *— Скомпилируется?*
> *— Не может быть.*
> *— Сложение коммутативно. Проверь.*

Стандарт определяет индексацию буквально: выражение `E1[E2]` тождественно `*(E1 + E2)`. Отсюда следуют три вещи, которые обычно узнают по отдельности:

1. **Нумерация с нуля** — не соглашение, а арифметика: смещение первого элемента равно нулю.
2. **`arr[i]` и `i[arr]` эквивалентны**, потому что сложение коммутативно. Писать так нельзя, но факт объясняет природу скобок.
3. **Проверки границ нет и быть не может** — компилятор видит сложение, а не «доступ к элементу».

## 2. Распад массива и три исключения

В большинстве контекстов имя массива превращается в указатель на первый элемент. Исключения:

| Контекст | Что получается |
|---|---|
| `sizeof arr` | размер всего массива, не указателя |
| `&arr` | указатель на **массив**, тип `int (*)[6]` |
| строковый литерал в инициализаторе | копирование содержимого, а не адреса |

Про `&arr` стоит знать отдельно: численно этот адрес совпадает с `&arr[0]`, но тип другой — а значит, другой и шаг арифметики:

```c
int arr[6];
arr + 1;      /* +4 байта: следующий int */
&arr + 1;     /* +24 байта: следующий массив из шести int */
```

Это не курьёз: на этом устроена работа с двумерными массивами (§6).

## 3. Правила, которые стандарт задаёт жёстко

Арифметика указателей определена **только внутри одного объекта** (массива).

**Разрешено:**

- получать адреса элементов с индексами от `0` до `n` **включительно**;
- сравнивать любые два таких указателя;
- вычитать их, получая `ptrdiff_t`.

**Неопределённое поведение:**

- вычислять `arr + n + 1` — даже без разыменования;
- разыменовывать `arr + n`;
- вычитать указатели на разные объекты;
- сравнивать указатели на разные объекты через `<` и `>` (равенство сравнивать можно).

Почему граница `n` включена: без этого невозможен идиоматический цикл `for (q = arr; q < arr + n; q++)`. Комитет сделал для «указателя за концом» специальное исключение.

Практическое следствие: проверка принадлежности вида `if (p < arr || p >= arr + n)` формально некорректна, если `p` пришёл из другого объекта — сравнение уже неопределено. Такие проверки либо пишут через `uintptr_t`, либо не пишут вовсе, а носят длину рядом с данными.

## 4. `ptrdiff_t` и `size_t`

```c
#include <stddef.h>
ptrdiff_t d = q - p;    /* знаковый: может быть отрицательным */
size_t    n = 10;       /* беззнаковый: размеры и количества */
```

Печатать: `%td` для `ptrdiff_t`, `%zu` для `size_t`.

Классическая ловушка на их смешении:

```c
for (size_t i = n - 1; i >= 0; i--)   /* бесконечный цикл */
```

`size_t` беззнаковый, поэтому `i >= 0` истинно всегда, а после нуля `i` становится огромным числом. Правильно — либо знаковый тип, либо разворот условия:

```c
for (size_t i = n; i-- > 0; )         /* корректно и при n == 0 */
```

## 5. Обход указателем против обхода индексом

```c
for (size_t i = 0; i < n; i++) sum += arr[i];    /* индексный */
for (int *q = arr; q < arr + n; q++) sum += *q;  /* указательный */
```

В K&R указательный вариант подавался как более быстрый, и в 1978 году это было правдой: компиляторы не умели превращать индексацию в инкремент. **Сегодня утверждение устарело** — любой современный компилятор порождает для обоих вариантов одинаковый код, а индексный иногда оптимизируется лучше, потому что векторизатору проще рассуждать о независимости обращений.

Практический вывод: выбирайте по читаемости. Указательный обход уместен там, где указатель и так есть — при работе со строками, при проходе по буферу из `fread`, в реализациях `str*`-функций.

Проверить утверждение можно самому:

```bash
gcc -O2 -S -o - file.c | less
```

Это, кстати, общее правило курса: если про производительность сказано «быстрее», должен быть способ это увидеть.

## 6. Двумерные массивы

```c
int m[3][4];
```

Это массив из трёх массивов по четыре `int`, лежащий в памяти одним непрерывным блоком, построчно. Отсюда:

```c
m[1][2]  ≡  *(*(m + 1) + 2)
m + 1        /* +16 байт: следующая строка */
m[0] + 1     /* +4 байта:  следующий элемент строки */
```

`m` распадается в `int (*)[4]` — указатель на строку, **а не** `int **`. Это принципиально разные вещи: `int **` предполагает массив указателей, каждый из которых ведёт в отдельный блок. Передать `int m[3][4]` в функцию, ожидающую `int **`, не получится — и хорошо, потому что в памяти это несовместимые раскладки.

Правильная сигнатура: `void f(int m[][4], size_t rows)` или `void f(int (*m)[4], size_t rows)`.

## 7. Где это используется в реальном коде

Арифметика указателей — не упражнение, а рабочий инструмент:

- **Разбор бинарных данных:** курсор двигается на размер прочитанного поля. Так вы будете разбирать пакеты в Season 3.
- **Строковые функции:** `strlen` — это буквально `while (*s) s++; return s - start;`.
- **Кольцевые буферы:** индекс по модулю вместо сдвига указателя.
- **Аллокаторы** (s02e05): служебный заголовок блока лежит непосредственно перед адресом, который вернул `malloc`, и добраться до него можно только арифметикой.
