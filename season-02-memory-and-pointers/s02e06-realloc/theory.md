# Теория — s02e06

## 1. Сколько раз ты готов переехать

> *— Ты снимаешь квартиру и через месяц понимаешь, что мала. Переезжаешь в чуть большую. Через месяц — снова.*
> *— И что делать?*
> *— Брать сразу вдвое больше. Переездов станет логарифмически мало, а лишнего места — не больше, чем вдвое. Плохая стратегия для квартир и отличная для буферов.*
> *— А почему именно вдвое?*
> *— Потому что любой множитель больше единицы даёт логарифм. Двойка просто удобно считается. Хочешь экономить память — бери полтора.*

Это и есть содержание серии. Всё остальное — детали реализации.

## 2. Что делает `realloc`

```c
void *realloc(void *ptr, size_t size);
```

Поведение зависит от того, хватило ли места на месте:

1. **Хватило** — блок расширяется, адрес прежний, копирования нет.
2. **Не хватило** — выделяется новый блок, содержимое копируется, старый освобождается, возвращается **новый адрес**.
3. **Не удалось** — возвращается `NULL`, **старый блок остаётся нетронутым**.

Особые случаи, полезные для сокращения кода:

```c
realloc(NULL, size);   /* эквивалентно malloc(size) */
realloc(ptr, 0);       /* поведение зависит от реализации — не используйте */
```

Первое позволяет писать рост единообразно, без ветки «первое выделение»:

```c
void *tmp = realloc(vec->data, cap * sizeof *vec->data);   /* data может быть NULL */
```

## 3. Две ловушки и почему они опасны именно вместе

**Переезд блока.** После `realloc` все ранее взятые указатели на элементы могут стать висячими. Отсюда правило: **в растущем массиве храните индексы, а не указатели**.

```c
int *p = &vec.data[5];
vec_push(&vec, x);       /* внутри realloc — блок мог переехать */
*p = 10;                 /* use-after-free */
```

Ошибка коварна тем, что проявляется не всегда: пока перевыделение попадает в тот же блок, всё «работает». Падает на том добавлении, где ёмкость исчерпалась, — то есть на конкретном размере данных, который на тестах может не встретиться.

**Потеря указателя при неудаче.**

```c
a = realloc(a, size);    /* при NULL старый блок недоступен навсегда */
```

Отдельно неприятно, что это утечка **в момент нехватки памяти** — то есть тогда, когда программа и так на грани. Правильная форма:

```c
void *tmp = realloc(a, size);
if (!tmp) { /* a ещё жив: можно сохранить данные или корректно завершиться */ }
a = tmp;
```

## 4. Амортизированный анализ: откуда берётся O(1)

Пусть добавляем `n` элементов, удваивая ёмкость при заполнении. Копирования происходят на размерах `1, 2, 4, 8, ..., n`:

```
1 + 2 + 4 + ... + n = 2n − 1 < 2n
```

Сумма геометрической прогрессии меньше удвоенного последнего члена. Значит, `n` добавлений стоят меньше `2n` копирований — в среднем меньше двух на добавление, независимо от `n`. Это и называется амортизированным O(1).

Сравнение с ростом на константу `c`:

```
c + 2c + 3c + ... + n = O(n²)
```

Разница на десяти тысячах элементов: около 20 000 операций против 50 000 000.

**Метод бухгалтерского учёта** объясняет это интуитивно: берём с каждого добавления «три монеты» — одну на саму запись, две откладываем. К моменту, когда буфер заполнится, отложенного ровно хватает, чтобы оплатить копирование всех элементов. Формально — CLRS, глава 17.

**Почему коэффициент бывает 1.5.** При удвоении сумма всех ранее освобождённых блоков всегда меньше нужного нового (`1+2+4 < 8`), поэтому переиспользовать освобождённую память нельзя — аллокатор всегда ищет новое место. При коэффициенте меньше золотого сечения (≈1.618) сумма прошлых блоков рано или поздно перекрывает новый запрос, и память переиспользуется. Поэтому в некоторых реализациях (например, в ряде версий std::vector в MSVC и в Facebook folly) берут 1.5.

## 5. Как выглядит нормальный динамический массив

```c
typedef struct { int *data; size_t len, cap; } Vec;

int vec_push(Vec *v, int x) {
    if (v->len == v->cap) {
        size_t ncap = v->cap ? v->cap * 2 : 4;
        if (ncap > SIZE_MAX / sizeof *v->data) return -1;   /* защита от переполнения */
        int *tmp = realloc(v->data, ncap * sizeof *v->data);
        if (!tmp) return -1;
        v->data = tmp;
        v->cap  = ncap;
    }
    v->data[v->len++] = x;
    return 0;
}
```

Что здесь неслучайно:

- **начальная ёмкость 4, а не 1** — первые три добавления не вызывают перевыделений;
- **проверка переполнения** перед умножением: `cap * sizeof` при больших `cap` переполнится, и `realloc` выделит крошечный блок;
- **возврат кода ошибки**, а не `exit` — библиотечная функция не решает за приложение, что делать при нехватке памяти;
- **длина и ёмкость раздельно** — `len` это сколько занято, `cap` сколько выделено.

## 6. Когда уменьшать

`realloc` умеет и сжимать, но делать это на каждом удалении нельзя — получится «дребезг»: массив на границе ёмкости будет расти и сжиматься на каждой операции, и амортизация сломается.

Стандартный приём: **сжимать при заполнении ниже четверти, до половины**. Гистерезис между порогом роста (100 %) и порогом сжатия (25 %) гарантирует, что между перевыделениями происходит достаточно операций.
