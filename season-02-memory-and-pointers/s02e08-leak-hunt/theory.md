# Теория — s02e08

## 1. Нельзя спросить дорогу у того, кого уже нет

> *Я показал ему цикл освобождения списка. Он прочитал и молча ткнул пальцем в две строки.*
>
> ```c
> free(e);
> e = e->next;
> ```
>
> — И?
> — Ты освободил узел, а потом спросил у него, где следующий.
> — Но оно работает.
> — Оно работает, пока никто не занял это место. Порядок операций с памятью важнее самих операций. Запомни это раньше, чем научишься их писать.

Правильная форма:

```c
while (e) {
    Node *nx = e->next;   /* спросить, пока жив */
    free(e->payload);     /* освободить изнутри */
    free(e);              /* потом наружу */
    e = nx;
}
head = NULL;
```

Два инварианта, которые стоит проговорить вслух: **`next` читается до освобождения** и **освобождение идёт изнутри наружу**. Нарушение первого — use-after-free, второго — утечка вложенных данных.

## 2. Владение: единственная дисциплина, которая масштабируется

Правила расстановки `free` не работают на большом коде. Работает понятие **владельца**: для каждого блока памяти в любой момент известно, кто отвечает за его освобождение.

Три способа зафиксировать владение в C:

**Парные функции.** `list_create` / `list_destroy`, `add_log` / `free_all`. Кто создал — тот и разрушает; вызывающий обязан вызвать пару.

**Соглашение в сигнатуре.** Функция либо **забирает** владение, либо **одалживает**:

```c
void list_push(List *l, char *owned);        /* забирает: освободит сам */
void list_print(const List *l);              /* одалживает: только читает */
char *list_take(List *l, size_t i);          /* отдаёт: освобождать вызывающему */
```

`const` в параметре — сильный сигнал «я только читаю».

**Документация в заголовке.** Одна строка комментария рядом с прототипом, отвечающая на вопрос «кто освобождает возвращённое?». Отсутствие этой строки — источник половины утечек в чужом коде.

Зачем это в языке без деструкторов: C не поможет вам автоматически. Единственная защита — чтобы у каждого блока был один названный владелец, и это решение принималось при проектировании, а не при отладке.

## 3. Почему утечка в демоне смертельна, а в утилите — нет

```
утилита:  запустилась, отработала, вышла — ОС вернула всё
демон:    работает месяцами — каждая утечка накапливается
```

Отсюда практическое следствие, которое многих удивляет: **не всякую утечку нужно чинить**. Если программа выделила таблицу при старте и живёт с ней до конца, освобождать её перед `exit` не обязательно — ОС сделает это быстрее и надёжнее.

Но есть два «но». Первое: санитайзер такую память покажет как утечку, и отличать намеренное от случайного придётся глазами. Второе: код имеет свойство переезжать — сегодня это `main`, завтра библиотечная функция, вызываемая в цикле.

Компромисс, принятый в индустрии: освобождать всё, а для намеренных исключений заводить файл подавления:

```
# lsan.supp
leak:one_time_global_init
```

```bash
LSAN_OPTIONS=suppressions=lsan.supp ./program
```

Так вы отличаете «мы знаем и согласны» от «мы не заметили».

## 4. Инструменты и что каждый видит

| Инструмент | Ловит | Не ловит | Замедление |
|---|---|---|---|
| `-fsanitize=address` | границы, UAF, double free, утечки | чтение неинициализированной памяти | ×2 |
| `-fsanitize=memory` | чтение неинициализированного | требует пересборки всех зависимостей | ×3 |
| `valgrind --leak-check=full` | всё вышеперечисленное | — | ×10–50 |
| `leaks` (macOS) | утечки | остальное | мало |

Практика: **ASan в CI на каждый прогон тестов**, valgrind — точечно, когда ASan чист, а поведение всё равно странное.

Категории valgrind, которые надо уметь читать:

- **definitely lost** — указателей на блок не осталось; настоящая утечка;
- **indirectly lost** — блок был доступен только через потерянный; чинится вместе с ним;
- **possibly lost** — остался указатель внутрь блока, но не на начало; часто ложная тревога;
- **still reachable** — указатель есть, просто не освободили перед выходом; обычно безобидно.

Разница между «definitely» и «still reachable» — ровно та, о которой шла речь в §3.

## 5. Как искать утечку в чужом коде

Порядок действий, экономящий часы:

1. **Воспроизвести под ASan.** Отчёт назовёт файл, строку и стек выделения.
2. **Смотреть на стек выделения, а не на стек ошибки.** Утечка регистрируется в конце программы; полезен второй стек — где блок родился.
3. **Считать выделения и освобождения.** Если `malloc` вызван 1000 раз, а `free` — 998, ищите путь, который выполнялся дважды: обычно это обработка ошибки.
4. **Проверить все `return` в функции.** Классика: `free` стоит перед последним `return`, а ранних выходов три.
5. **Проверить пути с `continue` и `break`.** Та же ошибка в цикле.

Пункты 3–5 покрывают подавляющее большинство случаев в реальном коде.

## 6. Приёмы, устраняющие проблему конструктивно

**Единая точка выхода.**

```c
int f(void) {
    char *a = NULL, *b = NULL;
    int rc = -1;
    if (!(a = malloc(N))) goto out;
    if (!(b = malloc(M))) goto out;
    /* работа */
    rc = 0;
out:
    free(b); free(a);
    return rc;
}
```

**Арена.** Всё, что живёт одинаково долго, выделяется из одного большого блока и освобождается разом. Утечка становится структурно невозможной: освобождать нечего, кроме арены. Так устроены компиляторы и парсеры, где время жизни данных совпадает с обработкой одного файла.

**Пул объектов.** Заранее выделенный массив с freelist. Ни одного `malloc` в горячем пути, предсказуемое поведение. Понадобится в Season 9 для страничного кэша.
