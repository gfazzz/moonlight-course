`buggy_logger.c` открыт на весь экран. Двести сорок строк, и он **работает** — печатает верно, не падает, годами делал ровно то, что от него ждали. Поэтому его никто и не проверял.

```
[LUNA] Каждая запись — два выделения: узел списка и строка сообщения.
[LUNA] Освобождений — ноль. Ни одного, ни для узлов, ни для строк.
[LUNA] Список растёт, пока процесс жив. А процесс живёт, пока есть данные.
```

Ты пишешь `free_all()`, прогоняешь — и санитайзер выдаёт то, чего ты не ждал: use-after-free в твоём собственном коде.

```c
while (e) { free(e); e = e->next; }    /* прочитал next у мёртвого узла */
```

Освободил узел, а потом спросил у него, где следующий. Иногда работает, иногда нет — блок ещё не переиспользован.

> *— Порядок операций с памятью важнее, чем сами операции, — говорил Виктор. — Ты не можешь спросить дорогу у того, кого уже нет.*

Правильно — сохранить `next` **до** освобождения. Одна строка разницы.

```
[LUNA] Вот теперь чисто. Осталось понять, зачем логгер так защищали.
[LUNA] Он ведь не просто течёт — он ещё и хранит всё, что через него прошло.
[LUNA] Ни одна запись не удалена. Включая самую последнюю.
```

## Теория: как разбирать за собой

### Освобождение списка

```c
LogEntry *e = head;
while (e != NULL) {
    LogEntry *nx = e->next;   /* сохранить ДО освобождения */
    free(e->message);         /* сначала то, чем владеет узел */
    free(e);                  /* потом сам узел */
    e = nx;
}
head = NULL;
```

Два правила в четырёх строках:

**Сохранить `next` заранее.** После `free(e)` поле `e->next` — освобождённая память. Чтение оттуда «часто работает», и именно поэтому ошибка доживает до продакшена.

**Освобождать изнутри наружу.** Сначала то, на что узел ссылается, потом сам узел. Обратный порядок теряет указатель на строку — утечка.

### Владение

`add_log` выделяет узел и строку — значит, он **создал владельца**. Освобождение — обязанность `free_all`, парной функции. Правило простое: у каждой функции, выделяющей память, должна быть парная, освобождающая, и в документации сказано, кто за что отвечает.

Нарушения этого правила дают либо утечку (никто не освободил), либо double free (освободили оба).

### Почему «работает» ничего не значит

Утечка не влияет на вывод. Программа с утечкой печатает то же самое, что и без неё, — просто занимает всё больше памяти. Корректность и чистота — независимые свойства, и второе видит только инструмент.

## Проверка на канале

```
[LUNA] Два вопроса. Финал не прощает «почти чисто».
```

**1.** LUNA: «Почему `free(e); e = e->next;` — ошибка?»

<details><summary>Ответ</summary>

Потому что `e->next` читается уже после освобождения узла — это use-after-free. Блок возвращён аллокатору, и его содержимое может быть перезаписано в любой момент. Работает такой код ровно до тех пор, пока память не переиспользована, — то есть непредсказуемо. Правильно: `nx = e->next; free(e); e = nx;`.
</details>

**2.** LUNA: «Логгер печатал правильно годами. Почему это не доказательство?»

<details><summary>Ответ</summary>

Потому что утечка на вывод не влияет вообще. Программа с утечкой ведёт себя идентично программе без неё — до того момента, когда память кончится. Корректность вывода и корректность работы с памятью — независимые свойства; второе проверяется только санитайзером или valgrind, и никак иначе.
</details>

```
[LUNA] Верно. На охоту.
```

## Разбор типичных ошибок

1. **`free(e)` до чтения `e->next`.** Use-after-free; работает через раз.
2. **Освобождён узел, забыта строка.** Два выделения на запись — два освобождения.
3. **`free_all` написан, но не вызван.** Санитайзер поймает.
4. **Освобождение только на успешном пути.** Ошибка в середине оставит хвост списка.
5. **«Вывод верный — значит чисто».** Не значит. Чистоту показывает инструмент.
