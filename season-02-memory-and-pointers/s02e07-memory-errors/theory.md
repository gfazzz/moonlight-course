# Теория — s02e07

## 1. Два вида плохого кода

> *— Есть два вида плохого кода. Первый падает сразу, и это подарок: ты знаешь, где ошибся. Второй работает. Работает час, неделю, полгода — а потом падает в другом месте, у другого человека, в три часа ночи.*
> *— И как отличить?*
> *— Никак. Глазами — никак, в этом всё дело. Поэтому есть инструменты, и поэтому взрослые люди ими пользуются.*

Особенность ошибок памяти в C: **место ошибки и место проявления не совпадают**. Программа портит структуру данных аллокатора, продолжает работать, и падает через десять минут внутри `printf` — который ни в чём не виноват.

Отсюда единственная работающая стратегия: не искать глазами, а инструментировать.

## 2. Утечка (CWE-401)

```c
char *p = malloc(100);
return;              /* указатель потерян, память занята */
```

Что важно понимать: **утечка при завершении процесса безвредна** — ОС вернёт всё. Смертельны утечки в двух случаях: в цикле и в долгоживущей службе.

Отдельный неочевидный источник — утечка на **пути ошибки**:

```c
char *a = malloc(100);
char *b = malloc(200);
if (!b) return -1;   /* a утёк */
```

Именно такие места пропускают чаще всего: основной путь вылизан, а обработка ошибок написана наспех. Лечится единой точкой выхода:

```c
int f(void) {
    char *a = NULL, *b = NULL;
    int rc = -1;
    if (!(a = malloc(100))) goto out;
    if (!(b = malloc(200))) goto out;
    rc = 0;
out:
    free(b); free(a);       /* free(NULL) безопасен */
    return rc;
}
```

Это один из немногих случаев, где `goto` в C общепринят: так написано ядро Linux и большинство системных библиотек.

## 3. Use-after-free (CWE-416)

```c
free(p);
printf("%s\n", p);      /* часто печатает верно */
```

`free` не стирает данные — он помечает блок свободным и связывает его в список. Содержимое остаётся, пока блок не выдадут по новому запросу.

**Почему это самый опасный класс.** Атакующий, обнаруживший UAF, добивается, чтобы освобождённый блок был выдан под контролируемый им объект. Тогда чтение по старому указателю возвращает его данные, а запись — портит его объект. Если в структуре есть указатель на функцию, это превращается в выполнение произвольного кода.

Именно так эксплуатируют браузеры и ядра: подавляющее большинство критических уязвимостей последних лет — это UAF.

Особый подвид — **возврат адреса локальной переменной**:

```c
char *bad(void) { char buf[64]; return buf; }   /* кадр стека умрёт */
```

Компилятор предупредит (`-Wreturn-local-addr`), и это предупреждение нельзя игнорировать никогда.

## 4. Double free (CWE-415)

```c
free(p);
free(p);      /* порча служебных структур аллокатора */
```

Исторически — способ получить произвольную запись: манипулируя списками свободных блоков, атакующий заставлял аллокатор выдать указатель на нужный адрес. Современные реализации glibc детектируют повтор и аварийно завершают программу с `double free or corruption`.

Частая причина не в двух подряд идущих `free`, а в **двух владельцах**: два указателя на один блок, и каждый считает себя ответственным. Отсюда правило: у блока ровно один владелец, и он должен быть назван.

## 5. Выход за границы (CWE-787, CWE-125)

```c
char *d = malloc(strlen(s));    /* нет места под '\0' */
strcpy(d, s);                   /* пишем на байт больше */
```

Один байт за границей кажется пустяком. На деле он попадает в служебный заголовок следующего блока, и падение произойдёт в чужом `free` — с бесполезным стеком вызовов.

Переполнение буфера **на стеке** опаснее: там рядом лежит адрес возврата, и его перезапись передаёт управление куда угодно. Это классика с 1988 года (червь Морриса) и до сих пор рабочий вектор в системах без современных защит.

Защиты, которые есть сегодня: канарейки стека (`-fstack-protector`), неисполняемый стек (NX), ASLR. Они поднимают стоимость атаки, но не устраняют ошибку.

## 6. AddressSanitizer: как он это делает

```bash
gcc -fsanitize=address -fno-omit-frame-pointer -g file.c && ./a.out
```

Механика в двух словах. ASan окружает каждое выделение **красными зонами** — областями, помеченными как «трогать нельзя», — и ведёт теневую память: на каждые 8 байт программы приходится 1 байт метаданных о доступности. Каждое обращение компилятор снабжает проверкой теневого байта.

Освобождённые блоки помещаются в **карантин** и не переиспользуются сразу, поэтому обращение после `free` обнаруживается, а не «срабатывает».

Что даёт вывод ASan: тип ошибки, файл и строка, стек в момент ошибки **и стек в момент выделения** блока. Последнее часто важнее первого.

Цена: примерно двукратное замедление и втрое больше памяти. Для тестов приемлемо, для продакшена — нет.

Полезные родственники:

| Санитайзер | Что ловит |
|---|---|
| `-fsanitize=address` | границы, UAF, double free, утечки |
| `-fsanitize=undefined` | переполнение знаковых, сдвиги, невыровненный доступ |
| `-fsanitize=leak` | только утечки, почти без накладных расходов |
| `-fsanitize=thread` | гонки данных (Season 7) |

`address` и `thread` вместе не работают — их выбирают по задаче.

**Valgrind** решает ту же задачу без пересборки, эмулируя выполнение. Медленнее в 10–50 раз, зато ловит чтение неинициализированной памяти, чего ASan не умеет.

## 7. Дисциплина, которая дешевле отладки

1. **Один владелец** у блока, названный явно.
2. **`free` на том же уровне абстракции**, где `malloc`.
3. **`p = NULL` после освобождения.**
4. **Единая точка выхода** с очисткой (`goto out`).
5. **Проверка каждого `malloc`** — сразу, а не «потом добавлю».
6. **`+1` под терминатор** — рефлекторно.
7. **Тесты под ASan** — в CI, а не по настроению.

Седьмой пункт важнее остальных шести: он единственный не зависит от вашей внимательности в четыре часа дня.
