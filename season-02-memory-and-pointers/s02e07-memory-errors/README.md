## Теория: четыре способа сломать память

| Ошибка | Как выглядит | Когда проявится |
|---|---|---|
| **Утечка** | `malloc` без `free` | через часы работы |
| **Use-after-free** | `free(p); ... *p` | когда блок переиспользуют |
| **Double free** | `free(p); free(p)` | при следующем `malloc` |
| **Выход за границы** | запись мимо блока | в чужом коде, позже |

Обратите внимание на правую колонку: **ни одна не проявляется там, где сделана**. Именно поэтому глазами их не найти.

### Почему use-after-free хуже падения

```c
free(p);
printf("%s\n", p);    /* часто печатает верно */
```

Освобождённый блок не стирается — аллокатор лишь помечает его свободным. Данные лежат на месте, пока блок не переиспользуют. Программа «работает», и вы уходите в продакшен с бомбой замедленного действия.

Хуже: атакующий может добиться, чтобы освобождённый блок занял **его** объект. Тогда обращение по старому указателю читает и пишет то, что подсунули. Это основной механизм эксплуатации браузеров и ядер за последнее десятилетие.

### Приёмы, снимающие большинство

```c
free(p); p = NULL;                  /* убирает UAF и double free разом */
char *d = malloc(strlen(s) + 1);    /* +1 под терминатор — всегда */
if (!d) return NULL;                /* проверять сразу */
```

Присваивание `NULL` работает против двух классов сразу: обращение по `NULL` даёт честное падение вместо тихой порчи, а `free(NULL)` по стандарту безопасен.

### Инструмент

```bash
gcc -fsanitize=address -g file.c && ./a.out
```

AddressSanitizer ловит все четыре класса и печатает файл, строку и стек — как в момент ошибки, так и в момент выделения блока. Замедление примерно вдвое, что приемлемо для тестов.

В этой папке лежит `buggy.c` с подписанными ошибками. `make asan-buggy` покажет, как выглядит его вердикт.

## Проверка на канале

```
[LUNA] Два вопроса. От них зависит, переживёт ли твой код час аптайма.
```

**1.** LUNA: «Программа с use-after-free печатает верно. Почему это ничего не значит?»

<details><summary>Ответ</summary>

Потому что `free` не стирает данные — он лишь возвращает блок аллокатору. Пока блок не выдан по новому запросу, старое содержимое на месте, и чтение «работает». Как только память переиспользуется — под другой объект, в другом потоке, при другой нагрузке, — там окажется чужое. Ошибка недетерминированная: на тестах не воспроизводится, в продакшене проявляется.
</details>

**2.** LUNA: «Как одно присваивание `p = NULL` убирает два класса ошибок?»

<details><summary>Ответ</summary>

Use-after-free превращается в разыменование `NULL` — мгновенное падение в точке ошибки вместо тихой порчи данных где-то потом. А double free перестаёт быть ошибкой вовсе: `free(NULL)` по стандарту не делает ничего. Одна строка вместо двух классов дефектов.
</details>

```
[LUNA] Верно. Пиши чисто.
```

## Разбор типичных ошибок

1. **`malloc(strlen(s))` без `+1`.** Терминатору некуда встать; запись уйдёт за границу.
2. **`free` до последнего использования.** Порядок: использовать, потом освобождать.
3. **Обращение после `free`.** Может «работать» — до первого переиспользования блока.
4. **Не проверен возврат `malloc`.** Падение при нехватке памяти.
5. **`strcpy` в буфер по чужой длине.** Длина должна считаться от источника, а не предполагаться.
