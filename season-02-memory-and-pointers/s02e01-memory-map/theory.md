# Теория — s02e01

## 1. Память — лента пронумерованных байтов

> *Виктор рисует на салфетке длинную полосу и делит её штрихами.*
>
> — Вот память. Каждая клетка — байт, у каждой номер. Всё.
> — Где здесь переменные?
> — Нигде. Переменных не существует. Есть адреса, которым ты дал имена, чтобы не сойти с ума. Компилятор помнит настоящие номера, ты — имена. Как только ты об этом забудешь, ты перестанешь понимать C.

Абстракция C такова: память — непрерывный массив байтов, у каждого свой номер. Объект занимает несколько подряд идущих байтов, и его адрес — номер первого.

Тонкость, о которой стоит знать сразу: **это модель, а не физическая правда**. Между вашим адресом и микросхемой лежат таблицы страниц и MMU, которые переводят виртуальный адрес в физический. Два процесса могут одновременно работать с адресом `0x7fff1234` и не мешать друг другу — у каждого своя карта. Именно поэтому дамп чужого процесса нужно снимать специально: просто прочитать его память по адресу нельзя.

## 2. `sizeof` — вопрос к компилятору

`sizeof` вычисляется на этапе компиляции и даёт размер **в байтах**, причём по определению `sizeof(char) == 1` — байт в C это столько, сколько занимает `char`.

Что гарантирует стандарт:

| Тип | Минимум по стандарту | Обычно на x86-64 Linux |
|---|---|---|
| `char` | 1 байт (≥ 8 бит) | 1 |
| `short` | ≥ 16 бит | 2 |
| `int` | ≥ 16 бит | 4 |
| `long` | ≥ 32 бита | 8 (на Windows — 4) |
| `long long` | ≥ 64 бита | 8 |
| указатель | не оговорён | 8 |

Стандарт фиксирует **соотношения**: `char ≤ short ≤ int ≤ long ≤ long long`. Конкретика — дело реализации, и она различается: модель LP64 (Linux, macOS) даёт `long` = 8, модель LLP64 (Windows) — 4. Код, полагающийся на «`long` восьмибайтовый», ломается ровно при переносе.

Когда нужны точные размеры, есть `<stdint.h>`:

```c
#include <stdint.h>
uint32_t crc;      /* ровно 32 бита, везде */
int64_t  offset;   /* ровно 64 бита */
```

Правило: для разбора бинарных форматов и протоколов — только фиксированные типы. Для счётчиков и индексов — `int` и `size_t`.

Две ловушки `sizeof`:

```c
sizeof arr / sizeof arr[0]     /* число элементов — только пока arr виден массивом */
sizeof(int) * n                /* верно */
```

И самая коварная: `size_t` **беззнаковый**. Выражение `sizeof(a) - 1` при пустом массиве даст не −1, а огромное число, и цикл `for (size_t i = 0; i < n - 1; i++)` при `n == 0` уйдёт почти в бесконечность.

## 3. Массив непрерывен, и это гарантия

Стандарт требует, чтобы элементы массива лежали подряд без промежутков. Отсюда:

```c
(char *)&arr[i + 1] - (char *)&arr[i] == sizeof(arr[0])
```

Приведение к `char *` обязательно, потому что арифметика указателей работает **в элементах**: компилятор сам умножает смещение на размер типа. `&arr[1] - &arr[0]` — это 1 элемент, а не 4 байта. `char` с его единичным размером превращает масштабирование в тождество.

Отдельно: разность указателей имеет тип `ptrdiff_t` (из `<stddef.h>`), и вычитать можно только указатели **внутри одного массива**. Разность указателей на разные объекты — неопределённое поведение, даже если арифметически она вычислима.

## 4. Выравнивание

Компилятор размещает объекты по адресам, кратным их требованию выравнивания, и вставляет пропуски в структурах:

```c
struct { char c; int i; };     /* c в 0, пропуск 1..3, i в 4; sizeof == 8 */
```

Посмотреть на это можно точно, а не на глаз:

```c
#include <stddef.h>
printf("%zu %zu\n", offsetof(struct S, i), sizeof(struct S));
_Static_assert(sizeof(struct S) == 8, "неожиданная раскладка");
```

`_Static_assert` (C11) проверяет утверждение на этапе компиляции — удобно, когда раскладка важна.

Зачем выравнивание нужно: невыровненный доступ либо медленнее (процессор делает два обращения вместо одного), либо запрещён аппаратно — на части ARM-платформ это исключение. Плюс атомарные операции требуют выравнивания, иначе не работают вовсе.

## 5. ASLR: почему адреса пляшут

Запустите программу дважды — адреса будут разными. Это **ASLR** (address space layout randomization): ядро случайно сдвигает базовые адреса стека, кучи, библиотек и (для PIE-сборок) самого кода.

Смысл защиты: эксплойты обычно требуют знания конкретных адресов — куда прыгать, где лежит буфер. Случайная раскладка превращает надёжную атаку в лотерею.

Практические следствия:

- **адрес нельзя сохранять между запусками** и уж тем более записывать в файл;
- **адрес нельзя проверять в тесте** — сравнивать можно только соотношения;
- отладка со стабильными адресами делается отключением ASLR, а не изменением кода:

```bash
setarch $(uname -m) -R ./program     # Linux: запуск без рандомизации
```

Внутри одного запуска адреса, разумеется, стабильны — иначе указатели были бы бессмысленны.

## 6. Что где лежит

| Область | Что | Время жизни |
|---|---|---|
| код (`.text`) | инструкции | всё выполнение, только чтение |
| `.rodata` | строковые литералы, константы | всё выполнение, только чтение |
| `.data` / `.bss` | глобальные и `static` | всё выполнение |
| стек | локальные переменные, аргументы | до выхода из функции |
| куча | `malloc` | до `free` |

`.bss` — отдельный любопытный случай: там лежат глобальные переменные, инициализированные нулём, и в исполняемом файле они **не занимают места**, только запись «сколько обнулить при запуске». Массив на миллион `int` в глобальной области добавит к файлу несколько байт, а не четыре мегабайта.

Стек и куча растут навстречу друг другу. Куча, `malloc` и всё, что с ними связано, — начиная с s02e05.
