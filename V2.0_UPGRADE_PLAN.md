## 0. Резюме (TL;DR)

Курс имеет сильную концепцию (story-driven обучение C, диегетический ИИ-помощник LUNA, сквозные проекты) и качественно проработанные Сезоны 1–4. Но у него три системные проблемы, которые v2.0 должна устранить:

1. **Резкая неравномерность.** Сезоны 1–4 переразвиты (серии по 850–2952 строки README), Сезоны 7–10 — заглушки (50–360 строк). Обучение «проваливается» после S4.
2. **Переусложнённость первых сезонов.** Отдельная серия = 2–3 часа плотного текста, дублирующиеся блоки вопросов, теория и код смешаны в одном файле. Это противоречит исходной цели «набить руку на интересных задачах».
3. **Накопленный технический долг в сюжете и документации.** Есть сюжетная дыра (совпадение имён), противоречия в версиях и статусах, теоретические зависимости «вперёд» (тема используется до объяснения), LUNA обещана на весь курс, но живёт только в S1.

**Ядро v2.0:**

- Посезонная нумерация серий по схеме `sNNeNN` (S2 становится `s02e01…`, а не `05…`) — чтобы дробить серии и вставлять новые, не сбивая нумерацию.
- Нормализация объёма: единая «серия-часть» на ≈250–650 строк README, один основной концепт + одна задача, ~45–90 минут. Тяжёлые серии дробятся, тонкие — дописываются до стандарта.
- Полный проход по сюжету/теории/упражнениям: закрыть дыры, выровнять зависимости, добавить недостающие решения и тесты.
- Единый источник правды по статусу и версии (SemVer на уровне курса: **v2.0.0**).
- Меньше эмодзи, более литературный и ровный тон (прямой ответ на комментарии к статье и на исходную задумку про «литературность»).
- Обновление GitHub через ветку `v2.0-refactor` с аннотированными коммитами и релизом; новая статья на Хабр «v2.0» с учётом комментариев.

Оценка объёма работ до полноценной v2.0 — см. раздел 11.

## 1. Методология аудита и опорные практики

Аудит опирается на признанные рамки в двух дисциплинах, которые и определяют решения ниже.

**Педагогика.** Cognitive Load Theory (Sweller) — обоснование дробления серий и выноса кода из README (снижаем внешнюю нагрузку). Backward Design / Understanding by Design (Wiggins & McTighe) и Constructive Alignment (Biggs) — каждая серия проектируется от измеримого результата к задаче и теории. Retrieval Practice и Spaced Repetition (Roediger, Bjork, «desirable difficulties») — переносим контроль из «стены вопросов в конце» в короткие распределённые проверки. Worked-Example Effect с последующим «faded guidance» и Productive Failure (Kapur) — обоснование прогрессивной автономии к S9–S10. Bloom's taxonomy — уровни контрольных вопросов. Mastery Learning (проблема «2 сигма» Блума) — роль LUNA как персонального тьютора. Project-Based / Authentic Tasks — «интересные задачи, близкие к реальным».

**Сценаристика.** Модель «сериал»: сезон/серия, cold open, cliffhanger, «previously on» (рекап), A/B/C-линии, арки персонажей (want vs need), try–fail циклы, «ружьё Чехова», эскалация ставок. Story Circle (Dan Harmon) и бит-структура (Save the Cat) — для арок сезонов. Kishōtenketsu (4-актная структура без обязательного конфликта) — для «обучающих» серий, где драма не нужна, но нужен ритм. Ключевой стилевой ориентир из задумки автора: «чуть более литературно, но не бульварное чтиво», плавные переходы за счёт хорошего interleaving.

Источники, на которых курс уже заявлен (сохраняем и усиливаем): CS50 (Harvard), Head First C, K&R, TAOCP (Knuth), Financial Markets (Shiller, Yale).

## 3. Целевая концепция v2.0 (принципы)

Не меняем ДНК курса, а доводим его до заявленного. Ориентиры цели сохраняются дословно: студент выполняет задачи с помощью ИИ, набивает руку на **интересных, близких к реальным** задачах, параллельно изучая теорию — и по книгам, и внутри курса. Оболочка — **Cursor в режиме IDE**.

**Семь принципов v2.0:**

1. **Одна серия — один концепт — одна задача.** Атомарность вместо «глав». Это и упрощение, и предпосылка для дробления/вставок.
2. **70/30 practice-first.** Теория подаётся ровно в объёме, нужном для текущей задачи; глубина — ссылками на книги (K&R/CS50/Head First/TAOCP/Shiller) и на «advanced»-врезки.
3. **Interleaving как основа литературности.** История → концепт → короткая проверка «в мире сюжета» → задача → поворот. Плавные переходы вместо монолитных блоков.
4. **AI-native, но с барьерами.** LUNA/Cursor — сократический напарник: объясняет, ревьюит, задаёт наводящие вопросы; не «решает за тебя». Явные «green/red» паттерны промптов в каждой серии.
5. **Прогрессивная автономия.** Подсказок и эталонов всё меньше к финалу; в S9–S10 студент сам ставит подзадачи (faded guidance → productive failure).
6. **Кумулятивность через `#include`.** Каждый сезон переиспользует артефакты предыдущих; сквозные проекты — реальные библиотеки, а не разрозненные файлы.
7. **Сдержанный тон.** Минимум эмодзи, литературные связки, диаграммы вместо украшательства.

## 4. Перенумерация: схема `sNNeNN` + карта миграции

**Схема (выбрана автором):** каждая серия получает идентификатор `sNNeNN` — сезон и посезонный номер, глобально уникальный и одновременно посезонный. Директории переименовываются в `season-NN-*/sNNeNN-slug/`.

**Карта миграции (базовая, до дробления):**

| Сейчас | v2.0 | Сейчас | v2.0 |
|--------|------|--------|------|
| S1 ep01–04 | s01e01–s01e04 | S6 ep21–24 | s06e01–s06e04 |
| S2 ep05–08 | s02e01–s02e04 | S7 ep25–28 | s07e01–s07e04 |
| S3 ep09–12 | s03e01–s03e04 | S8 ep29–32 | s08e01–s08e04 |
| S4 ep13–16 | s04e01–s04e04 | S9 ep33–37 | s09e01–s09e05 |
| S5 ep17–20 | s05e01–s05e04 | S10 ep38–42 | s10e01–s10e05 |

**Почему это решает задачу автора:** когда серию S2 нужно разбить на 2–3 части, части получают номера `s02e01a/b` → нормализуются в `s02e01, s02e02, s02e03`, и это **не трогает** нумерацию S3+. Новые серии внутри сезона просто продолжают ряд.

**Правила дробления серии (когда бить на части):** делим, если README > ~700 строк, ИЛИ серия покрывает больше одного «крупного» концепта, ИЛИ оценка прохождения > ~90 минут. Каждая часть — самостоятельный `sNNeNN` со своим cold open и cliffhanger.

## 5. Упрощение: стандарт «лёгкой» серии

### 5.1. Единый шаблон серии v2.0 (цель ≤ ~600 строк README)

```
sNNeNN-slug/
├── README.md          # только: cold open → теория(1 концепт) → interleaved-проверки → задача → debrief/cliffhanger → ссылки
├── mission.md         # краткое ТЗ (что сдать, критерии приёмки)
├── starter.c          # каркас с TODO
├── theory.md          # (опц.) углубление и ссылки на книги — вынесено из README
├── solution/          # эталон (открывать после попытки)
├── tests/             # автотесты + данные
└── artifacts/         # сюда пишет студент; отсюда собирается Season Project
```

Структура README (беат-лист, ~6 блоков):

1. **Cold open** — 1 сюжетная сцена-крючок (5–15 строк), задаёт задачу серии.
2. **Теория, 1 концепт** — с одной сильной метафорой; длинный код и справочники — в `theory.md`/`solution/`, не в README.
3. **Проверка «в мире сюжета»** — 1–3 коротких вопроса от персонажа/LUNA (retrieval practice), а не «стена» в конце.
4. **Задача** — один артефакт, критерии приёмки в `mission.md`, автотест в `tests/`.
5. **Debrief + cliffhanger** — что узнали, что дальше (крючок в следующий `sNNeNN`).

### 5.2. Тактики снижения объёма (применить ко всем сериям S1–S4)

- **Убрать дублирующий контроль.** Оставить только распределённые короткие проверки; финальную «стену вопросов» либо удалить, либо свернуть в компактный `quiz.md` со spaced-repetition набором (5–8 пунктов).

**Ожидаемый эффект:** S1–S4 из ~29 000 строк в 16 «главах» → ~35–40 коротких серий по 400–600 строк; каждая проходится за один присест, а не за вечер.

## 9. GitHub workflow (ветка + аннотированные коммиты)

Выбор автора: изменения готовятся в отдельной ветке; автор ревьюит, финальный push и cutover — с вашего явного подтверждения (см. примечание о доступе ниже).

Предлагаемый порядок:

1. Ветка `v2.0-refactor` от `main`.
2. Коммиты — по действующему в репо стилю Conventional Commits, атомарно и аннотированно:
   - `docs: add V2.0 upgrade plan` (этот документ);
   - `refactor(numbering): migrate to sNNeNN scheme (git mv, fix links)`;
   - `refactor(sN): split heavy episodes into parts`;
   - `feat(sN): author episodes to v2.0 standard (solutions+tests)`;
   - `fix(story): resolve name collision, Marcus nationality`;
   - `docs: unify version scheme and STATUS single-source`.
3. Пул-реквест `v2.0-refactor → main` — как витрина для ревью полного diff (по чек-листу §12).
4. **Cutover на релизе (стратегия автора).** Заархивировать текущий `main`: тег `v0.3.5-archive` + ветка `archive/v0.3` (история сохраняется целиком). 5. Тег `v2.0.0` + GitHub Release: таблица соответствия старых/новых путей `sNNeNN`, краткое «что изменилось».
6. Обновить бейджи в README (версия/статус/язык) на реальные значения.

Доступ и права: ассистент выполняет git-операции (`git mv`, commit, при необходимости push) в терминале **по вашему явному разрешению**; финальный push в публичный `gfazzz/moonlight-course`, cutover `main` и смену default-ветки подтверждаете вы.
