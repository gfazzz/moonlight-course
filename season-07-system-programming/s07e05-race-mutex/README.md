## Теория: где теряются обновления

### Три операции вместо одной

```c
counter++;
```

разворачивается в

```
load  r1, [counter]     ; прочитать
add   r1, 1             ; прибавить
store [counter], r1     ; записать
```

Прерывание между первой и третьей строкой — и работа второго потока стёрта. Окно узкое, но при восьмистах тысячах повторений теряются сотни тысяч обновлений.

### Определение

Гонка — это когда два потока обращаются к **одной ячейке**, хотя бы один доступ на запись, и между ними нет отношения «происходит-раньше».

Все три условия обязательны. В прошлой серии первое не выполнялось: диапазоны не пересекались.

### Критическая секция

```c
pthread_mutex_lock(&lock);
long tmp = counter;
counter = tmp + 1;
pthread_mutex_unlock(&lock);
```

Мьютекс даёт **две** гарантии, и вторую обычно не замечают:

| Гарантия | Что означает |
|---|---|
| взаимное исключение | в секции не более одного потока |
| барьер памяти | записи до `unlock` видны тому, кто сделает `lock` |

Без второй даже строгая очерёдность не спасла бы: процессор и компилятор вправе держать значение в регистре или кэше, и следующий поток прочитал бы устаревшее.

### Что этим платят

| Проблема | Причина |
|---|---|
| падение скорости | захват и освобождение стоят тактов |
| вырождение в очередь | блокировка слишком крупная |
| вечная остановка | забытый `unlock` при раннем выходе |
| взаимная блокировка | два мьютекса захвачены в разном порядке |

Последняя лечится единственным способом: **глобальным порядком захвата**. Если все берут мьютексы в одном и том же порядке, цикл ожидания невозможен.

## Проверка: LUNA задаёт вопросы
```
[LUNA] Два вопроса про общую память.
```

**1.** LUNA: «В прошлой серии четыре потока писали в общий массив — и гонки не было. Почему теперь есть?»

<details><summary>Ответ</summary>

Потому что гонка требует доступа к **одной и той же ячейке**. В прошлой серии диапазоны `[lo, hi)` не пересекались: каждый индекс писал ровно один поток, и общим был массив как объект, но не его элементы. Здесь же все потоки пишут в одну переменную — условие выполнено, обновления теряются. Отсюда практический вывод: общий объект сам по себе не опасен, опасен общий **изменяемый элемент**.
</details>

**2.** LUNA: «Почему тест проверяет инварианты, а не конкретное число потерь?»

<details><summary>Ответ</summary>

Потому что число потерь зависит от планировщика и меняется при каждом запуске — сравнивать его бессмысленно. Устойчивы другие утверждения: незащищённый итог **не больше** ожидаемого (потерять обновление можно, лишнего не появится), а защищённый **в точности** равен ожидаемому. Оба свойства верны всегда. Плавающие числа выводятся в поток ошибок — для глаз, не для сравнения. Приём общий: недетерминированный код тестируется утверждениями, которые не зависят от того, что именно произошло в этом запуске.
</details>


## Разбор типичных ошибок

1. **Результат гонки печатается в стандартный поток.** Он плавающий — тест становится нестабильным.
2. **Забыт `unlock` при раннем выходе.** Остальные потоки встанут навсегда.
3. **`counter++` считается атомарным.** Это три операции; атомарность даёт `<stdatomic.h>`.
4. **Один мьютекс на всё подряд.** Параллелизм вырождается в очередь за общим замком.
5. **Мьютексы захватываются в разном порядке.** Классическая взаимная блокировка.
6. **Гонка «не воспроизвелась» — значит, её нет.** Она есть; просто окно не открылось в этом запуске.
