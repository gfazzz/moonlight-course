## Теория: параллельно и воспроизводимо

### Поток против процесса

| | Процесс (`fork`) | Поток (`pthread_create`) |
|---|---|---|
| адресное пространство | своё | **общее** |
| глобальные переменные | копия | **общие** |
| дескрипторы | копии | **общие** |
| стек | свой | свой |
| стоимость создания | выше | ниже |
| падение одного | остальные живы | **процесс умирает целиком** |

Последняя строка — цена, которую платят за общую память. Разыменование неверного указателя в одном потоке роняет все шестнадцать.

### Запуск и сбор

```c
pthread_create(&th[t], NULL, worker, &rng[t]);   /* каждому свой Range {lo, hi} */
...
pthread_join(th[t], NULL);
```

Функция потока имеет вид `void *(*)(void *)`: указатель на входе, указатель на выходе. Без `pthread_join` ресурсы потока не освобождаются — точный аналог зомби из s07e01.

Ловушка на этой строке одна и встречается почти всегда: передать всем потокам указатель на переменную цикла. К моменту запуска потока она уже изменилась. Нужен массив аргументов — по элементу на поток.

### Параллелизм без синхронизации

Каждый поток пишет **только** в свой полуинтервал `pnl_par[lo..hi)`. Диапазоны не пересекаются, значит одну и ту же ячейку никогда не трогают двое — блокировки не нужны вовсе.

Это лучший вид параллелизма и, к сожалению, редкий: задача должна разбиваться на независимые куски. Монте-Карло разбивается идеально, потому что траектории друг о друге не знают.

### Откуда берётся воспроизводимость

```c
seed = 12345 + path * 2654435761;   /* сид от НОМЕРА траектории, не общий генератор */
```

Общий генератор на все потоки даёт две беды сразу: гонку за его внутреннее состояние и зависимость результата от порядка обращений, то есть от планировщика.

Привязка сида к номеру траектории делает каждую траекторию самодостаточной. Кто её посчитает и когда — неважно; её поток случайных чисел определён её номером. Отсюда побитовое совпадение с последовательной версией.

### Чего так делать нельзя

Параллельно **суммировать** вещественные числа и ждать битового совпадения не выйдет: сложение с плавающей точкой не ассоциативно, и другой порядок даёт другие младшие биты.

Поэтому сравнивается массив траекторий, а не их сумма. Разница принципиальная: воспроизводим тот параллелизм, где переупорядочивание не меняет вычислений, а не тот, где оно «почти не меняет».

## Проверка на канале

```
[LUNA] Два вопроса, прежде чем ты запустишь потоки.
```

**1.** LUNA: «Почему нельзя дать всем потокам один общий генератор случайных чисел?»

<details><summary>Ответ</summary>

По двум причинам сразу. Первая: внутреннее состояние генератора — общая изменяемая переменная, а значит, гонка. Вторая, менее очевидная: даже если состояние защитить блокировкой, **порядок** обращений к генератору будет зависеть от планировщика, и каждая траектория получит разные числа при разных запусках. Результат станет невоспроизводимым, оставаясь при этом правдоподобным. Привязка сида к номеру траектории убирает обе проблемы: общего состояния нет, и порядок ни на что не влияет.
</details>

**2.** LUNA: «Мы пишем в общий массив из четырёх потоков. Почему это не гонка?»

<details><summary>Ответ</summary>

Потому что гонка — это конкурентный доступ к **одной и той же ячейке**, где хотя бы один доступ на запись. Здесь диапазоны `[lo, hi)` не пересекаются, и каждый индекс пишет ровно один поток. Общий у потоков массив как объект, но не его элементы. Синхронизация не нужна — и это не оптимизация, а следствие того, как задача разбита.
</details>

```
[LUNA] Верно. Запускай потоки.
```

## Разбор типичных ошибок

1. **Общий генератор на все потоки.** И гонка, и невоспроизводимость.
2. **Всем потокам передан `&i` из цикла.** Переменная изменится до старта потока.
3. **Забыт `pthread_join`.** Ресурсы не освободятся, а `main` может завершиться раньше работы.
4. **В выводе есть время выполнения.** Оно зависит от машины и загрузки.
5. **Диапазоны считаются с округлением вниз.** Последние траектории не попадут ни в один поток.
6. **Возврат `pthread_create` не проверен.** Потоки тоже могут не создаться.
