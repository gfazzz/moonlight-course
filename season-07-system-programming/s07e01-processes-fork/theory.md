# Теория — s07e01

## 1. Что такое процесс

> *— Программа — это текст. Процесс — это текст, которому дали память, права и время процессора. Убить программу нельзя, её можно только удалить. Убивают процессы.*

Процесс — выполняющаяся программа со своим адресным пространством, таблицей дескрипторов, идентификатором и набором прав. Ядро изолирует процессы друг от друга: залезть в чужую память напрямую невозможно.

Всё, что в Season 6 делалось с железом напрямую, здесь раздаётся процессам через системные вызовы. Разница принципиальная: там код был единственным хозяином машины, здесь он один из многих и обязан спрашивать.

Состав процесса, который придётся держать в голове весь сезон:

| Часть | Что содержит | При `fork()` | При `exec()` |
|---|---|---|---|
| код | машинные инструкции | копируется | **заменяется** |
| данные и куча | переменные, выделенная память | копируется | заменяется |
| стек | локальные переменные, кадры вызовов | копируется | заменяется |
| дескрипторы | открытые файлы, сокеты | копируются | **сохраняются** |
| идентификатор | номер процесса | новый | **сохраняется** |

Две выделенные ячейки — вся суть связки `fork` + `exec`, и обе понадобятся в следующих сериях.

## 2. Двойной возврат

```c
pid_t rc = fork();
/* здесь уже ДВА процесса, и оба продолжают с этой строки */
```

| Возврат | Кто это |
|---|---|
| `> 0` | родитель; значение — идентификатор потомка |
| `0` | потомок |
| `-1` | порождение не удалось |

Асимметрия возврата не случайна. Потомку идентификатор родителя не нужен — он берётся вызовом `getppid()`. Родителю идентификатор потомка нужен обязательно, иначе он не сможет его дождаться. Интерфейс отдаёт каждому ровно то, чего он сам получить не может.

Третий случай проверяют реже всего, а он возникает при исчерпании таблицы процессов или предела `RLIMIT_NPROC`. Цена пропуска высока: `-1` не равно нулю, значит, код пойдёт по ветке родителя и попытается дождаться несуществующего потомка.

## 3. Копирование при записи

Физически память при `fork()` не копируется. Страницы помечаются «только для чтения» и остаются общими; при первой попытке записи ядро перехватывает исключение, делает копию именно этой страницы и разрешает запись.

Отсюда три следствия:

**`fork()` дёшев.** Стоимость пропорциональна размеру таблиц страниц, а не объёму памяти. Порождение потомка у процесса на гигабайт занимает микросекунды.

**Раздельность реальна.** `x += 1` в потомке родителю не виден — при записи страница уже разошлась.

**Расход памяти отложен.** Процесс, порождающий потомка, может исчерпать память **позже** — когда потомок начнёт писать. Отсюда практика перевыделения памяти в Linux и связанный с ней механизм принудительного завершения при нехватке.

Исторически всё было иначе: ранние UNIX копировали адресное пространство целиком, и `fork` перед `exec` был чистым расточительством. Из этой боли выросли `vfork` и позже `posix_spawn` — оба стали ненужны, как только появилось копирование при записи.

## 4. Ловушка буфера

```c
printf("...");   /* ещё в буфере, наружу не вышло */
fflush(stdout);  /* обязательно до fork() */
fork();
```

`printf` пишет не в файл, а в буфер внутри памяти процесса. При `fork()` буфер копируется вместе со всей памятью, и невыведенный текст напечатают оба процесса.

Коварство в том, что **режим буферизации зависит от того, куда идёт вывод**:

| Назначение | Режим | Когда сбрасывается |
|---|---|---|
| терминал | построчный | на каждом переводе строки |
| файл или канал | полный | при заполнении буфера |
| `stderr` | без буферизации | немедленно |

На экране программа работает правильно, при перенаправлении в файл — задваивает строки. Ошибка находится не тогда, когда её сделали, а тогда, когда вывод впервые направили в файл. Тест этой серии читает вывод через канал именно поэтому.

По той же причине потомок завершается через `_exit()`: `exit()` сбросил бы унаследованный буфер и выполнил обработчики `atexit`, зарегистрированные родителем.

## 5. Ожидание, зомби, сироты

```c
int status;
waitpid(rc, &status, 0);
if (WIFEXITED(status))   code   = WEXITSTATUS(status);
if (WIFSIGNALED(status)) signum = WTERMSIG(status);
```

Когда потомок завершается, ядро освобождает его память, но сохраняет запись с кодом возврата — иначе родителю нечего будет забрать. Процесс в этом состоянии называется **зомби**.

Зомби не занимает ни памяти, ни процессора. Он занимает **строку в таблице процессов**, и таблица конечна. Долгоживущий сервер, порождающий обработчики и не вызывающий `wait`, отказывает не сразу, а через часы — характерная ошибка, которую не ловят ни тесты, ни код-ревью, только длительная работа.

Если родитель умирает раньше потомка, потомок становится **сиротой** и переходит к процессу с номером 1, который забирает статусы автоматически. Демоны в s07e03 используют это намеренно.

`status` — упакованное слово, а не число. В нём уложены код возврата, номер сигнала, признак дампа памяти и признак остановки. Прямое чтение даёт число, похожее на код возврата, умноженный на 256, — и такое сравнение иногда даже «работает», что делает ошибку живучей.

## 6. Инварианты вместо значений

Идентификаторы процессов назначает ядро, и при каждом запуске они разные. Проверять в тесте нужно то, что обязано совпадать:

| Проверяемое свойство | Почему устойчиво |
|---|---|
| `fork()` вернул `0` в потомке | определено стандартом |
| `getppid()` в потомке равен идентификатору родителя | следует из родства |
| `waitpid()` вернул того же потомка | следует из аргумента |
| код возврата равен `7` | задан программой |

Приём шире тестирования. Он же лежит в основе проверки инварианта свечи в s05e01 и проверки чётности в s06e04: сравнивают не значения, а свойства, которые не могут измениться.

## 7. Почему `-std=gnu11`

`fork`, `waitpid`, `getppid` — часть POSIX, а не ISO C. При строгом `-std=c11` их объявления скрыты, компиляция даёт предупреждение о неявном объявлении, и функция вызывается с неверным предположением о типе возврата.

Два законных выхода:

```c
#define _POSIX_C_SOURCE 200809L   /* до всех #include */
```

или `-std=gnu11` при компиляции. В сезоне используется второй; первый предпочтителен, когда важна переносимость на компиляторы без расширений.

Порядок в первом случае существенен: макрос должен быть определён **до** первого `#include`, иначе заголовки уже раскрылись в урезанном виде.
