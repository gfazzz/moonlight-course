## Теория: один процесс становится двумя

### Двойной возврат

```c
fflush(stdout);              /* иначе буфер скопируется и текст задвоится */
pid_t rc = fork();
if (rc == 0) {               /* потомок */
    _exit(7);
}
int status;
waitpid(rc, &status, 0);     /* родитель ждёт своего потомка */
int code = WEXITSTATUS(status);
```

После вызова исполняются **две** программы, различающиеся только возвращённым значением. Ноль — потомок, положительное число — родитель, минус единица — порождение не удалось.

Третий случай забывают проверять чаще всего, а он реален: у процессов есть предел, и в системе под нагрузкой `fork()` возвращает ошибку.

### Копирование при записи

Потомок получает **копию** памяти родителя. Физически копирования не происходит: страницы помечаются только для чтения и разделяются, а настоящая копия создаётся при первой попытке записи.

Следствие для программиста простое — `x += 1` в потомке родителю не виден. Следствие для системы: `fork()` дёшев ровно до тех пор, пока процессы не начинают писать.

### Ожидание и статус

```c
if (WIFEXITED(status))   code   = WEXITSTATUS(status);
if (WIFSIGNALED(status)) signum = WTERMSIG(status);
```

Переменная `status` — упакованное слово, а не число. Читать её напрямую нельзя: там уложены и код возврата, и номер сигнала, и признак остановки.

| Состояние | Что означает |
|---|---|
| **зомби** | потомок завершился, родитель не забрал статус |
| **сирота** | родитель умер раньше; потомка усыновляет процесс с номером 1 |

Зомби занимает не память, а запись в таблице процессов. Программа, порождающая потомков в цикле и не вызывающая `wait`, исчерпает таблицу — отказ наступит не сразу, а через часы работы.

### Почему потомок выходит через `_exit`

`exit()` выполняет обработчики, зарегистрированные через `atexit`, и сбрасывает буферы потоков вывода. Но потомок унаследовал и то и другое от родителя — значит, выполнит **чужие** обработчики и выведет **чужой** буфер.

`_exit()` завершает процесс немедленно, без этих действий. В потомке после неудавшегося `exec` это единственный правильный выход.

**1.** LUNA: «Почему `fflush(stdout)` обязателен именно **до** `fork()`?»

<details><summary>Ответ</summary>

Потому что `printf` не пишет сразу, а копит текст в буфере внутри памяти процесса. `fork()` копирует память вместе с буфером, и оба процесса потом выведут его содержимое — текст задвоится. Особенно заметно при перенаправлении вывода в файл: там буферизация становится полной, и накопиться успевает больше. `fflush` опустошает буфер до раздвоения, после чего копировать нечего.
</details>

**2.** LUNA: «Почему тест запрещает печатать сами идентификаторы процессов?»

<details><summary>Ответ</summary>

Потому что их назначает ядро, и при каждом запуске они разные — вывод перестал бы быть воспроизводимым. Проверять нужно **инварианты**: `fork()` вернул ноль в потомке, `getppid()` в потомке равен идентификатору родителя, `waitpid()` вернул того же потомка, которого породили. Эти свойства не меняются от запуска к запуску, а конкретные числа меняются всегда. Правило работает шире тестов: сравнивать имеет смысл то, что обязано совпадать.
</details>

## Разбор типичных ошибок

1. **Печатаются идентификаторы процессов.** Вывод перестаёт быть воспроизводимым — тест падает на втором прогоне.
2. **Забыт `fflush` перед `fork()`.** Строки задваиваются, особенно при перенаправлении.
3. **В потомке вызван `exit()`.** Сбросит унаследованные буферы и выполнит обработчики родителя. Нужен `_exit()`.
4. **`status` читается напрямую.** Это упакованное слово; только через `WIFEXITED` и `WEXITSTATUS`.
5. **Возврат `-1` не проверен.** Порождение процесса может не удаться, и тогда «потомок» продолжит выполняться как родитель.
6. **Вызван `wait()` вместо `waitpid()`.** Заберёт статус любого потомка, а не того, которого ждали.

## Debriefing

Программа отработала. Ты породил процесс, дождался его и снял код возврата — те же четыре системных вызова, которыми пользуется `surveillance_d`.

```
[parent] потомок завершился нормально:  да
[parent] код возврата потомка:          7
[parent] потомок менял x, у родителя x = 100 (память раздельна)
```

Последняя строка важнее остальных. Потомок изменил переменную, и родитель этого не заметил. Два процесса с общей историей и раздельной памятью — ровно то, что делает `fork()` полезным и опасным одновременно.

Ты возвращаешься к дереву противника.

```
  surveillance_d
   ├─ tracker
   ├─ tracker
   └─ tracker
```

И замечаешь несоответствие. Все три потомка называются `tracker`. Но `fork()` делает **копию родителя**, а родитель называется иначе.

```
[LUNA] Верно. Копию fork() и делает — только копия им не нужна, нужна другая программа.

[LUNA] Вызов называется exec. Идентификатор процесса при этом сохраняется —
[LUNA] снаружи выглядит так, будто процесс просто стал кем-то другим.
```
