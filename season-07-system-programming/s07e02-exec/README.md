## Теория: `fork` даёт процесс, `exec` даёт программу

### Связка

```c
pid_t pid = fork();
if (pid == 0) {
    execv(path, argv);
    _exit(127);            /* достижимо ТОЛЬКО если exec провалился */
}
waitpid(pid, &status, 0);
```

Разделение обязанностей выглядит избыточным — почему не один вызов «запусти программу»? — но оно даёт то, ради чего UNIX и устроен так.

**Между `fork` и `exec` потомок уже существует и ещё не заменён.** В этом промежутке он может перенастроить себя: перенаправить вывод, сменить каталог, понизить права, закрыть лишние дескрипторы. Всё это делается обычным кодом, а не флагами гипотетического «запусти-с-параметрами».

Именно так работает перенаправление в оболочке. `ls > out.txt` — это `fork`, затем открытие файла и подмена дескриптора, и только потом `exec`. Сама программа `ls` о перенаправлении не знает ничего.

### Что заменяется, а что нет

| Сохраняется | Заменяется |
|---|---|
| номер процесса и родителя | код программы |
| открытые дескрипторы | данные и куча |
| текущий каталог | стек |
| права и владелец | обработчики сигналов сбрасываются |

Первая строка правого столбца объясняет невозвратность: возвращаться некуда, старого кода в памяти уже нет.

Первая строка левого столбца объясняет, почему это удобно: снаружи процесс тот же самый, а изнутри — другая программа.

### Семейство

| Функция | Аргументы | Поиск по `PATH` | Окружение |
|---|---|---|---|
| `execl` | списком | нет | наследуется |
| `execv` | массивом | нет | наследуется |
| `execlp` / `execvp` | списком / массивом | **да** | наследуется |
| `execve` | массивом | нет | **задаётся** |

Все, кроме последней, — обёртки над `execve`, единственным настоящим системным вызовом. Буква `p` означает поиск по `PATH` и заслуживает осторожности: программа с поиском по `PATH` запустит то, что найдёт первым, а порядок каталогов задаёт окружение.

### Коды возврата

| Код | Смысл по соглашению |
|---|---|
| `0` | успех |
| `1`–`125` | ошибка, определённая программой |
| `126` | файл найден, но не исполняемый |
| `127` | команда не найдена |
| `128 + N` | процесс убит сигналом `N` |

Соглашение, а не стандарт языка: его соблюдают оболочки и утилиты, и потому на него можно опираться.

## Проверка: LUNA задаёт вопросы
```
[LUNA] Два вопроса про подмену образа.
```

**1.** LUNA: «Что случится, если после `execv` в потомке забыть `_exit()`?»

<details><summary>Ответ</summary>

При успешном `exec` — ничего: до этой строки уже не дойдут. Но при **провале** потомок продолжит выполнять код родителя дальше по функции. Получатся два процесса, делающих одну и ту же работу: двойной вывод, двойные запросы, двойная запись в файл. Ошибка особенно неприятна тем, что проявляется только в аварийной ветке — там, где тестируют реже всего. Поэтому строка после `exec` — это всегда обработка ошибки, завершающаяся `_exit()`.
</details>

**2.** LUNA: «Программа завершилась с кодом 127. Что это значит?»

<details><summary>Ответ</summary>

По соглашению оболочки — команда не найдена; в нашей задаче это код, с которым потомок выходит после провала `exec`. Рядом стоят `126` — файл существует, но не является исполняемым, и `128 + N` — процесс убит сигналом с номером `N`. Отсюда знакомое `130` при нажатии Ctrl-C: `128 + 2`, где двойка — номер сигнала прерывания.
</details>

```
[LUNA] Верно. Запускай.
```

## Разбор типичных ошибок

1. **Нет `_exit()` после `exec`.** При провале потомок проваливается в логику родителя.
2. **Массив аргументов не завершён `NULL`.** Поведение не определено; чаще всего — мусор в аргументах.
3. **Первый элемент `argv` не задан.** По соглашению это имя программы, и многие утилиты на него смотрят.
4. **Провал `exec` считается крахом.** Это обычная ошибка с `errno`; процесс продолжает работу.
5. **`status` читается напрямую.** Только через `WIFEXITED`, `WEXITSTATUS`, `WTERMSIG`.
6. **Используется вариант с поиском по `PATH` там, где путь известен.** Лишняя зависимость от окружения.
