# Теория — s07e02

## 1. Почему запуск программы разделён на два вызова

> *— Все спрашивают, почему нельзя одним вызовом. А потом хотят перенаправить вывод, сменить каталог, сбросить права и закрыть лишние дескрипторы — и оказывается, что промежуток между двумя вызовами и есть то место, где это делается.*

`fork()` создаёт процесс. `exec()` не создаёт ничего — он заменяет содержимое текущего процесса новой программой. Разделение выглядит избыточным ровно до первой нетривиальной задачи.

**Между вызовами потомок уже существует и ещё не заменён.** В этом промежутке он выполняет обычный код и настраивает себя как угодно:

```c
if (fork() == 0) {
    int fd = open("out.txt", O_WRONLY | O_CREAT | O_TRUNC, 0644);
    dup2(fd, STDOUT_FILENO);      /* перенаправление */
    chdir("/tmp");                /* смена каталога   */
    setgid(gid); setuid(uid);     /* понижение прав   */
    execv(path, argv);
    _exit(127);
}
```

Так работает `ls > out.txt` в оболочке, и сама программа `ls` о перенаправлении не знает ничего. Альтернатива — единый вызов с флагами на каждый мыслимый случай; именно этим путём пошли системы с `CreateProcess`, и список параметров там соответствующий.

## 2. Что сохраняется, а что заменяется

| Сохраняется | Заменяется |
|---|---|
| номер процесса и родителя | код программы |
| открытые дескрипторы | сегмент данных и куча |
| текущий и корневой каталог | стек |
| маска сигналов | обработчики сигналов → умолчания |
| идентификаторы пользователя и группы | таблица отображённой памяти |
| ограничения ресурсов | |

Наследование дескрипторов — основа каналов из s07e06: родитель создаёт канал, потомок наследует его конец и получает связь с родителем, ничего об этом не зная.

Сброс обработчиков сигналов логичен: обработчик — это адрес функции в коде, которого больше нет. Но **маска** блокировки сигналов сохраняется, и это регулярный источник неприятностей: программа, запущенная с заблокированным сигналом, унаследует блокировку и не сможет объяснить, почему не реагирует.

Дескрипторы можно исключить из наследования флагом `FD_CLOEXEC` — и в новом коде это разумное умолчание. Утечка дескриптора в запущенную программу означает, что она держит открытым файл или сокет, о котором не знает.

## 3. Невозвратность

```c
execv(path, argv);
/* сюда попали -> exec ПРОВАЛИЛСЯ */
perror("execv");
_exit(127);
```

При успехе возвращаться некуда: адрес возврата лежал на старом стеке, которого больше нет.

Отсюда правило: **всякий код после `exec` — обработчик ошибки**. Забытый `_exit()` в нём даёт ошибку, которая проявляется только в аварийной ветке: при провале запуска потомок продолжит выполнять код родителя, и два процесса начнут делать одну работу.

Диагностируется тяжело — в норме всё правильно, а ломается ровно тогда, когда что-то уже сломалось.

## 4. Семейство

| Функция | Аргументы | Поиск по `PATH` | Окружение |
|---|---|---|---|
| `execl` | списком | нет | наследуется |
| `execlp` | списком | **да** | наследуется |
| `execle` | списком | нет | **задаётся** |
| `execv` | массивом | нет | наследуется |
| `execvp` | массивом | **да** | наследуется |
| `execve` | массивом | нет | **задаётся** |

Суффиксы читаются буквально: `l` — список, `v` — вектор, `p` — поиск по `PATH`, `e` — своё окружение. Настоящий системный вызов один — `execve`; остальные пять реализованы поверх него в библиотеке.

**Про поиск по `PATH`.** Он берёт первое совпадение в списке каталогов, а список задаётся окружением. Программа, запускающая `execvp("tracker", ...)`, выполнит то, что противник положил в начало `PATH`. Для привилегированного кода это прямой путь к повышению прав, и потому правило простое: там, где путь известен, используется вариант без `p`.

**Про `argv[0]`.** По соглашению это имя программы. Соглашение не пустое: `busybox` по нему выбирает, какой утилитой притвориться, а оболочка по ведущему дефису понимает, что она стартовая. Массив обязан завершаться `NULL` — без него `exec` читает за границу.

## 5. Коды возврата

```c
if (WIFEXITED(status))   code = WEXITSTATUS(status);
if (WIFSIGNALED(status)) code = 128 + WTERMSIG(status);
```

| Код | Смысл |
|---|---|
| `0` | успех |
| `1`–`125` | ошибка, определённая программой |
| `126` | файл найден, но не исполняемый |
| `127` | команда не найдена |
| `128 + N` | завершён сигналом `N` |
| `130` | `128 + 2` — прерывание с клавиатуры |
| `137` | `128 + 9` — принудительное завершение |

Это соглашение оболочек, а не требование стандарта. Практическая ценность в том, что коды `126` и `127` различают две разные беды: «не нашли что запускать» и «нашли, но запустить не смогли». Первое — опечатка в пути, второе — права или неверный формат.

Ограничение, о котором стоит помнить: код возврата — восемь бит. Возвращать из программы `exit(256)` бессмысленно — придёт ноль.

## 6. Провал `exec` — обычная ошибка

Возврат `-1` и `errno`:

| Значение | Причина |
|---|---|
| `ENOENT` | нет такого файла |
| `EACCES` | нет прав на выполнение |
| `ENOEXEC` | формат не распознан |
| `E2BIG` | слишком длинный список аргументов |
| `ELOOP` | циклическая символическая ссылка |

Процесс при этом продолжает жить — можно обработать ошибку, попробовать другой путь, сообщить осмысленно.

Строка `E2BIG` объясняет знакомое `Argument list too long`: суммарный размер аргументов и окружения ограничен, и именно поэтому существует утилита `xargs`, разбивающая список на порции.

## 7. Оболочка как инструмент и как риск

`/bin/sh -c "..."` удобен: одна строка даёт перенаправления, конвейеры, подстановки, `exit N`.

Цена — строку интерпретирует оболочка. Подстановка непроверенных данных в неё называется инъекцией команд и остаётся одной из самых частых уязвимостей: имя файла `; rm -rf /` в аргументе делает ровно то, что написано.

Правило: если возможности оболочки не нужны, программа вызывается напрямую через `execv`, без интерпретатора посередине. Аргументы тогда передаются массивом, и никакая строка не разбирается — разделение на слова уже произошло в коде.

Тот же принцип, что разделение кода и данных в s09e02 и параметризованные запросы к базам: **данные не должны попадать туда, где их прочитают как команды**.
