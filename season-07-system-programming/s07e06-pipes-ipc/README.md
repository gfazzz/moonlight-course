## Теория: буфер в ядре

### Устройство

```c
int fd[2];
pipe(fd);      /* fd[0] — читать, fd[1] — писать */
```

Канал однонаправлен: у него один пишущий конец и один читающий. Для диалога нужны **два** канала — в задаче они называются «вниз» и «вверх».

После `fork()` таблица дескрипторов копируется, и оба конца оказываются у обоих процессов. Дальше каждый закрывает лишнее.

```
до fork():        родитель [r][w]
после fork():     родитель [r][w]     потомок [r][w]
после закрытия:   родитель [ ][w]     потомок [r][ ]
```

Отсюда ограничение: канал соединяет **родственные** процессы, потому что дескриптор передаётся только по наследству. Для неродственных существует именованный канал — тот же механизм с именем в файловой системе.

### Правило концов

| Ситуация | Что происходит |
|---|---|
| закрыты все пишущие концы | `read()` возвращает 0 — конец потока |
| остался живой писатель | `read()` ждёт новых данных |
| закрыты все читающие концы | `write()` даёт сигнал разрыва или ошибку |
| буфер полон | `write()` блокируется |
| буфер пуст, писатели живы | `read()` блокируется |

Вторая строка — источник почти всех зависаний с каналами. Симптом: программа стоит на `read()` без единого сообщения об ошибке.

Третья объясняет, почему `yes | head -5` завершается, а не крутится вечно: `head` прочитал пять строк и закрылся, `yes` получил сигнал разрыва.

### Конвейер

```c
dup2(pfd[1], STDOUT_FILENO);   /* левая часть пишет в канал   */
dup2(pfd[0], STDIN_FILENO);    /* правая часть читает из него */
```

`dup2(old, new)` делает `new` копией `old`, предварительно закрыв прежний `new`.

Работает это потому, что дескрипторы переживают `exec` — свойство из s07e02. Запущенная программа не знает, что её ввод и вывод перенаправлены, и знать не должна: она читает стандартный ввод и пишет в стандартный вывод, а соединяет их тот, кто её запустил.

Это и есть та самая философия, ради которой всё затевалось. Программа делает одно дело и не знает, откуда пришли данные и куда уйдут.

### Чтение — потоковое

`read()` может вернуть **меньше**, чем запрошено. Это не ошибка, а норма потокового интерфейса: границ сообщений в канале нет.

Надёжный код читает в цикле, пока не наберёт нужное или не получит ноль. Ошибка «прочитал один раз и решил, что всё» проявляется только на больших объёмах или на медленном писателе.

## Проверка на канале

```
[LUNA] Два вопроса, прежде чем ты свяжешь процессы.
```

**1.** LUNA: «Читатель повис на `read()`, хотя писатель давно всё отправил. Что не так?»

<details><summary>Ответ</summary>

Кто-то не закрыл пишущий конец — чаще всего сам читатель, унаследовавший его при `fork()`. Конец потока наступает, только когда закрыты **все** пишущие дескрипторы канала; пока жив хоть один, `read()` добросовестно ждёт новых данных. Ошибка тем неприятнее, что не даёт никакой диагностики: нет ни сообщения, ни ошибки, программа просто стоит. Правило простое — сразу после `fork()` каждая сторона закрывает то, чем не пользуется.
</details>

**2.** LUNA: «Почему для диалога нужны два канала, а не один?»

<details><summary>Ответ</summary>

Потому что канал однонаправлен: у него один пишущий конец и один читающий. Если оба процесса будут писать в один канал и из него же читать, каждый прочитает собственное сообщение — данные не разойдутся по адресатам. Для диалога нужны два канала, по одному на направление, либо сокет домена UNIX, который двусторонний по устройству и вдобавок сохраняет границы сообщений.
</details>

```
[LUNA] Верно. Связывай.
```

## Разбор типичных ошибок

1. **Не закрыт неиспользуемый конец.** Программа висит на `read()` без видимой причины.
2. **Один канал для диалога.** Процессы читают собственные сообщения.
3. **`read` вызван один раз.** Он может вернуть меньше запрошенного; нужен цикл.
4. **Родитель не закрыл оба конца конвейера.** Правая часть не дождётся конца потока.
5. **Сигнал разрыва не обработан.** Запись в канал без читателей убивает процесс по умолчанию.
6. **Дескрипторы не закрыты после `dup2`.** Лишние копии удерживают канал открытым.
