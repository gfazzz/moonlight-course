# Теория — s07e06

## 1. Почему процессам нужен посредник

> *— Указатель — это адрес в твоей карте города. Отдать его соседу, у которого своя карта, бессмысленно: он придёт не туда. Между процессами передают не адреса, а содержимое.*

У процессов раздельные адресные пространства, и это доказывалось в первой серии сезона: изменение переменной в потомке родителю не видно. Следствие — обмен идёт **через ядро**.

```c
int fd[2];
pipe(fd);      /* fd[0] — читающий конец, fd[1] — пишущий */
```

Канал — это буфер в памяти ядра с двумя дескрипторами. Однонаправленный: для диалога нужны два.

Механизм появился в 1973 году. Дуглас Макилрой продвигал идею несколько лет, пока Кен Томпсон за одну ночь не реализовал её вместе с синтаксисом оболочки. Наутро набор разрозненных утилит превратился в систему, из которой можно собирать.

## 2. Почему это работает после `fork()`

`fork()` копирует таблицу дескрипторов, и оба конца оказываются у обоих процессов:

```
до fork():        родитель [r][w]
после fork():     родитель [r][w]     потомок [r][w]
после закрытия:   родитель [ ][w]     потомок [r][ ]
```

Отсюда ограничение: обычный канал соединяет только **родственные** процессы, потому что дескриптор передаётся по наследству.

Для неродственных существует **именованный канал** — тот же механизм, но с именем в файловой системе:

```bash
mkfifo /tmp/ch
```

Файл при этом создаётся особого типа и данных не хранит: он служит только точкой встречи. Открытие на чтение блокируется, пока кто-нибудь не откроет на запись, и наоборот.

## 3. Правило концов

| Ситуация | Что происходит |
|---|---|
| закрыты все пишущие концы | `read()` возвращает 0 |
| остался хоть один писатель | `read()` ждёт |
| закрыты все читающие концы | `write()` даёт `SIGPIPE` или `EPIPE` |
| буфер полон | `write()` блокируется |
| буфер пуст, писатели живы | `read()` блокируется |

Вторая строка — источник почти всех зависаний. Причём чаще всего лишний пишущий конец держит **сам читатель**, унаследовавший его при `fork()` и забывший закрыть. Диагностика отсутствует полностью: программа просто стоит.

Третья строка объясняет знакомое поведение:

```bash
yes | head -5
```

`head` печатает пять строк и закрывается. Следующая запись `yes` попадает в канал без читателей, приходит сигнал разрыва, процесс завершается. Без этого механизма конвейер с бесконечным источником крутился бы вечно.

Сигнал по умолчанию убивает процесс. Программа, которая хочет обработать ситуацию сама, игнорирует его и разбирает ошибку `EPIPE` — так поступают все сетевые серверы, для которых обрыв соединения клиентом является нормой, а не аварией.

## 4. Конвейер своими руками

```c
dup2(pfd[1], STDOUT_FILENO);   /* левая часть  */
dup2(pfd[0], STDIN_FILENO);    /* правая часть */
```

`dup2(old, new)` делает `new` копией `old`, предварительно закрыв прежний `new`. Отличие от `dup` в том, что номер задаётся явно, — а именно это и нужно: перенаправить требуется конкретный дескриптор 0 или 1.

Работает приём потому, что **дескрипторы переживают `exec`**. Запущенная программа не знает, что её ввод и вывод перенаправлены, и не должна знать.

Здесь и лежит то, ради чего всё затевалось. Программа делает одно дело, читает стандартный ввод, пишет в стандартный вывод; откуда пришли данные и куда уйдут — забота того, кто её запустил. Пятьдесят лет спустя это по-прежнему самая работоспособная модель композиции в системном софте.

Обязанность родителя после запуска обеих сторон — закрыть **оба** конца. Иначе правая часть не дождётся конца потока.

## 5. Атомарность и размер

Буфер канала в Linux по умолчанию 64 килобайта; размер можно изменить через `fcntl` с `F_SETPIPE_SZ`.

Записи размером до `PIPE_BUF` (не менее 512 байт по стандарту, 4096 в Linux) **атомарны**: сообщения от разных писателей не перемешаются. Более крупные могут переплестись.

Практическое следствие для схемы «много писателей, один читатель»: пока сообщения укладываются в `PIPE_BUF`, никакой синхронизации не нужно. Как только перестают — нужен либо протокол с длиной в заголовке, либо отдельный канал на писателя.

**Границ сообщений в канале нет.** Это байтовый поток: два вызова `write` по 10 байт читатель может получить одним `read` на 20 или тремя по 7. Отсюда правило — читать в цикле:

```c
size_t got = 0;
while (got < need) {
    ssize_t n = read(fd, buf + got, need - got);
    if (n <= 0) break;
    got += (size_t)n;
}
```

Ошибка «прочитал один раз и решил, что всё» на локальных тестах не проявляется — данные помещаются в буфер целиком и приходят разом. Проявляется на объёме или на медленном писателе, то есть в работе.

## 6. Семейство механизмов

| Механизм | Направление | Границы сообщений | Родство |
|---|---|---|---|
| канал | одностороннее | нет | обязательно |
| именованный канал | одностороннее | нет | не нужно |
| сокет домена UNIX | двустороннее | опционально | не нужно |
| очередь сообщений | одностороннее | **да** | не нужно |
| разделяемая память | — | — | не нужно |
| сигнал | одностороннее | уведомление без данных | не нужно |

Сокет домена UNIX сегодня — умолчание для нового кода: он двусторонний, работает между неродственными процессами, умеет режим сохранения границ сообщений и вдобавок способен передавать **сами дескрипторы** между процессами.

Разделяемая память стоит особняком: она не передаёт данные, а делает их общими. Скорость максимальна, синхронизация полностью на программисте — следующая серия.
