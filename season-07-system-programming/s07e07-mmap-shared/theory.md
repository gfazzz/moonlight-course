# Теория — s07e07

> **Место в курсе.** `mmap` упоминался в Season 2 при разговоре об адресном пространстве, детально разбирается здесь и понадобится в Season 8 — для работы с большими наборами данных без чтения их целиком в кучу.

## 1. Что делает `mmap`

> *— Обычное чтение файла — это «дай мне копию». Отображение — это «положи его в мою карту адресов и разбуди меня, когда я туда посмотрю». Второе звучит сложнее, а работает проще.*

```c
void *p = mmap(NULL, len, PROT_READ | PROT_WRITE,
               MAP_SHARED | MAP_ANONYMOUS, -1, 0);
if (p == MAP_FAILED) { /* именно MAP_FAILED, не NULL */ }
...
munmap(p, len);
```

Вызов добавляет область в адресное пространство процесса. Физической памяти при этом может не выделяться вовсе: страницы подгружаются по первому обращению.

Два вида отображений:

| Вид | Что отображается | Применение |
|---|---|---|
| **файловое** | содержимое файла | чтение и запись без `read`/`write` |
| **анонимное** | чистая память | крупные блоки, обмен между процессами |

Анонимное отображение — то, чем внутри пользуется `malloc` для больших запросов: выделять гигабайт через приращение кучи неудобно, а отобразить и потом вернуть системе — легко.

## 2. Общее против приватного

Ключевая развилка:

| | `MAP_SHARED` | `MAP_PRIVATE` |
|---|---|---|
| после `fork()` | одна физическая память | копирование при записи |
| запись видна другому процессу | **да, мгновенно** | нет |
| для файла | изменения идут на диск | остаются в памяти |
| расход памяти | одна копия | по копии на пишущего |

Правый столбец описывает механизм, на котором построена вся система. `fork()` — это приватное отображение всей памяти родителя. Запуск программы — приватное отображение её файла: десять одновременно работающих экземпляров делят один физический экземпляр кода.

Отсюда неочевидное следствие: **страницы кода в памяти общие, пока никто в них не пишет**. Отладчик, ставящий точку останова, вызывает копирование страницы — и отлаживаемый экземпляр перестаёт делить код с остальными.

## 3. Почему это быстрее канала

| | Канал | Общая память |
|---|---|---|
| копирований на передачу | два | **ноль** |
| системных вызовов на передачу | два | ноль после настройки |
| синхронизация | встроенная | **полностью на программисте** |
| границы сообщений | нет | нет |
| обнаружение конца | `read` вернёт 0 | нужен свой протокол |

Первые две строки объясняют выигрыш, две последние — цену.

Канал даёт последовательный поток с внятным концом; общая память не даёт ничего, кроме адреса. Читатель не знает, дописал ли писатель, писатель не знает, прочитал ли читатель, и всё это приходится строить самому.

Практическое правило: **команды — каналом, данные — общей памятью**. Так устроены и системы, где это сделано хорошо: небольшое управляющее сообщение по каналу или сокету сообщает, что в общем сегменте появилось новое.

## 4. Мьютекс между процессами

Два условия, оба обязательны.

**Первое — расположение.** Мьютекс должен физически лежать в общем отображении:

```c
typedef struct {
    pthread_mutex_t lock;
    long counter;
    char msg[64];
} Shared;
```

Мьютекс в глобальной переменной после `fork()` попадёт в приватную копию, и каждый процесс будет запирать свой собственный. Симптомов нет: код исполняется, блокировки берутся и отпускаются, защиты не существует.

**Второе — атрибут.**

```c
pthread_mutexattr_t attr;
pthread_mutexattr_init(&attr);
pthread_mutexattr_setpshared(&attr, PTHREAD_PROCESS_SHARED);
pthread_mutex_init(&sh->lock, &attr);
pthread_mutexattr_destroy(&attr);
```

Без него поведение не определено. На части систем реализация окажется совместимой случайно, на других процесс встанет намертво — и это худший вариант сочетания «иногда работает» с «невозможно воспроизвести».

**Отдельная проблема — смерть владельца.** Если процесс умер, держа блокировку, остальные будут ждать вечно. Решение — устойчивые мьютексы (`PTHREAD_MUTEX_ROBUST`): следующий захватывающий получает особый код возврата, означающий «предыдущий владелец умер, состояние может быть несогласованным», и обязан восстановить инварианты.

Механизм громоздкий, но для долгоживущих служб с общей памятью — единственный корректный.

Альтернативы мьютексу: семафоры POSIX с признаком разделяемости, файловые блокировки, атомарные операции C11 прямо в общей памяти.

## 5. Соседние механизмы

| Механизм | Между неродственными | Особенность |
|---|---|---|
| `mmap` анонимный | нет | простейший случай, наследуется через `fork` |
| `shm_open` + `mmap` | **да** | сегмент с именем в `/dev/shm` |
| System V `shmget` | да | старый интерфейс, встречается в наследуемом коде |
| файловое отображение | да | заодно сохранность на диске |

Именованная разделяемая память POSIX — то, чем пользуются сегодня: сегмент создаётся с именем, любой процесс с правами может его открыть и отобразить. Живёт до перезагрузки или явного удаления, что требует аккуратности с уборкой.

## 6. Подводные камни

**Округление до страницы.** Отображение всегда кратно размеру страницы, обычно 4096 байт. `mmap` на один байт займёт страницу целиком.

**Ошибка — `MAP_FAILED`.** Это `(void *)-1`, а не `NULL`. Сравнение с нулём пропустит ошибку и даст падение при первом обращении.

**Наследование.** Отображение переживает `fork()`, но не `exec` — новый образ получает своё адресное пространство. Передать отображение запущенной программе можно только через именованный сегмент или наследуемый дескриптор.

**Запись файла не мгновенна.** Изменения в файловом отображении попадают на диск по решению ядра; для гарантии есть `msync()`. Программа, рассчитывающая на сохранность после падения, обязана его вызывать.

**Расход адресного пространства.** На 32-битной системе отобразить большой файл целиком не выйдет — адресов не хватит. На 64-битной это перестало быть проблемой, но привычка отображать окнами осталась и полезна.
