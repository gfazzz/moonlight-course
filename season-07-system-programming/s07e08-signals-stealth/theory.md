# Теория — s07e08

## 1. Что такое сигнал

> *— Сигнал — это стук в дверь, а не письмо. Он сообщает, что что-то случилось, но не говорит что именно и не оставляет содержимого. Всё, что у тебя есть, — номер и факт, что стучали.*

Сигнал — асинхронное уведомление процессу. Источников два: ядро (обращение по неверному адресу, запись в закрытый канал, деление на ноль) и другой процесс через `kill(pid, sig)`.

Ключевое свойство — это **уведомление, а не передача данных**. У сигнала нет полезной нагрузки, кроме номера. Нельзя «прислать сигналом» строку или число; можно лишь сообщить, что произошло событие заранее условленного типа.

| Сигнал | Номер | Смысл |
|---|---|---|
| `SIGHUP` | 1 | закрытие терминала; у демонов — перечитать настройки |
| `SIGINT` | 2 | прерывание с клавиатуры (Ctrl-C) |
| `SIGKILL` | 9 | немедленное завершение, не перехватывается |
| `SIGSEGV` | 11 | обращение по неверному адресу |
| `SIGPIPE` | 13 | запись в канал без читателей |
| `SIGTERM` | 15 | просьба завершиться (по умолчанию у `kill`) |
| `SIGCHLD` | 17 | потомок завершился |
| `SIGSTOP` | 19 | приостановка, не перехватывается |
| `SIGUSR1`, `SIGUSR2` | 10, 12 | свободны для своих нужд |

Строка `SIGHUP` объясняет живучую традицию: у демонов этот сигнал давно означает «перечитай конфигурацию». Терминала у демона нет, а значит, и повода получить настоящий `SIGHUP` — сигнал освободился и был переиспользован.

## 2. Граница, которую не перейти

`SIGKILL` и `SIGSTOP` невозможно перехватить, заблокировать или проигнорировать. Это гарантия ядра, и она намеренна: у администратора всегда должен оставаться способ остановить процесс, что бы тот о себе ни думал.

Отсюда разделение ролей:

| | `SIGTERM` | `SIGKILL` |
|---|---|---|
| можно перехватить | да | нет |
| даёт прибраться | да | нет |
| судьба данных | сохранены | потеряны |
| судьба блокировок | сняты | зависли |
| роль | просьба | приказ |

Проектирование чистого завершения происходит целиком на стороне `SIGTERM`. К `SIGKILL` подготовиться нельзя по определению — можно лишь сделать так, чтобы даже внезапная смерть не разрушала данные, но это уже задача журналирования и атомарной записи, а не обработки сигналов.

Практика супервизоров прямо следует из таблицы: послать `SIGTERM`, подождать отведённое время, при отсутствии реакции — `SIGKILL`. Значение таймаута — компромисс между «дать корректно завершиться» и «не висеть вечно из-за зависшего процесса».

## 3. Главное правило обработчика

Обработчик прерывает программу в **произвольной** точке. В том числе — посреди `malloc`, `printf`, `free`, когда их внутренние структуры временно несогласованны.

Вызов той же функции из обработчика означает повторный вход в код, который к нему не готов. Результат — взаимоблокировка на её собственном замке или порча кучи.

Разрешён только узкий список функций, безопасных в контексте сигнала: `write`, `_exit`, `kill`, `sigaction` и немногие другие. Полный перечень — в `man 7 signal-safety`.

Практическое правило снимает проблему целиком:

```c
static volatile sig_atomic_t got_term = 0;
static void handler(int s) { (void)s; got_term = 1; }
```

| Элемент | Что гарантирует |
|---|---|
| `volatile` | значение перечитывается из памяти, а не берётся из регистра |
| `sig_atomic_t` | чтение и запись происходят одной неделимой операцией |
| только присваивание | ничего небезопасного не вызывается |

Без `volatile` компилятор вправе решить, что переменную в цикле никто не меняет, и прочитать её один раз — цикл никогда не заметит сигнала. Без `sig_atomic_t` запись многобайтового значения может прерваться на середине.

Решение принимает основной цикл: увидел флаг — завершил дела, закрыл ресурсы, вышел. Это и есть чистое завершение.

## 4. `sigaction` против `signal`

`signal()` исторически неоднозначен. На системах в традиции System V обработчик сбрасывается в умолчание после первого срабатывания, и сигнал нужно устанавливать заново — с гонкой в промежутке. В традиции BSD обработчик сохраняется. Один и тот же код ведёт себя по-разному.

`sigaction()` задаёт всё явно:

```c
struct sigaction sa;
memset(&sa, 0, sizeof sa);
sa.sa_handler = handler;
sigemptyset(&sa.sa_mask);     /* что блокировать на время обработчика */
sa.sa_flags = SA_RESTART;     /* прерванные вызовы перезапускать       */
sigaction(SIGTERM, &sa, NULL);
```

Поле `sa_mask` решает тонкую проблему: пока работает обработчик, перечисленные в маске сигналы отложены, что защищает его от прерывания самим собой или родственным сигналом.

Флаг `SA_RESTART` избавляет от ручной обработки прерванных системных вызовов. Без него долгий `read()` или `waitpid()`, прерванный сигналом, вернёт `-1` с `errno == EINTR`, и это придётся ловить и повторять вручную — код замусоривается циклами перезапуска.

## 5. Доставка, объединение, ожидание

Обычные сигналы **не считаются**. Если `SIGUSR1` пришёл трижды, пока был заблокирован, обработчик вызовется один раз. Сигнал отвечает на вопрос «случилось ли», а не «сколько раз».

Практический вывод: **нельзя использовать сигналы как счётчик событий**. Обработчик, увеличивающий переменную, недосчитается при всплеске. Реальные системы применяют сигнал как звонок «проверь состояние», а само состояние читают из надёжного источника.

Для случаев, где счёт важен, существуют сигналы реального времени — они выстраиваются в очередь и несут небольшую нагрузку, но применяются редко.

Отложить доставку на время критического участка можно через `sigprocmask`. Ждать сигнал следует через `sigsuspend` или `pause`, а не крутить переменную в цикле — иначе процесс зря занимает процессор.

## 6. Season Project: stealth_agent

Финал связывает сезон в одну систему:

```
приём  →  проверка  →  разбор  →  действие  →  чистое завершение
```

| Подсистема | Серия | Что даёт |
|---|---|---|
| процессы | e01 | порождение и ожидание |
| запуск программ | e02 | подмена образа |
| демонизация | e03 | жизнь без терминала |
| потоки | e04 | параллелизм |
| мьютексы | e05 | безопасность общего состояния |
| каналы | e06 | связь между процессами |
| разделяемая память | e07 | обмен без копирования |
| сигналы | e08 | управляемость и чистый выход |

Это полный набор системного программиста. Всё дальнейшее — сети, базы данных, серверы — строится из этих восьми примитивов.

Проектная сборка собирается из модулей **трёх** сезонов: `ml_crypto` из Season 1 скрывает полезную нагрузку, `ml_crc` из Season 6 упаковывает кадр, `ml_proc` из этого сезона запускает команды. Проектный тест проверяет, что модули действительно подключены, а не скопированы.
