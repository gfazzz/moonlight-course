# Теория (углублённо) — s07e07

> **Место в курсе.** `mmap` упоминался в Season 2 (память и адресное пространство), детально разбирается здесь и понадобится в Season 8 — для работы с большими наборами данных без чтения их целиком в кучу.

## 1. Что делает mmap

`mmap()` отображает область в адресное пространство процесса: ты получаешь указатель, а ядро само подгружает страницы по обращению. Отображать можно **файл** (тогда чтение/запись памяти = чтение/запись файла) или **анонимную** память (`MAP_ANONYMOUS`) — как более гибкая замена `malloc` для крупных блоков.

```c
void *p = mmap(NULL, len, PROT_READ|PROT_WRITE, MAP_SHARED|MAP_ANONYMOUS, -1, 0);
if (p == MAP_FAILED) { /* ошибка: сравнивать именно с MAP_FAILED, не с NULL */ }
```

Освобождается через `munmap(p, len)`.

## 2. MAP_SHARED против MAP_PRIVATE

Это ключевая развилка серии:

- **`MAP_SHARED`** — отображение общее. После `fork()` родитель и потомок видят **одну и ту же физическую память**: запись одного мгновенно видна другому. Для файла — изменения попадают на диск.
- **`MAP_PRIVATE`** — copy-on-write. Пока читаешь — страница общая; при первой записи ядро делает **личную копию**. Твои изменения не видит никто (и в файл они не попадают).

В задаче это видно буквально: под `MAP_SHARED` счётчик доходит до 200000 и строка от потомка читается родителем; под `MAP_PRIVATE` потомок пишет 999, а у родителя остаётся 100.

Именно `MAP_PRIVATE`-семантика лежит в основе `fork()` (s07e01) и загрузки исполняемых файлов.

## 3. Почему это быстрее канала

Канал (s07e06) копирует данные дважды: из буфера процесса в буфер ядра и обратно. Разделяемая память — **ноль копирований**: оба процесса адресуют одни и те же физические страницы. Для больших объёмов (таблицы, кадры, индексы) разница принципиальная.

Плата: канал сам по себе синхронизирован (последовательный поток байт, EOF), а разделяемая память — просто память. Гонки из s07e05 возвращаются в полном объёме, и защищаться надо явно.

## 4. Мьютекс между процессами

Обычный `pthread_mutex_t` рассчитан на потоки одного процесса. Чтобы он работал **между процессами**, нужны две вещи:

1. Сам мьютекс лежит **в разделяемой памяти** (у нас — поле структуры внутри `MAP_SHARED`).
2. Он создан с атрибутом `PTHREAD_PROCESS_SHARED`:

```c
pthread_mutexattr_t attr;
pthread_mutexattr_init(&attr);
pthread_mutexattr_setpshared(&attr, PTHREAD_PROCESS_SHARED);
pthread_mutex_init(&sh->lock, &attr);
```

Забыть первое — мьютекс окажется в приватной копии у каждого, и защиты не будет вовсе. Забыть второе — поведение не определено (на части систем «повезёт», на других зависнет).

Альтернативы: POSIX-семафоры (`sem_init` с `pshared=1`), файловые блокировки (`flock`, `fcntl`), атомарные операции C11 в общей памяти.

## 5. Соседние механизмы

- **`shm_open` + `mmap`** — именованная разделяемая память (POSIX): доступна неродственным процессам по имени.
- **System V IPC** (`shmget`/`shmat`) — старое API, ещё встречается в легаси.
- **Файловое отображение** — быстрый доступ к большому файлу без `read()` в буфер; ядро подгружает страницы по требованию. Это и пригодится в Season 8.

## 6. Подводные камни

- Размер округляется до страницы (обычно 4 КБ) — `mmap(1)` займёт целую страницу.
- Ошибка — это `MAP_FAILED` ((void*)-1), а **не** `NULL`.
- Отображение переживает `exec` только если явно этого хотеть (по умолчанию — нет, память заменяется новым образом), а вот `fork()` наследуется.
- Данные файла попадают на диск не мгновенно: для гарантий есть `msync()`.
