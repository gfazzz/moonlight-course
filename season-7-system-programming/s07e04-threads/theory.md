# Теория — s07e04

## 1. Поток и процесс

> *— Процессы — это соседи в разных квартирах. Потоки — это соседи в одной комнате. Второе дешевле и быстрее ровно до первого спора о том, чья это чашка.*

`fork()` даёт процесс с отдельным адресным пространством. Поток живёт **внутри** процесса и делит с остальными почти всё.

| | Общее у потоков | Своё у каждого |
|---|---|---|
| код программы | ✓ | |
| куча и глобальные переменные | ✓ | |
| таблица дескрипторов | ✓ | |
| текущий каталог, права | ✓ | |
| обработчики сигналов | ✓ | |
| стек | | ✓ |
| регистры и счётчик команд | | ✓ |
| маска сигналов | | ✓ |
| локальные переменные потока | | ✓ |

Первая колонка объясняет и дешевизну, и опасность. Обмен данными не требует копирования — но любая общая изменяемая переменная становится потенциальной гонкой, а разыменование неверного указателя в одном потоке роняет весь процесс.

Правило выбора, которое стоит запомнить: **процессы для изоляции, потоки для скорости**. Браузер разносит вкладки по процессам не из-за производительности, а чтобы падение одной страницы не уносило остальные.

## 2. Жизненный цикл

```c
pthread_t th;
int rc = pthread_create(&th, NULL, worker, arg);
if (rc != 0) { /* rc — код ошибки, errno не ставится */ }
pthread_join(th, NULL);
```

Особенность интерфейса: функции `pthread_*` возвращают код ошибки **напрямую**, а не через `errno`. Причина в том, что `errno` в многопоточной программе должна быть отдельной для каждого потока, и авторы стандарта предпочли не полагаться на это.

Функция потока имеет вид `void *(*)(void *)`: один указатель на входе, один на выходе. Без `pthread_join` (или явного перевода потока в отсоединённое состояние) его ресурсы не освобождаются — точный аналог зомби.

**Ловушка с аргументом.** Почти каждый пишет это хотя бы раз:

```c
for (int i = 0; i < N; i++)
    pthread_create(&th[i], NULL, worker, &i);   /* НЕВЕРНО */
```

Все потоки получают адрес одной переменной, которая изменится до того, как они успеют её прочитать. Правильно — массив аргументов, по элементу на поток. Ошибка коварна тем, что при малом числе потоков иногда «работает».

## 3. Разделяй и не синхронизируй

Лучший параллелизм — тот, где синхронизация не нужна вовсе. Условие простое: **никакие два потока не пишут в одну ячейку**.

```
поток 0: pnl[    0 ..  2500)
поток 1: pnl[ 2500 ..  5000)
поток 2: pnl[ 5000 ..  7500)
поток 3: pnl[ 7500 .. 10000)
```

Массив общий, ячейки — нет. Такие задачи называют неприлично параллельными, и Монте-Карло — их канонический пример: траектории друг о друге не знают.

**Ложное разделение.** Тонкость, которая портит производительность, не портя корректности. Кэш работает линиями по 64 байта; если два ядра пишут в разные переменные, попавшие в одну линию, линия мечется между кэшами, и параллельная версия может оказаться **медленнее** последовательной.

Лечится крупными непрерывными кусками — как здесь, по 2500 элементов. Разбиение по чередованию (`i % nthreads`) даёт ту же корректность и катастрофическую производительность.

**Остаток от деления.** `10000 / 4` делится нацело, но в общем случае — нет. Разбиение `lo = t * n / T`, `hi = (t + 1) * n / T` покрывает диапазон целиком при любых `n` и `T`; наивное `t * (n / T)` теряет хвост.

## 4. Воспроизводимый параллелизм

Обычный параллельный Монте-Карло даёт «примерно такой же» ответ, и это считают нормой. Норма плохая: если результат зависит от числа потоков, отличить ошибку в модели от ошибки в реализации невозможно.

Источник недетерминизма всегда один — **общее состояние генератора случайных чисел**:

```c
double u = next_random(&global_state);   /* порядок обращений задаёт планировщик */
```

Даже под блокировкой порядок будет разным при разных запусках, и траектория номер 137 каждый раз получит другие числа.

Решение — сделать каждую задачу самодостаточной:

```c
uint32_t seed = 12345 + path * 2654435761u;   /* сид от номера траектории */
```

Константа `2654435761` — это `2³² / φ`, отношение золотого сечения. Умножение на неё хорошо перемешивает близкие номера, разводя соседние траектории в далёкие друг от друга области последовательности. Тот же множитель встречался в s04e02 как основа хеша Кнута.

Теперь номер траектории полностью определяет её случайные числа. Кто и когда её посчитает — не влияет ни на что, и `memcmp` двух массивов даёт ноль.

Серьёзные библиотеки решают ту же задачу иначе — через **счётчиковые генераторы** вида Philox, где случайное число вычисляется прямо из номера как из ключа шифрования, без состояния вообще. Идея та же: убрать порядок из уравнения.

## 5. Чего воспроизводимость не переживает

Параллельное **суммирование** вещественных чисел не даёт битового совпадения:

```
(a + b) + c  ≠  a + (b + c)      /* для чисел с плавающей точкой */
```

Сложение не ассоциативно из-за округления на каждом шаге, и другой порядок даёт другие младшие биты. Разница мала, но она есть, и `memcmp` её видит.

Отсюда правило: сравнивают массив результатов, а не их сумму. Если сумма всё же нужна битово одинаковой, её считают последовательно по готовому массиву — это дёшево — либо применяют компенсированное суммирование Кэхэна, которое делает результат устойчивым к порядку в пределах точности.

## 6. Замер ускорения

Время выполнения зависит от загрузки машины, числа ядер и режима работы процессора. В проверяемый вывод оно не попадает никогда.

Мерить полезно — `clock_gettime(CLOCK_MONOTONIC)`, вывод в `stderr`, — но результат для глаз, а не для теста.

**Закон Амдала** ставит потолок:

```
ускорение ≤ 1 / (s + (1 - s) / N)
```

где `s` — доля последовательной части. При `s = 0.05` даже на бесконечном числе ядер ускорение не превысит двадцати.

Практический вывод неочевиден: оптимизировать надо не параллельную часть, а последовательную. Уменьшение `s` с 5% до 2% поднимает потолок с 20 до 50 — больше, чем даёт удвоение числа ядер.

## 7. Флаг `-pthread`

Нужен и при компиляции, и при компоновке:

```
cc -Wall -Wextra -std=gnu11 -pthread prog.c -o prog
```

Он не просто подключает библиотеку. Он задаёт макросы (`_REENTRANT`), включает потокобезопасные варианты библиотечных функций и настраивает модель обработки исключений.

Указание только `-lpthread` при компоновке иногда работает, а иногда даёт тонкие ошибки в библиотечном коде, которые невозможно диагностировать по симптомам. Разница из тех, что стоит запомнить один раз.
