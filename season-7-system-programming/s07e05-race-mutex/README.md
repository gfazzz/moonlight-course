## Previously

Параллельный Monte Carlo дал побитово тот же результат, что и последовательный, — потому что потоки не пересекались. Но `tracker` противника ведёт **общий** счётчик найденных целей, и туда пишут все его потоки разом.

## Сцена

LUNA сравнивает два лога `tracker` за одну и ту же минуту.

```
[LUNA] Смотри: одинаковая работа, а счётчик целей разный. Каждый раз разный.
[LUNA] Они инкрементируют общую переменную из четырёх потоков. Без защиты.
[LUNA] counter++ — это прочитать, прибавить, записать. Между шагами тебя прерывают.
[LUNA] Два потока прочитали одно и то же — и одно обновление исчезло. Навсегда.
```

Сегодня — самая коварная ошибка параллельного кода.

## Теория: где теряются обновления

```
поток A: читает 100      поток B: читает 100
поток A: пишет  101      поток B: пишет  101      // два инкремента -> +1
```

Лечение — критическая секция:

```c
pthread_mutex_lock(&lock);
long tmp = counter; counter = tmp + 1;
pthread_mutex_unlock(&lock);
```

`lock` не только исключает одновременность, но и создаёт **барьер памяти**: то, что записано до `unlock`, увидит следующий захвативший. Про цену блокировок, deadlock и `atomic_fetch_add` — [`theory.md`](theory.md).

## Проверка на канале

```
[LUNA] Два вопроса про общую память.
```

**1.** LUNA: «В прошлой серии четыре потока писали в общий массив — и это не было гонкой. Почему теперь гонка?»

<details><summary>Ответ</summary>

Гонка — это конкурентный доступ к **одной и той же ячейке**, где хотя бы один доступ на запись. В s07e04 диапазоны не пересекались: каждый индекс писал ровно один поток. Здесь же все четыре потока пишут в одну переменную — отсюда потерянные обновления.
</details>

**2.** LUNA: «Почему тест проверяет инварианты, а не конкретное число потерь?»

<details><summary>Ответ</summary>

Число потерь зависит от планировщика и меняется каждый запуск — сравнивать его бессмысленно. Инварианты стабильны: незащищённый итог **не больше** ожидаемого (потерять можно, «наприбавлять» лишнего — нет), а защищённый **в точности** равен ожидаемому. Плавающие значения выводим в stderr, для глаз.
</details>

```
[LUNA] Верно. Показывай гонку.
```

## Задача: `race.c`

Воспроизвести гонку на общем счётчике, починить мьютексом, вывести инварианты в stdout и фактические числа в stderr. ТЗ — в [`mission.md`](mission.md), каркас — в [`starter.c`](starter.c).

```bash
cp starter.c artifacts/race.c
make test     # инварианты
make race     # увидеть, как «плавает» результат: пять запусков подряд
```

Ожидаемо — `PASS`. А `make race` покажет что-то вроде `249388`, `256145`, `403019` вместо `800000` — до 70% обновлений теряется. Эталон — [`solution/race.c`](solution/race.c).

## Разбор типичных ошибок

1. **Печатать результат гонки в stdout.** Он плавающий — тест сразу становится нестабильным.
2. **Забыть `unlock`** при раннем выходе — все остальные потоки встанут навсегда.
3. **Считать `counter++` атомарным.** Это три операции; атомарность даёт `<stdatomic.h>`, а не привычка.
4. **Один мьютекс на всё подряд.** Параллелизм вырождается в очередь: потоки стоят за общим замком.

## Debriefing

Общая память внутри процесса приручена. Но `stealth_agent` состоит из **разных процессов** — а у них адресные пространства раздельные (это ты доказал ещё в s07e01). Переменную между ними не разделишь: нужен канал связи.

```
[LUNA] Мьютекс спасает потоки одного процесса. Но у нас процессы разные.
[LUNA] Память у них раздельная — общую переменную не подсунешь. Нужен канал.
[LUNA] pipe(): один пишет, другой читает, ядро посередине. Дальше — s07e06.
```

**Навык разблокирован:** data race, мьютексы, критические секции, детерминированные проверки недетерминированного кода.
