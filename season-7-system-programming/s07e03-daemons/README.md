## Теория: ритуал

```c
fork();            // 1) потомок гарантированно не лидер группы -> можно setsid
setsid();          // 2) новая сессия без управляющего терминала
fork();            // 3) больше не лидер сессии -> терминал не подцепить никогда
chdir("/");        // 4) не держим занятым каталог запуска
umask(0);          // 5) свои права на файлы
dup2(devnull, 0/1/2);   // 6) консоли нет
```

После ухода промежуточного процесса демона усыновляет `init`/`systemd` (PID 1) — он же пожнёт его статус, зомби не останется. Логи демон пишет в файл или syslog: stdout у него уже `/dev/null`. Подробнее — [`theory.md`](theory.md).

## Проверка на канале

```
[LUNA] Два вопроса про уход в тень.
```

**1.** LUNA: «Зачем второй `fork()`, если `setsid()` уже отвязал нас от терминала?»

<details><summary>Ответ</summary>

После `setsid()` процесс — лидер новой сессии, а лидер может **случайно приобрести** управляющий терминал, открыв терминальное устройство. Второй `fork()` делает демона рядовым членом сессии: терминал ему уже не достанется. Заодно демон становится сиротой и его усыновляет PID 1.
</details>

**2.** LUNA: «Почему дескрипторы 0/1/2 переоткрывают на `/dev/null`, а не просто закрывают?»

<details><summary>Ответ</summary>

Если фд 1 закрыт, следующий `open()` получит именно номер 1 — и случайный `printf` начнёт писать в этот файл, портя данные. Держать 0/1/2 занятыми `/dev/null` безопаснее: запись уходит в никуда, номера не переиспользуются.
</details>

## Разбор типичных ошибок

1. **Пропустить второй `fork`.** Демон остаётся лидером сессии и может подцепить терминал.
2. **`setsid()` в родителе.** Он лидер группы — вызов провалится. Сначала `fork`.
3. **Закрыть 0/1/2 вместо `dup2` на `/dev/null`.** Следующий `open()` займёт эти номера — жди испорченных файлов.
4. **Ждать вывод демона в stdout.** Его нет: отчёт только через файл/сокет/syslog.
