## Теория: флаг и основной цикл

### Обработчик умеет одно

```c
static volatile sig_atomic_t got_term = 0;
static void handler(int s) { (void)s; got_term = 1; }   /* и ничего больше */

while (working) {
    if (got_term) { /* дописать, закрыть, выйти */ break; }
    ...
}
```

Сигнал прерывает программу **в произвольной точке** — возможно, посреди той самой функции, которую вы захотите вызвать из обработчика. Поэтому обработчик ставит флаг, а решение принимает основной цикл.

| Элемент | Зачем |
|---|---|
| `volatile` | компилятор не закеширует флаг в регистре |
| `sig_atomic_t` | чтение и запись атомарны относительно сигнала |
| флаг, а не действие | из обработчика почти ничего нельзя вызвать |

### Что можно из обработчика

Только функции из списка безопасных в контексте сигнала: `write`, `_exit`, `kill` и немногие другие. `printf`, `malloc`, почти вся стандартная библиотека — **нельзя**: они не рассчитаны на повторный вход.

### Почему `sigaction`, а не `signal`

```c
struct sigaction sa;
memset(&sa, 0, sizeof sa);
sa.sa_handler = handler;
sigemptyset(&sa.sa_mask);
sa.sa_flags = SA_RESTART;
sigaction(SIGTERM, &sa, NULL);
```

`signal()` ведёт себя по-разному на разных системах: где-то обработчик сбрасывается после первого срабатывания, где-то нет. `sigaction()` задаёт поведение явно, а `SA_RESTART` избавляет от перезапуска прерванных системных вызовов вручную.

### Иерархия сигналов

| Сигнал | Смысл | Перехватывается |
|---|---|---|
| `SIGTERM` | просьба завершиться | да |
| `SIGINT` | прерывание с клавиатуры | да |
| `SIGHUP` | у демонов — перечитать настройки | да |
| `SIGUSR1`, `SIGUSR2` | свободны для своих нужд | да |
| `SIGKILL` | немедленное завершение | **нет** |
| `SIGSTOP` | приостановка | **нет** |

Две нижние строки — граница, которую нельзя перейти. Всё проектирование чистого завершения происходит выше неё.

## Проверка на канале

```
[LUNA] Два вопроса. Последние в этом сезоне.
```

**1.** LUNA: «Почему из обработчика нельзя вызвать `printf`?»

<details><summary>Ответ</summary>

Потому что обработчик прерывает программу в произвольной точке — возможно, ровно посреди `printf`, когда его внутренний буфер и блокировка в несогласованном состоянии. Повторный вход в ту же функцию даёт либо взаимоблокировку на её же замке, либо порчу данных. Разрешён только узкий список функций, безопасных для вызова из обработчика; для вывода это `write`, но и его обычно заменяют установкой флага, а печатает основной цикл, которого сигнал уже не прерывает.
</details>

**2.** LUNA: «Зачем нужен `SIGTERM`, если есть `SIGKILL`, который точно сработает?»

<details><summary>Ответ</summary>

Потому что `SIGKILL` не даёт процессу прибраться: несохранённые данные теряются, открытые файлы и захваченные блокировки остаются в неопределённом состоянии. `SIGTERM` — просьба завершиться штатно, и процесс успевает дописать, закрыть и освободить. Поэтому супервизоры и системы инициализации сначала посылают `SIGTERM`, ждут отведённое время и лишь затем прибегают к `SIGKILL` как к крайней мере. Гарантия ядра, что `SIGKILL` нельзя перехватить, существует ровно для случая, когда процесс на просьбу не отвечает.
</details>

```
[LUNA] Верно. Завершай чисто.
```

## Разбор типичных ошибок

1. **`printf` в обработчике.** Небезопасно в контексте сигнала: возможна взаимоблокировка.
2. **Флаг без `volatile` или `sig_atomic_t`.** Компилятор закеширует значение — цикл не заметит сигнала.
3. **`signal()` вместо `sigaction()`.** Поведение различается между системами; нет `SA_RESTART`.
4. **Попытка перехватить `SIGKILL`.** Невозможна по определению.
5. **Гонка при установке барьера готовности.** `SIGTERM` послан раньше, чем потомок установил игнорирование.
6. **`EINTR` не обработан там, где нет `SA_RESTART`.** Прерванный системный вызов принят за ошибку.
