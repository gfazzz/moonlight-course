# Теория (углублённо) — s07e08

Финал сезона собирает всё: процессы (e01–e03), параллелизм (e04–e05), связь (e06–e07).

## 1. Что такое сигнал

Сигнал — асинхронное уведомление процессу: от ядра (`SIGSEGV` при обращении по неверному адресу, `SIGPIPE` при записи в закрытый канал) или от другого процесса (`kill(pid, sig)`). Это **уведомление**, а не канал передачи данных: у сигнала нет полезной нагрузки, кроме номера.

Частые: `SIGTERM` (15) — вежливая просьба завершиться, шлёт `kill` по умолчанию; `SIGINT` (2) — Ctrl-C; `SIGHUP` (1) — закрытие терминала, у демонов традиционно «перечитай конфиг»; `SIGCHLD` — потомок завершился; `SIGUSR1`/`SIGUSR2` — свободны для своих нужд.

## 2. Чего нельзя перехватить

`SIGKILL` (9) и `SIGSTOP` (19) невозможно ни перехватить, ни заблокировать, ни проигнорировать. Это гарантия ядра: администратор всегда может убить процесс. В задаче потомок демонстративно игнорирует `SIGTERM` и переживает его — но `SIGKILL` завершает его немедленно, и `WTERMSIG(status)` это подтверждает.

Отсюда практика: `SIGTERM` — «сохранись и выйди», `SIGKILL` — крайняя мера без шанса прибраться (незаписанные данные теряются). Поэтому `systemd` сначала шлёт `SIGTERM`, ждёт, и только потом `SIGKILL`.

## 3. Главное правило обработчика

Обработчик прерывает программу **в произвольной точке** — возможно, посреди `malloc` или `printf`, когда их внутренние структуры в несогласованном состоянии. Вызвать оттуда те же функции — путь к взаимоблокировке или порче кучи.

Разрешён лишь узкий список **async-signal-safe** функций (`write`, `_exit`, `kill`, …; полный перечень — `man 7 signal-safety`). Практическое правило:

```c
static volatile sig_atomic_t got_term = 0;
static void handler(int s) { (void)s; got_term = 1; }   // и всё
```

- **`volatile`** — компилятор не имеет права закешировать флаг в регистре;
- **`sig_atomic_t`** — тип, чтение/запись которого атомарны относительно сигналов.

Решение принимает основной цикл: увидел флаг — завершил дела, закрыл файлы, вышел. Это и есть *graceful shutdown*.

## 4. sigaction вместо signal

`signal()` исторически неоднозначен: на одних системах обработчик сбрасывается в умолчание после первого срабатывания, на других нет; поведение прерванных системных вызовов тоже разное. `sigaction()` задаёт всё явно:

```c
struct sigaction sa;
memset(&sa, 0, sizeof sa);
sa.sa_handler = handler;
sigemptyset(&sa.sa_mask);     // какие сигналы блокировать на время обработчика
sa.sa_flags = SA_RESTART;     // прерванные syscall'ы перезапускать, а не рвать с EINTR
sigaction(SIGTERM, &sa, NULL);
```

Без `SA_RESTART` долгие `read()`/`waitpid()` будут возвращать `-1` с `errno == EINTR`, и это придётся обрабатывать вручную.

## 5. Доставка, объединение, блокировка

Обычные (не-realtime) сигналы **не накапливаются**: если `SIGUSR1` пришёл трижды, пока он заблокирован, обработчик вызовется один раз. Считать сигналы как события нельзя — можно лишь узнать «что-то произошло». (В задаче `raise()` доставляет синхронно, поэтому счётчик равен двум.)

Временно отложить доставку можно через `sigprocmask` — так защищают критические участки. Ожидать сигнал правильно через `sigsuspend`/`pause`, а не «крутить» переменную в цикле.
