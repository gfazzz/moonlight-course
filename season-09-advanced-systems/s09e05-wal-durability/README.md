## Теория: журнал впереди данных

### Порядок

```
1) записи намерений (было -> стало) в журнал
2) fsync(журнал)                       <-- без этого шага всё бессмысленно
3) COMMIT + fsync
4) страницы данных (можно лениво)
```

Четвёртый шаг может произойти через секунду, через минуту или не произойти вовсе до сбоя — восстановление доиграет его по журналу.

### Почему журнал дешевле данных

| | Журнал | Страницы данных |
|---|---|---|
| характер записи | последовательная, в конец | случайная, по всему файлу |
| стоимость | минимальная | высокая |
| что содержит | намерения | состояние |

Выгода двойная: и надёжность, и скорость. Дорогую случайную запись откладывают, дешёвую последовательную выполняют сразу.

### Точка фиксации

Транзакция зафиксирована тогда, когда **подтверждение оказалось в журнале на диске**, а не когда обновились страницы данных.

Из этого следуют две политики:

| Политика | Что разрешает | Что требует |
|---|---|---|
| **no-force** | не сбрасывать страницы при фиксации | повтор при восстановлении |
| **steal** | вытеснять изменённые страницы до фиксации | откат при восстановлении |

Промышленные СУБД используют обе сразу — самый гибкий вариант и самый требовательный к журналу. Отсюда обязательное хранение обеих версий в каждой записи.

### Восстановление

```
есть COMMIT в устойчивой части журнала  ->  redo: применить новые значения
нет COMMIT                              ->  undo: вернуть старые, с конца к началу
```

Откат идёт **от конца к началу**: если одна ячейка менялась дважды, вернуться нужно к самому раннему состоянию.

### Идемпотентность

Восстановление может прерваться и начаться заново. Значит, повтор обязан давать тот же результат.

Отсюда правило: повтор применяет **абсолютные** значения, а не приращения. Запись «стало 70» безопасна при любом числе повторений; запись «вычесть 30» — нет.

### Устойчивая часть журнала

Дописанное в память ещё не устойчиво. Устойчива только та часть, для которой завершилась синхронизация. Смешение этих двух понятий — самая частая ошибка в самодельных журналах.

## Проверка: LUNA задаёт вопросы
```
[LUNA] Два вопроса про надёжность.
```

**1.** LUNA: «Транзакция считается зафиксированной, когда данные записаны в файл?»

<details><summary>Ответ</summary>

Нет — когда подтверждение оказалось **в журнале на диске**. Страницы данных могут быть записаны позже или не записаться вовсе: если сбой случится до этого, восстановление доиграет их по журналу. Именно поэтому синхронизируется журнал, а данные могут подождать — и именно поэтому фиксация транзакции стоит одну последовательную запись, а не десяток случайных. Обратное утверждение тоже верно и важно: пока подтверждения в журнале нет, транзакция не зафиксирована, сколько бы страниц уже ни изменилось.
</details>

**2.** LUNA: «Зачем в журнале хранить старое значение, если для восстановления достаточно нового?»

<details><summary>Ответ</summary>

Нового достаточно только для повтора — то есть для случая, когда транзакция была подтверждена. Но сбой случается когда угодно, в том числе до подтверждения, а изменённые страницы к этому моменту могли уже попасть на диск: базы данных разрешают вытеснять их из буфера, не дожидаясь фиксации. Тогда нужен откат, а для него необходимо знать, что было раньше. Поэтому запись хранит обе версии: новую для повтора, старую для отката.
</details>

```
[LUNA] Верно. Роняй питание.
```

## Разбор типичных ошибок

1. **Данные пишутся до синхронизации журнала.** Порядок нарушен — журнал перестаёт защищать.
2. **Зафиксированным считается всё дописанное в журнал.** Устойчива только синхронизированная часть.
3. **Хранится лишь новое значение.** Откат становится невозможен.
4. **Повтор неидемпотентен.** Приращение при повторном восстановлении применится дважды.
5. **Откат идёт от начала к концу.** При двух изменениях одной ячейки вернётся не то состояние.
6. **Синхронизация вызывается один раз.** Подтверждение требует своей.
