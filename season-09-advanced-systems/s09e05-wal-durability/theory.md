# Теория — s09e05

## 1. Запись не атомарна

> *— Надёжность — это не когда ничего не ломается. Это когда после поломки известно, что делать.*

Обновление страницы на диске — не мгновенная операция. Атомарность накопитель гарантирует в лучшем случае для сектора; страница в четыре килобайта записывается несколькими операциями, и между ними возможен сбой.

Хуже того: одна логическая операция трогает **несколько** страниц. Между их записями существует окно, в котором данные противоречивы — деньги списаны, но не зачислены.

Файловая система здесь не помогает. Она гарантирует целостность **своих** метаданных: файл не потеряется, каталог не испортится, размер будет корректным. Про смысл записей внутри файла она не знает ничего.

Отсюда: **целостность данных не является свойством диска или файловой системы**. Это свойство порядка, в котором приложение пишет.

## 2. Правило упреждающей записи

Прежде чем менять данные, записать намерение в журнал и убедиться, что журнал на диске.

```
1. в журнал: BEGIN, acc0: 100 -> 70, acc1: 100 -> 130
2. fsync(журнал)          <-- без этого шага всё остальное бессмысленно
3. COMMIT в журнал, fsync
4. страницы данных (лениво)
```

Выгода двойная, и вторая половина неочевидна:

| | Журнал | Страницы данных |
|---|---|---|
| характер записи | последовательная, в конец | случайная, по всему файлу |
| стоимость операции | минимальная | высокая |
| когда выполняется | сразу | можно отложить |

Дорогая случайная запись откладывается, дешёвая последовательная выполняется немедленно. Журналирование не только надёжнее — оно **быстрее** прямой записи данных.

## 3. Точка фиксации

Транзакция зафиксирована тогда, когда подтверждение оказалось в журнале **на диске**, а не когда обновились страницы данных.

Из этого следуют две политики управления буфером:

| Политика | Разрешает | Требует |
|---|---|---|
| **no-force** | не сбрасывать страницы при фиксации | повтор при восстановлении |
| **force** | обязательный сброс при фиксации | ничего, но медленно |
| **steal** | вытеснять изменённые страницы до фиксации | откат при восстановлении |
| **no-steal** | держать изменения в буфере до фиксации | много памяти |

Промышленные СУБД выбирают **steal + no-force** — самое гибкое сочетание и самое требовательное к журналу: нужны обе операции восстановления.

Отсюда обязательное хранение обеих версий значения в каждой записи. Новая нужна для повтора, старая — для отката.

## 4. Восстановление

```
есть подтверждение в устойчивой части  ->  повтор: применить новые значения
нет подтверждения                      ->  откат: вернуть старые, с конца к началу
```

**Направление отката существенно.** Если одна ячейка менялась дважды, обход от начала к концу вернёт промежуточное состояние, а не исходное.

**Идемпотентность обязательна.** Восстановление может прерваться сбоем и начаться заново. Поэтому повтор применяет абсолютные значения:

```
безопасно:   acc0 = 70
опасно:      acc0 -= 30      /* повторится дважды */
```

Промышленный алгоритм — **ARIES** (Mohan, 1992): три прохода — анализ, повтор, откат — плюс точки сохранения, чтобы не перечитывать журнал с начала времён.

Важная деталь ARIES: повтор применяется **ко всем** транзакциям, включая неподтверждённые, и только потом выполняется откат. Это выглядит избыточным, но приводит систему в состояние на момент сбоя, из которого откат корректен независимо от того, какие страницы успели записаться.

## 5. Синхронизация — самая недооценённая операция

`write()` кладёт данные в страничный кэш ядра, а не на диск. Без явной синхронизации они могут жить в памяти секундами.

Классические ошибки:

| Ошибка | Последствие |
|---|---|
| нет синхронизации журнала | журнал становится декорацией |
| накопитель лжёт о завершении записи | всё корректно и всё равно теряется |
| не синхронизирован каталог при создании файла | файл существует, но не найдётся после сбоя |
| синхронизация вызвана один раз на всё | подтверждение может уйти раньше данных журнала |

Вторая строка не гипотетическая: дешёвые накопители с кэшем без защиты питания массово подтверждали запись до её завершения, и производители СУБД годами вели списки таких моделей.

Синхронизация дорога — единицы миллисекунд. Отсюда **групповая фиксация**: несколько транзакций дожидаются одной общей операции. Она же объясняет, почему SQLite с отключённой синхронизацией кратно быстрее — и почему так делать нельзя.

## 6. Где ещё та же идея

| Область | Форма |
|---|---|
| журналируемые файловые системы | журнал метаданных перед их изменением |
| хранение событий | состояние как свёртка журнала |
| распределённый консенсус | Raft — это реплицируемый журнал |
| очереди сообщений | Kafka хранит журнал, а не очередь |
| системы контроля версий | git — журнал неизменяемых записей |

«Сначала запиши, что собираешься сделать» — одна из самых универсальных идей в системном программировании. Она встречалась в курсе и раньше: проверка контрольной суммы до разбора кадра в Season 6 — тот же принцип, применённый к другому объекту.

## 7. Чего журнал не даёт

Стоит очертить границы:

- **защита от ошибки в логике.** Журнал добросовестно доиграет неверную транзакцию.
- **защита от повреждения носителя.** Для этого нужны контрольные суммы страниц и резервные копии.
- **атомарность между машинами.** Распределённая транзакция требует отдельного протокола.
- **изоляция параллельных транзакций.** Это другая буква в аббревиатуре ACID и другой механизм — блокировки или версионность.

Журнал закрывает атомарность и устойчивость. Согласованность и изоляция обеспечиваются иначе.
