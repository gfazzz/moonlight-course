## Теория: приоритет — это глубина

### Грамматика

```
expr   := term   (('+' | '-') term)*        левоассоциативно
term   := factor (('*' | '/') factor)*      левоассоциативно
factor := NUM | '(' expr ')' | '-' factor   унарный минус правоассоциативен
```

Звёздочка означает «ноль или более повторений» — и именно она превращается в цикл.

### Почему порядок вызовов задаёт приоритет

`expr` вызывает `term`, а не наоборот. Значит, `term` успевает собрать своих операндов и вернуть готовый узел раньше, чем `expr` увидит результат. Умножение оказывается **под** сложением.

Добавить новый уровень — например, возведение в степень — значит вставить ещё одну функцию между `term` и `factor`. Больше ничего менять не придётся.

### Левая ассоциативность = цикл

```c
Node *n = parse_term(lx);
while (op) n = node_new(kind, n, parse_term(lx));   /* накапливаем влево */
```

| Выражение | Правильно | Если собирать вправо |
|---|---|---|
| `100 - 20 - 5` | `(100−20)−5 = 75` | `100−(20−5) = 85` |
| `8 / 4 / 2` | `(8/4)/2 = 1` | `8/(4/2) = 4` |

Для сложения и умножения разницы нет, для вычитания и деления — принципиальная.

### Почему левую рекурсию нельзя записать буквально

```
expr := expr '+' term        /* так нельзя */
```

Функция вызовет себя первым же действием, не потребив ни одного токена. Состояние не изменилось — значит, следующий вызов сделает ровно то же самое.

Правоассоциативные операторы, наоборот, пишутся рекурсией: `factor := '-' factor` работает, потому что минус потребляется до вызова.

### Три обхода одного дерева

| Обход | Даёт | Применение |
|---|---|---|
| префиксный | `(+ 3 (* 4 2))` | форма Лиспа, отладка |
| инфиксный | `3 + 4 * 2` | привычная запись, нужны скобки |
| постфиксный | `3 4 2 * +` | скобки не нужны, вычисляется стеком |

Последняя строка — прямой путь к кодогенерации: постфиксный обход есть последовательность инструкций стековой машины, то есть байткод.

### Что ещё надо проверить

Остаток непрочитанных токенов после разбора — тоже ошибка. Без этой проверки строка `1 + 2)` молча разберётся как `1 + 2`.

```
[LUNA] Два вопроса про разбор.
```

**1.** LUNA: «Почему `100 - 20 - 5` нужно собирать циклом, а не рекурсией?»

<details><summary>Ответ</summary>

По двум причинам сразу. Первая — семантика: вычитание левоассоциативно, и правильный ответ `(100−20)−5 = 75`, тогда как правая сборка дала бы 85. Вторая — техническая: попытка записать это рекурсивно даёт грамматику `expr := expr '-' term`, где функция вызывает себя первым же действием, не потребив ни одного токена. Состояние не изменилось, значит следующий вызов сделает то же самое — бесконечный спуск и переполнение стека. Цикл решает обе проблемы: он накапливает результат влево и потребляет по токену на итерацию.
</details>

**2.** LUNA: «Парсер разобрал `1 + 2)` без ошибки. Что забыли проверить?»

<details><summary>Ответ</summary>

Остаток токенов после разбора. Выражение `1 + 2` действительно корректно и разобралось успешно, но закрывающая скобка осталась непрочитанной, а никто не спросил, дошли ли мы до конца ввода. После вызова корневого правила необходимо убедиться, что следующий токен — конец файла. Пропуск этой проверки — одна из самых частых ошибок в самодельных разборщиках: мусор в хвосте проходит незамеченным, и ошибка проявится намного позже и в другом месте.
</details>

## Разбор типичных ошибок

1. **Левая рекурсия записана буквально.** Переполнение стека на первом же выражении.
2. **Вычитание собирается вправо.** `100-20-5` даст 85 вместо 75.
3. **Конец ввода не проверяется.** `1 + 2)` пройдёт как корректное выражение.
4. **`expr` вызывает `factor` напрямую.** Уровень умножения потеряется вместе с приоритетом.
5. **Узлы выделяются через `malloc` без освобождения.** В задаче используется статический пул.
6. **Деление на ноль роняет программу.** По ТЗ оно даёт ноль.
