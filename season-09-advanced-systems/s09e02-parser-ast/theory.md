# Теория — s09e02

## 1. Зачем дерево

> *— Список говорит, что было. Дерево говорит, что с чем связано. Между этими двумя вещами лежит вся разница между текстом и программой.*

Токены `3 + 4 * 2` — плоский список. Он не отвечает на вопрос «что вычисляется первым»:

```
(+ 3 (* 4 2))  =>  11        умножение сильнее
(* (+ 3 4) 2)  =>  14        если бы приоритет был другим
```

Дерево называют **абстрактным**, потому что в нём нет скобок, разделителей и пробелов — только смысл. Скобки исходного текста уже отражены во вложенности и потому не нужны.

Отличие от **дерева разбора** (parse tree), которое содержит все узлы грамматики, включая промежуточные вроде «term, состоящий из одного factor». Такое дерево строят генераторы парсеров; для интерпретации оно избыточно.

## 2. Рекурсивный спуск

Самый практичный ручной метод: одна функция на каждый уровень приоритета, каждая вызывает следующий, более сильный уровень.

```
expr   -> term   -> factor
(+ -)     (* /)    NUM, (…), унарный минус
```

Такой парсер разбирает грамматики класса **LL(1)**: решение о ветке принимается по одному текущему токену, разбор идёт слева направо, вывод строится левый.

Читается он как сама грамматика — отсюда популярность. Рекурсивный спуск используют GCC, Clang, Go и большинство современных компиляторов, хотя генераторы парсеров существуют полвека.

Причина, по которой от генераторов отказались: **качество сообщений об ошибках**. Автоматически построенный разборщик знает, что вход не соответствует грамматике, но плохо объясняет, чего именно не хватило. Ручной код может сказать «пропущена точка с запятой после объявления» — потому что знает контекст.

## 3. Приоритет — это глубина

Чем сильнее оператор связывает, тем глубже в дереве он оказывается.

Механика проста: `expr` вызывает `term` **до** того, как посмотрит на свой оператор. Значит, `term` успевает собрать `4 * 2` в готовый узел, и `expr` получает его как единый операнд.

Добавление нового уровня — механическая операция. Возведение в степень встраивается между `term` и `factor`:

```
term  := power (('*' | '/') power)*
power := factor ('^' power)?        /* правоассоциативно: 2^3^2 = 2^(3^2) */
factor := NUM | '(' expr ')'
```

Остальной код не меняется.

## 4. Ассоциативность

| Выражение | Левая сборка | Правая сборка |
|---|---|---|
| `100 - 20 - 5` | **75** | 85 |
| `8 / 4 / 2` | **1** | 4 |
| `2 ^ 3 ^ 2` | 64 | **512** |
| `a = b = 5` | ошибка | **b=5, затем a=5** |

Первые две строки левоассоциативны, последние две — правоассоциативны. Выбор диктуется математикой и удобством, а не вкусом.

**Левая ассоциативность — цикл:**

```c
Node *n = parse_term(lx);
while (op) n = node_new(kind, n, parse_term(lx));
```

**Правая ассоциативность — рекурсия:**

```c
Node *left = parse_factor(lx);
if (op) return node_new(kind, left, parse_power(lx));   /* вызов после потребления op */
```

Разница в том, где стоит рекурсивный вызов: после потребления оператора он безопасен.

## 5. Левая рекурсия

```
expr := expr '+' term        /* так нельзя */
```

Функция вызывает себя первым же действием, не потребив ни одного токена. Состояние не изменилось, значит следующий вызов сделает ровно то же — бесконечный спуск.

Формальное правило: **каждый рекурсивный вызов обязан работать с меньшим входом**. Левая рекурсия его нарушает.

Устранение делается механически:

```
A := A α | β        превращается в        A := β α*
```

То есть повторение выносится в цикл. Существует и общий алгоритм устранения косвенной левой рекурсии — когда `A` вызывает `B`, а `B` вызывает `A`, — но на практике грамматики сразу пишут в удобной форме.

Разборщики класса LR (те, что строят генераторы) левую рекурсию обрабатывают естественно и даже предпочитают её — там она не расходует стек. Это одно из немногих преимуществ генераторов.

## 6. Три обхода

| Обход | Порядок | Результат |
|---|---|---|
| префиксный | корень, потомки | `(+ 3 (* 4 2))` |
| инфиксный | левый, корень, правый | `3 + 4 * 2` |
| постфиксный | потомки, корень | `3 4 2 * +` |

**Префиксный** — форма Лиспа. Скобки в ней есть, но они не про приоритет, а про границы вызова.

**Инфиксный** требует расстановки скобок при печати, иначе теряется структура: `(3+4)*2` и `3+4*2` дадут одинаковый текст при наивном обходе.

**Постфиксный** не требует скобок вовсе. Порядок операций записан в самой последовательности, а вычисление идёт стеком:

```
3      -> [3]
4      -> [3, 4]
2      -> [3, 4, 2]
*      -> [3, 8]
+      -> [11]
```

Отсюда прямой путь к кодогенерации: **постфиксный обход — это последовательность инструкций стековой машины**. Байткод Python и виртуальной машины Java устроен именно так, и алгоритм получения байткода из дерева — тот же обход, что печатает эту строку.

Запись предложена Лукасевичем в 1920-е годы; «обратной польской» её называют по национальности автора.

## 7. Ошибки и восстановление

Наш парсер помечает ошибку флагом и останавливается — минимальный вариант.

Промышленные разборщики применяют **режим паники**: при ошибке пропускать токены до ближайшей точки синхронизации — обычно `;` или `}` — и продолжать разбор. Так за один проход выдаётся несколько ошибок.

Риск режима паники — каскад ложных сообщений: одна настоящая ошибка порождает десяток производных. Компиляторы борются с этим, подавляя сообщения, следующие слишком близко за предыдущим.

Отдельный практический пункт: **остаток токенов после разбора — тоже ошибка**. Без этой проверки `1 + 2)` молча разберётся как `1 + 2`, и проблема всплывёт много позже.

## 8. Альтернативы

| Метод | Плюс | Минус |
|---|---|---|
| рекурсивный спуск | понятные ошибки, полный контроль | по функции на уровень |
| разбор Пратта | приоритеты таблицей | менее очевидный код |
| генератор (LR) | мощнее LL, левая рекурсия | плохая диагностика, сложная отладка |
| комбинаторы | компактность | производительность, неясные ошибки |

**Разбор Пратта** (он же восхождение по приоритетам) стоит знать: приоритеты задаются таблицей вместо отдельной функции на уровень. При двадцати операторах это разница между двадцатью функциями и одной таблицей.
