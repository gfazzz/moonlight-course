## Теория: слова без грамматики

### Конвейер

```
текст -> [лексер] -> токены -> [парсер] -> дерево -> [интерпретатор] -> результат
```

Каждый этап понижает уровень хаоса: символы становятся словами, слова — структурой, структура — действием. Разделение не обязательно (существуют однопроходные компиляторы), но оно делает каждый этап проверяемым отдельно.

### Что несёт токен

| Поле | Зачем |
|---|---|
| тип | чтобы парсер знал, что это |
| текст | для диагностики и для идентификаторов |
| значение | для чисел, чтобы не разбирать повторно |
| **позиция** | чтобы сказать, **где** ошибка |

Последняя строка — та, о которой забывают. Компилятор без позиций умеет говорить только «где-то есть ошибка», и это делает его бесполезным.

### Два правила

**Максимальное совпадение.** Увидев `>`, надо посмотреть на следующий символ: `>=` — это один токен, а не два.

```
">= 10"   правильно:  GE, NUM
          неправильно: GT, ASSIGN, NUM
```

**Ключевые слова — потом.** Сначала слово читается целиком по правилу идентификатора, затем сверяется с таблицей. Иначе `iffy` разрежется на `if` и `fy`.

### Чего лексер не умеет

Он не может проверить парность скобок. Принципиально, а не по недосмотру.

Лексика описывается регулярными выражениями, а регулярные языки не считают вложенность — у них нет памяти о глубине. Парность требует контекстно-свободной грамматики и стека, то есть парсера.

### Восстановление после ошибок

Неизвестный символ — не повод падать. Лексер выдаёт токен ошибки и продолжает, чтобы пользователь увидел все проблемы сразу, а не по одной за прогон.

## Проверка: LUNA задаёт вопросы

```

**1.** LUNA: «Почему нельзя выдавать ключевое слово сразу, как увидел буквы `if`?»

<details><summary>Ответ</summary>

Потому что идентификатор `iffy` начинается точно так же, и его разрежет пополам: получатся ключевое слово `if` и идентификатор `fy`. Программа при этом не выдаст ошибку — она просто окажется другой программой. Правильный порядок обязателен: прочитать слово целиком по правилу идентификатора, а затем проверить полученную строку по таблице ключевых слов. Это частный случай максимального совпадения, применённый к словам вместо операторов.
</details>

**2.** LUNA: «Может ли лексер проверить, что скобки расставлены парно?»

<details><summary>Ответ</summary>

Нет, и это ограничение принципиальное. Лексика описывается регулярными выражениями, а регулярные языки не умеют считать вложенность: у конечного автомата нет памяти о том, на какой глубине он находится. Формально это следствие леммы о накачке — язык правильных скобочных последовательностей нерегулярен. Парность проверяет парсер, у которого есть стек либо рекурсия, то есть механизм памяти неограниченной глубины.
</details>

```

## Разбор типичных ошибок

1. **`>=` разбирается как два токена.** Нарушение максимального совпадения.
2. **Ключевые слова опознаются на лету.** `iffy` разрежется пополам.
3. **Позиции не сохраняются.** Диагностика становится бесполезной.
4. **Столбец не сбрасывается после перевода строки.** Позиции уедут со второй строки.
5. **Лексер падает на неизвестном символе.** Пользователь увидит одну ошибку вместо всех.
6. **Комментарий обрабатывается как оператор деления.** Два слэша подряд — особый случай.
