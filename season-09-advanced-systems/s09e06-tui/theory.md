# Теория — s09e06

## 1. Терминал — устройство, а не поток

> *— Терминал притворяется печатной машинкой из уважения к прошлому. На самом деле это экран с адресуемыми ячейками, и байты, которыми им управляют, никто не прятал.*

Обычная программа пишет строки последовательно. Терминал понимает **управляющие последовательности**, которыми ставят курсор, меняют цвет, очищают области:

```
\033[<y>;<x>H     поставить курсор в строку y, столбец x
\033[2J           очистить экран
\033[K            очистить до конца строки
\033[7m           инверсия;  \033[0m — сброс атрибутов
\033[?25l         спрятать курсор — обязательно при перерисовке
\033[?1049h       альтернативный экран
```

`\033` — байт ESC. Никакой магии: терминал перехватывает эти байты вместо того, чтобы напечатать.

Последняя строка объясняет знакомое поведение: после выхода из редактора содержимое терминала возвращается, потому что редактор работал на отдельном экране.

Наследие настоящее: последовательности стандартизованы для терминала VT100 фирмы DEC в 1978 году, и современные эмуляторы по-прежнему говорят на его языке.

## 2. Сырой режим

По умолчанию терминал работает в **каноническом** режиме: копит строку в собственном буфере, обрабатывает забой и отдаёт программе только по нажатию ввода, попутно печатая набранное.

Для интерактивного интерфейса нужен посимвольный ввод без эха:

```c
struct termios raw;
tcgetattr(STDIN_FILENO, &raw);
raw.c_lflag &= ~(ECHO | ICANON | ISIG);   /* без эха, без строк, Ctrl-C как символ */
raw.c_iflag &= ~(IXON | ICRNL);           /* без Ctrl-S/Q, без замены CR на NL */
tcsetattr(STDIN_FILENO, TCSAFLUSH, &raw);
```

**Железное правило: всегда восстанавливать режим при выходе.** Через `atexit` и обработчик сигнала из s07e08. Программа, упавшая в сыром режиме, оставляет терминал неработоспособным — пользователю придётся вслепую набирать `reset`.

Это же объясняет, почему в этой задаче термиос не используется: тест не должен требовать терминала. Решение архитектурное, а не упрощающее — см. следующий пункт.

## 3. Разделение рисования и вывода

Ключевая идея серии:

```
состояние -> [рендер] -> буфер ячеек -> [вывод] -> терминал
```

| Что даёт | Почему важно |
|---|---|
| рендер — чистая функция | те же данные дают тот же буфер |
| буфер сравнивается с эталоном | тест не требует терминала |
| логика отделена от вывода | работает в автоматической сборке |
| есть предыдущий кадр | появляется возможность послать разницу |

Последняя строка — приятное следствие, а не цель. Разделение делалось ради проверяемости, а оптимизация вывода досталась бесплатно.

В графике тот же приём называется двойной буферизацией: рисуем в задний буфер, показываем передний, меняем их местами. Причина та же — недопустимость показа наполовину нарисованного кадра.

## 4. Отслеживание изменений и когда оно невыгодно

Полная перерисовка в цикле даёт мерцание и лишний трафик — особенно по медленному каналу.

Но выигрыш от разницы не безусловен:

| Что отправляем | Байт |
|---|---|
| символ подряд | 1 |
| символ с позиционированием | ~10 |

Порог проходит примерно на пятнадцати процентах экрана. В задаче видно на числах: первый кадр (186 из 480 ячеек) выгоднее вывести целиком, последующие (7–42 ячейки) — разницей, с выигрышем до девяти раз.

Настоящие библиотеки поднимают порог, применяя оптимизации:

- **группировка соседних изменений** в один прогон — позиционирование платится раз на серию;
- **возможности конкретного терминала** из базы описаний: вставка строки, удаление, прокрутка области;
- **алгоритмы поиска общих подпоследовательностей** между кадрами, чтобы находить прокрутку.

Последний пункт объясняет, почему прокрутка длинного файла в редакторе не перерисовывает экран: терминалу отправляется команда сдвинуть область, а дорисовывается одна строка.

## 5. Один байт на ячейку

Наивный буфер хранит `char`, и тогда текст обязан быть ASCII. С UTF-8 это ломается сразу:

| Символ | Байт в UTF-8 | Колонок на экране |
|---|---|---|
| латинская буква | 1 | 1 |
| кириллическая буква | 2 | 1 |
| иероглиф | 3 | **2** |
| эмодзи | 4 | **2** |
| комбинирующая диакритика | 2 | **0** |

Байты, кодовые точки и колонки — три разные величины, и они не совпадают.

Настоящие интерфейсы хранят **кодовую точку** вместо байта, считают ширину отображения отдельно и обрабатывают **кластеры графем**, где несколько кодовых точек образуют один видимый символ.

Та же беда встречалась в курсе раньше: `printf("%-16s")` выравнивает по байтам, и русские подписи ломали колонки. Причина одна и та же, только проявляется на другом уровне.

Лечится она тоже одинаково: ячейка хранит символ целиком, а курсор двигается на его ширину. Разбор UTF-8 и таблица ширин разобраны в s05e08 — здесь они прикладываются к сетке экрана. Остаётся честная оговорка: ширина эмодзи и составных графем определена нестрого, и полного решения не существует ни у одного терминала.

## 6. Событийный цикл

```
цикл: читать ввод (неблокирующе)
      обновить состояние
      отрисовать в буфер
      вывести разницу
```

Ввод читают в сыром режиме через `read()` либо через `poll()` с таймаутом — чтобы одновременно ждать и клавиши, и данные из сокета.

Отдельно обрабатывают **сигнал изменения размера окна**: буфер надо пересоздать и перерисовать всё целиком. Обработчик при этом подчиняется правилам из s07e08 — только флаг, вся работа в основном цикле.

Тонкость с клавишами: стрелки и функциональные клавиши приходят как **последовательности** из нескольких байт, начинающиеся с ESC. Отличить нажатие Escape от начала последовательности можно только по таймауту — отсюда задержка при выходе из некоторых программ по Escape.

## 7. C++ как опция сезона

Интерфейс — самый естественный кандидат на объектную структуру: виджеты просятся в классы с виртуальным методом отрисовки, контейнеры избавляют от фиксированных размеров, а автоматическое управление ресурсами гарантирует восстановление режима терминала в деструкторе.

Полезное упражнение — переписать фреймворк на C++ и сравнить, что стало выразительнее, а где появились скрытые выделения памяти.
