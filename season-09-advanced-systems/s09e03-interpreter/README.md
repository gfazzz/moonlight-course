## Теория: разбирать ≠ исполнять

### Два флага вместо одного

Функции разбора принимают признак исполнения:

```c
block(L, exec && cond);      /* тело if: только при истине */
block(L, exec && !cond);     /* тело else: только при лжи  */
```

Невыбранная ветвь **разбирается**, но не исполняется. Разбирается — потому что иначе поток токенов собьётся и следующий оператор начнёт читаться с середины предыдущего.

Это тот же принцип, что у логических операторов в C: правая часть `&&` вычисляется только при необходимости.

### Цикл читает текст несколько раз

```c
size_t cond_pos = L->pos;      /* запомнили начало условия */
for (;;) {
    L->pos = cond_pos;         /* вернулись и перечитали   */
    long cond = expr(L, exec);
    block(L, exec && cond);
    if (!cond) return;
}
```

`while` — единственная конструкция в языке, где один и тот же текст обрабатывается многократно.

В интерпретаторе по дереву этой возни нет: узел цикла хранит поддеревья условия и тела, и обходить их можно сколько угодно. Наш однопроходный вариант компактнее, но платит именно здесь — хороший повод понять, зачем вообще строят дерево.

### Предел итераций

```c
if (++iters > MAX_ITERS) { runtime_error("вечный цикл"); }
```

Не каприз. Интерпретатор чужих скриптов обязан уметь остановиться: один битый конфиг иначе вешает систему целиком.

### Два класса ошибок

| | Когда | Пример |
|---|---|---|
| синтаксическая | до запуска | незакрытая скобка |
| времени выполнения | во время | обращение к неопределённой переменной |

Вторая строка синтаксически безупречна: программа разбирается, но не может быть исполнена. Языки со статической типизацией переносят часть таких ошибок в компиляцию — отдельным этапом проверки типов, которого у нас нет.

## Проверка: LUNA задаёт вопросы
```
[LUNA] Два вопроса про исполнение.
```

**1.** LUNA: «Почему нельзя вычислить обе ветви и вернуть нужную?»

<details><summary>Ответ</summary>

Из-за побочных эффектов. Обе ветви присвоят переменные и напечатают свой текст, а вернётся только одно значение — остальное уже произошло и отменить это нельзя. В чистой арифметике лишнее вычисление стоило бы только времени, но как только в языке появилось состояние, оно стало давать неверный результат. Тот же принцип действует в C для операторов `&&` и `||`: правая часть вычисляется только при необходимости, и это не оптимизация, а часть семантики — на ней строится идиома `p != NULL && p->x`.
</details>

**2.** LUNA: «Если невыбранная ветвь не исполняется, зачем её вообще разбирать?»

<details><summary>Ответ</summary>

Чтобы не потерять место в потоке токенов. Разборщик обязан пройти текст ветви целиком и остановиться ровно там, где она заканчивается, — иначе следующий оператор начнёт читаться с середины пропущенного блока, и дальше поедет всё. Формулировка правила: разбираем всегда, исполняем по условию. В интерпретаторе по дереву проблема не возникает вовсе, потому что разбор уже завершён и структура известна — но у нас разбор и исполнение идут одним проходом.
</details>

## Разбор типичных ошибок

1. **Вычисляются обе ветви.** Побочные эффекты сработают дважды.
2. **Пропускаемая ветвь не разбирается.** Поток токенов собьётся.
3. **Цикл не возвращает позицию.** Условие проверится один раз.
4. **Нет предела итераций.** Битый скрипт повесит интерпретатор.
5. **Повторное присваивание добавляет новую переменную.** Окружение растёт, читается старое значение.
6. **`print` печатает после ошибки.** Выполнение должно остановиться.
