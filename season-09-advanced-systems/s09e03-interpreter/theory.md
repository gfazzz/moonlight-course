# Теория — s09e03

## 1. Что добавляет исполнение

> *— Формулу можно вычислять сколько угодно раз, ответ не изменится. Действие — ровно столько, сколько нужно. Разница между этими двумя вещами и есть разница между калькулятором и программой.*

Арифметика из прошлой серии была **чистой**: одно и то же выражение всегда даёт один результат, порядок вычислений не важен, лишнее вычисление стоит только времени.

Настоящий язык вводит состояние:

| Появляется | Следствие |
|---|---|
| окружение «имя → значение» | результат зависит от истории |
| побочный эффект присваивания | порядок начинает иметь значение |
| вывод | лишнее вычисление становится видимым |
| ошибки времени выполнения | синтаксически верная программа может не исполниться |

Последняя строка вводит новый класс ошибок. Обращение к неопределённой переменной безупречно с точки зрения грамматики — проблема обнаруживается только при исполнении.

## 2. Отложенное вычисление ветвей

Наивная реализация:

```c
long a = eval(then_branch);      /* НЕПРАВИЛЬНО */
long b = eval(else_branch);
return cond ? a : b;
```

Вычисляются обе ветви. С чистой арифметикой это лишь трата времени; с побочными эффектами — неверный результат: обе присвоят переменные, обе напечатают текст.

Правильно — исполнять только выбранную. В однопроходной реализации это делается флагом:

```c
block(L, exec && cond);        /* тело if   */
block(L, exec && !cond);       /* тело else */
```

Невыбранная ветвь **разбирается**, но ничего не делает: разборщик обязан пройти её текст целиком, иначе потеряет место в потоке токенов.

Формулировка правила: **разбираем всегда, исполняем по условию**.

Тот же принцип в C для `&&` и `||` — и это не оптимизация, а часть семантики языка. На нём стоит идиома `p != NULL && p->field`, которая при вычислении обеих частей падала бы.

## 3. Цикл требует возврата назад

```c
size_t cond_pos = L->pos;
for (;;) {
    L->pos = cond_pos;
    long cond = expr(L, exec);
    block(L, exec && cond);
    if (!cond) return;
}
```

`while` — единственная конструкция, где один и тот же текст обрабатывается многократно.

В интерпретаторе по дереву проблемы нет: узел цикла хранит поддеревья условия и тела, обходить их можно сколько угодно раз. Однопроходная реализация компактнее, но платит именно здесь — и это хороший ответ на вопрос, зачем вообще строят дерево.

Разница проявляется и в производительности: однопроходный интерпретатор **заново лексирует** тело цикла на каждой итерации. При тысяче итераций текст разбирается тысячу раз.

**Предел итераций** — обязательная мера, а не удобство:

```c
if (++iters > MAX_ITERS) runtime_error("вечный цикл");
```

Интерпретатор чужих скриптов должен уметь остановиться. Тот же принцип применяют в реальных песочницах, добавляя к нему пределы по памяти и по времени.

## 4. Окружение и области видимости

У нас окружение плоское — все переменные глобальны. В настоящих языках это цепочка:

```
локальное -> охватывающее -> глобальное
```

Поиск идёт от ближайшего к дальнему; так работают лексические области видимости и замыкания.

Добавить в MOON функции — значит завести стек окружений, где каждый вызов создаёт своё, а поиск проваливается наружу. И сразу возникает вопрос **времени жизни**: замыкание может пережить вызов, создавший его окружение.

Отсюда потребность в сборке мусора — подсчёт ссылок либо обход достижимых объектов. Ровно с этого места «маленький язык» становится большим проектом, и авторы учебных интерпретаторов обычно останавливаются перед ним.

Реализация окружения тоже не так проста, как выглядит. Линейный поиск по массиву приемлем при десятке переменных; дальше нужна хеш-таблица — та самая, что писалась в Season 4.

## 5. Дерево, байткод, машинный код

Наш интерпретатор обходит структуру напрямую. Прост, но медленный: каждый шаг — разыменование указателей и ветвление по типу узла, что плохо ложится на предсказатель переходов процессора.

| Подход | Скорость | Примеры |
|---|---|---|
| обход дерева | ×1 | учебные интерпретаторы, ранний Ruby |
| байткод и виртуальная машина | ×5–20 | Python, Lua, JVM, CPython |
| компиляция на лету | ×50–500 | V8, LuaJIT, PyPy, HotSpot |
| опережающая компиляция | ×100–1000 | C, Rust, Go |

Переход к байткоду ближе, чем кажется: постфиксный обход дерева из s09e02 — это уже почти последовательность инструкций стековой машины.

Компиляция на лету добавляет к этому наблюдение за исполнением: горячие участки определяются счётчиками, компилируются в машинный код и специализируются под фактические типы. Отсюда парадокс — динамический язык с хорошей такой компиляцией может обгонять статический без неё.

## 6. Два класса ошибок

| | Когда обнаруживается | Пример |
|---|---|---|
| лексическая | при разборе слов | недопустимый символ |
| синтаксическая | при разборе структуры | незакрытая скобка |
| семантическая | между разбором и исполнением | несовпадение типов |
| времени выполнения | при исполнении | деление на ноль |

Третья строка у нас отсутствует: в MOON нет типов, и проверять нечего. В языках со статической типизацией это отдельный этап, переносящий часть ошибок из четвёртой строки в третью — то есть из эксплуатации в компиляцию.

Смысл статической типизации ровно в этом переносе. Спор о ней — это спор о том, стоит ли раннее обнаружение накладываемых ограничений.
