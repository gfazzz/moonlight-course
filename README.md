## Что это

Не учебник с упражнениями, а **сериал, в котором задачи — часть сюжета**. Каждая серия: сцена, теория, задача, зелёный тест, клиффхенгер. Код, который ты пишешь, действительно нужен герою — расшифровать сообщение, перехватить трафик, поймать манипуляцию на бирже, посчитать окно связи со спутником.

Три отличия от обычных курсов:

**LUNA — тьютор, который существует на самом деле.** В сюжете это ИИ Виктора. В реальности — чат Cursor рядом с твоим кодом. Обращаясь к LUNA, ты обращаешься к настоящему ассистенту, и курс учит спрашивать «почему», а не «сделай за меня». В Season 8 ты **пишешь LUNA сам**. Границы наставника и разбор зелёных и красных запросов — в [`docs/LUNA.md`](docs/LUNA.md).

> **Режим — `Ask`, а не `Agent`.** Это важнее, чем кажется. В режиме `Agent` ассистент сам правит файлы: серия окажется решённой, а ты не напишешь ни строки и ничего не поймёшь. В режиме `Ask` он только отвечает — объясняет, разбирает ошибку, показывает пример на другой задаче, — а код пишешь ты. Курс рассчитан именно на это.

**Ничего не выбрасывается.** Артефакты серий собираются в сквозной проект сезона, а проекты поздних сезонов **линкуются с модулями ранних**: хеш из Season 4 работает индексом тикеров в Season 5 и адресацией устройств в Season 6.

**Числа честные.** Всё, что звучит в тексте, получено кодом серии: CRC-16 совпадает с эталоном Modbus, период орбиты 7000 км — 97.1 минуты, перцептрон на XOR даёт ровно 50%, потому что иначе не может.

## Быстрый старт

Нужны `gcc` (или `clang`), `make` и [Cursor](https://cursor.com) — ради LUNA. Подойдёт и VS Code, но тогда тьютора придётся заменить любым ИИ-чатом.

```bash
git clone https://github.com/<your>/moonlight-course.git
cd moonlight-course

cd season-01-foundations/s01e01-strange-message
cat README.md          # сцена, теория, задача
```

> **Читай `README.md`, `mission.md` и `theory.md` в режиме предпросмотра, а не в редакторе.**
> `Cmd+Shift+V` (macOS) или `Ctrl+Shift+V` — предпросмотр во вкладке; `Cmd+K V` — сбоку от кода.
> Так работают таблицы и **сворачиваемые ответы** в блоке «Проверка на канале».
> В Cursor не используй кнопку `Preview` в тулбаре — её урезанный рендерер не сворачивает спойлеры.

### Как проходить серию

```bash
cp starter.c artifacts/parse.c     # каркас → твой рабочий файл
# ... пишешь код, спрашиваешь LUNA (режим Ask!) ...
make test                          # зелёный тест = серия пройдена
```

- **`starter.c`** — каркас с интерфейсом. К поздним сезонам подсказок всё меньше: в Season 10 остаётся только брифинг.
- **`artifacts/`** — твой код. Подробности ниже.
- **`solution/`** — эталон. Открывай после честной попытки: чужое решение полезно, только когда своё уже болит.
- **`mission.md`** — ТЗ и критерии приёмки. **`theory.md`** — теория вглубь и книги.

```bash
make test        # в папке серии — одна серия
make test        # в папке сезона — все 8 серий + сквозной проект
make test        # в корне — весь курс
make projects    # запустить сквозные проекты всех сезонов
make progress    # где ты сейчас: сколько серий пройдено и какая следующая
```

### Твой код и git

Форкни репозиторий и работай в своей ветке — **исходники в `artifacts/` отслеживаются намеренно**:

```bash
git checkout -b my-run
# ... проходишь серии ...
git add season-01-foundations/s01e01-strange-message/artifacts/
git commit -m "s01e01: первый байт"
```

Зачем: за курс ты напишешь 80 программ. История прохождения — это возможность откатиться, сравнить своё решение трёхмесячной давности с сегодняшним и не потерять всё при переустановке системы. Плюс наглядное портфолио.

Что при этом **не** попадает в git: собранные бинарники, `.o`, дампы, `notes.md` — их ловит `.gitignore`. Отслеживаются только `*.c`, `*.h` и `*.md` внутри `artifacts/`.

Конфликтов при обновлении курса не будет: в апстриме эти папки пустые, git о твоих файлах с той стороны просто не знает.

```bash
git fetch upstream && git rebase upstream/main   # твои решения на месте
```

Одно правило: **если делаешь pull request в курс — заводи ветку от чистого `main`**, а не от рабочей. Иначе в PR уедут твои решения; CI такое отклонит.

## Сквозные проекты

К концу каждого сезона артефакты серий собираются в работающую программу. Проекты поздних сезонов **используют модули ранних** — не копипастой, а через заголовки и линковку:

```make
$(CC) -I$(S4) -I$(S6) -I$(S8) -I$(S9) -o moonlight_core \
      $(S4)/ml_hash.c $(S6)/ml_crc.c $(S8)/ml_stats.c $(S9)/ml_kalman.c main.c
```

```bash
cd season-10-final-mission/project
make modules     # из чего собрана программа
make run
```

Финальный `moonlight_core` линкует пять единиц трансляции из четырёх сезонов. Тесты проектов проверяют **сам факт сборки**: что реализации лежат в своих сезонах, а не скопированы.

## Как поучаствовать

Твои решения живут в твоей ветке (см. [«Твой код и git»](#твой-код-и-git)). Улучшения **самого курса** — отдельной веткой от чистого `main`: исправил ошибку в теории, уточнил формулировку, добавил пример, поймал неверное число в тесте.

```bash
git checkout main
git checkout -b fix/s05e03-ema-formula
# ... правишь ...
make test                      # проверь, что ничего не сломалось
git commit -am "fix(s05e03): уточнить формулу EMA"
git push origin fix/s05e03-ema-formula
```

Дальше — pull request. Две проверки в CI: весь курс должен оставаться зелёным на Linux и macOS, и PR не должен содержать файлов из `artifacts/`. Требования к коду и стилю текста — в [CONTRIBUTING.md](CONTRIBUTING.md).

## Требования

- `gcc` или `clang`, `make`
- macOS, Linux или WSL
- Cursor (для LUNA) — рекомендуется
- Все задачи собираются **без внешних библиотек**, включая `-lm`: `sqrt`, `exp`, ГПСЧ написаны вручную ради воспроизводимости на любой машине
