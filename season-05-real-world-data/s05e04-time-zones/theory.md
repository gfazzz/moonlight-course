# s05e04 — Теория: момент, календарь, пояс

> Серия про то, что «время» в программе — это три разных объекта, и почти все ошибки берутся из их смешения.

---

## 1. Три объекта

| Объект | Что это | Однозначен? |
|---|---|---|
| **момент** | точка на оси, одна для всех наблюдателей | да |
| **календарная дата** | человеческая запись: год, месяц, день, часы | нет — без пояса это текст |
| **пояс** | правило перевода между ними | меняется во времени |

Третья строка — источник большинства неприятностей. Правило перевода определяется не астрономией, а решением законодателя, и меняется задним числом: в 2011 году Россия отменила переход на летнее время, в 2014-м сдвинула шкалу на час, Египет вводил и отменял переход четырежды за десятилетие. База IANA обновляется несколько раз в год.

Практический вывод: **хранить нужно момент**. Момент не устаревает. Местная запись — производная от него, и пересчитывается при показе.

Исключение — будущие события, привязанные к местному времени. «Совещание в 10:00 по Нью-Йорку через год» нельзя хранить моментом: если правила изменятся, момент останется прежним, а совещание уедет. Такие события хранят как «местная дата + идентификатор пояса», и это единственный случай, когда так правильно.

## 2. Эпоха

```c
typedef int64_t timestamp;    /* секунды от 1970-01-01 00:00:00 UTC */
```

Почему не 32 бита: `int32_t` секунд переполняется 19 января 2038 года. Это не отдалённая гипотеза — тридцатилетние финансовые инструменты уже упираются в эту дату.

Почему секунды, а не миллисекунды: вопрос области. Биржевым данным нужны наносекунды, бухгалтерии хватает секунды. Важно выбрать единицу один раз и не смешивать — та же дисциплина, что с деньгами в s05e02.

Отдельно: секунды эпохи **не считают високосных секунд**. Шкала намеренно устроена так, что в сутках ровно 86400 секунд; високосная секунда «размазывается» или повторяется в зависимости от реализации. Для финансовых расчётов это не важно, для астрономии — важно, и там используют другие шкалы.

## 3. Календарь арифметикой

Перевод даты в число дней делается без циклов и таблиц. Идея — сдвинуть начало года на март:

```c
y -= (m <= 2);
```

Тогда 29 февраля становится **последним** днём такого года, и номер дня в году считается одной формулой для всех месяцев:

```c
doy = (153 * (m + (m > 2 ? -3 : 9)) + 2) / 5 + d - 1;
```

Множитель `153/5 = 30.6` — средняя длина месяца в схеме, где после марта месяцы чередуются 31, 30, 31, 30… Формула точно воспроизводит эту последовательность.

Дальше — счёт в эрах по 400 лет:

```
146097 дней = 400 лет = 400*365 + 97 високосных
```

Григорианский календарь повторяется ровно через этот период, поэтому вся арифметика сводится к «номер эры» и «день в эре».

### Деление вниз, а не к нулю

```c
int64_t days = t / 86400, rem = t % 86400;
if (rem < 0) { rem += 86400; days -= 1; }
```

Целочисленное деление в C округляет **к нулю**: `-1 / 86400` даёт `0`. Значит, момент за секунду до эпохи попадёт в 1 января 1970 года вместо 31 декабря 1969-го. Ошибка проявляется только на датах до 1970 года и потому живёт в коде годами.

### Високосный год

```c
leap = (y % 4 == 0 && y % 100 != 0) || (y % 400 == 0);
```

1900 год не был високосным, 2000 — был. Проверка только на кратность четырём даёт правильный ответ на промежутке 1901–2099 и потому кажется работающей.

## 4. Переход на летнее время

Дважды в год местная шкала рвётся:

```
весна:  01:58  01:59  →  03:00  03:01     часа 02:xx не существовало
осень:  01:58  01:59  →  01:00  01:01     час 01:xx прожит дважды
```

Следствия:

- отображение «местное время → момент» **не биекция**: у метки может быть два прообраза или ни одного;
- сутки не всегда 86400 секунд: в дни перехода их 82800 или 90000;
- «завтра в это же время» — не «плюс 86400 секунд».

### Обратное преобразование

Прямое направление тривиально: момент → смещение → местное. Обратное содержит круг: чтобы вычесть смещение, нужно знать смещение; чтобы узнать его, нужен момент.

Круг разрывается перебором гипотез с проверкой на самосогласованность:

```c
int64_t c1 = local - std_off;
int64_t c2 = local - dst_off;
int ok1 = (offset_at(c1) == std_off);
int ok2 = (offset_at(c2) == dst_off);
```

| `ok1` | `ok2` | Смысл | Что вернуть |
|---|---|---|---|
| да | нет | зимнее время | `c1` |
| нет | да | летнее время | `c2` |
| да | да | час прожит дважды | оба момента |
| нет | нет | часа не было | ничего |

Приём обобщается: он не зависит от числа возможных смещений и работает для поясов с получасовыми и сорокапятиминутными сдвигами (Индия `+05:30`, Непал `+05:45`, Чатем `+12:45`).

### Что делать с неоднозначностью

Ошибкой это не является. Варианты обработки, в порядке убывания честности:

1. **Вернуть оба момента** и заставить вызывающего решить — так делает `java.time`, так сделано здесь.
2. **Взять более ранний** — молчаливое соглашение POSIX; работает, пока никто не заметит.
3. **Отвергнуть запись** — потеряются настоящие данные: в нашем журнале тридцать семь сделок.

Третий вариант выглядит строгим и потому соблазнительным. Он неверен: неоднозначность — свойство календаря, а не признак порчи данных.

### Несуществующее время

Здесь наоборот: если метка попала в пропавший час, она **не могла быть порождена часами этого пояса**. Варианты: метка из другого пояса, ошибка преобразования — или её записал человек.

Признак ценен именно тем, что не требует доступа к системе: он проверяется по самим данным.

## 5. Монотонные часы

Настенные часы не обязаны монотонно расти. Их переводят вручную, их подтягивает синхронизация по сети, и подтягивать она может назад.

| Часы | Что показывают | Идут назад? | Для чего |
|---|---|---|---|
| `CLOCK_REALTIME` | дату и время | да | отметить событие |
| `CLOCK_MONOTONIC` | время от произвольного нуля | нет | измерить интервал |
| `CLOCK_BOOTTIME` | то же, включая сон системы | нет | интервал через сон |

Правило: **отметить момент — настенными, измерить промежуток — монотонными.**

Замер длительности настенными часами даёт ошибку, которая проявляется редко, не воспроизводится по команде и выглядит как случайный сбой. Такие ошибки живут в коде дольше всех — по той же причине, что и невоспроизводимый вывод в s08e01.

## 6. Контекст рынка

**Метки времени на бирже.** Каждая сделка получает метку в момент исполнения; точность — микросекунды, а в высокочастотной торговле наносекунды. Регуляторы требуют синхронизации часов участников с эталоном: европейский регламент MiFID II задаёт допуск в сто микросекунд для алгоритмической торговли.

**Почему выгрузка приходит в местном времени.** Историческая инерция: биржа работает по местным часам, и торговый день в отчётах определён местной датой. Внутри систем при этом всё живёт в UTC — местное время появляется на границе, при выгрузке.

**Ночь перехода.** Американские биржи в момент осеннего перехода закрыты — переход происходит в воскресенье ночью. Но внебиржевые и круглосуточные площадки работают, и их журналы содержат удвоенный час полностью.
