## Теория: запись на диске — не запись в памяти

### Дыры

Компилятор обязан разместить поле по адресу, кратному его выравниванию. Если поля идут не по убыванию размера, между ними появляются пустые байты.

```c
struct {
    uint16_t symbol_id;   /* смещение  0 */
                          /* дыра      2..3 */
    uint32_t ts;          /* смещение  4 */
    int32_t  price;       /* смещение  8 */
    uint32_t qty;         /* смещение 12 */
    uint8_t  flags;       /* смещение 16 */
                          /* хвост    17..19 */
};                        /* sizeof == 20, полезных 15 */
```

Двадцать байт вместо пятнадцати — четверть впустую. На двенадцати миллионах записей это шестьдесят мегабайт ни за что.

Перестановка полей по убыванию размера убирает дыры **между** полями. Хвостовое выравнивание остаётся: размер структуры кратен выравниванию самого строгого поля, иначе в массиве сбилось бы выравнивание второго элемента.

Существует `#pragma pack`, убирающий и хвост. Пользоваться им для файлов не нужно: он нестандартен, а невыровненный доступ на части архитектур медленный, а на некоторых — сигнал. Правильный ход другой.

### Структуру не пишут в файл целиком

```c
fwrite(&tick, sizeof tick, 1, f);   /* так не делают */
```

Три причины:

| Что зависит от платформы | Следствие |
|---|---|
| раскладка полей | другой компилятор — другие смещения |
| порядок байтов | младший байт может оказаться последним |
| содержимое дыр | не определено; сравнение через `memcmp` бессмысленно |

Правильный способ — сериализация поле за полем, байт за байтом:

```c
static void put_u32(uint8_t *p, uint32_t v) {
    p[0] = (uint8_t)(v & 0xFF);
    p[1] = (uint8_t)(v >> 8);
    p[2] = (uint8_t)(v >> 16);
    p[3] = (uint8_t)(v >> 24);
}
```

Этот код даёт **одинаковый файл на любой платформе**, потому что сдвиги и маски определены стандартом и не зависят от того, как машина хранит числа. Приведение `(uint32_t *)p` не годится дополнительно: указатель может оказаться невыровненным, а это уже неопределённое поведение.

### Порядок байтов

Младшим байтом вперёд — «little-endian» — принято в сетевых форматах последних тридцати лет, потому что x86 и ARM хранят числа именно так и преобразование обходится бесплатно. Старшим вперёд — «big-endian», он же сетевой порядок, — остаётся в старых протоколах.

Важно не какой выбран, а что он **записан в спецификации формата** и соблюдается явно.

### Заголовок и версия

```
0..3    сигнатура "MLTK"
4..5    версия формата
6..7    байт на запись
8..11   число записей
12..15  запас
```

Три поля здесь несут разную работу:

- **сигнатура** отвечает на вопрос «это вообще наш файл?»;
- **версия** — «понимаю ли я его?»;
- **байт на запись** — «где следующая?».

Последнее — самое недооценённое. Читатель, берущий размер записи из `sizeof` своей структуры, ломается при первом же расширении формата. Читатель, берущий его из заголовка, **пропускает незнакомые байты и продолжает работать**. Это и есть совместимость вперёд.

Именно поэтому лишний байт вообще удалось заметить: файл сам сказал, какого размера его записи, и это не совпало с документацией.

### Дельта-кодирование

Временной ряд обладает свойством, которого нет у произвольных данных: соседние значения близки.

```
метки:  34205  34208  34212  34213  ...
дельты:     3      4      1  ...
цены:   18742  18741  18744  18740  ...
дельты:    -1     +3     -4  ...
```

Абсолютное значение требует четырёх байт, разность — одного. Первую запись кладут целиком как опорную точку, дальше — только разности.

Разности бывают отрицательными, а старший бит отрицательного числа — единица, и в беззнаковом виде `-1` превращается в максимальное значение. Лечится **зигзагом**: числа перекладываются так, чтобы малые по модулю оставались малыми.

```
 0 -> 0     -1 -> 1     1 -> 2     -2 -> 3     2 -> 4
```

```c
uint32_t zigzag(int32_t v) { return ((uint32_t)v << 1) ^ (uint32_t)(v >> 31); }
```

Дельта-кодирование **не теряет ничего**: это смена представления, а не сжатие с потерями. Ряд восстанавливается точно — и это свойство обязательно проверять кодом, а не рассуждением.

## Проверка на канале

```
[LUNA] Два вопроса про формат.
```

**1.** LUNA: «Почему структуру нельзя записать в файл одним `fwrite`, если читать её будет та же программа?»

<details><summary>Ответ</summary>

Потому что «та же программа» — это ненадолго. Она будет пересобрана другим компилятором, другой версией того же компилятора, под другую архитектуру или с другими ключами выравнивания, и раскладка полей изменится. Файл, записанный вчера, перестанет читаться сегодня — молча, с правдоподобными числами.

Три вещи, зависящие от платформы: раскладка полей (смещения и дыры), порядок байтов внутри числа и содержимое дыр. Последнее означает вдобавок, что записанный файл будет содержать неопределённые байты — а значит, две записи одной и той же логической величины могут отличаться побайтово.

Сериализация поле за полем через сдвиги и маски даёт один и тот же файл везде. Это не педантизм: формат — договор с будущим, а будущее собирается другим компилятором.
</details>

**2.** LUNA: «Зачем в заголовке размер записи, если он и так известен из структуры?»

<details><summary>Ответ</summary>

Затем, чтобы читатель старой версии не сломался о файл новой.

Если размер берётся из `sizeof`, то читатель версии 1, встретив файл версии 2, начнёт разбирать записи со сдвигом: пятнадцать байт вместо шестнадцати, и со второй записи всё поедет. Причём поедет **правдоподобно**: числа останутся числами, просто неверными.

Если размер берётся из заголовка, читатель разбирает известные ему поля, пропускает остаток записи и переходит к следующей по правильному смещению. Незнакомое поле теряется — но данные остаются целыми, и об этом можно сообщить.

Здесь это дало ещё один эффект: именно несовпадение размера из заголовка с размером из документации показало, что в формате есть недокументированное поле.
</details>

## Разбор типичных ошибок

1. **`fwrite` структуры целиком.** Файл перестанет читаться при смене компилятора.
2. **Приведение `(uint32_t *)p` вместо сдвигов.** Невыровненный доступ — неопределённое поведение, и на части архитектур это не теория.
3. **`p[3] << 24` без приведения к `uint32_t`.** Байт продвинется до `int`, и сдвиг на 24 у знакового типа даст переполнение.
4. **Сравнение записей через `memcmp`.** В дырах лежит неизвестно что; совпадение на своей машине ничего не доказывает.
5. **Размер записи берётся из `sizeof`, а не из заголовка.** Читатель сломается о первое же расширение формата.
6. **Дельты пишутся без зигзага.** Первая же отрицательная разность займёт четыре байта вместо одного.
7. **`v >> 31` для знакового `v` считается определённым.** Сдвиг вправо отрицательного числа реализационно-зависим; в зигзаге это работает по соглашению, но приведение к беззнаковому надёжнее.
8. **Опорная точка не сохранена.** Ряд из одних разностей восстановить невозможно.
9. **Временный файл с фиксированным именем.** Два экземпляра на одной машине подерутся — та же ошибка, что в s07e03.
