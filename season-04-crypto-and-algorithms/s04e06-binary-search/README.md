## Теория: отсекать половину

### Алгоритм

```c
size_t lo = 0, hi = n;              /* полуинтервал [lo, hi) */
while (lo < hi) {
    size_t mid = lo + (hi - lo) / 2;
    steps++;
    if (a[mid] == key) return (long)mid;
    if (a[mid] <  key) lo = mid + 1;
    else               hi = mid;
}
return -1;
```

Четыре детали, каждая из которых ломается, если сделать иначе.

**`lo + (hi - lo) / 2`, а не `(lo + hi) / 2`.** Сумма может переполниться. Ошибка прожила в стандартной библиотеке Java девять лет и была описана Джошуа Блохом в 2006 году под заголовком «почти все реализации двоичного поиска сломаны».

**Полуинтервал `[lo, hi)`.** Правая граница исключена — тогда `hi = mid` не требует вычитания единицы, а `hi - lo` сразу даёт число оставшихся элементов. Меньше мест, где можно ошибиться на единицу.

**`lo = mid + 1`, а не `lo = mid`.** Без прибавления цикл зациклится, когда останется два элемента.

**Условие `lo < hi`.** При `lo <= hi` с полуинтервалом получится обращение за границу.

### Сложность

Каждый шаг уменьшает диапазон вдвое. Через `k` шагов остаётся `n / 2^k` элементов; поиск заканчивается при единице, откуда `k = log₂ n`.

Логарифм растёт настолько медленно, что для практических целей это почти константа: удвоение данных добавляет **один** шаг.

### Когда двоичный поиск не подходит

| Условие | Почему |
|---|---|
| данные не отсортированы | требуется порядок |
| данные меняются часто | поддержание сортировки дороже выигрыша |
| нет произвольного доступа | связный список — переход в середину сам O(n) |
| элементов мало | линейный проще и с лучшей локальностью |

Третья строка объясняет, почему двоичный поиск работает на массиве и не работает на списке. А если данные постоянно меняются — берут дерево или хеш-таблицу, смотря нужен ли порядок.

**1.** LUNA: «Чем `(lo + hi) / 2` хуже, чем `lo + (hi - lo) / 2`?»

<details><summary>Ответ</summary>

Тем, что сумма может переполниться. При больших индексах `lo + hi` выходит за диапазон типа: для знакового `int` результат становится отрицательным, что даёт обращение по отрицательному индексу. Форма `lo + (hi - lo) / 2` математически та же, но промежуточный результат всегда помещается. Ошибка была в реализации двоичного поиска в стандартной библиотеке Java девять лет и вскрылась только на массивах длиннее миллиарда — до этого её просто нечем было воспроизвести.
</details>

**2.** LUNA: «Сортировка стоит O(n log n), поиск даёт O(log n). Когда это окупается?»

<details><summary>Ответ</summary>

Когда поисков много. Один поиск по неотсортированным данным стоит O(n), что дешевле сортировки. Но `m` поисков стоят `O(mn)` против `O(n log n + m log n)` — второе выгоднее уже при небольшом `m`. Для 2.8 миллиона записей и сорока семи запросов сортировка окупается многократно. Правило общее: разовую операцию не оптимизируют предобработкой, повторяющуюся — почти всегда.
</details>

## Разбор типичных ошибок

1. **`(lo + hi) / 2`.** Переполнение на больших индексах.
2. **`lo = mid` вместо `lo = mid + 1`.** Бесконечный цикл на двух элементах.
3. **Смешение полуинтервала и отрезка.** Либо `[lo, hi)` с `hi = mid`, либо `[lo, hi]` с `hi = mid - 1`; смешивать нельзя.
4. **`size_t` и `hi = mid - 1` при `mid == 0`.** Беззнаковое переполнение даёт огромное число.
5. **Поиск на неотсортированных данных.** Вернёт «не найдено» для существующего элемента.
6. **Шаги считаются только при успехе.** Неуспешный поиск тоже стоит шагов, и их надо показать.
