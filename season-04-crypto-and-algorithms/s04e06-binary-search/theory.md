# Теория — s04e06

## 1. Вопрос, который отсекает половину

> *— Ты играл в «угадай число от одного до тысячи»?*
> *— За десять вопросов.*
> *— За десять. Не за тысячу. Потому что каждый вопрос отсекал половину, а не одного кандидата.*

Идея старше информатики: вавилонские таблички второго тысячелетия до нашей эры уже содержат отсортированные таблицы, рассчитанные на такой поиск.

Первое описание алгоритма для компьютера — Джон Мокли, 1946 год. Первая **корректная** реализация для массивов произвольной длины опубликована в 1962-м. Шестнадцать лет между «идея очевидна» и «наконец без ошибок» — это не курьёз, а точная характеристика задачи.

Кнут писал: «хотя основная идея двоичного поиска сравнительно проста, детали могут быть на удивление коварными». Джон Бентли на семинарах давал профессиональным программистам два часа на реализацию — корректно писали около десяти процентов.

## 2. Инвариант — единственный способ не ошибиться

Все ошибки в двоичном поиске одного типа: сдвиг на единицу. Лечится не внимательностью, а явно записанным инвариантом:

> Если элемент существует, он находится в `[lo, hi)`.

Из инварианта механически следует всё остальное:

| Решение | Почему так |
|---|---|
| `hi = n` при старте | полуинтервал: `[0, n)` — весь массив |
| условие `lo < hi` | пустой диапазон означает конец |
| `lo = mid + 1` | `a[mid] < key`, значит `mid` точно не подходит |
| `hi = mid` | `a[mid] > key`, значит `mid` тоже не подходит, но он уже вне полуинтервала |

Альтернативный вариант с отрезком `[lo, hi]` требует `hi = n - 1`, условия `lo <= hi` и `hi = mid - 1`. Он тоже корректен — но **смешивать две схемы нельзя**, а именно это происходит, когда пишут по памяти.

Отдельная ловушка беззнаковых типов: при `size_t` и `mid == 0` выражение `hi = mid - 1` даёт не `-1`, а `SIZE_MAX`. Полуинтервальная схема от этого свободна — ещё одна причина предпочесть её.

## 3. Переполнение, прожившее девять лет

```c
int mid = (lo + hi) / 2;          /* ошибка */
int mid = lo + (hi - lo) / 2;     /* верно  */
```

При `lo` и `hi` около миллиарда сумма превышает диапазон `int`, результат становится отрицательным, и происходит обращение по отрицательному индексу.

Эта ошибка была в `java.util.Arrays.binarySearch` с 1997 по 2006 год. Обнаружил её Джошуа Блох — тот самый человек, который эту реализацию и написал, — и опубликовал заметку с заголовком «почти все реализации двоичного поиска и сортировки слиянием сломаны».

Урок из заметки важнее самой ошибки: код был **доказан** корректным, прошёл ревью, работал в стандартной библиотеке девять лет. Не проявлялся он потому, что массивов на миллиард элементов в 1997 году просто не бывало.

> «Ошибка проявится, только когда данные вырастут. А данные растут всегда.»

## 4. Логарифм на практике

```
n = 2^k  ⟹  k = log₂ n шагов
```

| n | Шагов | Комментарий |
|---|---|---|
| 10³ | 10 | |
| 10⁶ | 20 | |
| 10⁹ | 30 | все люди на Земле |
| 10¹² | 40 | |
| 10¹⁸ | 60 | больше, чем есть данных у кого-либо |

Удвоение объёма добавляет **один** шаг. Практически логарифм — это константа с очень медленным ростом, и именно поэтому логарифмические структуры доминируют там, где данных много.

Оборотная сторона: у двоичного поиска **плохая локальность**. Прыжки по массиву дают промах кэша почти на каждом шаге, тогда как линейный проход читает память последовательно и работает на скорости упреждающей выборки. На массивах до нескольких десятков элементов линейный поиск быстрее, несмотря на худшую асимптотику.

Отсюда практический приём: двоичный поиск до маленького диапазона, дальше линейный. Так устроены реализации в промышленных библиотеках.

## 5. Родственники, которые нужны чаще, чем кажется

Чистый «найти элемент» на практике требуется реже, чем его варианты:

```c
lower_bound(a, n, key)   /* первый элемент >= key */
upper_bound(a, n, key)   /* первый элемент >  key */
```

Через них выражаются запросы, ради которых данные и сортируют:

- **сколько элементов равно `key`** — `upper − lower`;
- **все элементы в диапазоне `[x, y]`** — `lower(x) … upper(y)`;
- **куда вставить, сохранив порядок** — `lower_bound`.

Обобщение ещё шире: двоичный поиск работает не только по массиву, а **по любому монотонному предикату**. Если функция `f(x)` при росте `x` один раз меняется с «ложь» на «истину», границу можно найти за логарифм:

```c
while (lo < hi) { mid = lo + (hi-lo)/2; if (pred(mid)) hi = mid; else lo = mid+1; }
```

Отсюда «двоичный поиск по ответу» — приём для задач вида «найти минимальное значение параметра, при котором решение существует». Он не про массивы вообще.

## 6. Что использовать вместо

| Задача | Структура |
|---|---|
| статические данные, нужен порядок | отсортированный массив + двоичный поиск |
| частые вставки, нужен порядок | сбалансированное дерево, O(log n) |
| порядок не нужен | хеш-таблица, O(1) |
| данные на диске | B-дерево — минимум обращений к диску (Season 9) |
| очень много данных, допустимы ложные срабатывания | фильтр Блума |

Строка про B-дерево объясняет, почему индексы баз данных устроены именно так: двоичный поиск делает `log₂ n` обращений, а B-дерево с ветвлением 100 — `log₁₀₀ n`, то есть втрое-вчетверо меньше. При стоимости обращения к диску в миллион раз выше памяти это решающий фактор.

## 7. Как проверять реализацию

Двоичный поиск — классический случай, где обычные тесты пропускают ошибку, а свойства ловят:

```c
/* найденный элемент действительно равен искомому */
if (idx >= 0) assert(a[idx] == key);

/* если не найдено — элемента действительно нет */
if (idx < 0) for (i = 0; i < n; i++) assert(a[i] != key);
```

Это сравнение с наивной реализацией на случайных данных — **property-based тестирование** в чистом виде. Оно ловит ошибки на единицу, которые ручные тесты пропускают: те обычно проверяют середину, а ломается на границах — первом элементе, последнем, отсутствующем меньше всех, отсутствующем больше всех, пустом массиве.

Тот же приём — проверять свойство, а не заученное значение — будет отдельной темой в финале курса.
