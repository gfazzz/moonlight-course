## Теория: отпечаток вместо копии

### Две функции

```c
uint32_t djb2(const char *s) {
    uint32_t h = 5381;
    while (*s) h = h * 33 + (unsigned char)*s++;
    return h;
}

uint32_t fnv1a(const char *s) {
    uint32_t h = 2166136261u;
    while (*s) { h ^= (unsigned char)*s++; h *= 16777619u; }
    return h;
}
```

Обе построены на одном принципе: **накопить состояние, смешивая его с каждым байтом**. Различаются порядком операций — djb2 умножает, потом прибавляет; FNV-1a сначала складывает по модулю два, потом умножает. Второй порядок даёт заметно лучшее перемешивание, и это видно на выводе задачи.

Константы не случайны: `33` в djb2 и `16777619` в FNV подобраны экспериментально. Дэниел Бернстайн честно писал, что не знает, почему `33` работает лучше многих других чисел, — просто работает.

### Приведение к `unsigned char` обязательно

```c
h = h * 33 + (unsigned char)*s;      /* верно   */
h = h * 33 + *s;                     /* неверно */
```

Знаковость `char` стандартом не определена. На платформах со знаковым `char` байты со старшим битом (кириллица, UTF-8, любые бинарные данные) станут отрицательными, и хеш одной и той же строки будет разным на x86 и на ARM.

Ошибка нередкая и крайне неприятная: она проявляется только при переносе и только на определённых данных.

### Лавинный эффект

Хорошая хеш-функция меняет примерно **половину выходных битов** при изменении одного входного:

```
"MOONLIGHT" -> 0x608EDF96
"MOONLIGHu" -> совершенно другое значение, а не соседнее
```

Свойство критично: без него похожие ключи попадают в соседние корзины таблицы, и она вырождается.

### Коллизии неизбежны

Строк бесконечно много, значений `uint32_t` — четыре миллиарда. Значит, разные входы обязаны иногда давать одинаковый выход — это принцип Дирихле, а не дефект реализации.

Вопрос не в том, есть ли коллизии, а в том, **насколько трудно их найти намеренно**. Для хеш-таблицы достаточно, чтобы они были редки; для криптографии нужно, чтобы их нельзя было построить.

**1.** LUNA: «Почему хеш — не шифрование?»

<details><summary>Ответ</summary>

Потому что у него нет обратной операции и не должно быть. Шифр обязан быть обратимым — иначе получатель не прочитает сообщение; хеш необратим по построению, из отпечатка данные не восстановить. И назначение разное: шифр отвечает на вопрос «кто может прочитать», хеш — на вопрос «изменилось ли». Это два разных инструмента, и подменять один другим бессмысленно в обе стороны.
</details>

**2.** LUNA: «Приведение к `unsigned char` — формальность?»

<details><summary>Ответ</summary>

Нет. Знаковость `char` стандартом не определена: на x86 он обычно знаковый, на ARM — беззнаковый. Для байтов со старшим битом — а это вся кириллица в UTF-8 и любые бинарные данные — знаковый `char` даст отрицательное значение, и хеш одной и той же строки на двух платформах окажется разным. Хеш-таблица, сохранённая на одной машине, не прочитается на другой.
</details>

## Разбор типичных ошибок

1. **`char` без приведения к беззнаковому.** Разные результаты на разных платформах.
2. **Знаковый тип для накопителя.** Переполнение знакового — неопределённое поведение; нужен `uint32_t`.
3. **Неверная начальная константа.** `5381` и `2166136261` — часть определения функций.
4. **Перепутан порядок в FNV-1a.** Сначала `^=`, потом `*=`; обратный порядок — это FNV-1, и он хуже.
5. **Печать через `%d`.** Нужен `%08X` для беззнакового с шириной.
