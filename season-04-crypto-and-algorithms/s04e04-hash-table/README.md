## Теория: адрес вместо поиска

### Устройство

```c
typedef struct Node { char *key; int value; struct Node *next; } Node;
Node *buckets[8];                       /* массив голов цепочек */

size_t idx = hash(key) % 8;             /* адрес вычислен */
```

Массив корзин, в каждой — связный список записей, попавших в эту ячейку. Поиск: посчитать хеш, взять остаток, пройти короткую цепочку.

Обратите внимание, что для цепочек понадобился связный список из s02e04. Это не совпадение: структуры данных собираются из более простых, и именно поэтому список изучается раньше таблицы.

### Коллизии неизбежны

Ключей бесконечно много, корзин восемь. Совпадения не «случаются иногда» — они гарантированы принципом Дирихле.

Два основных способа разрешения:

| Способ | Как | Плюсы | Минусы |
|---|---|---|---|
| цепочки | список в каждой корзине | просто, работает при любом заполнении | лишняя память на указатели, промахи кэша |
| открытая адресация | искать следующую свободную ячейку | компактно, дружелюбно к кэшу | деградирует при заполнении, сложное удаление |

В задаче используются цепочки — они проще и нагляднее. Промышленные реализации чаще берут открытую адресацию именно из-за кэша.

### Коэффициент заполнения

```
α = число записей / число корзин
```

При цепочках средняя длина цепочки равна `α`. Пока `α` около единицы, поиск — константа. При `α = 100` таблица превращается в сто связных списков и работает как перебор.

Отсюда правило: при превышении порога (обычно 0.75) таблицу **перестраивают** — заводят массив вдвое больше и раскладывают всё заново. Операция дорогая, но редкая, и амортизированно доступ остаётся константным — та же логика, что с удвоением буфера в s02e06.

### Освобождение

Таблица владеет и узлами, и скопированными ключами. Освобождать надо изнутри наружу и по всем корзинам:

```c
for (size_t i = 0; i < n; i++) {
    Node *e = buckets[i];
    while (e) { Node *nx = e->next; free(e->key); free(e); e = nx; }
}
```

Порядок ровно тот же, что в s02e08: сохранить `next` до освобождения, освобождать содержимое перед узлом.

**1.** LUNA: «Почему хеш-таблица даёт O(1) в среднем, но не в худшем случае?»

<details><summary>Ответ</summary>

Потому что O(1) держится на предположении о равномерном распределении по корзинам. В худшем случае все ключи попадают в одну — тогда таблица вырождается в связный список и поиск становится O(n). Обычно так не бывает случайно, но может быть построено намеренно: зная хеш-функцию, атакующий подбирает ключи-коллизии и превращает сервис в неработающий. Защита — рандомизированное хеширование с секретом, своим у каждого процесса.
</details>

**2.** LUNA: «Коэффициент заполнения 0.75. Что произойдёт при 10?»

<details><summary>Ответ</summary>

Средняя длина цепочки станет равна десяти, и каждый поиск превратится в проход по десяти узлам, разбросанным по куче. Формально сложность останется O(1) относительно числа корзин, практически это будет перебор с плохой локальностью. Именно поэтому таблицу перестраивают при превышении порога: удваивают число корзин и перекладывают записи. Операция дорогая, но редкая — амортизированно доступ остаётся константным.
</details>

## Разбор типичных ошибок

1. **Ключ не скопирован.** Таблица хранит указатель на чужую строку; она изменится или исчезнет.
2. **Сравнение ключей по указателю.** Нужен `strcmp`: одинаковые строки могут лежать по разным адресам.
3. **Хеш совпал — значит нашли.** Коллизия даёт тот же хеш при разных ключах; сравнивать надо ключи.
4. **Освобождены узлы, забыты ключи.** Два выделения на запись — два освобождения.
5. **`% buckets` на знаковом хеше.** Отрицательный индекс; хеш должен быть беззнаковым.
6. **Вставка дубликата без проверки.** В таблице окажутся две записи с одним ключом, и найдётся всегда первая.
