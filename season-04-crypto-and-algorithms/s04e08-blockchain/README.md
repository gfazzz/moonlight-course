## Теория: связь через содержимое

### Блок

```c
typedef struct {
    uint32_t index;
    char     data[64];
    uint32_t prev_hash;
    uint32_t nonce;
    uint32_t hash;      /* от всего перечисленного выше */
} Block;
```

`hash` считается от индекса, данных, `prev_hash` и `nonce`. Изменение **любого** поля меняет отпечаток — а он записан в следующем блоке как `prev_hash`.

Отличие от связного списка принципиальное: там связь была отдельным полем и правилась независимо от данных. Здесь связь **выводится** из данных и подделать её отдельно нельзя.

### Доказательство работы

```c
do { block->nonce++; block->hash = compute_hash(block); }
while ((block->hash >> 20) != 0);      /* старшие 12 бит нулевые */
```

`nonce` — вспомогательное число, не несущее смысла. Его подбирают, пока отпечаток не удовлетворит условию.

Асимметрия здесь и есть суть:

| Действие | Стоимость |
|---|---|
| проверить условие | одно сравнение |
| подобрать `nonce` | в среднем 2¹² попыток при 12 битах |

Обойти перебор нельзя: хеш-функция устроена так, что по требуемому результату нельзя вычислить вход. Только пробовать.

Сложность регулируется числом нулевых бит. Каждый дополнительный бит **удваивает** работу: 12 бит — тысячи попыток, 20 бит — миллион, 76 бит (как в биткойне сегодня) — величина, для которой строят отдельные фабрики.

### Проверка цепи

```c
for (i = 1; i < n; i++) {
    if (chain[i].prev_hash != chain[i-1].hash)      return i;  /* связь порвана */
    if (compute_hash(&chain[i]) != chain[i].hash)   return i;  /* данные изменены */
    if ((chain[i].hash >> 20) != 0)                 return i;  /* работа не выполнена */
}
```

Три проверки, и каждая ловит своё. Первая — разрыв цепи, вторая — правку данных без пересчёта, третья — блок, вставленный без выполнения работы.

Проверка всей цепи стоит O(n) вычислений хеша, то есть мгновенна. Построение той же цепи стоило перебора на каждом блоке. Эта разница — то, ради чего конструкция существует.

## Проверка: LUNA задаёт вопросы
```
[LUNA] Последние два вопроса сезона.
```

**1.** LUNA: «Почему блокчейн защищает от подделки, если хеш-функция всем известна?»

<details><summary>Ответ</summary>

Потому что защита не в секретности, а в стоимости. Изменив блок, атакующий обязан заново подобрать `nonce` для него и **для всех последующих** — иначе связь не сойдётся. Работа растёт линейно по числу блоков после подделанного, а честная цепь тем временем продолжает расти. Догнать её надо быстрее, чем она удлиняется, — то есть иметь вычислительную мощность больше, чем у всех остальных вместе. Это и есть смысл принципа Керкгоффса: стойкость не зависит от секретности алгоритма.
</details>

**2.** LUNA: «Каждый дополнительный нулевой бит удваивает работу. Почему проверка при этом не дорожает?»

<details><summary>Ответ</summary>

Потому что проверка и подбор — принципиально разные операции. Проверить, что старшие биты нулевые, — это один сдвиг и одно сравнение, независимо от числа бит. Подобрать `nonce`, дающий такой хеш, можно только перебором, и число попыток растёт как 2^k. Асимметрия между дешёвой проверкой и дорогим построением — общий принцип, на котором стоит не только доказательство работы, но и вся асимметричная криптография.
</details>

## Разбор типичных ошибок

1. **`hash` включён в собственное вычисление.** Замкнутое определение; поле хеша в расчёт не входит.
2. **`prev_hash` не участвует в хешировании.** Связь перестаёт быть связью.
3. **Проверяется только цепь, но не сами хеши.** Данные можно изменить, пересчитав всё, — третья проверка ловит отсутствие работы.
4. **`nonce` не сбрасывается для нового блока.** Не ошибка, но результат перестаёт быть воспроизводимым.
5. **Сравнение хешей знаковыми типами.** Сдвиг вправо у знакового — расширение знака.
6. **Условие сложности как `hash < X`.** Работает, но менее наглядно; проверка старших бит явнее.
