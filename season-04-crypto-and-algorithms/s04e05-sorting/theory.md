# Теория — s04e05

## 1. Считать операции, а не секунды

> *— Не измеряй время. Время зависит от твоего ноутбука и от того, что на нём ещё крутится. Считай операции.*
> *— Но пользователю важно время.*
> *— Пользователю важно, закончится ли вообще. На это отвечают операции.*

Правило, из которого выросла вся теория сложности: **асимптотика описывает алгоритм, время описывает запуск**.

Практическая шкала, которую стоит держать в голове:

| Сложность | n = 10 | n = 1000 | n = 10⁶ |
|---|---|---|---|
| O(log n) | 3 | 10 | 20 |
| O(n) | 10 | 1 000 | 10⁶ |
| O(n log n) | 33 | 10 000 | 2·10⁷ |
| O(n²) | 100 | 10⁶ | 10¹² |
| O(2ⁿ) | 1024 | не существует | — |

Последняя строка не преувеличение: при n = 100 экспоненциальный алгоритм требует больше операций, чем атомов в наблюдаемой Вселенной.

Ключевое наблюдение из таблицы: при малых n разница неважна, при больших — определяет всё. Поэтому «на тестовых данных работало» ничего не значит, если тестовые данные были маленькими.

## 2. Сортировка вставками

```c
for (i = 1; i < n; i++) {
    key = a[i];
    for (j = i; j > 0 && a[j-1] > key; j--) a[j] = a[j-1];
    a[j] = key;
}
```

| Случай | Сравнений |
|---|---|
| лучший (отсортирован) | n − 1 |
| средний | ~n²/4 |
| худший (обратный порядок) | n(n−1)/2 |

Три свойства, за которые её держат в промышленных библиотеках:

**Адаптивность.** На почти отсортированных данных — O(n). Если каждый элемент отстоит от своего места не более чем на `k`, работа составит O(nk).

**Устойчивость.** Равные элементы сохраняют относительный порядок. Это важнее, чем кажется: сортировка по фамилии после сортировки по имени даёт список, упорядоченный по обоим полям, только если обе устойчивы.

**Работа на месте.** Дополнительной памяти O(1).

Плюс крошечная константа: нет рекурсии, нет выделений, идеальная локальность. Поэтому `std::sort`, Timsort в Python и сортировка в Java переключаются на вставки для подмассивов короче 16–32 элементов.

## 3. Сортировка слиянием

Придумана Джоном фон Нейманом в 1945 году — одна из первых нетривиальных программ вообще.

```
разделить пополам → отсортировать половины → слить
```

Рекуррентное соотношение `T(n) = 2T(n/2) + O(n)` даёт O(n log n) по основной теореме о рекуррентных соотношениях. Интуиция: `log n` уровней деления, на каждом сливается `n` элементов.

| Свойство | Значение |
|---|---|
| сложность | O(n log n) **всегда**, включая худший случай |
| память | O(n) — нужен буфер |
| устойчивость | да, если при равных брать из левой половины |
| локальность | хорошая: последовательный проход |
| параллелизуемость | отличная: половины независимы |

Строка про худший случай — главное отличие от быстрой сортировки. Merge sort не деградирует никогда, поэтому его выбирают там, где важна предсказуемость: сортировка на диске, внешняя сортировка больших файлов, реальное время.

**Устойчивость требует внимания к одному знаку:**

```c
if (left[i] <= right[j]) take_left();   /* устойчиво   */
if (left[i] <  right[j]) take_left();   /* неустойчиво */
```

При равных элементах брать надо из левой половины, потому что она была раньше в исходном массиве.

## 4. Нижняя граница: почему быстрее O(n log n) нельзя

Для сортировки **сравнениями** доказана нижняя граница Ω(n log n), и доказательство красивое.

Любой алгоритм сравнений — это дерево решений: каждое сравнение даёт два исхода. Чтобы различить все `n!` перестановок, дерево должно иметь `n!` листьев, а значит, глубину не менее `log₂(n!)`. По формуле Стирлинга `log₂(n!) ≈ n log₂ n − 1.44n`.

Отсюда: merge sort, heap sort и Timsort **асимптотически оптимальны**. Лучше — только если отказаться от сравнений.

**Сортировки без сравнений** обходят границу, используя структуру данных:

| Алгоритм | Сложность | Условие |
|---|---|---|
| подсчётом | O(n + k) | целые из диапазона `k` |
| поразрядная | O(nd) | ключи фиксированной длины `d` |
| корзинная | O(n) в среднем | равномерное распределение |

Классический пример: отсортировать миллион чисел от 0 до 999 подсчётом — один проход. Никакого противоречия с нижней границей: она относится только к алгоритмам, которые ничего не знают о данных, кроме результата сравнений.

## 5. Быстрая сортировка и почему её здесь нет

Quicksort в среднем быстрее merge sort по константе (сортирует на месте, отличная локальность), но:

- **худший случай O(n²)** при неудачном выборе опорного элемента;
- **неустойчива**;
- уязвима к намеренной атаке: зная стратегию выбора опорного, можно построить вход, дающий квадратичное поведение. В 2003 году это была реальная атака на сервисы, сортирующие пользовательские данные.

Промышленное решение — **introsort**: начинать с quicksort, считать глубину рекурсии и при превышении `2 log n` переключаться на heap sort, гарантируя O(n log n). Так устроен `std::sort` в C++.

В курсе выбран merge sort, потому что он демонстрирует «разделяй и властвуй» в чистом виде и даёт гарантию без оговорок. Quicksort и heap sort ждут в s08e04, где будет сравнение на измеренных данных.

## 6. Timsort: как это делают на самом деле

Стандартные сортировки Python и Java — Timsort, гибрид, придуманный Тимом Питерсом в 2002 году:

1. найти в массиве уже упорядоченные участки («прогоны»);
2. короткие расширить сортировкой вставками до минимальной длины;
3. слить прогоны в порядке, поддерживающем инвариант на их размеры.

Смысл в том, что **реальные данные почти никогда не случайны**: логи почти упорядочены по времени, списки почти отсортированы после небольшой правки. Timsort на таких данных приближается к O(n).

Это иллюстрация общего принципа: асимптотика в худшем случае — не единственный критерий. Алгоритм, использующий структуру реальных данных, выигрывает у теоретически равного, который её игнорирует.

## 7. Как измерять честно

```c
static long comparisons = 0;
#define CMP(a, b) (comparisons++, (a) > (b))
```

Правила, чтобы измерение было воспроизводимым:

1. **Считать операции, а не время** — число сравнений одинаково на любой машине.
2. **Обнулять счётчик перед каждым замером.**
3. **Сравнивать алгоритмы на одних данных** — копия исходного массива для каждого.
4. **Проверять несколько размеров** — одна точка не показывает характер роста.
5. **Проверять худший случай явно** — обратно отсортированный массив.

Если всё же меряется время, то многократно, с взятием минимума (а не среднего: посторонние помехи только замедляют, поэтому минимум ближе к истине).
