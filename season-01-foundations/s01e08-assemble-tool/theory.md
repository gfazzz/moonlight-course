# Теория — s01e08

## 1. Структура — это имя для набора данных

> *Последний вечер перед его отъездом. Виктор смотрит на мой код и считает вслух.*
>
> — `lat1`, `lon1`, `time1`, `lat2`, `lon2`, `time2`. Что будет на десятой точке?
> — Заведу массивы.
> — Три массива, которые обязаны быть одной длины и в одном порядке, и никто, кроме тебя, об этом не знает. Саша, у тебя есть сущность — точка. Дай ей имя.

`struct` не добавляет возможностей: те же поля можно держать врозь. Он добавляет **имя для связи между ними** — и вместе с ним компилятор, который эту связь проверит.

```c
typedef struct {
    const char   *label;
    int           len;
    unsigned char sum;
    char          text[128];
} Message;
```

`struct { ... }` описывает тип, `typedef` даёт ему псевдоним. Без псевдонима всюду писали бы `struct Message m;` — так делали до C89, и в ядре Linux делают до сих пор, считая, что слово `struct` полезно видеть глазами.

Три способа создать значение:

```c
Message a;                                  /* мусор в полях */
Message b = {0};                            /* всё обнулено */
Message c = { .label = "V", .len = 75 };    /* назначенные инициализаторы, C99;
                                               остальные поля обнуляются */
```

Второй и третий — правильные. Первый оставляет неинициализированную память, чтение которой — неопределённое поведение.

## 2. Выравнивание: откуда берутся лишние байты

```c
struct A { char a; int b; char c; };    /* sizeof == 12 */
struct B { int b; char a; char c; };    /* sizeof ==  8 */
```

Поля одинаковые, размер разный. Причина в **выравнивании**: тип с размером `N` требует адреса, кратного `N` (упрощённо, но близко к правде на x86-64 и ARM). Компилятор вставляет пропуски между полями, а в конце структуры — так, чтобы в массиве каждый следующий элемент тоже оказался выровнен.

Почему так: невыровненное чтение либо медленнее (два обращения к памяти вместо одного), либо вовсе запрещено — на некоторых ARM-платформах это аппаратное исключение.

Практические следствия:

- **порядок полей влияет на размер** — от большего к меньшему обычно плотнее;
- **`sizeof` структуры ≠ сумма `sizeof` полей**, и рассчитывать на равенство нельзя;
- **структуру нельзя вслепую накладывать на сетевой пакет или содержимое файла**: раскладка зависит от компилятора, платформы и флагов.

Последнее — самая частая ошибка при разборе бинарных форматов. `#pragma pack(1)` убирает пропуски, но делает доступ к полям невыровненным, а такой код непереносим. Правильный путь — читать поля по одному и собирать значения явно. Этим ты займёшься в Season 3.

Посмотреть смещения полей можно так:

```c
#include <stddef.h>
printf("%zu %zu\n", offsetof(Message, len), sizeof(Message));
```

## 3. Копирование структур: что происходит на самом деле

Присваивание структуры копирует **все байты**:

```c
Message a = b;      /* побайтовая копия, включая массив text[128] */
```

Это удобно и опасно одновременно. Удобно — не нужен `memcpy`. Опасно — копия **поверхностная**: если в структуре лежит указатель, копируется сам указатель, а не то, на что он указывает. Две структуры начинают ссылаться на одни данные, и первый же `free` оставляет вторую с висячим указателем.

В нашей `Message` поле `label` — как раз `const char *`. Это работает, потому что указывает на строковый литерал, живущий всё время работы программы. С динамической памятью так делать нельзя — и почему именно, ты увидишь своими глазами в Season 2.

Возврат структуры по значению стоит копирования. На современных компиляторах он часто бесплатен благодаря оптимизации возвращаемого значения, но полагаться на это не стоит: для больших структур передают указатель на буфер, который заполняет функция.

## 4. Массив структур против структуры массивов

```c
Message msgs[100];              /* array of structs — записи подряд */

struct { int len[100]; unsigned char sum[100]; } columns;  /* struct of arrays */
```

Первый вариант естественнее и лучше, когда работают с записью целиком. Второй — когда проходят по одному полю у всех записей: тогда в кэш-линию попадают только нужные данные, а не вся структура.

Разница на больших объёмах достигает кратной, и в Season 8 ты её измеришь. Сейчас достаточно знать, что выбор раскладки — это решение о производительности, а не о вкусе.

## 5. Гибкий массив в конце структуры

Приём, который встретится в реальном коде и в Season 2:

```c
typedef struct {
    size_t len;
    char   data[];      /* flexible array member, C99 */
} Buffer;

Buffer *b = malloc(sizeof(Buffer) + n);
b->len = n;
```

Заголовок и данные лежат в одном выделении — одна аллокация вместо двух, лучше локальность. До C99 то же делали через `char data[1]` и считали руками, что технически было нарушением правил.

## 6. Makefile: три вещи, которые надо понять

**Правило** — цель, зависимости, команда:

```make
moonlight_decoder: artifacts/crypto.o artifacts/decoder.o
	$(CC) $(CFLAGS) -o $@ $^
```

Отступ обязан быть **табуляцией**. Пробелы дают загадочное «missing separator» — самая известная ловушка `make`.

**Автоматические переменные** избавляют от повторов:

| Переменная | Значение |
|---|---|
| `$@` | цель |
| `$<` | первая зависимость |
| `$^` | все зависимости без дублей |

**Шаблонные правила** описывают класс целей:

```make
artifacts/%.o: artifacts/%.c
	$(CC) $(CFLAGS) -c $< -o $@
```

Что стоит добавить в любой Makefile сразу:

```make
.PHONY: clean test all
```

Без этого `make clean` не сработает, если в каталоге появится файл с именем `clean`: `make` решит, что цель уже собрана.

И зависимость от заголовков — иначе правка `crypto.h` не вызовет пересборки:

```make
CFLAGS += -MMD -MP
-include $(OBJS:.o=.d)
```
