# Теория — s01e06

## 1. Единица трансляции

> *— Сколько программ ты собираешь? — спросил Виктор, глядя на два моих файла.*
> *— Одну.*
> *— Компилятор считает, что две. Он видит их по очереди и не помнит первую, когда читает вторую. Всё, что он знает о твоей функции во втором файле, ты обязан ему сказать заголовком.*

**Единица трансляции** (translation unit) — это один `.c` со всеми подставленными заголовками. Компилятор обрабатывает их **независимо**, ничего не зная о существовании остальных. Отсюда всё устройство модулей в C.

Полный конвейер:

```
crypto.c ──препроцессор──> crypto.i ──компилятор──> crypto.s ──ассемблер──> crypto.o ─┐
                                                                                       ├─линкер─> decoder
decoder.c ─────────────────────────────────────────────────────────────────> decoder.o ┘
```

Посмотреть на любой этап можно руками — это полезнее любого объяснения:

```bash
gcc -E crypto.c            # после препроцессора
gcc -S crypto.c            # ассемблер
gcc -c crypto.c            # объектный файл
nm crypto.o                # какие символы в нём есть
```

`nm` показывает таблицу символов: `T` — функция определена здесь, `U` — используется, но определения нет (его должен дать кто-то другой). Именно по этим буквам линкер и сводит программу.

## 2. `#include` — это буквально вставка текста

Препроцессор не понимает C. Он подставляет содержимое файла в точку включения, разворачивает макросы, вырезает ветки `#ifdef` — и отдаёт результат компилятору.

Из этого следуют все правила работы с заголовками:

- `#include "file.h"` — ищет рядом с текущим файлом, потом в путях `-I`;
- `#include <file.h>` — только в системных путях;
- включение `.c` вставит **тело функции** — и оно окажется в двух объектных файлах.

Проверить, во что развернулся заголовок, можно `gcc -E`. При странных ошибках это первое, что стоит сделать: часто оказывается, что макрос из чужого заголовка переопределил ваше имя.

## 3. Header guard и его альтернатива

```c
#ifndef CRYPTO_H
#define CRYPTO_H
/* ... */
#endif
```

Механика простая: при первом включении `CRYPTO_H` не определён — содержимое проходит и макрос определяется. При втором — блок вырезается целиком.

Имя макроса должно быть уникальным в пределах всей программы, включая библиотеки. Отсюда практика префиксов: `ML_CRYPTO_H`, а не `CRYPTO_H`. Реальный случай из этого курса: константа `ML_NN_H` в нейросетевом модуле совпала с header guard того же файла — и константа молча исчезла при втором включении. Диагностировать такое неприятно.

Есть альтернатива — `#pragma once`: одна строка, поддерживается всеми основными компиляторами, но **не входит в стандарт**. Работает через идентификацию файла, из-за чего может сбоить при жёстких ссылках и сетевых файловых системах. В курсе используется классический guard.

## 4. Что класть в заголовок, а что нет

| В `.h` | В `.c` |
|---|---|
| прототипы публичных функций | тела функций |
| `typedef`, `struct`, `enum` из интерфейса | внутренние структуры |
| макросы-константы интерфейса | внутренние макросы |
| `extern int counter;` (объявление) | `int counter;` (определение) |
| | `static` функции-помощники |

Последняя строка — про **сокрытие**. `static` у функции в файле означает «видна только в этой единице трансляции»: имя не попадёт в таблицу символов, не столкнётся с чужим и не будет вызвано снаружи. Это единственный механизм инкапсуляции в C, и им стоит пользоваться по умолчанию: публичным делать то, что нужно снаружи, остальное — `static`.

Отдельная ловушка: `int counter;` в заголовке. Это **определение**, и оно попадёт в каждый включивший файл. Раньше такое иногда линковалось (общие символы), с современным `-fno-common` — честная ошибка `multiple definition`. В заголовке — только `extern`, определение — ровно в одном `.c`.

## 5. Порядок объектных файлов и библиотек

Для объектных файлов порядок в команде не важен: линкер видит все символы разом.

Для **статических библиотек** — важен, и это регулярно ставит людей в тупик:

```bash
gcc main.o -lcrypto     # правильно
gcc -lcrypto main.o     # undefined reference!
```

Линкер идёт слева направо и берёт из библиотеки только те объекты, которые нужны **уже накопленным** неразрешённым символам. Если библиотека встретилась раньше, чем тот, кто её использует, — брать было нечего.

Собрать свою библиотеку из этого модуля можно так:

```bash
ar rcs libcrypto.a crypto.o
gcc decoder.o -L. -lcrypto -o decoder
```

## 6. Инкрементальная сборка и зачем нужен `make`

Раздельная компиляция окупается на масштабе: поменял `decoder.c` — пересобирается только он, `crypto.o` остаётся. На проекте из сотен файлов это разница между секундой и минутами.

Отслеживать зависимости руками невозможно, поэтому существует `make`:

```makefile
decoder: crypto.o decoder.o
	$(CC) $^ -o $@

%.o: %.c crypto.h
	$(CC) -c $< -o $@
```

Правило простое: цель пересобирается, если она старше любой из зависимостей. Тонкость, о которой забывают: **зависимость от заголовка надо указать явно** — иначе правка `crypto.h` не вызовет пересборки, и вы получите объектные файлы, собранные по разным версиям интерфейса. Симптомы у этого крайне странные, вплоть до порчи памяти.

В больших проектах зависимости генерируют автоматически (`gcc -MMD -MP`), и это стоит завести сразу.

## 7. Модуль как единица переиспользования

Хороший модуль отвечает трём признакам:

1. **Одна ответственность.** `crypto` занимается шифрованием — не разбором файлов и не выводом.
2. **Минимальный интерфейс.** В заголовке — то, что нужно снаружи. Всё прочее `static`.
3. **Отсутствие скрытого состояния.** Глобальные переменные внутри модуля превращают его в источник сюрпризов, особенно в многопоточной программе (Season 7).

Модуль из этой серии — не учебное упражнение. Он вырастет в `season-01-foundations/lib/ml_crypto.{h,c}` и будет линковаться в `crypto_toolkit` (Season 4), `stealth_agent` (Season 7) и `moonlight_core` (финал). Проверьте сами:

```bash
grep -rn "ml_crypto.h" --include=*.c .
```
